# fresh 재개 확인 기억 후보 — 오프라인 인과 비교(인계 시점 기록)

2026-10-30. GPT 검토 결정에 따른 묶음이다. 측방 팽창·0명령·임계값은 런타임 그대로 두고, **재개 확인 수를 지우는지 여부만** 다른 오프라인 상태 후보를 만들었다. 런타임·기본값에는 연결하지 않았다. Claude 5시간 사용량 경고(utilization 0.9)로 아래 시점에서 GPT에 인계했다.

## 후보 — [`candidate_state.py`](candidate_state.py), [`make_candidate.py`](make_candidate.py)

- 매 호출의 적격성과 명령은 런타임 proposal 그대로이며, 거절이면 반드시 0을 낸다. [`candidate_speed.py`](candidate_speed.py)는 런타임 사본에 `padding_reference_s` 인자 하나만 더했다. 이 인자는 분류용 반사실 계산에만 쓴다.
- 확인 스캔: fresh 스캔이 적격이고 resume 여유 이상이면 기록한다(원래 시각·raw 광선 취득 시각·점·조향·벽).
- 기억 조건: 같은 스캔을 재사용하는 주기에 점유 여유 거절(또는 HOLD 중 resume 미만)이 나고, 아래를 모두 만족할 때만 그 스캔의 확인 1회를 남긴다.
  - 같은 epoch/source/raw 취득 시각, 같은 벽
  - 점 이동 ≤ 5 mm, 현재/직전 조향 변화 ≤ 0.005 rad
  - 확인 후 0.15 s 이내
  - 팽창 나이만 확인 시각 기준으로 되돌린 반사실이 적격·resume 이상
- 기억은 확인 수를 늘리지 않고 확인 시각도 갱신하지 않는다. 다음 fresh 스캔이 거절되거나 스캔 간격이 0.15 s를 넘으면 지운다. 같은 스캔에서 조건 밖 거절이 한 번이라도 나면 그 스캔의 기록을 버린다. 시간 역행·epoch·reset은 런타임과 같이 처리한다.
- 5 mm·0.005 rad·0.15 s는 오프라인 분류 기준이며 측정 정밀도나 운영 임계값이 아니다.

## 인계 시점의 미완료·해석 대기

- 결론 문장은 아직 확정하지 않았다. 현재까지의 관찰은 다음과 같다. 후보는 같은 스캔 재사용으로 인한 확인 초기화를 줄여 정체를 2.9→1.0 s(합성)로 줄였다. 저장 Gazebo 오른쪽에서는 0→양수 102건을 만들었다. 그러나 복합 오른쪽 장면은 회복하지 못했다.
- 미분석: 합성 복합 오른쪽에서 보존하지 않은 59건 중 `same_points` 38건(점+조향 15건 포함). 정지 중에도 점이 5 mm 넘게 움직였다는 뜻인데, gyro 잡음/편향에 따른 운동 보정 차이로 추정한다(**미확인**). 이 허용치를 넓히는 것은 판정 완화이므로 하지 않았다. 다음 단계는 호출별 점 이동량 분포와 원인 분해다.
- 남은 정지 1.0 s와 장면 미성립의 기여 분해(측방 팽창 자체 vs 확인 초기화)는 아직 하지 않았다. 이전 [옆면 예외 후보](../rear_right_combined_stall_v1/README.md)와의 조합 비교도 하지 않았다.
- [측방 속도 기반 팽창 설계안](DESIGN_LATERAL_INFLATION.md)은 문서뿐이며 구현·연결하지 않았다.
- 원시 trace/records와 호출별 결과는 로컬 보존 대상이다.
