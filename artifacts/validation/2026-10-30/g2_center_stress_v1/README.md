# G2 중앙 표적: 복합 오차 Gazebo 1회

2026-10-30. GPT가 설계·분석을, GPT-6 Luna가 실행·회수를 맡았다. Claude 5시간 사용량 경고 뒤의 후속 묶음이며 [실행 전 등록](DRIVE_PLAN.md)을 지켰다. 기존 명목 주행과 실패 원본은 수정하지 않았다.

## 결과

독립 보호와 제어기의 실제 `/scan` 구독 및 `/drive`→`/drive/safe` 연결을 확인했다. 이것은 토픽 연결 증거이며 내부 판단의 일치 증거와는 구분한다. [보호 함수 그림자 분석](analyze_run.py)은 같은 저장 입력·저장 명령으로 별도 수행하며 ROS 수신 순서를 재현하지 않는다.

## 정체 순서

원시 판단·구동 진단에서 다음 순서를 확인했다. 아래 시각은 **시뮬레이션 절대 시각**이다. 정답 차체 속도는 원인 분석에만 사용했다.

1. **11.24 s:** `large_motion_region_unobserved`로 한 틱0명령. 직전/직후에는0.35 m/s 후보가 나왔다.
2. **11.289 s 근처:** 왼쪽 바퀴−26.70 rad/s·오른쪽+10.81 rad/s, 모터축−119.16 rad/s였지만 정답 차체 종속도는+0.336 m/s였다.
3. **11.30 s:** 모터축 측정 환산−0.2431 m/s를 `EntryGuide`가 입력 무효로 처리하여 우회 기하를 초기화했다.
4. 이후 출발 때의 양쪽 벽 확인으로 돌아갔고, 안쪽 왼쪽 벽이 짧다는 `wall_segment_short`로 대기했다. 늦은 구간의 실제 `/drive`와 `/drive/safe`는 모두0이었다.

따라서 지속 정체는 단순히 바퀴에 양의 명령을 주고도 움직이지 못한 상황이 아니다. **순간 역방향 피드백으로 경로를 지운 뒤 다시 초기 경계를 만들지 못한 상태**가 남았다. 다만 한 기록의 시간 순서만으로 초기0명령과 역회전의 기계적 인과를 모두 확정하지는 않는다. 음수 엔코더를 센서 잡음이라고 단정하거나0으로 잘라 쓰지도 않는다.

[시점 분석](run1_timeline.json), [원본 주행 판정](run1_g2_evaluation.json), [원시 결과](run1/report.json), [등록 소스](run1_sources.zip)를 보존한다. 최초 명목 주행에서 문제가 없었다는 사실을 복합 오차 대응 성공으로 확대하지 않는다. 균등 오차는 실물 C1의 측정 분포가 아니다.
