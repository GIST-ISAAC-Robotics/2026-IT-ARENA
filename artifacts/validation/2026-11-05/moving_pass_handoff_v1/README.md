# 이동차 복귀에서 추종으로 넘어갈 때의 연속성

[r14 뒤 합류](../moving_pass_withdrawal_v1/README.md)는 상대 가속 시 옆 경로에서 양보하고 앞차 뒤로 돌아왔다. 그러나 [사후 속도 기록](../moving_pass_withdrawal_v1/candidate_r14/continuity.json)을 보면, 8.519초에 `owner.reset()`으로 추종 경계와 앞차 관측을 함께 지우면서 10호출·약 0.20초 동안 0명령이 나왔다. 실제 차체가 0.05 m/s 아래였던 표본 시간은 0.256초였다. 복귀는 성공했지만 연속 주행의 불필요 손실이다.

**r16 후보:** 복귀 경로를 따라가는 동안 별도 G1과 앞차 관측기를 현재 센서로 미리 준비한다. 이들은 준비 중 명령을 발행하지 않는다. 중앙 복귀가 확인되면 우회/모드 상태는 초기화하되, 이때 준비된 현재 경계·측방·앞차 관측을 G1으로 넘긴다. 실제 점유나 가림에 따른 G1 정지·독립 보호·STOP은 그대로 적용된다. 옛 진입 전 경로를 현재의 허가로 복사하지 않는다.

- `before_moving_pass.py`: r14 이후 작업트리 원본. 해당 파일은 현재 런타임에서 따로 보존했다.
- `candidate_moving_pass.py`: 먼저 격리 검증한 뒤 단독 속도 시험 종료 후 런타임에 적용한 후보. 실행 중인 단독 입력은 바꾸지 않았다.
- `replay.py`: 후보 모듈만 격리 로드해 이전 저속 추월 성공과 r14 뒤 합류 입력을 재생한다. 실제 인계 전 속도·조향이 같아야 하며, 인계 뒤의 정지·감속 변화를 구분한다.

## 검증과 정리 지점

- [저장 입력 재생](replay1.json): 이전 저속 추월 752판단과 r14 뒤 합류 551판단 모두 실제 인계 전 속도·조향 변경 0. 인계 뒤 0.5초 창의 0명령은 각각 10→0회다. 기존 `follow_boundary_unconfirmed`·`follow_release_wait` 대신 현재 관측의 `local_follow`로 이어졌다. 실제 차체가 정지하지 않았다는 뜻은 아니다.
- 관련 회귀 `test_moving_pass.py`·`test_bypass_handoff.py` 128개 통과(5.84초, GPT 직접 실행, exit 0). 현재 준비한 G1의 0명령을 양수 복귀 후보로 덮지 않는 경우와 reset 때 준비 관측을 버리는 경우를 포함한다. 출처 계약 검사 1개도 통과했다(0.60초).
- [실행 입력 등록](../moving_pass_withdrawal_v1/candidate_r16/registered.json), 소스 ZIP, `config/tests/moving_pass_handoff_r16_sha256.json`을 보존했다. 중간에 적용된 r15 단독 속도 후보는 교통에서는 OFF이며, 이 변경도 등록에 포함했다. `before_r16.zip`은 실제 적용 직전 바이트다.
- **사용자 정리 요청으로 새 Gazebo 주행은 시작하지 않았다.** r16은 적용·정적/재생 검증·등록까지이며, 폐루프 검증 전이다. 기본 `moving_pass_trial`도 OFF다.

다음 작업 재개 시 등록 입력과 현재 소스를 확인한 뒤 실행 담당 GPT-6 Luna에게 아래 **1회**를 맡긴다. 기존 포기·접촉·노면·STOP 판정과 함께 인계 순간 0명령·실제 정지·복귀 후 진행을 비교한다. 실패 원본을 지우거나 같은 실패를 반복하지 않는다.

```powershell
wsl.exe -e bash artifacts/validation/2026-11-05/moving_pass_withdrawal_v1/run.sh candidate_r16
```

그다음 실제 저속 추월·포기·인계의 연결 상태를 보고 중속 상대와 자차 속도를 함께 높인다. 단독 속도 후보의 43.6 m 정지 분석은 별도 작업으로 남긴다.
