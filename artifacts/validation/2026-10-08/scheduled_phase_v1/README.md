# 고정 요청의 시뮬레이션 시계 격자 발행과 위상·step 변동

2026-10-08 후속. [step 민감도](../step_sensitivity_v1/README.md)에서 같은 프로필 값이라도 `/drive` 발행 위상이 실행마다 0~19 ms 달랐고, 같은 1 ms 재실행에서 0명령 전 불일치(0.593→0.019 m/s)가 재현되지 않아 step 단독 효과를 식별하지 못했다. 이번 범위는 **시험용 고정 명령의 시간 재현성 개선**과 **등록 위상에서 1 ms/0.25 ms 결과 변동의 확인**이다. 제어기 성능 개선·G1 재주행·기본 모델 변경은 범위 밖이다. GPT 주 에이전트가 설계와 최종 검토를, Claude Opus 5.5가 구현·분석·문서를, Claude Sonnet 5.5 서브에이전트가 Gazebo 실행·대기·회수를 맡는다.

## 실행 전 등록 (Gazebo 실행 전 작성)

### 사전 조사로 확인한 시계 구조

| 단계 | 시계·주기 | 근거 |
|---|---|---|
| 평가기 `/drive` (기존) | `spin_once(5 ms 벽시계)` 폴링, sim `now-last>=.019`면 발행. 시작 시각 `ARM+1 s`는 격자 정렬 없음 | `probe_braking_contact.py` |
| `lidar_safety` → `/drive/safe` | sim 시간 20 ms 타이머에서 최신 `/drive`를 제한해 발행 | `lidar_safety.py` `create_timer(.02)` |
| 관측된 safe 위상 | 직전 4개 실행의 활성 구간 safe stamp가 모두 **sim 20 ms 배수**(간격 20 ms 175/175) | `../step_sensitivity_v1/*/safe_commands.jsonl` 사후 점검 |
| `actuation_host` | `/drive/safe` 수신 즉시 프레임 송신 | `actuation_ros.py` `on_drive` |
| `virtual_mcu` | 프레임 수신 즉시 목표 변경, 즉시 `/actuation/status`(now_us) 발행. 별도 1 ms 벽시계 타이머·5 ms sim 간격 tick | `ActuationReceiver.receive`, `on_tx` |
| `guarded_sim_actuator` | **벽시계 10 ms** 타이머로 `/sim/cmd_vel` 발행 | `actuation_ros.py` |
| 구동 플러그인 | gz 수신 스레드가 값을 저장, 다음 PreUpdate에서 적용. 진단은 sim 약 20 ms 간격 | `single_motor_drive.cpp` |

따라서 평가기가 sim 시각 20 ms 배수(위상 0)에 발행하면 같은 `/clock` 값에서 보호층 타이머와 **경합**한다(보호층이 먼저 돌면 다음 tick까지 20 ms 지연). 위상 10 ms는 보호층 tick 사이 중앙이다. 정해진 sim 시각에 발행을 요청해도 DDS 전달·벽시계 타이머(10 ms)·플러그인 적용까지 결정론적이지는 않다. 이번 실행은 이 잔여 변동이 **어디서, 얼마나** 남는지를 측정한다.

### 구현 (평가 전용, 기본 경로 불변)

- `scripts/scheduled_command.py`(신규): 정수 ns 격자 스케줄러. 예정 tick은 `origin+k·20 ms`로만 계산(drift 없음), 한 poll에 최대 한 tick(누락 tick burst 재생 금지, 진단 계수), 같은 시계값 반복은 미발행, 시계 역행·100 ms 초과 점프는 `ScheduleError`로 중단, 위상은 `[0, period)` 정수만 허용. 프로필은 1 µs 격자 정수 ns로 표본화해 경계 float 오차를 없앤다. 격자 모드 전용 요청 감사 `audit_scheduled_requests`(모든 등록 tick 1회, 예정 시각 표본값 일치, backdate 없음, header stamp=판정 시계값, 지연 ≤10 ms, 누락 없음)를 둔다. 실제 발행 시각으로 표본화했다면 달랐을 tick 수를 따로 보고한다. 기존 `audit_requests`는 바꾸지 않았다.
- `scripts/probe_braking_contact.py`: `--command-schedule {poll,sim_grid}`(기본 `poll`=기존 발행), `--schedule-phase-ms {0,10}`(sim_grid 필수). sim_grid에서는 ARM 확인 시계값 이후 첫 격자점부터 발행하고(ARM 전 미발행), `ARM+1 s` 이후 첫 격자점을 프로필 0으로 둔다. header stamp는 **실제로 읽은 시계값**이며 예정 시각으로 바꾸지 않는다. 행마다 예정/관측/header ns·tick 번호·지연·직전 누락 수·평가기 `/clock` 구독의 마지막 값을 남긴다. 추가 구독(`/clock` best-effort, `/actuation/status`, `/actuation/output_status`)은 sim_grid에서만 만든다. 기본 경로의 launch 인자·구독·report 키·소스 목록은 그대로다.
- 소스 계약: `config/tests/scheduled_command_r0_sha256.json`(부모 `physics_step_r0_sha256.json`). 런타임 소스·구동 플러그인 해시는 부모와 같고 평가 스크립트 두 개의 변경만 등록한다. `test_physics_step_option.py`의 현재 해시 검사는 이 후속 계약을 거치도록 연결했다(검사 삭제 없음).
- 기본값 유지: `legacy` 구동식, G1 꺼짐, 월드 1 ms, `/drive`→독립 보호층→`/drive/safe`→가상 MCU 경계, 모터축 단일 28카운트·15:1·65 mm, 차량 물성·마찰·토크·보호 판정선·센서 주기·기본 공식 트랙·상위 제어기. step 변경은 기존 `evaluation_physics_step=0.00025`만 쓴다. 보호층·MCU·플러그인 코드는 수정하지 않는다(lockstep/step pause 없음).

### 위상 정의 (등록)

- 위상은 **sim 절대 시각 mod 20 ms**다. 보호층 tick은 위상 0에 있다(위 사후 점검, 실행마다 safe stamp로 다시 확인).
- **기준 위상 = 10 ms**(보호층 tick 사이 중앙, 경합 회피 설계). **대조 위상 = 0 ms**(보호층 tick과 같은 시계값, 경합 조건).
- 지시의 "phase0 반복"은 **기준 위상(10 ms) 반복**으로 둔다. 실행 전 기제(보호층 tick 위상)로 정했으며 결과를 보고 바꾸지 않는다. 대조 위상 0 ms는 경합 결과를 그대로 보고한다.

### 실행 행렬 (정상 계획 최대 6회 새 Gazebo, 환경/종료 오류 재시도 1회)

공통: 분할 노면 `official`, `passive_damping`, 슬롯 3, [`command_profile.json`](../braking_ab_v1/command_profile.json)(SHA-256 `a792af4a13cebaa5450bb0188b72b955c91488e2b95c7be69ce8f9daac055a08`), 제동 창 1.75~2.85 s, 프로필 종료 후 1 s 0명령, 명시 STOP 후 1 s. `run_case.sh <step> <phase> <name>`.

|---|---|---|---|---|
| R1 | `o1ms_p10_a` | 1 ms(기본) | 10 ms | 기준 조건 첫 실행 = **pilot** |
| R2 | `o025_p10_a` | 0.25 ms | 10 ms | dt 대조 |
| R3 | `o1ms_p0` | 1 ms | 0 ms | 위상 대조 |
| R4 | `o025_p0` | 0.25 ms | 0 ms | 위상 대조 |
| R5 | `o1ms_p10_b` | 1 ms | 10 ms | 같은 조건 반복 |

**Pilot 관문(R1).** `report.passed`, 격자 요청 감사 전부 통과(모든 tick 1회, 지연 ≤10 ms, 누락 0), safe stamp가 20 ms 격자 위상 0, MCU/출력 상태 기록 존재, STOP `software_stop`, 정상 종료. 스케줄 자체 실패(지연·누락·시계 오류)이면 다음 실행을 멈추고 원인을 본 뒤 한 번만 미세 수정(이 문서에 사유·변경을 추가)하고 pilot을 새 이름으로 다시 실행한다. 다시 실패하면 무한 조정 없이 실패와 잔여 지연 위치를 보고하고 마감한다.

**중단 조건.** MCU latch, 보호층 사유가 `clear`가 아닌 활성 표본, 소스 변경, 시계 역행/점프 중단, 잔존 프로세스. 환경·종료 오류(시작 실패, 종료 코드 등)는 자료를 보존하고 `_retry1` 새 이름으로 1회만 재시도한다.

### 분석 축 (실행 후 각각 따로 판정)

1. **실행 유효성**: report 통과, 입력 유효, STOP 확인·`software_stop`, 안정 정지, 정상 종료, 소스 불변, 원시 해시·소스 ZIP, 단일 모터축 피드백·좌우 엔코더 부재, `passive_damping` 관측, 실측 step=선언 step, 프로필 해시 재계산 일치.
2. **스케줄 충실도**: 격자 요청 감사, 지연 분포, 누락·중복 poll, 실제 시각 표본 차이 tick 수, `/clock` 간격 분포(최소 양의 간격=관측 해상도, 역행), 평가기 노드 시계와 `/clock` 구독값 차이.
3. **전달 재현성**: 프로필 속도 전환 16개·조향 전환마다 프로필 시각 → 예정 tick → 실제 발행 → safe stamp → MCU 목표 적용(`/actuation/status` now_us) → 출력(`/actuation/output_status` now_us) → 플러그인(마지막 0목표만 `zero_steps`로 step 단위 역산, 나머지는 20 ms 진단 구간으로 경계만). MCU 목표값별 유지 시간. 식별할 수 없는 표본은 `null`/`unknown`으로 둔다.
   - 두 실행의 **전달 비교 가능** 판정(등록): 요청·safe 사건 시각(시작 기준) 차 0, MCU 사건 시각 차 ≤1 ms·유지 시간 차 ≤2 ms, 출력 사건 시각 차 ≤2 ms, 플러그인 마지막 0목표 적용 시각 차 ≤2 ms(관측 가능할 때). 하나라도 넘으면 "전달 비교 불가"이며 물리 차이에 전달 시각 차이가 섞인 것으로 본다.
4. **물리 지표 일관성**: 0명령 전/후 평균 바퀴–차체 최대 차, 제동 창 최대 차, 좌우 표면 속도 차, 개별 바퀴 역회전(최소 단일 바퀴 표면 속도·표본 수), PreUpdate 양의 동력·0목표 양의 일, 정지 sim 시간·XY 거리, RTF, 진단 coverage. 쌍 비교 허용치는 step 민감도와 같은 `속도 max(0.05 m/s, 10%)`, `거리 max(0.01 m, 20%)`, `시간 max(0.05 s, 20%)`(비율은 두 값 중 큰 절댓값 기준).
5. **원인 식별 가능성(등록 규칙)**:
   - 같은 조건 반복(R1/R5, R2/R6): 전달 비교 가능이고 주요 물리 지표가 허용치 안이면 "이 dt·위상에서 2회 재현"이라고만 쓴다(분포 확정 아님).
   - 위상 효과(R1/R3, R2/R4): 같은 dt 기준 위상 반복이 재현되고, 위상 쌍의 차이가 허용치를 넘으면 "전달 위상(지연 구조) 민감"으로 한정 식별한다. 반복이 재현되지 않으면 식별 불가.
   - dt 효과(R1/R2, R3/R4, R5/R6): 두 dt의 기준 위상 반복이 각각 재현되고 같은 위상 dt 쌍이 전달 비교 가능일 때만 "ROS 전달 위상과 분리된 dt 효과(플러그인 PI·토크 응답 이산화 포함)"로 한정 식별한다. 플러그인 적용 시각은 step 해상도로 다르게 양자화되고 플러그인 이산화도 함께 바뀌므로 **`step_only_effect_identifiable`은 계속 false**로 둔다. 20 ms 격자 표본값 일치만으로는 동일 입력을 주장하지 않는다.
   - 분리하지 못하면 분리하지 못했다고 마감한다.

원시 고빈도 자료(진단·접촉·요청·safe·MCU 상태·출력 상태)는 로컬 보존/Git 제외(`.gitignore`), report·소스 ZIP·해시·분석은 보존한다. 커밋·푸시·PR·외부 게시·Jetson·전원 변경은 하지 않는다.

## 실행 결과 (R1~R6 뒤 작성)

새 Gazebo 실행은 등록 상한인 **6회**였고 재시도는 없었다. 6회 모두 STOP `software_stop`, 안정 정지, 정상 종료, 소스 불변, 잔존 프로세스 0을 만족했다. R1은 pilot이었고, R2~R6은 Claude Sonnet 5.5 서브에이전트가 `run_batch_r2_r6.sh`로 순차 실행했다. 최초 분석은 [`analysis_v1.json`](analysis_v1.json), 최종 검토 분석은 [`analysis_v2.json`](analysis_v2.json)이다. Claude 사용량 한도 도달 뒤 GPT-6 Astra 주 에이전트가 분석 검토·회귀 보완·기록 마감을 직접 수행했다.

### 실행기 결함과 사후 재검증

R1~R6에 쓴 실행기(계약 r0의 `probe_braking_contact.py` `fc4e0ab8…`)는 격자 모드에서 **진단 coverage·최종 정지 coverage·요청 감사·발행 그래프를 `input_valid`에 반영하지 못했다**. 원래 `if profile:` 블록을 `if profile and grid_spec: … elif profile:`로 나누면서 뒤쪽 검사가 `elif`에만 남았기 때문이다. 이 결함은 R4 결과 확인 중에 발견했다. 그래서 6회의 `report.passed`는 이 네 검사를 포함하지 않으며, R4·R6처럼 요청 감사가 실패해도 `passed=true`, 종료 코드 0이 되었다. 정상이었다면 배치는 R4에서 멈췄을 것이다. 실제로는 기존 실행판으로 R5·R6까지 진행되었다. 이 배치 중단 실패도 시험 절차의 결함으로 남기며, 6회가 모두 유효하게 통과했다고 해석하지 않는다. 등록 상한 뒤 추가 실행은 하지 않았다.

- 보존: 6회의 `report.json`은 덮어쓰지 않았다.
- 사후 재검증: 분석기가 같은 정의로 원시 기록에서 진단 coverage(최대 간격 ≤50 ms, 시작/끝 ≤50 ms)·최종 정지 coverage·발행 그래프·격자 요청 감사를 다시 계산했다. 결과는 `validity`/`schedule` 축이며, 6회 모두 coverage·그래프는 통과했다.
- 수정: 실행 뒤 probe를 고쳐 격자 모드도 같은 블록을 거치게 했다(`a7c85ff3…`). 기본 폴링 경로의 문장은 같다(직전판과 diff로 확인). 수정판은 [`scheduled_command_r1_sha256.json`](../../../../config/tests/scheduled_command_r1_sha256.json)에 등록했고, 구조 회귀 `test_grid_mode_shares_profile_validity_block`를 추가했다. 수정판으로 새 Gazebo 실행은 하지 않았다.

### 1. 실행 유효성

6회 모두 입력 무결성·정지·종료 축은 사후 재검증을 통과했다(입력 프로필 해시, 원시·추가 원시 해시, 소스 ZIP, 등록 실행판 소스, 단일 모터축 피드백·좌우 엔코더 부재, `passive_damping` 관측, 실측 step=선언 step, coverage, 발행 그래프, STOP·정지·종료). **스케줄까지 포함한 전체 등록 조건을 충족한 것은 R1·R2·R3·R5 네 회**다. R4·R6은 다음 절의 지연 기준 실패로 제외한다. RTF는 1 ms 0.083~0.086, 0.25 ms 0.028~0.032였다.

### 2. 스케줄 충실도

| 실행 | step·위상 | 감사(등록 창) | 지연 tick(전체) / 최대 | 누락 | `/clock` 간격 |
|---|---|---|---|---|---|
| R1 `o1ms_p10_a` | 1 ms·10 | 통과 | 3 / 5 ms | 0 | 1 ms ×6499 |
| R2 `o025_p10_a` | 0.25 ms·10 | 통과 | 1 / 11 ms(4.26 s, 창 밖) | 0 | 0.25 ms ×25999 |
| R3 `o1ms_p0` | 1 ms·0 | 통과 | 1 / 2 ms | 0 | 1 ms |
| R4 `o025_p0` | 0.25 ms·0 | **실패**(지연 18.75 ms > 10 ms) | 4 / 18.75 ms | 0 | 0.25 ms |
| R5 `o1ms_p10_b` | 1 ms·10 | 통과 | 3 / 8 ms | 0 | 1 ms |
| R6 `o025_p10_b` | 0.25 ms·10 | **실패**(지연 13.25 ms) | 6 / 13.25 ms | 0 | 0.25 ms |

- 모든 실행에서 등록 tick이 각각 한 번씩 나갔다. 값은 예정 시각 표본과 같았고, backdate는 없었으며, header는 판정 시계값과 같았다. 누락·burst는 없었다.
- `/clock`은 평가기 구독에서 물리 step마다 1개씩 관측됐다(역행·반복 0). best-effort 구독이므로 유실이 전혀 없다는 증명은 아니다.
- 평가기 노드 시계는 자체 `/clock` 구독 처리값보다 최대 10~25 ms 앞섰다. 같은 노드 안에서 구독 처리 순서가 다르다는 뜻이며, 노드 간 시계 수신 순서는 측정하지 않았다.
- 10 ms를 넘은 지연은 R4(2.92 s)·R6(2.94 s)에 있었다. 모두 프로필 상대 2.256 s 이후 **값이 0으로 일정한 구간**이었다. 그래서 요청·safe·MCU 전환 사건 시각은 같은 조건의 다른 실행과 같았다(아래 3). 등록 판정은 바꾸지 않으므로 R4·R6이 들어간 비교는 `valid=false`다.
- 지연 원인(평가기 단일 스레드 폴링 루프의 벽시계 정체로 추정, RTF 0.03에서 18.75 ms는 약 0.6 s 벽시계)은 확인하지 못했다.

### 3. 전달 재현성 (속도 전환 16개, 조향 전환 11개, 모든 단계에서 대응 성공)

| 구간 | 위상 10 ms | 위상 0 ms |
|---|---|---|
| 프로필 전환 → 예정 tick | 0~18 ms(20 ms 격자 양자화, 6회 동일) | 동일 |
| 예정 tick → 실제 발행 | 0(전환 tick 기준) | 0 |
| 실제 발행 → safe | **+10 ms 고정** | **+20 ms 고정**(R3·R4 모두 보호층 tick이 먼저 처리됨) |
| safe → MCU 목표 적용 | 0(같은 sim 시각) | 0 |
| MCU → 출력 `/sim/cmd_vel` | 5~6 ms(1 ms), 5~5.25 ms(0.25 ms) | 같음 |
| 출력 → 플러그인 마지막 0목표 | +1 step(1 ms / 0.25 ms) | 같음 |

- safe 위상은 6회 모두 sim 20 ms 배수 위상 0이었고 보호 사유는 `clear`뿐이었다.
- **MCU→출력 5 ms**는 16개 전환 모두에서 같은 원인으로 생겼다. MCU가 같은 `now_us`에서 5 ms tick 상태(이전 목표)를 먼저 내면, 수신 즉시 낸 새 목표 상태를 `AppliedGuard.update`가 `stamp <= last_stamp`로 버린다. 새 목표는 다음 5 ms tick 상태에서야 출력된다(`same_stamp_old_status_first` 16/16). 현재는 진단 관측이며, 보호 계약은 수정하지 않았다.
- 같은 조건 쌍의 출력 시각 차는 1 ms 실행에서 최대 1 ms(16개 중 7개 사건), 0.25 ms 실행에서 최대 0.25 ms(5개 사건)였다. 플러그인 마지막 0목표 적용 시각은 반복 사이에 같았다.
- 플러그인의 중간 전환 적용 시각은 진단이 약 20 ms 표본이라 **알 수 없다**.
- 위상 0/10 쌍은 safe 이후 모든 단계가 정확히 10 ms씩 밀렸다(출력 9~11 ms). 등록 기준으로는 "전달 비교 불가"다.

### 해석과 한계

1. **같은 위상에서 관측한 요청·safe·MCU의 속도/조향 전환 시각은 일치했다.** 전체 발행 tick의 무지연이나 결정론성을 증명한 것은 아니다. 두 실행은 유지값 발행 지연 기준에 실패했다. 관측한 전환 중 MCU→출력 단계의 반복 차이는 step 하나 이하였다. 플러그인 중간 적용 시각은 미관측이다.
2. **1 ms 분할 노면은 이 전환 시각들을 맞춘 반복에서도 재현되지 않았다.** 유효한 R1/R5의 요청·safe·MCU 전환 시각은 같고 출력은 7개 전환에서 1 ms 달랐다. 그런데 0명령 전 차이 0.010/0.116, 좌우 차 0.76/1.22 m/s, 정지 이동 0.050/0.099 m로 갈렸다. 즉 `/drive` 발행 위상 정렬만으로 반복 차이가 사라지지는 않았다. 이 1 ms 이하 출력 적용 시각 차이가 원인인지, 관측하지 못한 플러그인 적용 시점 또는 물리 계산 변동인지는 이번 자료로 **분리하지 못했다**.
3. **0.25 ms는 이번 세 실행(R2·R4·R6)에서 서로 가까웠다**(0명령 후 0.397~0.400, 좌우 0.788~0.799 m/s). 다만 R4·R6이 등록 스케줄 감사에 실패했으므로 등록 판정은 무효다. 반복 2회는 분포가 아니므로 0.25 ms의 안정성을 확정하지 않는다. 직전 폴링 발행 0.25 ms(A4/D2)의 좌우 차 0.658/0.660과는 약 0.13 m/s 달랐다. 소스·발행 방식이 달라 비교는 참고로만 둔다.
4. 위상 효과·dt 효과·step 단독 효과는 모두 식별되지 않았다. 기본 `legacy`·G1 꺼짐·기본 1 ms 월드·보호/MCU 계약은 바꾸지 않았다. 이 결과로 수동 근사·0.25 ms를 기본으로 채택하지 않으며, G1 재주행·고속으로 확장하지 않는다. `passive_damping`은 평가 전용 저항 근사이며 MD20A 회로가 아니다.
5. 다음 최소 작업 순서:
   - (a) 수정한 r1 실행기의 실환경 실패 전파와 지연 tick 발생 위치부터 확인한다. 등록 스케줄 감사 실패 시 배치가 멈추는 것을 확인하기 전에는 물리 반복 횟수를 늘리지 않는다.
   - (b) 플러그인 중간 명령 적용 시각을 평가 전용 전환 이벤트로 계측한 뒤, 유효한 동일 조건 반복에서 입력 시점 변동과 물리 출력 변동을 구분한다. 기본 제어/물성은 유지한다.
   - (c) `AppliedGuard`의 같은 stamp 버림은 의도와 실차 계약상 의미를 별도 검토한다. 관측된 지연만으로 보호 계약을 바꾸지는 않는다.
