# 단독 고속 코너의 공통 호길이 확인 후보

상태: **단독 1회 37.934초 완주·최고 2.422 m/s(8.72 km/h)**. 접촉·노면 이탈 표본 0, 모터·STOP·정상 종료를 확인했다. 관련 210회귀·저장 입력 대조를 마쳤고 기본 OFF를 유지한다. 10 km/h 실도달은 아직 아니다.

[고속 코너 분석](../fast_corner_review_v1/README.md)에서 실패본 1,099개 출력을 재현했다. 22.32초의 현재 경로는 이전 관측보다 코너 뒤쪽까지 길어져, 고정 x=0.05–0.65 m 창이 실제로 겹치지 않는 먼 곡선까지 함께 비교했다. x 방향 비교 오차는 0.323 m였으나 가까운 공통 호길이에서는 기존 0.08 m 허용값 안이었다. 정지 후에는 같은 경로끼리도 x 폭 0.167 m가 최소 공통 폭 0.25 m에 못 미쳐 확인을 지웠다.

현재 경로의 형상·점유 검사는 그대로 수행하고, 엔코더/IMU로 옮긴 직전 경로와 일치하는지 볼 때 **기존 x 비교를 먼저 적용한 뒤, 실패하면 기존 공통 호길이 비교를 추가**한다. 가까운 호길이 0.05–1.0 m 중 양쪽에 실제 존재하는 범위만 사용한다. 같은 0.25 m 공통 길이·5점·0.08 m 대칭 80백분위 기준이며 없는 경로를 외삽하지 않는다. 큰 이동·오래된 이력·현재 기하 부재·실제 점유·확인 횟수·부분 관측·독립 보호와 STOP은 그대로다.

현재 벽의 정체나 멀리 갈라지는 두 길을 인증하지는 않는다. 기존 비교와 마찬가지로 공통 구간의 뒤쪽에서 늦게 갈라지는 분기를 놓칠 수 있다. 이번 연결은 명시 단독 `corridor_arc_agreement`에만 허용하며, 교통 구성이나 기존 단독 프로필을 자동 변경하지 않는다. ROS 프로필은 `g1_open_10kmh_solo_gap05_arc`이며 실패했던 `g1_open_10kmh_solo_gap05`에 이 옵션 하나만 추가한다.

## 구현 전 저장 입력의 근거

출력에 연결하지 않은 [독립 비교](../fast_corner_review_v1/arc_compare_summary.json)에서 실패본은 13회, 완주본은 20회의 0명령이 양수로 바뀌었다. 새 0명령은 없었고 첫 실패 변화는 22.32초 0→0.8 m/s였다. 정지 뒤의 원래 센서 입력은 그대로여서 이후 재출발이나 실제 랩을 증명하지 않는다. 차체·모터축 속도 차이가 사라진다는 의미도 아니다.

## 검증 및 실행 범위

1. 실제 실패 경로 조각과 반대 방향/분리 경로, 같은 스캔 반복·새 스캔 확인, 현재 점유/기하/TTL, 기존 단독·교통 회귀를 확인한다.
2. 옵션 OFF의 기존 출력을 재현하고 ON의 명령이 앞선 독립 후보와 같은지 두 단독 기록으로 확인한다.
3. 근거가 갖춰지면 같은 0.5초 간격·2×5 신호·방지턱 OFF·C1 순차 10 Hz·8.970588:1·28카운트·65 mm로 단독 1랩을 한 번 실행한다. 성공할 때까지 반복하지 않는다.

최고속도만 아니라 완주·랩 시간·큰 감속/정체·접촉·노면·STOP·정상 종료를 비교한다. 기존 0.8초·41.075초 완주본과 0.5초·19.837 m 실패를 보존한다. 정답은 평가에만 사용하고 모터축을 정답 차체 속도로 대체하지 않는다.

[수정 전 소스](before.zip), [출처 계약](../../../../config/tests/solo_corridor_arc_r1_sha256.json), [연결 대조](compare.py).

## 연결 검증

최초 테스트 209통과/1실패는 프로필 목록 갱신 중 단일 키를 tuple로 바꾼 테스트 오타였다. tests.log/.exit를 보존하고 해당 테스트 파일만 고쳐 16개를 재검사해 통과했다. 제어 소스나 판정값 변경은 없었다. 전체 지정 묶음 210개가 최종 통과했다.

[연결 대조](arc_compare_summary.json)는 실패본 1,099개·완주본 2,176개 기본 출력을 재현했고 ON 명령도 앞선 독립 후보와 모두 일치했다. 명령 변화는 13/20회, 모두 0→진행이며 새 0명령은 0이다. ON의 진단 필드 추가로 detail_changed는 모든 호출에 표시되므로 실제 명령 변경수와 구분한다. 입력·소스 해시 불변을 확인했다.

[원 보고](run1/report.json), [속도](run1_metrics.json), [노면](run1_surface.json), [모터](run1_motor_audit.json), [판단 재현](run1_replay.json), [같은 진행 위치 비교](lap_comparison.json). 노면은 23,587개 평가 표본이며 실물 접촉 증명이 아니다. 단일 모터축 28카운트·8.970588:1·65 mm와 제어/보호 구독을 확인했다. 주 에이전트는 실행 뒤 등록 165파일 해시를 대조해 변경이 없음을 확인했다. 결과를 추가하기 전 문서는 [README.before-result.md](README.before-result.md)에 등록 해시와 같은 바이트로 보존했다. 실행 source_snapshot.zip에는 이 README가 포함되지 않아 별도 보존했다.

이전 0.8초 완주본 41.075초보다 **3.141초(약 7.6%) 짧다**. 비교에는 시간 간격 0.5초와 회랑 보완이 함께 포함되며, 이 감소 전부를 새 호길이 비교 하나의 이득으로 돌리지 않는다. 같은 0.5초의 이전 실행은 19.837 m에서 멈췄지만 실제 센서 시각/궤적은 실행마다 달라질 수 있다.

[사용 기록](usage.json)에서 회랑 채택은 75회, 공통 호길이 확인은 1회였다. 그 한 번은 23.02초·진행 약 19.797 m에서 회랑 확인을 유지했지만 최종 출력은 정상 경로의 release wait 0명령이었다. 따라서 해당 호출 하나가 직접 가속을 만들었다고 해석하지 않는다. 후속 실제 완주와 저장 입력에서의 개선 근거를 함께 남기며 반복 재현성을 주장하지 않는다.

[3인칭 영상](run1/lidar_third_person_simtime_1x.mp4)은 20 fps·773프레임·38.65초, [전 프레임 디코딩](run1_video_review/video_inspection.json) 통과다. 주 에이전트가 9.65초 직선과 28.95초 이후 구간을 직접 확인했다. 영상 길이와 첫 녹색부터의 랩 시간은 기준 시각이 다르다.

측정 도구 첫 호출의 지원하지 않는 --output 옵션 오류(exit 2)를 보존했다. 실제 주행은 반복하지 않고 올바른 positional CLI의 stdout으로 run1_metrics.json을 회수했다. 후처리 전체와 분석은 통과했다.

## 다음 속도 병목

[상한 분해](speed_budget.json)는 정상 경로 1,760판단을 오차 0으로 재현했다. 0.5초로 줄인 시간 간격 자체는 약 0.58초에서 최저 제한이었다. 이제 기존 조향 유지 원호의 제동거리 제한 17.54초(그중 2.60초는 기존 코너 예측으로 보완), 경로 끝의 제동 제한 5.94초가 더 크다. 최고 목표 약 2.559 m/s 구간도 실제 관측 경로 끝의 제동 제한을 받았다.

다음은 관측 벽을 따라 확보한 경로 길이와 필요한 제동 길이를 대조하는 저장 입력 진단이다. 한도·마찰·토크·제동 가정을 단순히 낮추거나 같은 코스를 이유 없이 재주행하지 않는다. 실제 관측 범위를 활용하는 개선의 근거가 있으면 좁게 구현한다.
