# r165 옆면 관측 공백의 실행 연결

등록: 2026-11-12, 새 주행 전. 기본 실행점은 바꾸지 않는다.

- r164는 r152 저장 469판단에서 9개 0명령을 0.15 m/s로 바꾸었다. 이는 실제 진행 결과가 아니다.
- 계획기만 바꾸면 독립 보호층과 지연 결과의 현재 재검사가 다시 정지시킨다. 이번에는 세 단계가 각자의 현재 스캔/이력으로 같은 한정 기하를 검사한다. 과거 허가를 복사하거나 미관측을 자유 공간으로 채우지 않는다.
- 대상은 실제/목표 속도 0.15 m/s 이하, 차체 옆 10 mm 이내, 실제 6도 이하 한 공백, 근접 점/과거 위협 없음이다. 전방 공백·추가 공백·오래된 운동 입력·현재 가까운 장애물은 기존 정지다.
- 독립 보호층은 기존 `/drive`→`/drive/safe`·제동/시각/STOP 검사를 모두 유지한다. 명시 launch prefix의 시뮬레이션 프로세스에만 후보를 적용한다.
- 저장 비교: 독립 보호 9개 정지→저속/반대 0개. 현재 재검사 27조건 중18개 진행, +40 ms의9개는 운동 이력 부족으로 정지했다. 8개 반례 검사 통과. 이는 실제 ROS 배송/주행 증명이 아니다.

## 제한 시험

`run.py`로 r152와 같은 두 0.8 m/s 각본 앞차/시설/마커 누락, 60초, 제어 수신50 Hz·계획0.1초·C1 native 순차10 Hz를 한 번 실행한다. 목표 속도/접촉/노면/종료 판정은 유지한다. 평가기와 제어기 입력을 분리한다. 결과는 `assess.py`와 원시 report 양쪽을 보존한다. 실패 원인 변화 없이 반복하지 않는다.

배송 지연은 과거 Jetson 단계 비용을 사용한 기존 하한 모델이다. 새 r164 Jetson 계산 중앙121.49 ms/p95 220.84 ms의 전체 CPU·지터를 정확히 재현하지 않는다. 따라서 성공해도 현재 Jetson 실시간 또는 실차 주행 완료가 아니다.

소스/설정/각본은 실행 전 `two_actor_run1/extra_sources.zip`, `registered.json`에 보존한다. 외부 모델/기본 코드 활성화 없음. 일반 Ubuntu WSL 시작은 여전히 실패하여 살아 있는 Ubuntu namespace를 기존 사용자로 진입하는 로컬 임시 도구를 사용한다. WSL 자체 복구로 보고하지 않는다.

## 결과

[결합 판정](two_actor_run1/combined_assessment.json): **18.51 m·최장 저속4.432초·미완주**다. 접촉/시설 겹침0·최대두바퀴노면 밖·STOP/정상종료·잔여 시험 프로세스0·등록 소스 불변은 통과했다. r152의18.48 m·7.646초와 달랐으나 한 번의 실행이고 새 보완이 해당 기록에서 사용되지 않아 후보 개선의 인과 효과로 보지 않는다. 새 후보는 기본 채택하지 않는다.

원467개 판단 중 양수447개이며 새 옆면 공백 허가0회다. 양수인데 현재 재계산을 거치지 않은 것 중388개는 측방차 통과 뒤 `RELEASED/baseline`이었다. 지금 현재 재계산 연결은 SOLO/평행/GUARD만 지원하고 RELEASED를 빠뜨리고 있다. 저속표본의 누적13.519초에서 원 /drive는 양수인데 보호층은 `stale_input`으로0이었다. 명령/스캔/벽시계의 개별 만료 원인은 이 상태 문자열만으로 완전히 분리되지 않으므로 후속 저장 대조에서 확인한다. [시간축/이유](live_diagnosis.json).

평가기 첫 호출은 노면 후처리 산출물 누락, 다음은 노면 CLI 인자 오류로 실행 전에 실패했다. 저장 원본으로 기존 노면 평가와 후처리를 순서대로 수행했으며 새 주행을 반복하거나 원 report를 덮어쓰지 않았다. 실패 로그와 최종 결과를 함께 보존한다.

다음은 작은 공백 예외를 더 늘리는 대신 **통과 뒤 정상 경로의 현재 재계산 누락**을 확인한다. 신선한 입력/원경로/측방 상태를 실제 재검사하는 경우에만 새 명령 시각을 부여하며 TTL 연장·과거명령 시간만 갱신하는 방식은 사용하지 않는다.
