# r256 계획·현재 확인의 주기 분리 사전 대조

실제 r248 p95를 반올림한 계획147ms·현재 확인34ms를 가정하면, 순차 실행의 계산만 합쳐181ms이고 다음 명령 직전의 현재 확인 기준 나이는215ms다. 두 작업을 겹치면 각각147ms/181ms로 줄일 수 있다. 이는 주기 대기·입출력 비용을 제외한 산술 하한이며 실제 성능이나 상한 보장이 아니다.

다른 방안인 ‘같은 이전 계획을100ms마다 반복 확인’은 현재 함수를 그대로 재사용할 수 없었다. 계획 시작147ms 뒤 첫 확인, 그100ms 뒤 두 번째 확인을 가정하고 그때 이상의 실제 저장 입력을 선택했다. r243 양수 경로794개와 r253의301개 모두 두 번째 입력에서는 원 `path_source_s`의300ms 수명이 지났다. 각각783/301개는 직전 적용 조향도 달랐다. 원 경로 시각을 현재로 덮거나 이전 조향을 같게 꾸미지 않았다.

저장 입력은 기존 폐루프가 만든 관측이므로 새 스케줄의 궤적이나 성공률을 뜻하지 않는다. 입력 간격 탓에 조회 시각보다 늦은 표본을 골랐다는 한계도 `result.json`에 남겼다. 최소한 현행 함수를 반복 호출하는 것만으로 해결할 수 없다는 구현 제약을 확인한 비교다.

주기 분리를 연결하려면 계획/현재 검사 프로세스의 동시 소유·최신 조향/상태·세대를 다루거나, 오래된 경로를 현재 관측으로 새로 검증하는 별도 정책이 필요하다. 아직 둘 다 연결하지 않았다. 우선 양 단계에서 공통으로 큰 투영 비용을 줄이는 작은 후보를 비교하며, TTL·STOP·독립 보호 경계는 유지한다.
