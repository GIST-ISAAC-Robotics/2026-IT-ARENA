# 개발 시험용 속도 상한

2026-11-12. 최초 저속 실차 시험을 준비하기 위해 기존 B3 운영 화면/CLI/명령을 확장했다. 기본 OFF이며 `development_speed_limit_enabled=true`, 초기 상한은 `development_speed_limit_mps`로 명시한다. G1 launch 인자와 노드 매개변수를 연결했다. 상한 설정은 같은 세션/경기/개입의 STOP 래치와 새 MCU 비ARM 상태가 있을 때만 수락한다. START 준비 중/주행 중/옛 번호/비유한·범위 밖 값은 거절한다.

상한은 `/drive` 목표의 크기만 줄이고 출발·재ARM을 수행하지 않는다. 기존 가속 상한·조향·0명령·역방향 부호·비동기 계산 대기의 미발행과 독립 보호를 유지한다. 기본 OFF에서는 추가 타이머/발행자/구독자가 없다. 기존 웹이 없으면 화면을 열어 둘 필요도 없다. 재시작하면 명시 초기값으로 시작하며 같은 프로세스의 STOP/경기 초기화/연결 상실로 상한을 자동 해제하지 않는다.

## 확인 범위

- 순수 상태·HTTP/CLI·기존 경기 복구181검사, 이후 실제 ROS 노드의 명령 콜백/고정 경로 출력 상한/계산 대기/STOP와 기존 발행 회귀를 포함한227검사 통과. `tests_initial.log`, `tests_connected.log` 보존.
- 테스트의 경로 출력은 고정 입력이다. Gazebo 궤적·실물 구동·실제 차체 최고속도/제동은 검증하지 않았다. `/drive/safe` 직접 발행은 없다.
- readonly 토큰의 설정 거절, 원격 요청의 숫자/세대 바인딩, MCU ARM/재개 작업을 만들지 않음을 확인했다. UI JavaScript 구문 검사는 통과했다.
- 최종 launch 인자/출처 검사 진입 시 WSL `E_UNEXPECTED`가 재발했다. 단순 `/bin/true`도 실패했고, 당시 Windows 가상 메모리 여유는약28 GiB였다. 메모리 부족으로 단정하거나 코드 실패로 덮지 않는다. Windows 정적 검사 뒤 기존 사용자 승인 범위의 Ubuntu-24.04만 종료/재시작해 정상 실행을 회복했다. 원 실패와 재시작 결과를 보존한다.

이전8개 소스는 `before_sources_v2.zip`, 변경 계보는 `config/tests/development_speed_limit_r162_sha256.json`에 등록한다. r161 격리 IMU 진단 두 신규 경로도 출처 목록에 포함했다. 기존 실패/실행 등록을 고치지 않았다. 원격 Jetson에는 상한 기능을 배포하거나 차량을 움직이지 않았다. WASD/짧은 전진·좌우 조작은 다음 별도 기능이다.


Windows에서 출처/순수 상태256검사가 통과했고 기존 테스트의 기본 CP949 파일 열기1건이 실패했다. 소스나 기대값을 바꾸지 않고 Python UTF-8 모드로 해당1검사를 다시 실행해 통과했다. WSL의227검사와 Windows의257검사는 범위가 겹치므로 합산하지 않는다. 재시작 뒤 관련3패키지 빌드가12.6초에 완료됐고 `ros2 launch --show-args`에서 두 인자와 기본 OFF/.3 m/s를 확인했다(`build.log`, `launch_args.txt`). 새 Gazebo 주행은 미실시다.
