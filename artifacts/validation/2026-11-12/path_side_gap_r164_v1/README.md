# 현재 이동 영역에 맞춘 차체 옆 결측 후보

2026-11-12. [r163 진단](../path_observation_r163_v1/README.md)의 후속 저장 비교이며 기본 미채택·실주행 미실시다.

범위는 기존 GUARD·현재 벽 경로·실측/목표0.15 m/s 이하, ±100° 경계에 걸친 단일 실제 무반환 성분이다. 기존 외곽1 cm·총6°·국소 폭5 cm와 실제 점유 여유를 유지하고, 이웃의 고정0.6 m 대신 모든 현재 질의의 센서 반경+기존 나이별 여유를 사용한다. NaN/최소거리 미만/다른 전방 결측/알려진 소실 위협/오래된 관측/구조 그림자0상한은 허용하지 않는다. 정상 경로의 재개 확인 횟수와 실제속도의 이동 외곽, selector와 독립 보호 검사는 유지한다. 거리를 보간하거나 unknown을 자유로 만들지 않는다.

첫 비교 실행은 WSL `E_UNEXPECTED`로 Python 진입 전 실패했다. 이때 Windows 물리 메모리 여유약16 GiB·가상 메모리약27 GiB였다. Windows 대체 실행의 첫 시도는 NumPy 미설치로 실패했다(`compare_windows.log`). 저장 입력용 수치 라이브러리만 공개 저장소 밖 Git 제외 `build/host_numeric`에 설치하며 운영 ROS/Jetson 환경은 바꾸지 않는다. 반복 WSL 재시작은 수행하지 않는다.

결과는 후속 `comparison.json`과 관련 검사에서 판정한다. 새 위험을 기본으로 채택하거나 제한 저장 입력 결과를 주행 성공으로 확대하지 않는다.

## Windows 저장 비교

Python3.14/NumPy2.5.4는 기존 2차원 `np.cross` 사용을 거절해 원본부터 재현에 실패했다. 이 결과를 `windows_numpy25_*`로 보존했다. 해당 문제는 후보 효과가 아니며 운영 Jetson의 NumPy1.21.5에서도 발생했다고 주장하지 않는다. Windows 진단에는 별도 Python3.12/NumPy1.26.4를 고정했다.

고정 환경에서는469명령이 원 기록과 같았다. 전체 출력68차이는 질의/가림/미관측의 개수 진단에 한정되고 엄격 전체 동일성은 실패로 남긴다. 동일 Windows 기준 구현과 후보를 비교하면31출력 차이 중 정지→0.15 m/s 진행9회, 추가 정지0회다. 전방 경계의 복수 성분/관측 기억 만료 때문에 남은 거절도 보존한다. 이 입력은 원래 정지해 있던 기록이므로 새 명령 뒤 차량 이동이나 완주를 증명하지 않는다.

후보 설치 상태의 기존 selector/부분 관측 연결 회귀와 새로운 반례를 합쳐93검사가 통과했다(`regression_pure.log`). 최초 넓은 검사 시도는 Windows의 ROS 메시지/PyYAML 부재로 수집 단계에서 실패했다(`regression.log`); 해당 ROS 의존 범위를 통과했다고 합산하지 않는다. 원 구현은 변경하지 않았고 Jetson 비교용162소스/입력 묶음은 `source_manifest.json`에 고정했다. 묶음SHA-256 `1b6a9080e3b0499d48566dc9e23ae879ccbdf1829cec7b50a402d5eaee36ea25`.

Jetson 전송 첫 시도는 `.local` 이름이 공인 IP로 잘못 조회되어 timeout이었다. 기존 내부 주소에 직접 연결하되 원 이름의 저장 SSH 호스트 키를 그대로 검증하여 업로드했다. 비밀값/SSH 검증 완화 없이 CPU 저장 비교만 수행하며 장치를 구동하지 않는다.

## WSL·Jetson 대조와 실행 연결의 한계

살아 있는 Ubuntu namespace에 기존 사용자로 진입해 운영 ROS Jazzy/NumPy1.26.4로 재생했다. 원469개 **전체 출력**이 같았으며 후보의 정지→저속9·추가 정지0도 동일하다. 관련 ROS 부분 관측/구조74검사 통과. 첫 ROS 검사는 진단 스크립트가 기존 `PYTHONPATH`를 덮어써 메시지 패키지를 찾지 못한 실패로 보존했고, 원 ROS 경로를 유지해 수정했다.

Jetson(Humble/NumPy1.21.5)에서는469개 명령이 모두 같고67개 개수 진단 차이가 있었다. 후보 효과는 같은9개이며 원본/후보 계산 중앙115.95→121.49 ms, p95 219.37→220.84 ms다. 임의의 계산 최적화나 실시간 통과로 보지 않는다. 입력/162소스 불변·정상 종료를 확인했다. 기기를 구동하지 않았다.

WSL 임시 접근으로 도구 실행은 회복했지만 일반 `wsl -d Ubuntu-24.04` 시작은 복구되지 않았다. WSL2.7.11.0의 로그에서 Interop SocketChannel183 Broken pipe와 init signal6을 확인했다. [WSL 공개 이슈 #41592](https://github.com/microsoft/WSL/issues/41592)에 같은 버전/오류가 보고되어 있으나 이 컴퓨터의 촉발 원인까지 확정하지 않았다. WSL 업그레이드/반복 재시작 없이 확인된 Ubuntu systemd namespace에 `nsenter` 후 기존 일반 사용자로 실행하는 로컬 임시 진입점을 사용했다.

계획기 저장 결과만으로는 독립 보호층과 배송 후 현재 입력 검사가 이 위험 분류를 허용하지 않는다. 따라서 [r165 실행 연결](../path_side_runtime_r165_v1/README.md)에서 세 단계가 각자 현재 입력을 다시 검사하도록 연결하고 단일 제한 주행을 별도로 판정한다. 현재 후보를 운영 기본값으로 채택하지 않는다.
