# 위협 기록 보존 수정 — 구현과 수용 경계

## 실제 변경

`release_to_baseline`을 명시한 M3 후보에만 적용한다. 기본값은 false로 유지한다.

- 측면별 최신 기록은 진단용으로 유지하고, 과거 기록을 별도의 유한 장부에 보존한다. 현재 새 반환이 같은 물체라는 가정을 하지 않는다.
- fresh 스캔마다 기존 `release_gate`로 각 가능 영역을 옮기고 관측한다. 같은 스캔의 재호출은 추가 기록·확인으로 세지 않는다.
- `detected_at_s`는 최초 탐지 기록으로 유지하고, 전체 가능 영역을 현 관측으로 설명한 경우에만 `last_confirmed_at_s`를 갱신한다. 부분 관측이나 새 반환만으로 미확인 기록의 시한을 늘리지 않는다.
- 현재 새 위협 때문에 전체 해제가 불가능한 동안에는, 이전 기록이 두 fresh 양의 확인을 마친 경우만 장부에서 정리한다. 위협이 없을 때는 전체 장부를 두 fresh에서 다시 확인해야 복귀한다. 완전히 free로 확인한 영역도 두 번째 확인을 위해 보존한다.
- 같은 측면당 16기록·32,768잔여칸 상한, 미확인 기록 만료, 운동 이력 실패는 자동 복귀만 래치해 보류한다. 불확실성을 버리고 기본 G1로 돌아가지 않는다. 명시 세션 reset과 별도다.
- 관측/물체 속도 상계·노면·간격·STOP·독립 보호층은 그대로다. 회전 사각이나 처음부터 숨은 상대차 미래 진입을 해결하지 않는다.

## 확인한 것

- 수정 전 run43: 좌우 두 물체 반례 2실패, A 단독 1통과. source snapshot·XML을 보존했다.
- 수정 후 run44: PYTHONPATH에 ROS 경로를 빼먹은 검사 스크립트 오류로 수집 중단. 코드 통과/실패와 구분한다.
- 경로만 고친 run45: 관련 **307회귀 통과**, 소스 불변. 같은 측면 좌우 위협 보존·중복 스캔·상한·정상 단독 복귀·기존 노드/보호 연결·출처 계약 포함.
- 저장 실제 입력 대조 run46은 run35 보존판을 별도 모듈로 로드했다. 이전 출력 4,772/4,772 재현·입력/소스 불변을 확인했다. run13/27/35 명령은 그대로지만 좌우 run17/21 복귀는 사라졌다. 최대 호출 비용은 약 1.25/1.33초였다. 실제 차량 이동 궤적을 바꾸는 시험이 아니다.
- run47로 비용과 최초 뒤쪽 기록의 미확인을 분해했다. x 범위로 거리 후보 쌍을 줄이고 광선 계산을 배치화한 후 run48 관련 315회귀를 통과했다. run49에서 다섯 저장 입력 4,772개 전체 출력 동일·소스/입력 불변을 확인했다. 같은 비교의 최대 호출은 run17 1,141→536 ms, run21 1,340→564 ms, run27 742→277 ms, run35 693→274 ms다. 실시간 적합성은 여전히 실패다.

## 아직 남는 것

현재 장부는 정체/연속 옆차에서 기록과 계산이 늘 수 있다. 상한에 걸리면 진행성 제한이 남는다. 단순 합성 정상 추월 복귀가 된다고 실제 코너나 여러 차량을 안전하게 처리한다고 할 수 없다. 새 안전 위험을 지우기 위해 기존 정상 주행이 얼마나 보수적으로 바뀌는지 저장 입력으로 확인한 후 제한 주행 필요성을 판단한다. 기존 run17/run21의 약 70 mm 측방 실패와 전체 랩 실패는 그대로다.
