# 측방 차량 통과 후 코너 정체의 작은 조향 후보

2026-11-10 관련414검사·저장 입력 비교와 같은 코너1회를 완료했다. 실제 주행에서 후보 채택0·진행10.71m·최장저속3.32초로 지속성/병렬 목표는 실패했다. 원시 결과를 보존하고 [r65](../released_straight_restore_r65_v1/README.md)에서 자동 연결을 r63 실행 바이트로 복원했다. 후보 함수는 미연결 연구용으로 남긴다.

[지속 코너 동행 실패](../corner_parallel_continuity_v1/README.md)에서 옆차가 통과한 뒤에도 큰 복귀 조향의 후반 외곽 미관측으로 멈췄다. 기존 저장 대조는 목표속도를 낮추거나 과거 광선을 재사용해도 거절이었다. 다만 모터축 속도0인 세 장면에서 바퀴를 직진각으로 정렬했다고 가정하면 현재 광선·노면·측방 검사가 통과했다.

새 비교는 현재 G1 경로가 있고 측방 통과가 확인된 상태에만 한정한다. 현재 광선의 명령별 이동 영역, 점유·제동 간격, 도로/두 바퀴 잔디·측방 여유를 모두 다시 검사하여 0.2 m/s 이하의 작은 직진을 검토한다. 직전 조향 때문에 막히면 모터축·자이로가 최근 정지에 일치하고 노출 바퀴 외곽이 관측된 경우에만 기존 3 rad/s 변화율로 0속도 조향 후보를 만든다. 정렬됐다는 가정은 조향 필요성 판단에만 쓰며 양수 명령은 실제 직전 발행각으로 검사한다.

모터축0은 미끄러지는 차체의 정지, 발행각은 서보 실제 각도의 증명이 아니다. 기존 M3의 제자리 조향 근거와 한계를 재사용하며 새 감속도·마찰·미관측 허용을 만들지 않는다. 경로/관측 상실·명시 STOP·입력 고장, 미통과 옆차를 대신 처리하는 기능이 아니다.

먼저 `probe.py`로 원1,732명령을 그대로 재현하면서 후보의 실제 센서 이력 조건을 확인한다. 연결 전에는 명령을 바꾸지 않는다. 근거가 성립하면 관련 회귀와 기존 대표 입력 비교 후 같은 코너1회를 검토한다. 성공할 때까지 같은 시험을 반복하지 않는다. 실제 동행0.5초·출구/지속성의 원 판정은 그대로 둔다.

## 읽기 전용 결과와 연결 범위

[저장 입력 비교](probe/summary.json)는 원1,732명령 불일치0·소스불변이었다. 35스캔 중39.42–42.22초의29스캔에서 최근 모터축/자이로 정지와 바퀴 외곽 관측을 확인해 **속도0의 조향 변경 후보**가 성립했다. 정렬 완료를 가정한 별도 비교29개는 모두0.2m/s 후보가 나왔다. 실제 명령이나 궤적을 변경한 결과는 아니다.

이후 기존 `traffic_recovery_trial`·`piecewise_wall_trial`을 명시한 구성에만 연결했다. 기본 설정은 바꾸지 않았다. 기존 selector가 정상 진행을 선택한 경우에는 개입하지 않고, 큰 이동 영역 미관측 때문에 정지한 뒤 현재 경로가 있는 경우만 비교한다. 실패 원인/원 영역과 새 명령 검사를 함께 기록한다. 0각 가정이 양수 명령에 쓰이지 않는지, 앞 장애물·노후 관측·이동 중 모터축/회전·미통과 측방 차량·노면 기하 반례를 검사한다.

`checks.sh`는 관련 회귀와 코너 실패·r63 재출발·중속 오목 차량·시설 결합 한 랩의 저장 입력을 비교한다. 이미 원명령 일치를 확인한 대조군은 그 해시와 결과를 확인해 같은 이전 제어기 실행을 반복하지 않는다. 새 r63 재출발 기록은 이번에 별도 이전/현재 제어기 두 개로 비교한다. 실제 궤적이 바뀐 뒤 저장 입력상의0명령 수만으로 개선을 주장하지 않는다.

`run.sh`는 이 검증이 통과한 뒤 기존 코너 각본/시간/평가를 그대로1회 수행한다. 시설 묶음의 새 통합 주행이나 카메라 배치/증속 시험으로 확대하지 않는다.

[연결 검사](tests.log)는414개 통과, [저장 입력](replay/summary.json)은 코너1,732판단 중145개의 속도0 조향만 변경했다. 0명령 수337개는 그대로다. 기록된 직전 발행각을 매번 입력하므로 실제 정렬 완료나 주행 개선을 뜻하지 않는다. r63 재출발943·중속 오목차753·시설 결합 한 랩3,060판단은 명령이 같았다. 이전 제어기 대조 불일치0·모든 입력/소스불변이다. 이 근거로 같은 코너의 실제 조향/진행을1회 확인한다.

## 실제 주행 결과와 후속 판단

[원 평가](run1/report.json)와 [변경하지 않은 별도 코너 평가](assessment_run1.json)는 실패다. 진행10.71m·코너 출구 조건은 통과했지만 실제20–70° 코너 병렬0초로 사전0.5초에 못 미쳤고, 최장저속3.32초는2.5초를 넘었다. 접촉/겹침0·최소간격 약0.100m·노면이탈0·명시STOP/정상종료·소스불변을 확인했다. 14개 자식 프로세스는 모두 종료했다. 출구가 전보다 나아진 것을 r64 효과로 해석하지 않는다.

[1,745판단의 후보 감사](released_straight_acceptance_summary.json)에서 새 후보 채택은0이었다. [기록 상태](recorded_state_summary.json)를 보면 긴 정지는 주로 옆차가 아직 통과하지 않은 GUARD 상태의 `baseline_not_normal`/`parallel_hold_baseline_unavailable`에 속한다. 35.22–37.90초 구간이 연속135판단이다. 새 후보가 겨냥한 RELEASED 상태의 큰 이동영역 미관측 정지는39.42–39.60초의7판단으로 짧았다. 따라서 이전 실패의 저장 입력 조건을 새 주행이 그대로 반복한 것은 아니다. 현재 경로 자체가 없는 상태까지 이번 후보의 허용을 넓히지 않는다.

첫 셸 호출은 CRLF 때문에 Gazebo 시작 전에 실패했다. [실패 근거](shell_failure.json)와 수정 전 바이트를 보존한 뒤 LF 구문 확인을 거쳐 실제 주행은1회만 수행했다. 이 실행기 오류와 위 주행 실패는 별개다.

[r64 조건 재생](activation_audit.json)은 실제1,745판단과 명령이 같았다. helper 호출 누락이 아니라 측정속도·현재 명령의 미관측·경로 대기 상태 때문에 후보가 적용되지 않았다. 세부 이유와 복원 판단은 [r65](../released_straight_restore_r65_v1/README.md)에 둔다.

정지 사유를 기본 경로 단계까지 분리하면 GUARD의 `follow_boundary_unconfirmed`155판단과 `follow_steer_in_place`76판단이 서로 다르다. 전자는 코너에서 현재 경계 확보 실패이고, 후자는 시작부의0목표 조향 대기다. 긴 코너 정지의 회랑 후보는 `not_consistent_inward_corner` 또는 `long_outer_reference_unavailable`였다. [재현 집계](baseline_summary_reproducible.json)는 정지 **명령** 수이며 차체의 실제 정지 시간으로 환산하지 않는다. 후속은 현재 벽 근거로 코너 경로를 확보하는 문제와, 측방 위협이 남은 동안 제자리 조향을 전달하는 문제를 분리해야 한다. r64 범위만 넓히는 것으로 둘을 해결하지 않는다.
