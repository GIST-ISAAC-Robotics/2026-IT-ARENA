# G1 비용 분해 v3 — 입력 전체 보유와 실행 비용의 구분

관련 회귀 **58개 통과**. 입력을 한 줄씩 읽고 사전 검증의 전체 출력 목록을 계측 전 해제했다. 제어 소스·임계값·GC 설정은 그대로다. 각 입력 워밍업 1회·계측 3회, 전체 출력 일치·입력/소스 불변을 확인했다.

| 입력 | 계측 호출 | 전체 p50 / p99 / 최대 ms | GC p50 / p99 / 최대 ms | 20 ms 초과 |
|---|---:|---:|---:|---:|
| 왼쪽 가림 | 1,122 | 4.442 / 8.841 / 10.415 | 0.089 / 3.505 / 5.029 | 0 |
| 앞차 초기 대기 | 1,656 | 3.424 / 7.025 / 7.900 | 0.090 / 3.611 / 4.421 | 0 |

v2의 최대 28.05/26.71 ms와 비교해, 전체 입력/결과를 붙잡지 않는 시험기에서는 긴 GC 비용이 줄었다. **제어기 최적화 성과가 아니라 시험기 메모리 보유 방식의 영향**으로 해석한다. 별도 실행 사이 OS/캐시 차이도 있으므로 정확한 개선율을 보장하지 않는다. 동작을 바꾸지 않고도 충분한 비용 범위가 나와 GC 비활성화나 운영 제어기 변경은 하지 않는다.

여전히 모든 호출에 GC가 관측돼 무GC 대조는 없다. 스레드 CPU 시간에는 타 스레드 계산이 포함되지 않으며, JSON 파싱/ROS/DDS·영상·보호층·구동·입력 수신은 총 비용 밖이다. **PC 제한 오프라인 비용 기준선이지 50 Hz 또는 Jetson 마감 보증이 아니다.** Jetson에서는 동일 입력·소스와 Python/NumPy 환경 차이를 기록한 별도 실행이 필요하다.

후속 입력 감사 CLI도 Python 3.11 전용 `file_digest`를 쓰지 않도록 고친 뒤 합성 예시를 재실행했다. 문법/API 의존성 대비일 뿐 Jetson Python 3.10에서 실행한 결과는 아니다. `hardware_compat_report.json`은 계속 `ready_to_drive=false`다.
