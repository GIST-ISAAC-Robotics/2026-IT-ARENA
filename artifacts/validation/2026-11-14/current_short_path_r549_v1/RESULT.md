# r549 짧은 현재 선호벽으로 저속 재획득

**현재 선택은 revision3이며, revision2의 저속 최소 관측 길이를 유지하고 실제 광선 방향 정렬을 추가했다.** 실측 서보 범위의 r544는19.56m에서 제어기가0속도를 요청했다. 최초 입력의 선호벽 관측 길이가0.300646m에서0.254690m로 줄면서 기존0.28m 경로 생성 조건에 걸렸다. 보호층 충돌 정지가 아니며, 같은 벽으로 만들 수 있는 경로는 전방 약0.50m까지 남아 있었다.

## revision2에서 유지한 수정

`local_path`의 기본 최소길이0.28m는 유지한다. **최대0.1m/s 재획득 helper에서만** `min(0.28, 차체 길이)`를 전달한다. 현재 차체에서는0.207m다. 벽의 관측 호길이와 오프셋 경로의 전방 길이는 다르므로, 경로 자체가 기존0.25m 전방 요구를 충족하는지 별도로 그대로 검사한다. 유효 점12개·형상 적합·외삽 금지·실측 조향 상한·각도 변화율·현재/직전 원시 점유·제동/독립 guard/STOP은 유지한다. helper 출력 상한이0.1보다 큰 호출은 기존0.28m를 사용한다.

현재 선호 방향과 기억을 바꾸지 않는다. 입력을 자유 공간으로 채우거나 정답 지도/자세를 사용하지 않는다. 이 변경은 관측 불확실성으로만 생긴 정체를 줄이기 위한 저속 경로 생성 기준 변경이며, 실차 제동이나 임의 벽 형상의 안전 증명이 아니다.

## 반대벽 전환 초안을 채택하지 않은 이유

처음에는 현재 반대벽의0.65m 경로를 그대로 사용했다. r544의 저장 입력에서는 두 벽이 같은 길을 만들었지만, [별도 Y갈림길2대표](junction_review/native_result.json)에서 왼벽이 짧아지면 왼쪽 선호+16.315°가 오른쪽−16.315°로 바뀌었다. 충돌 여유만으로 원하는 분기임을 보장할 수 없었다.

따라서 [초안 기록](REVISION1_NOT_SELECTED.md)과 소스를 보존하고 반대벽 자동 전환을 제거했다. [최종 같은 Y대표](junction_review/native_result_revision2.json)는 연속 선호벽에서 기존 좌측 명령을 유지하고, 선호벽이 너무 짧은 입력에서는 기존0을 유지했다. 이 Y대표까지 계속 주행하도록 해결한 결과는 아니다. 그 문제 때문에 전체 관측 규칙을 더 복잡하게 만들지는 않았다. source-only `selected_v3`는 초안을 포함하므로 현장 실행본으로 선택하지 않는다.

## 검증

- [저장 전후6입력](revision2/transition_compare.json): 직전 양수2개의 속도·각도는 동일. 최초 정지 관련4입력은 선호벽을 유지하며0.1m/s 후보가 됐다. 실제 수락된 정지 입력에서는−0.144625rad, 남은 경로 약0.476m다. 상세에는 새 최소 관측값이 추가된다.
- [관련42회귀](revision2/regression.xml)8.94초, 최종 저속 조건과 높은 cap의 기존 기준을 포함한 [helper15개 재확인](revision2/final_helper.xml)1.75초 통과. 갈림길·현재 경로·이동차 복귀·실제 전방 장애물·양벽 소실을 포함한다.
- 저장 helper 재계산은 전체 상태 있는 제어기 재생이나 개선 주행 결과가 아니다. [r550 결과](../measured_steering_reacquire_lap_r550_v1/RESULT.md)는 이전19.56m 정체를 통과했으나25.81m에서 다시 멈춰 미완주다. 벽 접촉0·최대1바퀴 도로 밖·명시 STOP·정상 종료와 실제 실행 입력 불변을 확인했다.
- Windows NumPy2.5.4의2D cross 호환 오류로 원 양수 입력이 재현되지 않아 실제 실행 환경인 WSL로 비교했다. 환경/공통 수치 함수를 그 오류 때문에 바꾸지 않았다. Y결과 첫 저장은 NumPy bool 직렬화 오류였고 기록 변환만 수정했다.

[최종 소스 SHA·변경](revision2/manifest.json), 원 r544 입력·실패·STOP/정상 종료를 보존한다. Jetson·ESP32 접속과 설치/flash는0이다.


## revision3 — 실제 광선 방향으로 벽 연결

추가 분석 결과, LiDAR가 차체 중심보다 약66mm 앞에 있어 차체 원점 기준 끝점 각도로 정렬할 때 가까운 벽과 먼 배경의 점이 교차 삽입됐다. 기둥 제거가 최초 원인이 아니며, 제거를 꺼도 짧은 관측 결과가 같았다. 보정 후 실제 광선 방향으로 정렬하면 이 인위적 단절이 사라진다. 실제 깊이 단절·원시 점유·UNKNOWN은 그대로다. LocalFollow의 부분 점군에서도 원래 반환점과 방향의 대응을 유지한다.

[이관 SHA](revision3/manifest.json), [독립 합성 검사](occluder_review/README.md)를 보존했다. 새 외부 artifact 없는7검사를 포함한 기능115개가 통과했다. 처음114통과2실패 중 ROS 환경을 source하지 않은 trace 실패는 [실제 ROS 환경 재검사1개](revision3/ros_native_verify/result.json)로 해소했다. 다른1개는10월 보관 계약의 HEAD 소스 SHA를 현재 파일과 비교하는 검사로, 수정 직전 SHA도 옛 기대값과 달랐다. 과거 계약/실패 XML은 변경하지 않았다. 따라서 전체116개가 모두 통과했다고 보고하지 않는다.

r550 최초 정체 입력은 revision3에서도 경로·추종 각도가 성립하지만 helper가0으로 남았다. 이는 광선 정렬과 별개의 원시 점유 팽창 계산으로 확인 중이며 [r552](../radial_motion_reacquire_r552_v1/)에서 분리한다. revision3 자체의 새 폐루프 주행은 아직 하지 않았다. 실제 실행한 r550은 revision2다.
