# r548 비대칭 변형 벽 한 대표와 실제 장애물 반례

**두 대표를 각각 한 번 계산했다. 비대칭 벽에서 옛 벽 기준0은 현재 경로 후보0.10m/s로 연결됐고, 같은 벽의 전방 실제 장애물은0을 유지했다.** 이번 한정 입력에서 새 잔여 정체를 찾지 못했으므로 수정 후보나 추가 탐색을 만들지 않았다. 공통 파일·WSL·Gazebo·Jetson 변경/실행0이다.

## 고정한 민감도 가정

- r525 ray 교차 생성기를 재사용하고 벽 좌표 부분만 artifact에서 변경했다. 모든 치수는 현장 실측이 아닌 가정이다.
- 좌벽 `y=0.505−0.100+0.060 sin(2πx)`, 우벽 `y=−0.505+0.060 sin(2πx+π/2)` m. 한쪽 벽만100mm 안쪽으로 이동하고 양벽의 사인 위상을90° 다르게 했다. 파장1m, 진폭60mm다. 따라서 이전처럼 두 벽을 평행 이동한 동일 폭 회랑이 아니다.
- x=0.40/1.00m에서 각50mm 접합 공백을 양 벽의 선분에서 제외했다. 50mm는 x축 투영 폭이며 벽 호길이가 아니다. 교차 엔진이 다른 면/장애물의 더 먼 유한 반환을 찾으면 그대로 사용하고, 교차가 없을 때만 UNKNOWN으로 남긴다.
- 장애물 반례는 r525와 같은 전방 `x=0.18m, y=−0.22…+0.22m` 실제 선분을 추가했다. 장애물 점을 벽 적합에서 선택하지 않더라도 원 점유에서 삭제하지 않는다.
- 현재 공통 코드와 r541 대칭 상한 **0.28475436568260193rad**를 사용했다. r521/r525 합성 fixture의500광선·원 index·방향·200μs 취득 간격·센서 원점 등 나머지 설정을 유지했다. 실제 C1 원시 패킷/현재 CAD 센서 장착을 정밀 재현한 시험은 아니다.

표의 주 비교는 r525의 active MOVING_PASS fixture다. 이전 직선벽/앞차 이력을 유지한 뒤 현재 비대칭 벽을0.7s에 입력한다. 앞차는 기존 fixture의1.2m 위치, 닫힌 양 끝면도 유지했다. baseline은 과거 코드를 가져온 것이 아니라 **동일한 현재 공통 코드에서 현재 경로 연결 함수만 시험 프로세스 안에서 비활성화**한 결과다.

별도 LocalFollow fixture도0→0.10m/s/장애물0→0이었다. 이것은 r525와 동일하게0.4/0.5/0.6s 과거 직선벽을 넣고1.1s 현재 입력을 보는 기억 만료 비교이며, 앞차·닫힌 끝면을 넣지 않는다. 이 조건을 정상 직선 주행의 영구 정지 근거로 해석하지 않는다. 이번 두 현재 baseline은 모두0이므로 기존 양수 명령 보존의 새로운 독립 근거는 아니다.

## 기억 불일치와 실제 점유를 구분한 근거

변형만 있는 조건의 기존 MOVING_PASS 정지 이유는 `entry_guide_current_outer_wall_unavailable`이다. LocalFollow는 `follow_boundary_unconfirmed`였다. 현재 후보는 관측 벽0.650m에서 짧은 경로를 만들고 경로 앞 길이0.378483m, 앵커 오차0.118518m를 얻었다. 과거 경로를 새 기억으로 승인하거나 오래된 점유 허가를 복사하지 않는다.

현재 조향−0.150185rad의 swept clearance는0.640m, 직전 조향0rad는0.880m다. 제동 속도 한도0.956466m/s보다 명시 후보 상한0.10m/s가 작아0.10을 제안했다. LocalFollow의 앞차 없는 별도 fixture에서는 직전 조향 여유가2.5m이고 현재 조향 여유는 같은0.64m다. 새 조향 상한 안의 후보이며 이 조건에서는 끝각에 포화되지 않았다.

장애물 반례는 경로 적합 자체는 반환했으나 **후륜축 기준 전방 목표점0개**여서 `pursue_path`의 `path_too_short` 단계에서 먼저 거절됐다. 따라서 helper가 직접 점유 검사를 실행해 정지했다고 설명하지 않는다. 저장된 원시500반환을 별도로 동일 외곽/광선별 여유로 계산한 직진 swept clearance도 **0m**였다. `obstacle_cause.json`에 최초 거절과 실제 점유 근거를 분리했다. 장애물이 틈/벽을 가려 UNKNOWN14가0으로 바뀐 것은 유한한 실제 반환의 결과이며 UNKNOWN을 free로 치환한 것이 아니다.

## 보존·실행 범위

MOVING_PASS 입력은 계산 전후 scene/ranges 동일, 원 source_index0…499 및 상태 배열 불변을 assert했다. 벽/장애물 label과 생성 정답은 ray 거리 생성에만 쓰며 제어기에는 전달하지 않았다. 현재 helper의 원 점유 개수·경로·제동 진단과 raw ranges를 저장했다. LocalFollow 별도 fixture의 출력도 `*_outputs.json`에 보존했다.

Windows Python/NumPy의 기존 r518 pytest 의존성과 process-local2D cross 호환만 사용했다. BLAS/OMP/MKL 스레드를1로 제한하고 프로세스 낮은 우선순위를 요청했다. 두 대표 본 계산은 약0.248/0.191초, 최초 Python 프로세스 전체는 약1.27초였다. 성공을 얻기 위한 재실행·조합 확장·상한 조정은 하지 않았다. 저장 장애물 경로/반환의 사후 산술 확인은 시나리오 재실행이 아니다.

이번0.10은 현재 경로/원시 점유·제동 조건을 통과한 **명령 후보**다. 실제 독립 lidar_safety→MCU 적용, 연속 재획득, 접촉으로 벽이 움직이는 동역학, 실차 주행 또는 UNKNOWN 사이의 모든 물체를 보장하지 않는다. `report.json`, `source_manifest.json`, `sensor_generator.py`, `probe.py`가 상세 근거다.
