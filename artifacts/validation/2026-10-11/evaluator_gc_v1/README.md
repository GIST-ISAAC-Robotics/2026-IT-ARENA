# 평가기 순환 GC 지연 대조 — 실행 전 등록

2026-10-11 KST. 사용자가 Claude 워커 없이 다음 작업을 승인했다. GPT 주 에이전트가 직접 구현·실행·검토한다.

## 범위와 변경

- `probe_braking_contact.py --evaluation-gc native|defer`만 추가한다. 기본 `native`는 GC 설정을 바꾸지 않는다.
- `defer`는 짧은 `sim_grid` 평가 프로세스의 자동 **순환 GC**만 연기한다. 참조 카운팅은 유지된다. 제어 노드/보호층/가상 MCU/플러그인/센서에는 적용하지 않는다.
- `gc.freeze()`는 당시 존재하는 객체만 고정한다. 시험 중 새로 누적하는 수신 로그 객체의 순환 GC 비용까지 피하려는 이번 대조에는 `gc.disable()`/원상 복원을 사용한다. 메모리 누적 해법이나 장시간 운용 최적화로 채택하지 않는다.
- 창은 Gazebo launch 전부터 해당 자식 프로세스 정리 후까지다. 예외·정리 오류에서도 `finally`로 원래 GC 활성 상태를 복원한다. 600초/평가기 최대 RSS 2 GiB 예산 초과는 실패로 종료한다. 기존 차량 보호 한도를 바꾸는 값이 아니다.
- 원시 GC 이벤트·tick/clock 자료·소스 ZIP·복원 여부·평가기 최대 RSS를 보존한다. 이전 r2 계약과 결과는 그대로 두고 r3 후속 계약에 변경을 등록한다.

## 사전 실행 순서와 수용 조건

최대 신규 Gazebo 4회: A1(native), B1(defer), B2(defer), A2(native), 같은 코드·1 ms·공식 분할 노면·평가용 passive_damping·기존 10/8 명령·위상 10 ms·명령 전환 추적 켬.

각 실행은 별도 plan/status로 한다. 실패 뒤 자동으로 다음 사례를 돌리지 않는다. A의 **자연 스케줄 지연 검사만** 실패하고 STOP/실제 정지/정상 종료·원시/소스/다른 입력이 유효하다면, 그 실패를 그대로 보존한 뒤 사전 계획한 B 진단을 수행할 수 있다. B 실패나 다른 실패는 중단하고 분석하며 성공할 때까지 재시도하지 않는다.

1. B는 모든 요청 tick ≤10 ms, 누락 0, 기존 입력/추적/STOP/정지/정상 종료 기준 통과.
2. B의 측정창 순환 GC 이벤트 0 및 원래 GC 상태 복원. RSS <2 GiB, native 대비 증가도 보고한다.
3. A/B 원시 자료 해시·소스 계약·바이너리 동일성·차량/월드 보존 확인.
4. A의 ≥5 ms 자연 지연/GC 정지와 B의 최대·p99 지연을 비교한다. A가 이번에 재현되지 않거나 B에 다른 지연이 남으면 그대로 기술한다. 두 반복을 분포/실차 성능으로 확대하지 않는다.
5. 물리 지표의 개선은 수용 조건이 아니다. GC를 바꾸면 명령 적용 시점도 달라질 수 있다. 스폰/적용 ±1 step 문제의 해결이나 G1 성공으로 해석하지 않는다.

## 시점 고정 설계 검토 — 이번에는 실행 코드 미변경

현재 서비스 스폰은 벽시계 TimerAction 뒤 `create`로 삽입되며 첫 PreUpdate가 2/3 step으로 달랐다. 평가 실행 사본 월드에 완성 차량과 같은 초기 pose를 포함시키는 방법은 이 비결정 요소를 제거하는 후보다. 원본 월드·모델을 건드릴 필요는 없지만, 첫 추적 이벤트/센서 수신을 놓치지 않도록 paused 시작과 구독 준비·unpause까지 함께 설계해야 한다. 단순 고정 sleep은 준비 완료 증거가 아니다.

출력 노드의 벽시계 타이머를 sim 타이머로 바꾸는 것만으로 Gazebo 적용 step까지 고정되지는 않는다. ROS→bridge→gz 전송은 여전히 비동기다. 기존 벽시계 watchdog을 빼면 시계 정지 중 보호가 멈출 위험도 있다. 따라서 이번에는 공통 출력 계약·`AppliedGuard` 같은 stamp 거부·보호 타이머를 바꾸지 않는다. 이후에는 평가 전용 시작 절차와 실제 적용 deadline/ack를 구분하여 설계하고, 지연된 입력을 소급 적용하거나 `/drive/safe`를 우회하지 않는 시험을 먼저 정의한다.

G1·우회/추월·고속·물성 조정·Jetson·전원 변경·커밋/푸시·외부 게시를 수행하지 않는다.

## 결과

신규 4회 모두 입력 유효·STOP·실제 정지·정상 종료를 통과했다. 다만 B1의 GC 계측 조건은 실패했으며 [추가 등록](ADDENDUM.md)에 따라 코드와 실행 순서를 변경했다. 원래 ABBA 반복은 완수하지 못했다.

| 실행/계약 | 최대 요청 지연 | GC 2세대 횟수 | 최대 GC 정지(벽시계) | 평가기 최대 RSS | GC 대조 판정 |
|---|---:|---:|---:|---:|---|
| A1 native/r3 | 0 ms | 8 | 177.3 ms | 400.1 MiB | 기준 유효 |
| B1 defer/r3 | 0 ms | 0 | 0.133 ms(0세대) | 415.5 MiB | 준비 중 1회가 계측 창에 포함되어 실패 |
| A2 native/r4 | 6 ms | 8 | 137.2 ms | 426.5 MiB | 기준 유효 |
| B2 defer/r4 | 0 ms | 0 | 0 ms | 398.0 MiB | 수정본 대조 통과 |

- r4 한 쌍은 같은 소스·플러그인·차량·정규화 월드/메시·프로필·초기 pose다. 예정 tick 326개씩, p99 요청 지연 0 ms, 누락 0. A2의 6 ms 지연은 87.5 ms 2세대 GC 정지와 겹쳤다. 최대 poll 공백은 A2 139.4 ms → B2 5.91 ms(벽시계).
- B2의 GC 누적 증가량 `[0,0,0]`, 종료 후 원래 활성 상태 복원, 최대 RSS 2 GiB 미만을 확인했다. 런타임 기본값은 여전히 native다. 표의 RSS 감소를 메모리 절약 효과로 해석하지 않는다(실행별 수신 수·메모리 할당 변동, 1쌍).
- A1은 긴 GC 정지가 있었는데도 요청 시각 감사상 지연 0이었다. 따라서 GC가 항상 늦은 tick을 만든다고 단정하지 않는다. 헤더 시각은 평가기가 관측한 ROS 시계이며 물리 적용 시각의 정답이 아니다.
- GC 정지 제거가 실제로 가능하다는 제한된 대조 결과다. 원래 10/9의 13 ms 위반이 모든 조건에서 해결됐다거나, ROS/MCU 지연·스폰/적용 ±1 step·분할 노면 물리 재현성이 해결됐다고 주장하지 않는다.
- Windows 기본 Python 분석 실행은 NumPy가 없어 한 번 실패했고 실행 환경인 WSL Python으로 분석했다. 실행 결과·원시 자료는 수정하지 않았다.
- 전체 회귀 최종 **1,326개 통과**. 최초 전체 검사는 1,325개 통과/1개 실패였으며 기존 시험이 현재 평가 스크립트에 r2 해시를 요구한 것이 원인이었다. r2의 기존 불변 검사를 유지하고 r3/r4 후속 해시 계약을 연결했다. `pytest_final.log`에 최초 실패, `pytest_final_v2.log`에 최종 통과를 보존했다.
