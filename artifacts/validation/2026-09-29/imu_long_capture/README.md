# 연속 재생용 새 원시 기록

기준 결과는 [A3 보고서](../../../../docs/simulation/JETSON_REPLAY_2026_09_28.md)에 정리합니다. 기존 21초 기록의 반복 대신 새 폐루프 주행 입력을 확보하는 작업입니다. 원시 bag·receipt는 Git 제외입니다.

## capture_v1 — 실패 보존

- `virtual_mcu`, `local_pursuit`, 순차 C1 10 Hz, 운동 보정 `both`, 제어 50 Hz, `local_fast`, 슬롯 3, 신호 대기 8초, 방지턱 임시 해제, NVIDIA 렌더링 조건을 유지하고 목표만 12→70 m로 늘렸습니다.
- 목표 전 **19.897 m**에서 `MCU latched before requested stop: invalid_drive`로 실패했습니다. 프로세스 종료는 정상, 기록은 완료/recorder 0/강제 종료 없음, bag 감사는 통과했습니다. 기록 구간은 **24.972초**이며 **정상 장시간 시험 입력으로 채택하지 않습니다**.
- `steering_failure_v1.json`: 포화 등가 조향각 `0.3756455765751818 rad`가 ROS float32 직렬화 후 `0.37564557790756226 rad`로 바뀌어 엄격한 MCU 상한을 약 `1.3324e-9 rad` 초과했습니다. 마지막 `/drive/safe`와 참조 MCU 재현 검사를 대조했습니다. 센서 지연이나 모터 성능 문제로 설명하지 않습니다.
- 원시 기록 폴더 106,196,382 bytes, 비압축 payload 합계 4,334,840,340 bytes는 서로 다른 수치입니다. `source_snapshot.zip`, `runner_v1.log`, `report.json`, `sensor_recording/audit.json`을 보존합니다. 실제 주행/기록/정지/프로세스 종료 판정도 구분합니다.

## 수정 범위

`simulation.launch.py`의 지역 제어기·LiDAR 보호층 송신 상한만 물리 한도 이내에서 표현 가능한 가장 큰 float32인 `0.37564554810523987 rad`로 설정합니다. 가상 MCU 수신 한도·엄격한 범위 검사·구동 계약·센서율·보호 시간은 그대로입니다. 허용 오차를 넓혀 범위 초과를 통과시키는 수정이 아닙니다.

`tests/test_steering_transport_limit.py`는 기존 오류 재현, 좌우 한계 수신, 안쪽 최대 표현값, 500개 표본, 비정상 입력, 실제 한계 초과 거절, ROS CDR 왕복을 검사합니다. 후속 시험은 새 `capture_v2`에 저장하며 v1 실패를 덮지 않습니다.

## capture_v2 — 시간·기록 한도 초과

- `pc_fix_tests_v1.log`: 관련 WSL 회귀 **100개 통과**. 수정 launch의 설치 경로 일치 확인 후 같은 70 m 조건으로 재시험했습니다.
- 기존 실패 지점 19.9 m를 지나 33.67 m까지 정상 진행한 중간 출력이 있었으나, 실행 담당의 마지막 runner 출력은 **43.433 m에서 실제 시간 한도 초과**입니다. 정상 70 m 완료 기록이 아닙니다.
- 당시 후속 확인은 승인 검토 서비스 `502 Bad Gateway`로 중단했습니다. 사용자 재개 요청 뒤 최종 파일과 프로세스를 확인했습니다. `shutdown_clean=true`, 프로세스 종료 코드 `[0, 0]`, 강제 정리/잔존 시험 프로세스 없음입니다. 요청한 주행/정지 검증의 통과와는 다릅니다.
- 최종 시뮬레이션 시각은 **40.389초**, 이동 진행량 **43.433 m**, 충돌/센서 정지 표본 0개이며 차량은 `RUNNING`이었습니다. 느린 시뮬레이션에서 실제 실행 900초 한도를 넘긴 것이며, 차량이 정체됐다는 근거는 없습니다.
- 그보다 먼저 기록기가 약 37.17초 입력에서 **비압축 6 GiB 한도**에 도달했습니다. `manifest.complete=false`, `raw byte limit reached; partial recording retained`, 기록기 종료 코드 1입니다. 불완전 기록은 정상 재생 입력으로 사용하지 않습니다. 기존 검증기는 기록기의 조기 종료를 주행 중 확인하지 않아 실행 시간 한도까지 계속 진행했습니다.
- v1/v2의 원본·보고서·실패 판정은 보존합니다. `resume_checks_v1.log`와 `resume_plan_v1.json`에 최종 확인과 자원 산정 근거를 남겼습니다.

## capture_v3 — 정상 기록 확보

기록기가 예정된 종료 전에 끝나면 즉시 시험을 실패 처리하도록 주행/정지 검증 루프에 감시를 추가했습니다. 종료 코드 0도 예외로 통과시키지 않습니다. `--record-max-raw-gib`와 `--record-max-wall-seconds`를 명시적으로 전달하고 기록 manifest에도 한도를 남깁니다. 기본값 6 GiB/1,200초 및 디스크 여유 보호는 그대로입니다.

`pc_recording_tests_v1.log`: 세 실행 파일 컴파일과 관련 검사 **193개 통과**. 기본값/명시 한도 전달·비정상 한도 거절·기록기 조기 종료 검사와 기존 구동/보호/경로/기록 계약 회귀를 포함합니다. 주행 결과를 대신하는 검사는 아닙니다.

v2 관측값으로 70 m와 출발/정지를 합쳐 약 60.4초 입력·9.75 GiB 비압축 payload·실제 약 1,346초가 예상됩니다. 이는 추정치이며 압축 bag의 디스크 사용량과 다릅니다. 새 시험만 실제 실행 2,400초·정지 120초·기록 16 GiB/2,700초로 제한합니다. 기록 시간에는 기동/정지 여유를 포함합니다. 센서율·센서 신선도/MCU 수신 한도·속도 정책은 변경하지 않습니다. 성공 시에만 무결성 감사 후 Jetson 연속 재생으로 진행합니다.

- 단일 실행 결과 **70.06927 m 주행·정지·정상 종료 통과**. 본선 약 1.5바퀴의 목표 진행량이며 경기 5랩 전체 시험은 아닙니다. 충돌/센서 정지 표본 0개, 코스 마커 ID 0/20/30/45 관측, 순차 취득·센서 전용 입력 경계 검사를 통과했습니다.
- 이동 속도 중앙값 1.4554 m/s, 최고 2.2794 m/s, 코너 표본 중앙값 1.3297 m/s. 약 5.24/8.21/4.79 km/h이며 20 km/h 검증은 아닙니다. 정지 요청 후 변위 0.7113 m, 검사 완료까지 시뮬레이션 1.404초, 최종 가상 MCU는 `ESTOP_LATCHED / software_stop`입니다. 실물 제동 거리로 사용하지 않습니다.
- `capture_v3/sensor_recording/audit.json`: **verified=true**, 연속 입력 **59.53초**, RGB 3,716개·IMU 14,883개·엔코더 5,953개·LiDAR 595개. 파일/CDR 해시·receipt 개수 일치, 알려진 큐 손실/시계 역행 없음. 모든 원본 센서 송신 표본의 수신까지 보증하는 검사는 아닙니다.
- 비압축 10,332,991,328 bytes, 기록기 실제 시간 1,338.17초. `manifest.complete=true`, 기록기 0 종료·강제 종료 없음. Gazebo/ROS 정상 종료·잔존 시험 프로세스 없음도 확인했습니다. 로그 `runner_v3.log`, 당시 소스 `capture_v3/source_snapshot.zip`, 최종 판정 `capture_v3/report.json`을 보존합니다.
- 후속 Jetson 시험은 이 정상 기록을 변조/반복 연결하지 않고 1배속으로 재생합니다. 원시 기록은 비공개 PC→사용자 Jetson 전송 범위이며 Git 제외를 유지합니다.

## Jetson 전송과 재개 지점

- 읽기 전용 사전 확인에서 `jetson-orin.local` 접속·약 33 GB 여유 공간·기존 재생 프로세스 없음·DDS 감사 라이브러리 존재를 확인했습니다. 환경/전력 설정은 바꾸지 않았습니다.
- `build/jetson_long_capture_v3.tar.gz`는 115,576,399 bytes이며 SHA-256은 `72303490e5c0c8e7a66d76311e0be93b756d060f8c7f26313eee5b6cf360d542`입니다. `transfer_manifest_v1.json`에는 **7파일**(MCAP·metadata·receipt·ready·parameters·manifest·audit)의 크기/해시가 있습니다. 원시 자료와 압축본의 Git 제외를 확인했고 추적 중인 원시 bag/receipt/ready는 없습니다.
- 처음에는 구체적 전송 승인 확인 불가로 중단했습니다. 이후 사용자가 명시된 자료/장치/경로에 대해 “어 시작해”로 승인했습니다. 실행 담당의 요청에는 같은 거절이 있었지만, 본 대화의 직접 승인 맥락을 포함한 **동일 `jetson_access.ps1 -Action put` 정식 검토**는 통과했고 전송을 완료했습니다. 다른 전송 경로나 키 검증 우회는 사용하지 않았습니다.
- 완료 목적지: **사용자 Jetson `q@jetson-orin.local`의 `/home/q/it_arena_a3_20260928/build/jetson_long_capture_v3.tar.gz`**. 원격 `sha256sum`이 위 로컬 해시와 일치합니다. `jetson_transfer_verified_v1.log`가 직접 확인 근거입니다. `jetson_resume_check_v1.log`는 전송 전 상태이며 그 안의 수기 로컬 해시에는 오기가 있으므로 실제 manifest와 원격 해시를 기준으로 합니다. GitHub/제3자 서비스 게시는 하지 않았습니다.
- 그다음 압축 구성파일 검증 요청에서 **자동 승인 검토 서비스의 사용량 한도 오류**가 발생해 즉시 실행을 중단한 이력이 있습니다. 사용자 승인 부족·SSH 접속 실패·센서 기록 결함으로 판정하지 않았습니다. 당시에는 압축 해제·재생 전이었으며, 이후 사용자 재개 요청에 따라 아래 작업을 완료했습니다.
- 재개 후 기존 원격 압축본의 안전 경로/일반 파일 여부 및 7파일 크기·해시를 검사했습니다. 재전송 없이 새 `artifacts/validation/2026-09-29/imu_long_capture/capture_v3/sensor_recording`에만 풀었고 추출 파일도 7/7 해시가 일치했습니다. 이후 `artifacts/jetson_a3/long_capture_v3_a`, `_b`에 각각 1배속·legacy·SHM 16 MiB·엔코더/IMU 발행 추적 ON·추가 최소 수신자 OFF로 실행했습니다. 독립 두 회이며 연속 2분 입력이 아닙니다.
