# 기존 먼 벽 연결과 현재 단독 구성의 저장 입력 비교

과거 `ray_wall_continuity` 후보는 최고속도가 더 높았지만 랩이 느려 선택하지 않았다. 현재는 경로 선행 감속·벽 전환 등 후속 변경이 있으므로, **새 알고리즘을 추가하지 않고** 현 단독 구성의 `ray_wall_continuity`만 켠 값을 저장 입력에서 비교한다.

저장 입력 비교 중에는 당시 경기 거리 시험과 소스를 변경하지 않았다. 새 정지, 조향 차이, 고속 명령 지속, 기준 재생 일치를 보고 실제 단독 비교의 가치가 있는지 판단한다. 이 계산은 원래 주행이 남긴 입력을 사용하므로 실제 랩 단축이나 무충돌 증명이 아니다.

## 저장 입력 결과와 후속 선택

[결과](summary.json): 기준 1,860판단 일치, 새 정지/해제 0, 최대 조향 차이 0.03089 rad. 계획 목표 최고는 2.70567→2.77778 m/s, 2.5 m/s 이상 목표는 0.58→4.28초였다. 현재 1.5 m/s² 증속률 계산 뒤에도 최고 2.38012→2.60412 m/s, 2.5 m/s 이상 0→1.06초로 개선 가능성이 남는다.

2.0/2.5 m/s² 계산은 더 높았지만 다음 폐루프에는 **가속 설정을 그대로 유지한다**. 기존 기능 조합 하나의 손익을 먼저 분리한다. [경기 거리5랩](../official_race_distance_v2/README.md)을 마친 뒤 별도 프로필 `g1_open_10kmh_solo_gap05_arc_preview_bridge_ray`를 추가했다. 기존 프로필과 기본값은 같으며, 집중 회귀·빌드 뒤 단독1랩만 비교한다. 실제1랩 시도는 아래와 같이 미완주했으며 후보는 보류한다.


## 연결과 검사

[수정 전](profile_before.zip), [소스 계약](../../../../config/tests/solo_ray_combination_r1_sha256.json), [실행 계획](PLAN.md)을 보존했다. launch에 기존 프로필 상속과 ray 옵션 하나를 더하고 평가 CLI의 선택/신호 조건/소스 보존 목록을 연결했다.

첫 집중 회귀는 **111통과·2실패**였다([원본](tests_attempt1.log)). 하나는 새 조합 이름을 기존 preview 프로필 검사 목록에 넣지 않은 것이었다. 다른 하나는 이전 반대 벽 고속 허가 수정 뒤 남은 오래된 단위시험 기대값이다. 같은 관측 스캔에서 마커 기준 벽이 바뀌어도 현재 경로는 유효하므로 단독 고속 허가를 유지한다. 반대로 이전 스캔의 기억 경로만 남은 경우에는 통상 상한을 유지하는 대조를 추가했다. 이 두 검사 수정으로 런타임 감속/관측 기준을 바꾸지는 않았다. 이전 기본13실패와 구별하며 원본을 덮어쓰지 않았다.


## 실제 주행 결과: 고속 달성, 미완주로 보류

집중 회귀 **113통과**·빌드·등록 뒤 1회 실행했다. [주행 수치](run1_metrics.json), [실패 포함 요약](run1_summary.json), [노면](run1_surface.json)에 근거를 남겼다.

- 최고 차체 속도 **2.73664 m/s(9.85 km/h)**, 최고1초평균2.62363 m/s. 목표10 km/h의95% 이상은0.309초·0.836m였다.
- **43.433 m에서 미완주**, 원시 `passed=false`, 종료코드1. 기록상 초록 구간36.834초 중0.05m/s 이하7.151초였다. 이전34.451초 완주 구성을 대체하지 않는다.
- 접촉·차체/바퀴 도로 이탈 표본0. 실패 정리의 STOP 응답·고밀도 자세 정지 및 소스불변·프로세스정상종료는 확인했지만 `stop_stable=null`이며 정상 완주 STOP 통과로 바꾸지 않는다.
- 원본/시뮬시간 보정 영상은733프레임 전체 디코딩 통과. [정지 장면](run1_video_review/frame_00695.jpg)에서 길을 가로막는 상대 차량은 없다. 이미지 한 장으로 모든 충돌 위험 부재를 주장하지 않는다.
- [모터 검사](run1_motor_audit.json)는 단일모터·28카운트·8.970588:1·65mm와 실제 카운트를 확인했으나, 실패 보고서에 제어기 구독 목록이 없어 그 항목은 미확인/실패다. 두 바퀴 엔코더로 실행된 것으로 해석하지 않는다.

## 저장 입력에서 구분한 원인과 재개 조건

[판단 전환](failure_transitions.json): s≈43.11m에서 좁은 무반환이 나타날 때 기존1.2m/s 초과 부분관측 조건으로0명령이 나왔다. 잠시0.5m/s 후보를 냈으나37.84초에 이전점이 새 무반환 구역과 주행 범위에 들어오는 가설로 `previous_point_in_missing_sweep`가 래치됐다. 해제에 쓰는 표면 대응은 미수렴으로 거부됐다. 이전34.451초 구성에서는 같은 후반 구간에 짧은 정지만 있었으며, 이번 후보의 다른 궤적·속도에서 장기 정지가 나타났다.

[수치 수렴 비교](numerical_fit_probe.json)는 첫 래치의 센서 좌표만 썼다. 원래6회,12회,24회와감쇠12/24회 모두 거부됐다. 원래값은 잔차RMS약8.01mm·대응167점인데 마지막 이동이약0.192mm로10µm 수렴 조건을 넘는다. 반복을 늘려도 약0.193mm의 왕복이 남았다. 이는 수치 조건을 검토할 구체적 근거이지만, 그 조건 하나를 바꾸면 전체 주행이 해결된다는 증명은 아니다. 실제 반환·기억 대응·경로와 정지 해제를 저장 입력에서 함께 비교한 뒤 필요하면 다시 후보를 시험한다. 이번에는 런타임 수렴 조건·보호 기준을 변경하지 않았다.

후처리도 실패를 보존한다. 최초 `post.py`는 lap=null을 더하려다 오류가 났으며 [원본 로그](run1_post_summary_attempt1.log)를 보존했다. 미완주에서는 마지막 관측 시각과 양쪽 기록이 실제로 덮는 거리만 집계하도록 고쳐 요약 생성만 다시 실행했다(`post_summary_fixed.exit=0`). 전체 후처리 종료코드1·모터 구독 미확인·원시 미완주 판정은 바꾸지 않았다.

**다음:** 이 후보를 선정하지 않고 기존34.451초 구성을 유지한다. [선두 카메라 후보의 신호·마커·화면STOP 통합 확인](../official_camera_mount_v1/PLAN.md)을 우선한다. 수치 수렴/정지 해제의 추가 개선은 필수 출발 기능을 확인한 뒤 속도 보강으로 돌아온다.
