# 실제 브라우저와 Gazebo 운영 연결

이전 e1의 조작 알림 실패 뒤 화면 연결만 b1으로 분리했다. [run.sh](run.sh), `b1/report.json`, `b1_console.log`, `b1/ops_log.jsonl`에 원본이 있다.

실제 운영 화면에서 출발 준비를 클릭했고, 가상 MCU ARM 뒤 RGB 신호로 출발했다. STOP도 실제 화면에서 클릭해 요청 ID `517a4158`의 정책 수락과 MCU 소프트웨어 정지 응답을 확인했다.

다만 **주행 중 브라우저 STOP으로 끝낸 시험은 실패다.** 평가기가 wall 198.219초에 화면 STOP을 기다렸고, 180초 뒤 wall 378.227초·sim 33.02초에 자체 `eval-001` STOP을 먼저 보냈다. 화면 요청은 그 뒤 도착했다. 따라서 화면 요청의 수락은 확인했지만 그것이 차량을 처음 멈췄다고 해석할 수 없다. 기다림 중 컨텍스트 재구성이 겹친 실행 조정 문제다. `await_browser_snapshot` 단계도 도달하지 않았다.

[실제 캡처](browser_stop.png)는 요청 수락·MCU 정지를 보여준다. 캡처 때 시험 서버 종료로 연결 끊김이 표시됐으며, 화면의 ‘실제 차체 정지 미확인’은 의도한 한계 표시다. 원격 상태만으로 실차 정지를 증명하지 않는다.

`source_unchanged=true`, 노드 종료 코드 `[0,0]`, 소유 프로세스 강제 종료·잔여 없음, Gazebo 종료 서비스 확인. 원본 `passed=false`를 유지했다. API STOP과 실제 정지는 다른 운영 시험에서 확인했고, 이 결과는 브라우저 연결·요청 수락의 제한 증거로만 쓴다. 같은 코스를 화면 증명만을 위해 반복하지 않고 다음 통합 주행 때 조작 대기 구간을 명시적으로 확보한다.
