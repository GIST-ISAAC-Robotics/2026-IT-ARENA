# 실센서·별도 주행 계산의 메모리/CPU 측정

사용자의 GUI 비용·주행 중 메모리 질문에 따라 기존 r363 비구동 동시 부하를 새 디렉터리에서 한 번 수행했다. C1/IMU/B0390 관측20초와 r353 저장 입력의 두 계산 프로세스31초를 겹쳤다. **실제 센서로 주행하거나 모터를 구동한 시험은 아니다.** GUI/NoMachine·전력 설정은 유지했다.

| 관측 | 결과 |
|---|---:|
| 전체 측정 표본 | 53개, 약1초 간격 |
| 최소 `MemAvailable` | 4,183.4MiB, 약4.09GiB |
| 최대 스왑 사용 | 1MiB |
| 스왑 입출력 증가 | 읽기0페이지·쓰기12페이지 |
| 센서/계산 동시 구간 CPU 평균·최대 | 전체72.29%·81.97% |
| 같은 구간 개별 코어 최대 | 100% |
| GPU 활성률 최대 | 50표본 중0% |
| 별도 계산 양수 발행 | 134회 |
| 양수 뒤 발행 간격 p95 | 219.07ms |
| 명령200ms 만료 뒤 누적 공백 | 8.0467초 |

CPU 수치는 `/proc/stat`의 1초 차분이며 전체 수치는 모든 코어 합계 대비, 개별 코어는 그 코어 대비다. 분석 구간21개는 계산 프로세스 시작부터 live 실행 종료까지로 시작/종료 준비가 일부 포함될 수 있다. GPU 수치는 그래픽 엔진 활성률이며 카메라 전용 하드웨어 전체 사용량이 아니다. 메모리 용량/반복적인 스왑 읽기가 병목이라는 증거는 없고, 현재 우선 개선 대상은 CPU의 계획/현재 관측 계산과 처리 일정이다. 전체CPU가100%가 아니어도 특정 코어·의존 단계가 다음 출력을 지연시킬 수 있다.

원r363의 카메라60Hz 취득·20Hz 전달과 같은 센서/소스를 썼다. 하지만 시간 재생 표본 선택·일정이 달라졌으므로 만료 공백의 전후 차이를 특정 기능 개선/악화로 귀속하지 않는다. 최신 차량 기하·실제 엔코더·실차 출력까지 포함한 전체 운영 성능 증명은 아니다.

최초 wrapper에서 기존 가상환경의 `serial` 경로를 빠뜨려 센서/계산 자식 실행 전에 실패했다. 실패 폴더는 보존하고 기존 run.sh의 의존 경로를 복구한 새 `r373b` 디렉터리에서 실행했다. 새 설치나 패키지 변경은 없었다. 새637·원752파일 불변, 부모/센서/계산 정상 종료·포트 반환과 실물 출력0을 확인했다. 센서 원시 자료는 `remote_result/` 및 `initial_failure/`에 로컬 보존하며 기존 Git 제외 정책을 따른다.

[집계](audit.json)·[측정 wrapper](resource_probe.py)·[환경](run.sh). 사용자 조작 없이 가능한 자원 확인을 마쳤으며, GUI 제거·메모리 용량 증설보다 경로 계산의 실제 비용을 우선한다.
