# 실행 지연 자문과 주 에이전트 검토

2026-11-13, Claude Fable 5.2/high에 반복되는 Jetson 계획 지연과 다음 변경의 우선순위만 읽기 전용으로 자문했다. [답변 원문](advice.md), [출처 메타데이터](metadata.json)를 보존한다. 코드/장치 변경은 하지 않았고 관측·추론·미열람 범위가 답변에 구분되어 있다.

## 참고할 발견

- 평균 비용만 보지 말고 SOLO/RELEASED 구간을 나눠 비교한다. r360과r363의 다른 발행량을 카메라 전달률 하나로 설명할 수 없다. 자문은 r360의 계산 분기가 RELEASED로 진입하지 않은 차이를 확인했다. 직접 원인은 아직 추론이다.
- RELEASED의 반복 영역검사 비용과, 새 계획 때문에 곧 폐기될 보관 경로 현재검사의 슬롯 점유를 우선 본다. 새 기한·관측 허용량을 늘리는 대신 쓸모없는 제출을 줄이는 후보가 제안됐다.
- 같은 상태 진입을 확인한 제한 비교에서 효과가 없으면 계산 미세조정에 머무르지 말고 주행 정체/실제 실행 연결로 이동한다. 제안 효과35%는 단순 모형의 추론이며 채택 성과가 아니다.

## 그대로 채택하지 않는 판단

답변은 `tof_safety.py`의 **수신 후300ms** 유지 조건으로 실제 정지가 드물 수 있다고 해석했다. 그러나 현 구성은 ToF가 없는 **`lidar_safety.py`** 경로다. 이 보호층은 명령 header 나이가 **200ms 초과이면 `stale_input`으로0출력**한다. 부분 관측 정책이 켜져 있으면 관측 기억은 갱신하지만 만료 명령의 구동 출력은 허용하지 않는다. 따라서 **“명령 발행간격이300ms 미만이면 실제 정지는 거의 없다”는 결론은 현재 연결과 맞지 않아 반려한다.** MCU도 별도 source_age/ttl과 임대 기한을 사용한다. r358/r363의 명령 만료 공백은 계속 미해결이며 실제 주행/보호 상태와의 연결을 추가로 봐야 한다.

실행 계약의 RELEASED 확장은 앞차/측방 상태 의미를 바꾸므로 이번 자문만으로 채택하지 않는다. 우선 제안A(진행 중 새 계획에 의해 폐기될 보관 검사 제출 억제)를 기존 입력·epoch·STOP 계약 아래 선택형 비교할 수 있다. 다만 현재 사용자의 수동 신호 출발·CAD 서보 반영과 r364 제한 주행을 먼저 마치고, 구현 소유권/시험 상태를 정리한 뒤 다음 독립 묶음으로 다룬다.
