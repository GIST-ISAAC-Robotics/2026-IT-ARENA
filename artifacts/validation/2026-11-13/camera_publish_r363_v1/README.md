# r363 카메라 취득60Hz·ROS 발행20Hz 제한 비교

2026-11-13. [사전 범위](PLAN.md)대로 기존20초 실제 센서 관측+31초 별도 계산 부하를 한 번 실행했다. [집계](audit.json), [재집계](audit.py), [추가 소스 해시](overlay_manifest.json)를 남겼다. 새 remote root만 사용했으며 원 r358/r360은 변경하지 않았다.

카메라 파이프라인/노출 설정을 바꾸지 않고, appsink 이후 프레임 메모리 복사·ROS 발행만 제한했다. 낮은 발행률에서도 영상 판단 완료 수는 유지됐고 이번20초에서는 전달 누락이 없었다. **취득 단계의 부하가 없어졌거나 움직이는 마커의 검출률을 입증한 결과는 아니다.** 프레임률 자체가 잔상을 결정하지 않으며 노출시간·조명도 관련되지만 이 시험은 노출/픽셀 품질을 측정하지 않았다.

별도 계획 계산은 오히려 양수143발행·명령 만료 뒤 공백7.53초로 r360의264발행·3.77초보다 나빴다. 비동기 일정/상태·클럭 조건을 통제하지 않은 한 번의 시간 재생이므로 전체 계획 성능의 개선이나 악화를 카메라 발행률 하나에 귀속하지 않는다. **계획10Hz 미달은 여전히 미해결**이며 이 결과를 카메라 최적화만으로 해결했다고 쓰지 않는다.

공통 bridge/runner에는 선택 CLI만 추가했다. 기본 모든 프레임 발행은 유지한다. 카메라 주기/실행 연결21개 검사와 별도 runtime48개 검사를 합친69개가 통과했다. 원본752파일과 새 root637파일 전후 변경0, 센서·계산 자식 정상 종료, IMU inactive·C1 STOP·카메라 NULL·포트 반환을 확인했다. 원시45개 결과는 `remote_result/`에 로컬 보존/Git 제외다.

사용자는60fps를 필수로 고집하지 않으며 실제 촬영30fps도 허용했다. 신호등은 수초 확인 지연을 감수하고 오출발 억제/가림 해소 뒤 출발을 우선한다. 현재는 선택20Hz 전달의 효과를 확인했으므로 fps 조합을 계속 나열하는 대신 실제 실행 연결·주행 정체 작업으로 이동한다. 촬영30fps와 이동 마커 검출은 필요한 경우 또는 현장 확인으로 남긴다.
