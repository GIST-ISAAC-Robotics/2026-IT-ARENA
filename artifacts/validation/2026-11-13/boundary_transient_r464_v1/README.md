# r464 최초 경계 정지 분석과 동일 벽 갱신 후보

## 결론과 범위

r457의 최초 두 plan 정지는 경계가 계속 사라진 사건이 아니다. 충분한 현재 직각 벽을 기존 경로와 비교할 때 `shared_x`의 잘린 x폭이 0.25 m에 못 미쳐 갱신을 놓쳤고, 경로 기억 만료 후 정지·재개 확인이 연달아 발생했다. **기존 호길이 비교를 이미 선택한 동일 벽의 현재 갱신에만 연결하는 10줄 후보를 stage에 구현했다.** 후속 승인된 WSL 검증에서 원본 405/405 exact, 후보 402/405 exact 및 두 정지의 plan 양수 전환을 확인했다. 공통 이관 전이며 실제 발행/주행 성공은 아니다. 최종 결과는 [RESULT.md](RESULT.md)를 기준으로 한다.

후속 100건 `route_current_large_motion_masked_toward_right`는 별도 r463 대상이다. 두 plan 정지를 줄여도 이 지속 교착을 해결했다고 할 수 없다. current 재검사·보호층·물성·속도·관측 문턱은 수정하지 않았다. 초기 분석은 Windows에서 했고, 후속 명시 배정으로 WSL 저장 재생만 수행했다. 새 주행, Jetson, 포트, 장치 접근은 하지 않았다.

## 경계 비교 진단

`geometry_diagnostic.py`는 원 scan/시각/엔코더·자이로 이력과 기록된 plan639 경로만 사용한다. Gazebo pose/지도/actor truth는 사용하지 않는다. Python 원 구현으로 점군·벽 후보·운동 보정·기존 비교를 호출했으며 전체 plan 상태를 재구성하지 않았다. 이 국소 계산은 Windows NumPy 2.5.4이며, 삭제된 2D `np.cross`만 기존 식 `a0*b1-a1*b0`로 진단 프로세스 안에서 호환했다. 원 소스는 바꾸지 않았다. 앞선 import/API 실패도 `geometry_attempt1.json`, `geometry_attempt2.json`에 남겼다.

| plan | 현재 왼쪽 벽 길이(m) / 앵커 오차(m) | shared_x 잘린 두 경로의 x폭(m) | shared_arc 공통 길이(m) / 점수 | shared_arc 대칭 p80 오차(m) |
|---|---|---|---|---:|
| 641 | 3.05699 / 0.02705 | 0.26546 / **0.23350** | 0.89259 / 15·15점 | 0.01951 |
| 643 | 3.04194 / 0.04766 | **0.24566** / 0.29449 | 0.88117 / 15·15점 | 0.02118 |

`shared_x`는 겹친 창 안에서도 각 경로의 x폭 0.25 m를 요구한다. 코너에서 전방 x길이가 짧아져 이 조건이 실패했다. 두 현재 후보 모두 기존 충분성(벽 0.65 m 이상, 앵커 0.12 m 이내)을 통과한다. 기존 `shared_arc`의 최소 공통 0.25 m/각 5점과 허용 오차 0.08 m도 통과한다. **원 641의 `wall_segment_short`는 최초 원시 벽이 아니라 x 비교 실패 뒤 support 재선택 결과**다. 초기 조사 메시지의 “새 경계가 짧아짐” 설명은 이 결과로 정정한다.

원 기록에는 원시 후보의 실제 길이가 따로 모두 저장되지는 않는다. 위 숫자는 저장 입력을 통한 순수 Python 기하 진단이며 ARM/native 전체 plan 일치 결과가 아니다. plan639/643의 기록된 관측 길이는 수치상 재현됐지만 이것만으로 모든 내부 상태·경로가 재현됐다고 하지 않는다.

## 최소 변경

`stage/src/arena_autonomy/arena_autonomy/local_follow.py`의 기존 유효 기억 갱신 분기만 수정했다.

- 기존 명시 `junction_continuity` + `expiry_route_reference_trial` + `piecewise_wall_trial`이 켜져 있어야 한다.
- 기존 TTL/운동 한도를 이미 통과한 `carried` 경로가 있고, 현재 충분한 `piecewise_corner` 후보가 **기존 선택 벽과 같은 쪽**일 때만 적용한다.
- 종전 `path_agrees`가 실패하면 기존 `path_agrees_arc`를 한 번 사용한다. 성공하면 현재 관측으로 경로를 갱신하고 `current_same_wall_corner_arc` 근거를 남긴다.
- TTL 연장, 만료 경로의 주행 재사용, 초기 획득, 다른 벽 전환, 짧은 현재 경계 채택, 재개 횟수 변경은 없다. 이후 원시 점유·제동·부분 관측·current·독립 guard 경계도 그대로다.

같은 선택 벽이라는 것은 객체 동일성/벽 정체의 증명이 아니다. 기존 호길이 비교 역시 가까운 공통 80% 밖의 분기를 완전 구별하지 못한다. 이 후보는 원 경계 표현의 연속성 수정이며 미관측 공간을 자유 공간으로 만들지 않는다.

## 최초 준비 당시 확인과 후속 검증 계획

완료: 원 자료 추출/해시, 경계 기하 5행 진단, stage 한 파일 구현, Python AST 정적 확인. `static_review.json`에 시험 파일 구문과 원본 불변을 기록한다. 새 국소 회귀 9개는 준비만 했으며 실행하지 않았다.

Linux 자원을 배정받으면 다음 한 묶음만 필요하다.

1. 기존 native 빌드의 C++ 소스 SHA가 동결본과 같음을 확인한 후 재사용한다. 별도 r464 overlay에 r457 동결 source를 복사하고 baseline/후보를 **각각 별도 프로세스**에서 실행한다. 공통 설치/빌드는 바꾸지 않는다.
2. `python3 run_focused_tests.py`로 국소 9개를 실행한다. 실제 기록으로 만든 같은 벽 갱신, 옵션 OFF/만료/다른 벽/이탈/같은 scan/epoch, 전방 점유, 기존 release 대기를 확인한다. 기록 경계로 만든 국소 fixture임을 전체 worker 재현과 구분한다.
3. r457의 `runtime_evaluator_header`와 고유 제출 405개·generation reset을 원 순서로 재생한다. 원 동결 baseline부터 원 출력 일치를 확인하고, 불일치면 해당 지점에서 멈춘다. 후보에서는 첫 변경 시점, 641/643/644/645의 경계/출력/side 상태, 기존 양수→0, 경로 변경 범위를 비교한다. 원 답으로 내부 상태를 채우지 않는다.
4. 이미 존재하는 실제 current 입력 쌍만 필요 최소 대조한다. 643/644에는 원 current 입력이 없으므로 합성해 “실제 발행 성공”으로 기록하지 않는다. 후속 100건 current 수정/새 주행은 여기서 하지 않는다.

추가 계산은 해당 조건에서 기존 x 비교 실패 뒤 호길이 비교 한 번이다. 641의 진단은 15×15 거리 행렬이지만 전체 입력의 최대 비용이나 Jetson 지연을 보증하지 않는다. WSL/Windows 비용을 섞어 비교하지 않는다. 후속 실행에서 계획 1–3을 수행했다. 계획 4의 current 추가 계산은 이번 root 승인 범위에 없었으므로 하지 않았다. **권고: 두 일시 정지에 대한 좁은 수정의 공통 통합 검토를 권한다. 지속 current 교착이나 완주 개선은 별도 검증 대상이다.**
