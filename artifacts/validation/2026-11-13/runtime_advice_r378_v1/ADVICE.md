# Claude Fable 5.2 자문 원문

## 결론

1. **한 호출 내 공유 정리가 band 공유보다 우선입니다.** 다만 처리량 때문이 아니라, r375 회복 경로의 현재 검사가 Jetson에서 200ms 명령 만료 안에 끝나는지가 걸려 있기 때문입니다. 리팩터 전에 이 소요 시간부터 한 번 측정하시기를 권합니다.
2. **계획 139ms를 100ms 아래로 내릴 숨은 단일 중복은 찾지 못했습니다.** 비용은 여러 곳에 분산되어 있습니다.
3. **이 지연은 실물 최소 준비를 막는 문제가 아니라 속도·연속성 문제로 보입니다.** 아래 한 묶음 뒤에는 CPU 작업을 닫고 필수 작업으로 넘어가셔도 된다고 판단합니다.

## (1) 우선순위: 호출 내 공유 > band 공유

**확인한 코드**
- `runtime_dual_state.py:132`는 스냅샷 나이+0.1s가 0.2s 미만일 때만 현재 검사를 제출합니다. `:195-196`은 적용 시점에 `now - cur.reference >= 0.2`이면 `current_command_expired`로 버립니다. 따라서 현재 검사에 허용되는 시간은 IPC를 포함해 약 100~200ms입니다.
- r375 회복 경로는 한 호출에서 다음을 순서대로 계산합니다.
  - prior 체인 전체(r281의 기하+region, 조건에 따라 `released_body_gap.check`가 같은 region을 한 번 더).
  - `core_policy.rebase`를 같은 인자로 다시 호출(`released_current_r375_v1/candidate.py:60`). 내부는 `_released_parallel.py:28-45`의 기하 재검사, 스캔 복원, 전방 관측, `threat_view`입니다.
  - `ps.motion_region` 재계산(`candidate.py:72`).
  - `bounded_body_nonreturn`. r359 index90에서 `_bounded_nonreturn` 60ms, `_query_brackets` 516회 30ms였습니다(PC, cProfile 포함).

**추론(미측정)**
- 정상 RELEASED 현재 검사가 Jetson 중앙 63~67ms이므로, 회복 경로는 그 2~3배인 130~200ms일 가능성이 있습니다.
- 그렇다면 PC의 r377 단일 주행에서는 저속 복원이 되어도 Jetson에서는 같은 결과가 만료로 폐기될 수 있습니다. r377은 PC 속도라 이 위험을 드러내지 못합니다.

**권고**
- r377은 동결한 r375로 그대로 진행하시고, 리팩터는 그 뒤라는 현재 순서에 동의합니다.
- 공유는 r374에서 이미 바이트 대조까지 마친 `motion_region` 캐시의 범위를 `select` 한 번에서 `rebase` 한 번으로 옮기는 방식이 새 고장 면적이 가장 작습니다. region 계산이 최대 3회에서 1회로 줄어듭니다. r374 `candidate.py` 본문은 읽지 않았고 README 기준입니다.
- r375의 `region != route.get('region')` 검사는 그대로 두시면 그 자체가 동등성 감시가 됩니다.
- `core_policy.rebase` 중복 제거는 새 배선이 필요하고 단독 비용이 계측되어 있지 않으므로, 측정 후 필요할 때만 하시기를 권합니다.

**band 공유는 후순위입니다**
- r359 index60/120에서 `band_check` 4회가 약 26ms이고, 그중 `depth_support`가 약 14ms(60.84−46.75)입니다. 절감 상한은 나머지 약 12ms 중 `masked_only` 몫이며, 저는 select의 5% 안팎 이하로 추정합니다. r374의 5% 기준에 미달할 가능성이 높습니다.
- 동등성 주의점이 있습니다. 현 band 경로는 `numeric_kernels.depth`와 `masked` 커널을 쓰고, 공유 경로는 `classes` 커널을 씁니다. chunk도 128과 512로 다르고, `masked_only`의 인접 판정은 `abs(index 차) <= 1`이며 `depth_support`는 `adjacent_indices(cycle_count)`입니다. `motion_region`에서 검증된 동등성을 차체 옆 띠 질의에 그대로 승계하지 말고 바이트 대조를 다시 하셔야 합니다.

**배포 취약점**
- 래퍼 체인은 11-12와 11-13 두 날짜 디렉터리의 6개 파일을 `spec_from_file_location`, `sys.path.insert`, `import overlap`으로 잇습니다. Jetson에서 하나라도 빠지면 현재 검사 자식이 import 단계에서 죽습니다.
- 평탄화는 r377 뒤로 미루되, Jetson에서 import 후 저장 입력 1건을 돌리는 preflight는 지금 필요합니다.

## (2) 놓친 구조적 비용

- **장면→배열 재추출이 호출마다 반복됩니다.** `observation_support.py:50-57`, `m3_execution_trial.py:227-233`, `ray_padding`(`:215`)이 매번 광선 약 1000개에서 배열 5~6개를 Python 순회로 다시 만듭니다. index60에서 `math.dist` 5020회, `np.array` 669회 9.3ms, `depth_support` 자체 시간 8.9ms(5회)였습니다. 장면 단위 메모는 같은 배열이라 동등성 위험이 가장 낮지만, 이득은 5~8% 수준으로 추정합니다.
- **장면 구성 자체가 광선별 Python입니다.** `native_geometry._geometry` 약 1020회 20ms, `_masked_by` 7.5ms, `builtins.all` 7.8ms로, 모든 상태의 계획에서 매번 25~30ms(프로파일 포함)가 듭니다. 현재 검사 자식도 같은 비용을 낼 것으로 추정합니다. 가장 큰 구조적 비용이지만 오늘 밤 손댈 범위는 아닙니다.
- **`motion_region`은 목표 속도에 비례합니다.** 1.5m/s에서 `classes` 커널 24회(512개 묶음 기준 약 1.2만 질의), 0.7m/s에서 9회입니다. 정당한 계산이며 중복이 아닙니다.
- **일정 측면 한 가지가 있습니다.** `may_finish_current`는 `selector_mode == 'SOLO'`만 허용합니다(`runtime_dual_state.py:34`). RELEASED에서는 새 계획이 완료될 때마다 `ready`가 지워집니다(`:102-104`). r369에서 폐기를 31→1로 줄여도 공백이 11%만 줄었으므로, 공백의 주원인이 계산량이 아니라 위상·만료일 수 있습니다. 이는 추론이며, 설계 변경을 제안하는 것은 아닙니다.
- **스레드·코어 설정이 없습니다.** `src`, `scripts`, `config`에서 BLAS 스레드 제한이나 코어 고정 설정을 찾지 못했습니다. 단일 스레드 자식 2개로 r373의 평균 72%가 설명되는지는 확인하지 못했습니다. BLAS 다중 스레드 경합은 제 추측이며, 자식 프로세스의 스레드 수를 한 번 조회하면 판별됩니다.

## (3) 넘어가는 기준

- **안전 관점:** `envelope_distance`가 장면 나이와 속도를 이미 반영하므로, 지연은 독립 보호층이 살아 있는 한 주로 속도·연속성 손실로 나타날 것입니다(추론). 0.35m/s에서 평균 공백 약 56ms(r369의 6.2s/107구간)는 약 2cm 이동에 해당합니다.
- **넘어가는 조건(실용 기준이며 안전 판정선이 아닙니다):**
  - Jetson 저장 입력에서 회복 경로를 포함한 현재 검사 p95가 약 100ms 미만일 것.
  - 강제 종료 0, import preflight 통과.
  - 만료 시 실제 출력 동작을 확인할 것. 부모가 0을 발행하는지, 발행을 멈추는지, 펌웨어 워치독이 타력인지 제동인지는 제가 보지 못했습니다. 이것이 공백의 실제 영향을 결정합니다.
- **반복 방지:** 동등 계산 후보는 기한 초과를 해소하거나 RELEASED 합계 10% 이상이 기대될 때만 착수하시기를 권합니다. r374(0.3%)와 band(5% 이하 추정)는 이 기준에 미달합니다. 조립 전 추가 후보는 한 건으로 제한하시고, r377이 시간 외 사유로 실패하면 r378 래퍼를 더 쌓지 않는 편이 좋겠습니다.
- **확인이 필요한 필수 항목:** r359 README 21행에 하드웨어 shadow 설정이 135mm 축거로 적혀 있습니다. 최종 128mm 반영 여부는 제가 확인하지 못했습니다.

## 반려하는 대안

- band 공유 단독 착수.
- `_query_brackets` 벡터화: 이득은 있어 보이나 동률·순서 동등성 검증 비용이 오늘 범위를 넘습니다.
- 질의 점 단위 메모로 저속 재시도를 부분 재사용하는 방식: 새 불변식이 필요합니다.
- 장면 구성 재작성.

## 다음 한 묶음의 최소 검증

1. **새 실행 없이:** r369 Jetson 이벤트에서 RELEASED 구간의 미적용·폐기 사유(`current_command_expired`, `new_plan_superseded_current_check`, `positive_application_interval`, 제출 거절)를 집계합니다. 계산량 문제인지 위상 문제인지 가려집니다.
2. **Jetson 1회:** r375 저장 입력 중 복원 93건과 반례 17건을 현재 검사 자식 단독으로 돌려 소요 p50/p95와 만료 여부를 봅니다. import preflight를 겸합니다.
3. **2에서 p95가 100ms를 넘을 때만:** `rebase` 범위의 region 공유를 적용하고, r374의 `--verify-hits` 방식으로 전체 진단 JSON 바이트를 대조한 뒤 2를 다시 측정합니다.
