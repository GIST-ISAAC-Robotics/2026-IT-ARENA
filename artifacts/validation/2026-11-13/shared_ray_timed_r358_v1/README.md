# r358 공유 계산의 두 프로세스 시간 재생

2026-11-13. 단일 현재 검사에서 확인한 r357 개선이 계획/현재 검사를 동시에 실행할 때도 이어지는지 실제 Jetson에서 비교했다. 같은 r353 센서 기록31초를 **분리 → 공유 → 공유 → 분리** 순서로 각각 한 번 재생했다. 공유 방식의 효과는 있으나 실시간 성능 확보는 미완료다.

두 회 평균의 만료 뒤 누적 공백은6.726→5.489초로 약18.4% 감소했다. **만료가 발생한 구간 수는104–106→106–110개로 줄지 않았다.** 개수와 누적 시간을 구별하며 실패가 해결됐다고 쓰지 않는다. 계획 계산 중앙은 여전히 약132ms로10Hz의100ms보다 길고, 공유 방식에서도 최대 갱신 간격202/323ms가 남았다. 두 회씩의 작은 비교이며 모든 부하/상태의 개선 보증이 아니다.

## 조건과 해석

- 명시 `native_v1`, r353/r352 현재 검사·r278 계획·r334 감속 인계. 분리/공유의 광선 탐색만 다르다. 제어기·독립 보호층의 조건은 바꾸지 않았다.
- 실제31초 벽시계, 인위 계산 대기0. IMU/엔코더는 기록된 취득값/시각에20ms 도착을 가정한다. 실제 수신 시각을 복원한 것이 아니다. 스캔은 기록에서 처음 나타난 뒤에만 공개한다.
- 원 call의200ms 공백 두 곳을 보존했다. r325의 조밀한 입력 전제에는 해당하지 않으므로 별도 시험으로 구분했다. 빠진 스캔·센서값을 보간하지 않는다. 이 기록 공백을 r353 원시 센서 취득 누락으로 바꾸어 해석하지 않는다.
- 원천300ms·명령200ms 기한, 새 상태/0명령/epoch 취소는 유지했다. 이전 양수 명령의200ms 기한 이후 다음 명령까지를 공백으로 셌고 마지막 꼬리 구간도 확인했다.
- **파일 발행만 수행했다.** 원 기록 차량 운동은 새 출력에 반응하지 않는다. ROS 콜백·보호층 발행·MCU·실제 주행·정지 거리의 증거가 아니다. 센서 포트/펌웨어/전력 설정은 바꾸지 않았다.
- PC 공유 방식 사전 확인은31초·양수218회·누적 공백0.0459초이며, Jetson 결과를 대신하지 않는다.

## 정리와 다음 작업

PC2개·Jetson8개 계산 자식은 모두 강제 종료 없이 정상 종료했다. 원 입력 해시와 동결752개 파일은 그대로다. 원격 시험 루트/실행 스크립트의 잔여 프로세스도 없다. 원 결과와 실패는 수정하지 않았다.

사용자 요청에 따라 이 비교를 마치고 정리했다. 다음은 조립 전 MCU/센서 운용 연결과 현재 실행 구성의 명령 수명 계약을 함께 확인하는 작업이다. 수치 미세 최적화를 같은 방식으로 계속 반복하지 않는다. 계획 비용/명령 공백은 P0 미해결로 유지하고, 새 기하의 r353 교통 해제 뒤 코너 정체도 별도 실패로 남긴다. 조향 CAD 수신은 후속 실장 보정과 함께 다루며 이번 묶음에서 서보/운영 한계를 바꾸지 않았다.
