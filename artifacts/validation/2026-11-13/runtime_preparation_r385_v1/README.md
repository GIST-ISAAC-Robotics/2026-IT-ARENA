# 운영 출력 준비와 명령 허가의 구분 r385

2026-11-13. **공통 연결 검사 203개와 새로 빌드한 수신기 대조 검사 7개를 통과했다.** 서보 준비 순서기와 결합하기 위한 최소 공통 연결이다. 기존 preview 앱은 계속 `ready=false`이며 모터/서보 출력·flash는 하지 않는다.

- 수신기는 이번 ARM 세대에서 실제 DRIVE를 받았는지 `drive_seen`으로 제공한다. 목표0의 DRIVE도 조향 명령이므로 포함하고, STOP/CLEAR/ARM·고장 등 상태 세대 변경 시 지운다. 기존 와이어 필드·ACK·기한은 바꾸지 않는다.
- `MotorControlCandidate.tick`의 명시 `inhibit_motor`는 서보 준비 중 출력0과 적분 초기화를 유지한다. 준비 증거가 사라지거나 원 명령/피드백/주기 조건이 실패하면 기존 고장 경로를 적용한다. 이 억제로 명령 수명을 늘리거나 새로운 DRIVE를 만들지 않는다. 생략 시 기존 동작 그대로다.
- `RuntimeTx`는 같은 호출의 준비 증거를 endpoint에 전달할 수 있다. 기본false와 기존 preview의 모든 호출은 유지한다. 송신 준비값이 모터 구동 허가를 대신하지 않는다.

관련 [자문](../mcu_engagement_advice_r383_v1/ADVICE.md)에서는 준비 중 PI 포화만으로 충분하다고 제안했으나, 실제로 출력하지 않은 동안 적분이 쌓이는 것은 피하도록 초기화를 선택했다. 서보가 정상 응답했다는 증거와 모터를 적용할 단계인지는 별개다. 서보 순서기·PWM/PCNT 실제 연결과 실장 교정은 후속이며 이 변경만으로 운영 펌웨어가 완성되지 않는다.

`test_preparation.py`는 공통 코드를 g++의 크기 최적화/ASan·UBSan 두 구성으로 빌드해 ARM 세대·0목표 조향·준비 중 적분·원 만료·출력 상실·송신 준비 전달을 검사한다. 실제 5ms 성능·차체 정지나 전기 출력을 증명하지 않는다. 기존 수신기/PI/주기 회귀를 함께 실행한다.

최초 [검사 기록](verify_v1/)은 203개 통과·3개 생략이다. 생략 원인은 수신기 드라이버 실행 파일 환경변수 누락이었다. 이후 sanitizer 수신기 드라이버를 새로 빌드해 [추가 기록](verify_receiver_v1/)에서 해당 3개를 포함한 7개를 생략 없이 통과했다. 두 실행의 원 로그를 모두 보존하며 같은 검사를 중복 합산해 210개 독립 검사라고 부르지 않는다. 대상 소스의 검사 전후 해시도 같았다. 실제 ESP32 빌드·장치 출력은 이번 범위가 아니다.
