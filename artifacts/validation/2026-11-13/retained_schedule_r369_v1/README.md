# 보관 재검사 제출 생략: PC·Jetson 비교, 기본 미채택

r367 자문의 제출 낭비 감소안을 시험 전용으로 구현했다. 새 계획이 실행 중일 때 아직 시작하지 않은 `RELEASED` 보관 경로 재검사만 생략한다. 기본값은 OFF이며 원천/명령/경로 유효 시간·현재 관측·STOP은 유지한다. [조건](PLAN.md)·[시험 구현](candidate.py).

관련 61회귀와 같은 r353 입력의 실제 시간 31초 재생을 baseline/선택 후보 각 한 번 수행했다. 센서 도착 +20ms를 가정하는 파일 출력 비교이며 ROS 발행이나 주행 시험은 아니다.

| PC 결과 | baseline | 제출 생략 |
|---|---:|---:|
| 발행/양수 명령 | 308/218 | 308/218 |
| 새 계획에 밀려 폐기된 현재 검사 | 59 | 2 |
| 양수 뒤 발행 간격 p95 | 102.42ms | 102.63ms |
| 다음 발행 직전 원 명령 나이 p95 | 194.47ms | 198.32ms |
| 200ms 만료 구간 수 | 5 | 9 |
| 만료 뒤 누적 공백 | 0.0481s | 0.0497s |

**폐기 수는 감소했지만 명령 갱신 개선은 확인하지 못했다.** 이 결과만으로 채택하지 않는다. 선택 후보의 `skipped=1153`은 반복 루프에서 제출을 생략한 시도 수이며 절약한 계산 작업 수가 아니다. 양쪽 계산 자식은 모두 exit0·강제 종료 없이 회수했다. 원 기록의 200ms 입력 공백 두 곳을 채우지 않았다.

[baseline](pc_baseline/report.json)·[후보](pc_skip/report.json)·[회귀](tests.log). 최초 Jetson SSH는 시간 초과였으며 이후 이름 조회 경로를 분리해 기존 호스트 키를 확인한 숫자 주소로 접속했다. 그 뒤 아래 원격 비교를 수행했다. 센서/펌웨어/전력·공통 기본 구현은 이 비교에서 바꾸지 않았다.

## Jetson의 동일 입력 31초 ABBA 비교

원 r358의 752파일을 새 시험 디렉터리로 보존·복사하고 8파일을 추가했다. 실행 전 비용 기록기의 `normal=None` 처리를 보완했으며 수정 전 파일/manifest를 보존했다. A=baseline, B=선택형 제출 생략으로 A1→B1→B2→A2를 수행했다. 사용자 요청으로 장비 이름을 바꾸기 **전**의 시험이다.

| 실제 시간 결과 | A1 | B1 | B2 | A2 |
|---|---:|---:|---:|---:|
| 발행/양수 | 210/149 | 218/156 | 218/155 | 209/147 |
| 새 계획에 밀린 현재 검사 | 33 | 1 | 3 | 31 |
| 양수 뒤 발행 간격 p95(ms) | 190.06 | 192.62 | 183.58 | 189.38 |
| 다음 발행 직전 원 명령 나이 p95(ms) | 316.37 | 315.78 | 296.13 | 308.71 |
| 만료 구간 수 | 107 | 115 | 113 | 108 |
| 만료 뒤 누적 공백(s) | 6.1769 | 5.4273 | 5.3185 | 5.8837 |

누적 공백 평균은 **6.0303→5.3729초(약10.9% 감소)**지만 만료 구간 수는 늘었고 발행 p95 개선도 일관되지는 않는다. 파일 재생의 제한 개선이며 실시간10Hz나 ROS/센서 전체 완료가 아니다. 제출 생략을 공통 기본값으로 채택하지 않는다.

완료한 계획 중 `SOLO` 중앙은59.65–60.54ms, `RELEASED`는138.74–141.40ms다. `RELEASED` 현재 재검사는 중앙63.50–66.70ms다. 상대가 사라진 뒤 경로를 유지하는 분기의 계획 비용 자체가 크며, 유휴 GUI 부담만으로 이 차이를 설명할 근거는 없다. 상태별 표본 수가 다르므로 이를 같은 호출의 전후 최적화 비교로 쓰지 않는다.
