# r407 운영 버튼과 새 runtime 실행 구성의 연결

## 목적과 범위

r404는 실제 센서 수신과 0명령 연결을 확인했지만 `race_control_mode=legacy`다. 이미 구현한 STOP·RESET 없는 재개·수동 출발·개발 속도 상한을 새 공통 runtime에 연결하는 운영 준비를 별도로 확인한다. 기본값·실물 firmware·포트·센서 장착과 주행 판정을 바꾸지 않는다.

1. r401의 최종4가림 runtime 프로필에서 planner/guard의 B3 선택, 개발 속도 상한 선택을 명시한 파생 설정을 만든다. 모든 geometry/time/profile 값은 유지하고 차이를 기록한다. 모니터는 별도 프로세스이고 일반 주행 시험에서 브라우저를 강제하지 않는다.
2. 기존 r394 실제ROS/PTY 가짜 MCU 실행기를 재사용할 수 있는지 검토한다. 실제 G1G2·guard·RaceOps의 상태/명령/서비스가 이어지는지 새 격리 domain과 localhost에서 검사한다. 실제 serial port나 실물 구동은 열지 않는다. 가짜 count를 실물 센서에 섞지 않는다.
3. 대표 확인은 초기 래치/STOP·정지 중 속도 상한·RESET 없는 재개 준비·신호 대기 밖 수동 출발 거절과 정상 종료다. 센서가 없을 때 재개 요청 수락을 주행 허가로 보지 않는다. 실제 신호 대기에서 수동 출발까지 확인하려면 합성 센서/영상의 범위를 분리하고 기존 r366 근거와 함께 판단한다.
4. 실제 모터/서보 출력 차단이 유지된 운영 명령과 PTY에서만 허용한 프로토콜 ARM을 구분한다. `/drive/safe` 직접 발행으로 독립 보호층을 건너뛰지 않는다. 웹/CLI는 `/race/command`와 기존 MCU 서비스만 사용한다.

현재는 준비 계획이며 실행 결과가 아니다. r405/r406 실행 담당과 WSL 자원을 공유하므로 동결·한 담당자 배정 후 수행한다. 가능한 대표 연결이 확보되면 운영 경계의 드문 예외를 계속 추가하지 않고 다음 주행 문제로 돌아간다.
