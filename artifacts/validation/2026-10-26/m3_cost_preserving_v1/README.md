# M3 출력 보존 계산 개선 — 10/26

[범위](PLAN.md): 사각이나 간격 기준을 바꾸지 않고, 저장 센서 입력의 판단을 유지하며 계산량을 줄일 수 있는지 확인한다. 새 Gazebo·Jetson 시험은 하지 않는다. 모든 후보는 우선 분석 프로세스 안에서만 대조한다.

## run1 함수별 비용 진단

좌우 피추월 run17/21의 처음부터 6초까지 원래 순서로 재생했다. 각 109판단·191 reset이며 이전 현재판본 저장 해시와 출력 차이는 0이다. 입력·소스 불변을 확인했다. cProfile을 사용했으므로 다음 시간은 계측 비용의 위치를 가리킬 뿐 실시간 성능 수치가 아니다.

| 함수 | 왼쪽 누적 s / 호출수 | 오른쪽 누적 s / 호출수 |
|---|---:|---:|
| 주 판단 command | 7.76 / 109 | 7.38 / 109 |
| release_gate | 2.23 / 56 | 2.55 / 56 |
| PathFrame.project | 1.70 / 1,997 | 1.68 / 1,833 |
| plan_check | 1.79 / 268 | 1.70 / 266 |
| _both_sides_returned | 0.69 / 55 | 0.82 / 55 |

누적 시간은 함수끼리 포함 관계가 있어 더하지 않는다. [원본](run1_profile/data/summary.json)과 함수별 표에 나머지 비용을 보존했다.

## 첫 후보

`projection_candidate.py`는 모든 선분에 대해 기존과 같은 투영을 수행한다. NxMx2 임시 배열·축 축약 대신 x/y 배열을 나누고, 점 128개씩 처리해 메모리 상한을 제한한다. 선분 제거·근사 최근접 탐색·이전 장면 캐시는 쓰지 않는다. 양 끝 접선 연장·sqrt·argmin 동률 우선순위·산술 순서를 유지한다.

순수 반례와 실제 저장 판단의 출력/진단 해시를 대조한 뒤 비용을 순차 교차 측정한다. 비교 코드 자체는 운영 제어기에 연결하지 않는다. 전체 랩·M3 간격/후방 사각 실패는 별개로 유지한다.

## run2 투영 후보 대조

직선·곡선·루프·중복점·큰 좌표·같은 거리·경로 밖 연장 등을 다룬 순수 **21검사**는 투영 결과 배열이 비트 단위로 같았다. 좌우 첫 구간 각각 109판단을 워밍업 뒤 기본/후보 교차 3회씩 순차 측정했으며 속도·조향·진단 전체 해시 차이는 0이다. [원본](run2_compare/data/summary.json)·소스 ZIP을 보존했다.

| 저장 구간 | 기본 p50 / p95 / max ms | 후보 p50 / p95 / max ms | 총 처리시간 s |
|---|---:|---:|---:|
| 왼쪽 run17 | 33.512 / 240.898 / 537.626 | 24.945 / 209.749 / 477.591 | 6.970 → 5.632 |
| 오른쪽 run21 | 36.326 / 244.525 / 557.027 | 25.385 / 212.515 / 513.521 | 6.819 → 5.525 |

표는 각 반복의 통계 3개를 산술 평균한 것이며 전체 표본을 합친 백분위가 아니다. 초기 입력 구간의 PC 오프라인 비용으로, 50 Hz 마감이나 Jetson 성능을 입증하지 않는다. 최대 호출이 약 0.5초인 문제는 남는다. 이득은 있지만 전체 저장 입력·코너까지 비교한 뒤 이관 여부를 결정한다.

추가 검토는 `_both_sides_returned`의 전광선 배열을 기존 `depth_support`와 같은 보수적 각도 창으로 좁히는 후보다. 질의점을 둘러싼 광선 원점 원 안에서는 전체 광선을 쓰며, 반환/unknown/마스크와 source 인접성·경계 동률을 그대로 보존해야 한다. 아직 운용 소스에 넣지 않았다.

## 반환 광선 후보의 반례 보충

run4는 순수 15통과·1실패로 비용 비교 전에 중단했다. 음수 각도 증분은 원래 `scene_from_scan`이 거절하는데 정상 입력 fixture로 만든 시험 오류였다. 기존 입력 계약을 바꾸지 않고 음수 증분 거절을 확인하도록 수정했다. [실패 원본](run4_returned/tests_stdout.txt)과 [실패 시험 본문 복원 범위](run4_returned/RECONSTRUCTION.md)를 보존한다. 후보 함수의 출력 불일치나 주행 실패가 아니다. 수정 후 검사는 별도 run5에서 수행한다.


## run5 반환 광선 검색의 같은 조건 대조

수정된 순수 16검사는 통과했다. 투영 개선을 양쪽에 적용한 상태에서 반환 광선 검색만 바꿔 워밍업과 교차 3회씩 측정했다. 좌우 109판단씩의 속도·조향·진단 해시는 모두 동일하고 소스/입력은 불변이다. [결과](run5_returned/data/summary.json).

| 저장 구간 | 기존 검색 p95 / max ms | 후보 검색 p95 / max ms |
|---|---:|---:|
| 왼쪽 run17 | 211.805 / 454.395 | 173.906 / 319.944 |
| 오른쪽 run21 | 196.424 / 464.159 | 156.824 / 324.549 |

각 반복 통계의 산술 평균이며, p50은 개선되지 않거나 조금 증가한 반복도 있다. 가까운 질의에서는 전광선 검사가 유지되고 각도 창 준비 비용도 있어 모든 호출이 빨라진다고 주장하지 않는다. 고비용 호출에서의 이득을 확인한 결과이며 ROS/Jetson 마감 충족은 아니다.

## run6 전체 대조와 실행 소스 이관

두 후보를 함께 적용한 전체 5기록 **6,165판단**에서 출력/진단 해시 차이 0·입력/소스 불변을 확인했다. [결과](run6_full_returned/data/summary.json). 이에 계산 함수 두 곳만 이관했으며 기본 옵션·판정선·물성·센서 입력은 그대로다. [이전 소스](before_integration_sources.zip)와 [후속 출처 계약](../../../../config/tests/m3_exact_cost_r0_sha256.json)을 보존했다. 실제 모듈의 회귀와 monkeypatch 없는 재생은 run7에서 별도로 확인한다.

이관 준비 스크립트의 첫 Windows 실행은 기본 cp949로 UTF-8 후보를 읽다가 중단했다. ZIP만 생성되고 실행 소스 변경 전이었으며, 후속 실행 전에 모든 소스 해시와 ZIP 본문이 원래와 같은지 다시 확인했다. UTF-8 읽기를 명시해 이관했다. 주행/후보 수학 결과의 실패와 구분한다.


## run7 실행 모듈 회귀·전체 재생

실제 `PathFrame.project`와 `_both_sides_returned`를 읽는 **관련 374검사**가 통과했다. 이어 후보 함수로 교체하지 않는 재생에서 5입력 **6,165판단 전체**의 속도·조향·진단 해시가 이전 현재판본과 같았다. 입력/소스 불변·정상 종료·잔존 0을 확인했다. [실제 모듈 결과](run7_integrated/data/summary.json)·[회귀](run7_integrated/tests_stdout.txt).

이번 이관의 범위는 두 함수의 동등 계산이다. 새 Gazebo/ROS 폐루프나 Jetson 실행은 하지 않았으며, 기존 M3 선택 옵션 기본 OFF를 유지한다. 50 Hz 실시간 처리·후방 사각·측방 간격·전체 랩 실패가 해결되었다고 표시하지 않는다. 계산 개선은 이 묶음으로 마감하고 다음은 현재 두 바퀴 잔디 정책 아래 정지차 우회 기하를 제한적으로 재검토한다.
