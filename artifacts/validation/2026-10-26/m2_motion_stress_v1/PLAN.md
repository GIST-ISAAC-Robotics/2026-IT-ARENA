# M2 단일 모터축·IMU 오차/지연의 교통 결합 시험

## 목적과 한 번의 조건

이미 통과한 코너 내부 앞차 정지·재개 run51의 현재 구동/제어/센서 구성에 기존 `config/tests/motion_combined.json`을 연결한다. 새 대표 조건은 한 개다. 단독 센서 허용오차 전수 탐색이나 M3 피추월 해결은 아니다.

- 기존 `g1_curve_stop_restart_v1.json`, case `curve_stop_restart`, seed 0, 40 sim s, run51과 같은 명시 M3 옵션/회랑·점별 팽창/독립 보호. 측방 actor 없음.
- 기존 프로필: IMU z +1°/s, IMU/모터축 피드백 추가 지연 10±3 ms, IMU 시각 −5 ms, 모터축 position/velocity ×0.95. 실제 센서의 분포나 보증 상한이 아니라 기존 시험 가정이다. 원시 펄스 누락·카운트 잡음과 다르며 단일 채널을 좌우 센서처럼 만들지 않는다.
- C1은 현재 순차 10 Hz를 유지하고 추가 거리 잡음/지연은 겹치지 않는다. LiDAR 스트레스·합류·운영 명령 시험을 동시에 추가하지 않는다.
- 기존 15 cm 종방향/전체 차체 도로 안·최대 재개 2.5초·진행/코너 정지/출구·실제 STOP·정상 종료를 그대로 평가한다. 실패에 맞춰 속도/간격/신선도/물성을 조정하지 않는다.
- ROS 입력 그래프에서 IMU와 `/drive_motor/encoder`의 유일 발행자가 중계기인지 확인한다. 실제 중계 로그의 단일 채널·변환·시각·주입 활성 구간·정상 닫힘과 실행 프로필 불변을 별도 감사한다. 미주입/감사 실패를 정상 주행으로 표시하지 않는다.
- 주행 전후 소스·설치본을 확인하고 source ZIP·원시 주입 기록·판단 재생·노면 평가를 보존한다. 전체 랩/Jetson·실차 결과는 아니다.

## 준비에서 발견한 문제

중계기 `motion_fault_relay`는 모터축 한 채널을 지원하지만 `motion_fault_audit`는 wheels 길이 2를 고정으로 기대했다. 구형 로그는 legacy로 유지하고, 명시 모드/로그 헤더를 검사한 뒤 단일 축 길이 1을 감사하도록 고친다. 현재 중계기의 실제 입력/출력은 바꾸지 않는다. 이 수정과 선택 CLI 연결을 검사한 뒤 위 조건을 한 번 실행한다.

실패하면 최초 원인을 분리하고 필요한 최소 수정의 근거를 남긴다. 같은 주행을 통과할 때까지 자동 반복하지 않는다. 커밋/푸시·Jetson·전원 변경 없음.

## run2 실패 뒤의 사전 등록 보충

위 position/velocity 직접 곱셈은 정수 모터축 계약에 맞지 않아 출발 시 실패했다. 원래 계획과 run2는 보존하며 후속 run4는 다음 수정만 적용한다. 모터축 누적 카운트 증분에 .95 이득을 누적하고 정수 반올림하며, 속도는 그 출력 카운트의 취득 시각 차분으로 계산한다. 구간 경계는 일정 회전 가정의 시간 비율을 사용하고 초기 원점·첫 NaN은 보존한다. IMU/전송 지연/시각 오차·계수·사례·seed·속도·물성·50 ms 피드백 시효·행동/종료 판정은 유지한다.

정수 입력이 실제 `VirtualMCU.on_motor`에 수용되는지와 잘못된 분수 입력의 기존 거절을 포함한 관련 224회귀를 통과했다. 빌드·설치본 일치 뒤 후속 주행은 한 번만 수행하며, 새 주입 감사나 행동 실패가 남으면 분리해 기록한다.
