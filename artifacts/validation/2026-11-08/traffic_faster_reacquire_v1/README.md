# 빠른 앞차 정체와 기존 현재 벽 재획득 비교

2026-11-08. [원 주행 실패](../traffic_faster_follow_v1/README.md)를 그대로 보존하고 저장 입력을 비교했다. 새로운 경로 알고리즘이나 보호 완화 없이 기존 `standing_wall_reacquire` 옵션만 대조했다.

## 원인과 저장 비교

0.8 m/s 두 앞차의 60초 시험은 23.09 m 진행 후 장기 정체했다. 36초 부근에는 독립 보호가 clear이고 전방 관측도 fully_observed였지만, 경로 기억이 끝난 뒤 양쪽 벽을 다시 확인하는 조건이 성립하지 않았다. 36.42초의 왼쪽 현재 경로는 앞쪽 3.081 m·앵커 오차 9.45 mm였고, 반대쪽은 0.366 m만 이어져 양측 확인의 0.65 m보다 짧았다.

| 항목 | 결과 |
|---|---|
| 입력 구간 | 원 실패 0–40초, 1,621 판단·376 reset |
| OFF 대조 | 모든 출력 원본과 일치 |
| ON 변화 | 전체 출력 164개, 속도/조향 명령 160개 |
| 최초 경로 재획득 | 36.42초 |
| 최초 명령 변화 | 36.72초, 조향 0 → -0.06 rad |
| 최초 양수 목표 | 36.82초, 0.7 m/s |
| 제한 | 저장된 이전 조향·이동이 고정된 비교이므로 실제 재출발 증명이 아님 |

기존 기능은 낮은 실측 속도, 긴 현재 선호 벽, 차체 기준 앵커와 서로 다른 스캔의 확인을 요구하며 점유 검사·독립 보호·STOP을 그대로 통과해야 한다. 단독 주행에서 선택했던 이 기능은 원 교통 실행에서 OFF였다. [comparison.json](comparison.json)과 재생 출력에 상세 결과를 보존했다.

## r27 명시 연결과 검증

교통 평가 CLI에 `--handoff-standing-wall-reacquire`를 추가하고 G1/G2 launch 및 실제 실행 헤더를 대조한다. 선택하지 않으면 기존 OFF이며 다른 제어 모드에서는 거부한다. 제어기 알고리즘·간격·물성·STOP은 바꾸지 않았다.

관련 회귀는 **191개 통과**했다([tests.txt](tests.txt)). 편집 중 달라진 기존 두 평가 파일의 줄바꿈을 원래 CRLF로 복구했으며 Python 코드 내용은 동일하다. 최종 바이트 기준 연결·출처 129개도 통과했으며 결과는 [final_bytes_tests.txt](final_bytes_tests.txt)에 별도로 남긴다. [r27 출처 계약](../../../../config/tests/traffic_standing_reacquire_r27_sha256.json)과 [수정 전 파일](before.zip)을 보존한다.

다음 단계는 [같은 60초 실제 주행](../traffic_faster_reacquire_live_v1/PLAN.md) 1회다. 원 실패의 접촉·노면·정지·한 랩 판정을 유지하며, 한 지점의 재출발만으로 전체 성공을 선언하지 않는다.
