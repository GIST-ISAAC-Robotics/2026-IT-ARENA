# START 수락 뒤 상태 지연과 운영 연결 보완 r26

[첫 재배치 실패](../ops_relocation_v1/README.md)와 같은 조건을 한 번 실행해 **사전 등록한 모든 목표를 모두 통과**했다. 신호 최초 출발 → STOP·정착 → RESET → 심판 배치를 흉내 낸 새 위치 → 한 번의 START → 새 방향 진행 → STOP 순서이다. s=12 m는 시험 위치이며 공식 세이브포인트 지정이나 실물 시험이 아니다.

| 항목 | 결과 |
|---|---|
| START → 정책 구동 허가 | 0.383 시뮬레이션 초, 같은 session/race/epoch 유지 |
| 배치 확인 → START 요청 | 같은 물리 시각에 요청 |
| 재개 뒤 새 방향 진행 | 1.2012 m, 횡편차 0.59 mm |
| 두 STOP의 연속 정착 창 | 각각0.5초·250표본, 최고0.04895/0.04937 m/s, 변위2.083/2.083 mm |
| 기존 조기 판정 직후 첫 창 | 0.06352/0.06457 m/s로 실패. 이후 정착과 구분해 보존 |
| 도로·종료·출처 | 차체 이탈0, 두 관리 프로세스 exit0, 잔존PID0, 등록886입력 불변 |

운영 HTTP 연결은 살아 있었지만 START 수락 응답과 다음 주기 상태 사이에 연결 유지 신호가 없던 것이 원인이었다. 이제 같은 경기/개입에 결속된 정책 수락을 받으면 요청 번호별 연결 신호를 보낸다. 주기 상태가 아직 없다고 MCU를 재무장하거나 이동을 허가하지 않는다. 실제 센서/경로/MCU 조건, 연결1초 감시, 명시STOP은 그대로다. 다른 요청/경기·완료·연결 끊김에는 적용하지 않으며 상태 자체를 확인하지 못하면 기존 응답 대기 시간 안에서 결과 미확인으로 마친다.

기존 코드에서 해당 공백·연결 끊김·상태 미도착을 단위 시험으로 재현했고, 수정 후 **관련230회귀가 통과**했다. [초기3실패](baseline_tests.txt) · [회귀](tests.txt) · [전후 소스](before.zip) · [r26 변경 계약](../../../../config/tests/operator_link_handoff_r26_sha256.json).
