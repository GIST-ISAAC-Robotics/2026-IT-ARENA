# C1 A/B 원본 증거 감사

2026-11-08. 작업은 Claude(Opus 5.5)가 했다. 완료된 A/B 원본을 읽기만 했다. Gazebo/ROS 재실행과 재생은 하지 않았다. 원 `report.json`, `assessment_run*.json`, `pair_comparison.json`과 판정선은 바꾸지 않았다.

- 스크립트: [audit_pair_evidence.py](audit_pair_evidence.py) (`python -I audit_pair_evidence.py`, 종료 코드 0, [audit_v1.exit](audit_v1.exit))
- 결과: [pair_evidence_audit.json](pair_evidence_audit.json). 입력 원본 파일의 sha256을 함께 기록했다.

## 1. `decision_scans_acquired` 실패(B): 기록 종료 경계

`not_in_acquisition=2`는 **판단 호출 2회**를 센 값이다. 서로 다른 스캔은 1개다(first-ray `68.203` s, seq 3415·3416, `reference_s` 68.38·68.40).

| 확인 항목 | B 값 | 판단 |
|---|---|---|
| 가장 가까운 취득 기록과의 차이 | 0.100 s(68.103) | 반올림 문제가 아니다. 모든 스탬프는 1 ms 단위이고, `round(...,6)` 비교에서 생기는 오차는 μs 미만이다 |
| 취득 first-ray 범위·간격 | 0.003–68.103 s, 간격 0.1 s 하나뿐 | 누락 스캔은 마지막 취득 바로 다음 순번(+0.1 s)이다 |
| 마지막 취득(68.103) | 완료 68.204, 지연 해제 68.262 | — |
| 누락 스캔 해제 시각 범위 | (68.36, 68.38] | 앞 스캔을 쓴 마지막 판단과 이 스캔을 쓴 첫 판단 사이에서 구했다 |
| 평가기 수신 종료 | 관측 종료 68.357, actor tail drain 종료 68.36 | 해제가 평가기 종료 뒤에 일어났다 |
| 사례 종료·STOP 요청 | 67.401·67.843 | 두 판단 호출 모두 사례 구간 밖, STOP 이후다 |
| 판단 노드 마지막 판단 | 68.40 | 평가기가 닫힌 뒤에도 판단 노드는 동작을 이어 갔다 |

출처 대조 결과는 다음과 같다.
- 판단 입력의 scan 헤더 변형은 전체 호출에서 1종이다.
- 취득과 짝이 맞는 3,039회 호출에서 판단 입력의 유한값은 `scans_received`와 정확히 같다. 판단 입력의 비유한 광선은 수신 원본의 비유한 광선에 고정 차폐 43개 광선을 더한 집합과 같다. A의 3,051회도 같은 관계이고, 차폐 광선 집합도 A와 같다.
- 누락 스캔의 두 호출도 같은 헤더를 쓰고, 고정 차폐 43개를 포함한다(비유한 43개).
- 다만 이 스캔은 `scans_received`·`acquisition`에 없다. 따라서 거리값이 실제 C1 주입 경로를 거친 바이트인지는 **직접 대조할 수 없다**. 위 정황은 출처 불일치를 시사하지 않지만 증명하지도 않는다.

A에는 누락이 없다. A의 마지막 취득은 68.504이고, 지연 없이 68.604에 발행되어 관측 종료 68.627 전에 기록됐다. 그다음 스캔은 68.704에 완료될 예정이었는데, 판단은 68.68에서 끝났다.

**결론:** 원인은 반올림이나 출처 불일치가 아니라 **기록 범위 끝 경계**다. 판단 노드가 평가기 수신 종료 뒤에도 지연 해제된 스캔으로 판단을 이어 간 것이다. 현재 게이트는 사례 종료 이후 호출까지 포함하므로, B처럼 지연을 주입하면 A보다 이 경계에 걸리기 쉽다(구조상 추정).

**정정 평가 필요성:** 원 실패(`decision_scans_acquired=false`)는 그대로 둔다. 범위를 바꾸려면, 예를 들어 평가기 수신 종료 이전에 해제된 스캔만 보거나 사례 구간 안의 호출만 보는 규칙이 필요하다. 이런 규칙은 다음 시험 전에 **별도 정정 평가로 사전 등록**해야 한다. 이 감사는 정정 판정을 만들지 않았다. 이 조건을 정정하더라도 B에는 다른 실패 조건 4개가 남으므로, B의 결과는 바뀌지 않는다.

## 2. B 추가 actor(`eval_second_lead`) 접촉과 정체 순서

| 시각(sim s) | 사건 | 근거 |
|---|---|---|
| 8.041 | 자차 출발(속도 > 0.10 m/s) | `trace.json` |
| 18.965 | 정체 시작(< 0.05 m/s 최장 구간 시작, `assess.py`와 같은 규칙). `HANDOFF_FOLLOW`/`HOLD`, drive 0, safe 0, `safety_reason=clear`, 주 actor는 자차 좌전방 1.29 m에서 90° 돈 상태 | `trace.json`·`actor_poses.jsonl`. 원인 해석은 범위 밖 |
| 18.965→64.845 | 자차 변위 1.4 mm | `ego_poses.jsonl` |
| 64.845 | **첫 접촉 메시지.** 상대가 자차 기준 뒤 0.209 m, 횡 −0.004 m, 같은 방향(Δψ 0.0015 rad)에 있었고, 직전 0.5 s 동안 상대는 0.80 m/s, 자차는 ≈0 m/s였다. 첫 쌍은 차체·뒷바퀴 | `additional_actors.json` |
| 65.100 | 중심 거리 최소 0.004 m(상대가 자차를 통과) | 자세 |
| 65.344 | 마지막 접촉 메시지. 상대는 자차 앞 0.193 m에 있었다. 뒤 기간에 앞바퀴 쌍이 나타난다 | 같은 파일 |
| 65.361 | 정체 구간 끝(`trace`) | — |

- **횟수 구분:** 연속 접촉 사건은 **1회**다(0.1 s 간격 기준, 0.499 s 지속). 접촉 메시지 표본은 500개(1 ms 간격)이고, 정규화한 충돌쌍 행은 1,840개다. 500과 1,840은 사건 수가 아니다.
- 접촉 동안 자차 변위는 21 μm, 상대 변위는 0.402 m다. 상대가 뒤에서 와서 정지한 자차를 관통해 앞으로 빠져나갔다.
- 첫 접촉 0.5 s 전까지 상대와 자차의 최소 중심 거리는 0.609 m다. 메시지는 사건이 있을 때만 발행되지만, 자세상 그 전의 근접 접촉 정황은 없다.
- **각본 성격:** 상대는 `static` 상자(0.2×0.15×0.12 m)이고 `set_pose` 명령으로 움직이는 운동학 actor다(`evaluation_actor.sdf`). 오버레이는 `role=lead`지만 `route_kind=full_course`, 0.8 m/s, 60 s 일정이다. 등록 경로는 s 49.26→97.26으로 한 랩 44.64 m를 넘는다.
  - A/B 명령 위치는 같은 경과시각 369개 표본(0–59.998 s)에서 최대 1.4e-14 m 차이다. B를 A의 선형 보간과 비교하면 최대 2.5 mm다.
  - 따라서 상대 경로는 자차 거동과 무관한 사전 일정이다.
  - 명령 속도의 0.566–0.8 m/s 9종은 A/B에 공통이다. 원인은 확인하지 않았다(곡선 구간 표본화 영향으로 추정).
- **해석:** 이 접촉은 자차가 다가가서 생긴 것이 아니다. 45.9 s 정체 뒤 한 바퀴를 돈 각본 actor가 뒤에서 통과한 결과다. `no_contacts`·`additional_valid` 실패는 정체의 **후속 결과**이며, 원 실패로 보존한다. 접촉을 따로 분류하거나 판정에서 빼는 것은 설계 판단이고 이 감사에서는 하지 않았다. 각본 actor가 한 바퀴를 돌아 정체한 자차에 닿을 수 있다는 점은 같은 overlay를 다시 쓸 때 시험 설계에서 고려할 사항이다.

## 3. A 같은 범위 검사

- 판단 3,051회, 고유 스캔 611개, 취득 누락 0이다. 판단 입력과 수신 원본의 관계도 B와 같은 모델로 일치한다.
- 주 actor 접촉 0줄, 추가 actor 접촉 메시지 0개다. 추가 actor와의 최소 중심 거리는 15.86 s의 1.83 m다.

## 한계

- 접촉 메시지는 사건이 있을 때만 발행되므로, 메시지가 없다는 사실이 무접촉을 증명하지는 않는다.
- 자차 기준 상대 위치는 자세 중심 기준이며, 차체 외곽의 기하 침투량은 다시 계산하지 않았다.
- 누락 스캔의 거리값 출처는 위 정황으로만 판단했다. 정체 원인은 GPT가 분석하는 범위다.
