# 새 코스 증속 편측 제동·접촉 진단 — 접촉 자료 확보·미완주

r14는 최고2.879m/s였으나35.15m에서 미완주했다. 감속 중 왼쪽 뒤바퀴가 역회전하고 오른쪽은차체약2m/s에맞춰굴러 모터축평균이차체진행을심하게과소평가했다. 당시접촉력이없어원인을확정하지못했다. 원시실패는보존한다.

이전 고정요청 `probe_braking_contact.py`는 옛코스/1m/s상한 전용이고 `analyze_contact_model.py` 일부는15:1을가정한다. 이를현재8.970588:1·2.8m/s진단으로그대로실행하지않는다. 먼저 현재 동일 단독 증속/사선공백 후보에 **바퀴접촉 계측만 추가한1회**로 실제 힘/반환을 확보한다. 실험소스가최신이므로원 r14와완전히같은실행을재현했다고하지않는다.

제어입력/센서/물성/마찰/토크/노면은바꾸지않고 원래1mm잔디를유지한다. 정답차체/접촉력은평가파일에만저장하고 제어기에입력하지않는다. 원래1랩/최대이탈/STOP/정상종료판정유지. 새관측목적없는반복을하지않는다. 원시접촉·구동gz JSONL은Git제외,해시/크기/요약만추적한다. Gazebo충돌이름재배열과force부호한계를검토하기전하중을단정하지않는다.

## 1회 계측 결과

최고 차체 종속도 **2.874 m/s**, 진행 **35.10 m·0랩**, `FOLLOW_BOUNDARY_UNCONFIRMED` 지속으로 종료했다. 원 r14와 비슷한 위치에서 속도 추정이 어긋났지만 이번에는 오른쪽 뒷바퀴가 느려졌고 차체는 도로 안에서 정지했다. 19,323개 자세 표본의 도로 밖 바퀴/벽 바퀴 표본 0, 정상 종료·872입력 불변·잔여 PID 0. 정상 완주 STOP 단계는 미실행이지만, 원 report의 failure_cleanup_stop에는 명시 STOP ACK·밀집 정지 통과·MCU ESTOP_LATCHED/stationary_ready=true가 있다. 명시 STOP 미실행으로 뭉뚱그린 초기 요약은 이 차이를 누락했다.

평가 수신기는 바퀴 접촉 155,792줄(146,215,635바이트), 구동 1,893줄을 받았다. 두 파일 모두 JSON 구문 오류 0·정상 종료·강제 종료 없음. 원시 파일은 로컬 보존하고 해시는 `reader_summary.json`에 남겼다.

`review_contacts.py`는 **힘을 보기 전에** 진행 33–35 m·차체 1.5 m/s 이상·한쪽 바퀴 표면속도 0.5 m/s 미만·다른 쪽은 차체와 0.25 m/s 이내로 구간을 선택했다. `force_review.json`의 오른쪽 감속 13개 공통 구동 시각 모두 왼쪽 뒤 접촉은 있었고, 오른쪽 뒤는 없었다. 왼쪽 뒤의 거의 수직 접촉쌍에서 위쪽 힘의 중앙값은 9.25 N이었다(양 바퀴가 함께 굴렀을 때 좌/우 약 3.69/3.93 N). 자료가 없는 바퀴 하중을 0 N으로 채우지 않았다.

`contact_coverage.py`의 1 ms 시각 대조에서는 **31.164–31.414초 251개 시각 모두** 앞 양쪽과 왼쪽 뒤의 명시적 접촉이 있었고, 오른쪽 뒤만 0개였다. 세 바퀴가 같은 `surface_main_190_col`에서 접촉했다. 직전 250 ms의 오른쪽 뒤는 107개, 직후 250 ms는 234개다. 수신기 전체 단절보다 해당 바퀴 접촉 경로의 상실과 들어맞는다. 이는 Gazebo 접촉 메시지·강체 무현가 모델에서의 관측이며, 실제 바퀴 부양이나 실물 하중, 미수신 시각의 0 N을 증명하지 않는다. 원 r14의 왼쪽과 방향이 바뀌어 특정 한쪽 엔코더 오류로 해석할 근거도 없다.

다음 [직각 접근 감속 후보](../solo_corner_approach_v1/README.md)는 값비싼 서스펜션/물성 변경에 앞서 실제 전방 반환으로 조금 일찍 감속할 수 있는지 저장 입력에서 먼저 비교한다. 현재 제어기 입력에는 정답 자세·접촉력·좌우 바퀴 속도를 추가하지 않았다.
