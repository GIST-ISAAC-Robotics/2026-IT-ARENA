# 지속 코너 병렬의 경계 끊김 분석

2026-11-08. r39 운영 시험을 기다리는 동안 r30의 코너 가림을 분석했다. 제어 소스나 Gazebo 입력은 바꾸지 않았다.

- r30 `source_snapshot.zip` 해시를 등록값과 대조하고 격리한 당시 코드로1,524판단·381 reset을 그대로 재현했다. 31.9–38.1초의 새 스캔62개에서 반환점과 이전 경로를 저장했다.
- 33.52–34.52초에는 반대 벽에서 코너를 만들고 유지했다. 34.62초 적합이 실패하고34.72초에는0.3초 기억이 만료됐다. 이후 새 적합은 가까운 직선만 반환했다. 따라서 처음부터 코너 형태를 전혀 못 본 상황과 다르다.
- [전환 전](corner_path_comparison.png)·[실패 구간](corner_failure_comparison.png)은 측정점, 운동 변환한 이전 경로, 현재 적합 경로다. 만료된 검은 경로를 그려 비교하는 것은 제어에서 계속 사용했다는 뜻이 아니다.
- `candidate.py`는 현재 두 직선 면과 가림 반환이 유효한 이전 코너를 지지하는지 비교하는 미연결 가설이다. 교차점은 관측하지 않은 **경로용 기하**이며 센서점/자유 공간으로 추가하지 않는다. 초기 가설은34.62초에서 실패했으나, 근거리 면에 붙은 두 끝면 반환을 기존3cm/70% 방식으로 분리한 뒤 최초 실패 스캔에서도 경로 가설이 나왔다. 판/벽 면 자체를 가림 물체로 재사용하지 않도록 구별했고, 최초 실패·현재 앞면 누락·만료·앞면 이동·가림 반환 누락·반대 방향·좌우 반사·직선 기억의8검사를 통과했다. 원 입력 점유는 보존했다. 이 결과는 한 스캔의 경로 제안이며 아직 주행 개선이 아니다.

코너 병렬은 계속 미해결이다. 운영 재출발의 가까운 통로 여유 문제를 먼저 분리하고, 이 후보는 실행 소스와 분리한 사본에서 최초 갱신 이후의 연속 저장 입력을 대조한다. 현재 분석을 개선 증명으로 올리거나 같은 실패 주행을 재실행하지 않는다.

## 미연결 선택기 사본 비교

`build_stage.py`는 현재 `local_follow.py`의 사본에서 기존 경계 선택이 모두 실패하고 유효한 직전 경로가 있을 때만 이 후보를 검토한다. 원본·TTL·점유·독립 보호는 바꾸지 않았다. 미관측 교차점까지의 길이를 ‘관측 길이’로 표시하지 않고 경로 길이와 실제 면의 합계 길이를 구분한다.

`stage_replay_result.json`의 현재 기준선은 r30 원본1,640판단과 모두 일치했다. 사본 최초 차이는34.62초이며, 같은 저장 입력에서0속도 명령은288→223회, 출력이 달라진 호출은70개다.34.72초의 기억 만료 직전 현재 두 면으로 갱신하는 제안이 사용됐다.36.04초 이후의 일부 정지는 남았다. 최초 명령 차이 이후 입력은 과거 실제 경로에서 얻은 고정 기록이므로 새 궤적이나 코너 병렬 성공이 아니다.

실행 중 다른 Gazebo 시험과 PC 자원을 공유한 전체 판단 비용 중앙31.47→31.56ms·p9553.70→54.60ms는 참고값이며 Jetson 처리율 검증이 아니다. 초기 출력 행에는 최상위 `handoff_follow` 이유만 기록되어 있어, 후속 실행 도구는 내부 `normal`의 경계/보호 이유도 저장하도록 보완했다. 이 진단 출력 보완을 이유로 동일 재생을 다시 돌리지는 않았다.
