# 후방 소실 직선 유지 v4 — 측정 속도와 목표 상한 분리

2026-10-29. 사용자 정리 요청에 따라 오프라인 비교까지 마치고 중단했다. **v4는 운영 코드에 연결하지 않았으며 Gazebo에서 주행하지 않았다.** 관련 원본과 실패는 보존한다.

## 수정 이유와 범위

앞선 [명시 observed 정책 Gazebo 시험](../rear_lane_preference_gazebo_v1/README.md)은 진행 4.63952 m·접촉 이벤트/바퀴 중심 이탈 0·STOP·14개 정상 종료·652판단 동일 재생을 확인했으나, 최소 측방 간격은 50.34 mm로 개선되지 않았다. 목표를 0.97569 m/s로 낮춰도 모터축 환산 측정값이 1.0210176 m/s가 되면 평행 후보의 `speed <= 1` 조건에서 탈락했다. 이는 차체 실제 속도가 정확히 1.021 m/s라는 뜻이 아니다.

v4는 정상 목표 상한과 측정 속도의 유효 범위를 분리한다. 측정값은 자르지 않고 기존 2.5 m 점유 스윕 범위, 측정 속도의 정지 거리와 현재 빈 공간, 그 경로의 실제 관측 영역을 검사한다. 현재/이전 조향·점유 팽창·1 cm 횡변위 조건·재개를 위한 새 스캔 확인은 유지한다. 다른 경로의 관측 승인을 복사하지 않는다. 시험 구현은 이 폴더의 `candidate.py`, `parallel_speed.py`, `parallel_state.py`다.

## 저장 입력 비교

- 반례 검사: **37건 통과** (`tests.log`). 미관측 이동 영역, 부족한 정지 공간, 비정상/스윕 범위 초과 입력, 정상 범위의 기존 출력, 새 스캔 재개 조건을 포함한다.
- 실제 Gazebo 실패 입력 652호출을 고정하고 v4를 두 번 계산한 결과, **652/652 결정론적 일치**와 입력 SHA-256 불변을 확인했다. 원래 명령과 같다는 의미는 아니다.
- 원래 명령과 다른 호출은 106개, 새로운 양수→0 출력과 0→양수 출력은 각각 0개다. 직선 선호 적용은 142개다. [전체 요약](shadow_gazebo.json).
- 최초 변화는 시뮬레이션 시각 12.94 s다. 측정 속도 1.0210176124 m/s를 그대로 사용하고, 관측된 이동 범위 0.52404 m를 확인해 목표 0.97569 m/s·조향 0.001596 rad를 제안했다. 원래 출력은 1 m/s·조향 0.061874 rad였다.
- 뒤 호출에는 원래 실패 주행에서 이미 증가한 조향이 입력으로 남아 있다. 따라서 곧이어 같은 횡변위 검사를 통과하지 못하는 구간도 있다. **이 비교로 새로운 궤적이나 측방 간격 개선을 주장하지 않는다.**

## 센서 합성 폐루프

명목 또는 거리 균등 ±30 mm·라이다 장착 yaw −0.5°·gyro 편향 +1°/s·gyro 잡음 표준편차 0.02 rad/s·모터축 양자화를 함께 넣은 제한 합성이다. 오차 분포의 실측 증명이 아니며, 구동 지연·슬립·통신 지연 전체를 재현하지 않는다. 단일 모터축 28카운트·15:1·65 mm와 수집 간격 20 ms를 유지했다.

|---|---|---|---:|---:|---:|
| ideal | `B_gazebo_left` | 성립 | 4.9577 | 140.00 | 0.20 |
| ideal | `B_gazebo_right` | 성립 | 4.9527 | 140.00 | 0.20 |
| ideal | `G_fast_lead_left` | 성립 | 4.9659 | 140.00 | 0.20 |
| combined | `B_gazebo_left` | 성립 | 4.6942 | 104.43 | 0.86 |
| combined | `B_gazebo_right` | **미성립** | 4.5873 | 140.00 | 2.90 |
| combined | `C_lead_stop_left` | 성립 | 4.2580 | 138.19 | 0.40 |

8개 실행 모두 자체 재생이 일치하고, 기하 접촉 사건은 기록되지 않았으며 접지면 모서리를 기준으로 도로 밖 바퀴 수의 최댓값은 0이었다. 종료 STOP의 0명령도 확인했다. 이 지표는 앞선 Gazebo의 **바퀴 중심** 판정과 구별한다. 오른쪽 복합 오차 조건은 초기 정지 2.9초 때문에 옆차가 먼저 앞으로 나가 후방 소실·재접근 장면이 만들어지지 않았다. 이를 후방 대응 통과로 세지 않는다.

C의 앞차 정지에서는 HOLD 2.28 s·재개 0.5 s·재개 뒤 진행 1.86584 m, D의 반대쪽 잔류 물체와는 최소 0.212713 m였다. 각 수치와 자체 재생 범위는 [검토 요약](review_summary.json), [명목](comparison_ideal/summary.json), [복합 오차](comparison_combined/summary.json)에 있다. 합성 결과만으로 실차 안전이나 모든 후방 상황 해결을 뜻하지 않는다.

## 소스와 남은 검토

- `offline_sources2.zip`과 `offline_sources2_sha256.json`에 실행 전 코드를 보존했다. 두 실행의 기록된 런타임 소스 해시는 검토 당시 로컬과 전부 일치했다.
- 원본 아카이브 목록에서 빠진 현재 런타임의 observed 모듈 2개는 실행 결과의 소스 해시와 일치하는 바이트를 `supplementary_dependencies.zip` 및 해시 JSON으로 추가 보존했다. 원본 ZIP을 덮어쓰지 않았다.
- 마감 코드 검토에서 추가 경계값 문제가 보였다. `proposal`의 기본 `target_cap=.35`가 설정 최대속도 0.35 m/s 미만일 때 거부된다. 현재 완료한 사례는 모두 최대속도 1.0 m/s이므로 해당 결과를 바꾸지는 않는다. **아직 수정·실행 검증하지 않았다.** 기존처럼 실제 경로 상한과 `min`으로 결합하도록 반례를 먼저 추가하고 수정한 뒤 연결한다.
- 운영 코드에는 [v3 연결](../rear_lane_preference_connection_v1/README.md)만 있고 기본값은 OFF/`timed`다. 이번 v4 실험 결과를 v3의 성공으로 소급하지 않는다.

## 다음 재개 순서

1. 위 저속 설정 반례를 추가하고 후보 입력 검사를 수정한다. 원본 v4 코드와 이번 결과를 보존하고 영향 범위만 재검사한다.
2. v3의 `observed` 기록을 기존 의미로 재생할 수 있게 v4는 별도 정책 이름 또는 버전을 사용해 연결한다. 기본 OFF/`timed`는 유지하며, 보존·이관 의존성과 필요한 회귀를 확인한다.
3. 동일한 옆차 0.15→1.0 m/s 일정으로 제한 Gazebo 1회를 수행해 최초 1.021 m/s 구간의 해제와 측방 간격이 실제로 달라지는지 확인한다. 같은 실패의 무근거 반복은 하지 않는다.
4. 오른쪽 복합 오차의 초기 정체는 별도 원인으로 남긴다. 기존 전체 랩·G2 편측 헛돎·실물 미검증을 해결한 것으로 표시하지 않는다.

현재는 사용자 요청으로 정리·중단한 상태다. Claude 5시간 한도 뒤 GPT 인계 상태를 유지하며 재개 시 자동으로 Claude를 다시 호출하지 않는다. 커밋·푸시·외부 게시·Jetson/전원 변경은 하지 않았다.
