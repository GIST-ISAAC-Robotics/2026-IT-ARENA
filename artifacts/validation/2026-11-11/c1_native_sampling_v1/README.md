# C1 원천 배열 연결과 선택형 시뮬 취득

현재 **입력 연결·42.06m 부분 주행 완료, 마지막 정체 원인 개선 중**이다. 실물 시각 교정이나 새 입력의 코스 완주를 완료한 기록이 아니다.

## 입력과 범위

- 11/10 Standard10 Hz SDK의 원시 각도/개수/순서를 기준으로 한다. 실내 거리·좌표 원본은 Git 제외 상태를 유지한다.
- `sdk10.json`·`sdk12.json`: 기존 저장344스캔·154,640점을 원천 인덱스와 점별 시각을 유지해 운동 보정/관측 관문까지 대조했다. 이 검사의 시간은 합성200μs/점, 운동은1m/s·0.8rad/s다. SDK 추정 시간을 그대로 승인하려는 호출은 모두 거절했다. 실측 시간·주행 검증으로 확대하지 않는다.
- 선택형 시뮬 템플릿은 [`c1_standard10_native_angles_v1.json`](../../../../config/tests/c1_standard10_native_angles_v1.json)이다. 성공10 Hz 기록의 처음32배열에서 각도만 추출했으며, 회전당504/508/512점을 순환한다. 전체 기록의500~524점 범위를 전부 재현한 것은 아니다.
- Gazebo의5000방향 순간 광선에서 실제 가장 가까운 방향의 거리·각도를 함께 가져온다. 각도 양자화 최대0.0361°·과거 source frame의 취득 근사 최대2.1ms를 감사한다. 새 점을 동일 거리로 복제해 빈 각도를 채우지 않는다.
- **시간 모델은 회전주기÷점수**인 합성 근사다. 실제 C1의 점별 주기·SDK batch 시각이 검증됐다는 뜻이 아니다. 기존500점 시뮬은 기본값으로 유지하고 새 표현은 `--lidar-native-sampling-profile`로 명시 선택한다.

## 수용 조건

1. 기존 균일 입력의 판단 재생 동일, 관련 입력/관측/기록 회귀 통과.
2. native 메시지의 점수·CW 순서·원천 각도·점별 시각이 제어기와 독립 보호층에 동일하게 전달. `/drive`→보호층→`/drive/safe` 유지.
3. 기존 단독 프리셋/속도·실측 IMU 산포·기어비·물성·정지/종료 판정을 유지한 공식 코스 한 번. 진행/접촉/노면·STOP/정상 종료·입력 해시와 source 취득을 확인한다. 실패 원본은 보존하고 같은 조건을 성공할 때까지 반복하지 않는다.

## 이미 확인한 부분과 남은 것

초기 입력·관측 연결 시점의 관련998검사와 기존 영점0 단독 기록1,586판단 동일 재생을 확인했다. 후속 native ROS/시뮬 선택 경로를 추가한 뒤 검증을 진행 중이며, 이전 통과를 새 코드 전체의 통과로 소급하지 않는다. 최초 새 검사2실패는 중첩 `pytest.approx`와 동일성 fixture의 부동소수점 연산 순서 차이를 고쳤고, 확장 실행의12수집 오류는 `scripts` 경로 누락이었다. 기존 계약 필드 목록 검사의1실패는 새 원천 각도 필드를 명시하는 것으로 수정했다. 출력 판정선을 바꾸지 않았다.

WSL이 단순 명령/root에서도 `E_UNEXPECTED`를 반환한 뒤 사용자 승인으로 Ubuntu-24.04만 재시작해 복구했다. 해당 시점에 새 Gazebo 주행은 실행 중이 아니었으며 기록은 보존됐다. Fable 예약은 사용자 요청대로 삭제했다.

세부 실행 로그와 저장 판단 재생은 Git 제외 `build/c1_native_sampling_2026_11_11/`에 두고 최종 공개 집계는 이 폴더에 남긴다. 실물 축/장착 yaw·취득 시각·동작 중 정적 벽 시험은 하드웨어를 움직일 수 있는 후속 점검에 남긴다.

후속 native ROS/시뮬 단위171검사는 통과했다. 기존 출처 계약 검사에서84실패가 발생한 것은 이번 변경을 후속 계보에 아직 등록하지 않았기 때문이다. 기존 계약의 해시를 바꾸지 않고 r66에19수정 파일의 이전 바이트와7신규 의존을 등록했다. 이전 바이트는 보존된11/10 주행 snapshot 또는 해당 해시와 일치하는 HEAD에서 가져왔다. 함께 발생한 fake node의 `native` 속성 누락은 기본값 없는 접근을 고쳤으며 후속 단위 검사에 포함됐다. 출처163검사와 네 패키지 빌드가 통과했고 overlay prefix/새 세 모듈 import가 현재 소스와 일치했다. 단독1회 실행을 시작했다. 진행 중인 입력은 동결하며81T 변경은 후속 적용 대기다.

## 두 실행 실패와 원인 수정

| 실행 | 실제 결과 | 원인/후속 |
|---|---|---|
| `solo_run1` | 출발 전 필수 데이터 부족, STOP 서비스 확인 불가·Gazebo 종료/잔류0,551입력 불변 | 실행 wrapper가 overlay의 `PYTHONPATH`를 덮어써 `arena-vehicle-interface` metadata를 잃었다. 원 wrapper/log 보존, 기존경로 추가 방식으로 수정 |
| `solo_after_overlay` | 15.18s·진행0m/0랩·접촉0, cleanup STOP/MCU software STOP·정상종료·551입력 불변 | native motion 입력 정상, 취득 감사 통과·504/508/512점. `follow_partial_scan_scene_mismatch`로 출발 거부 |

두 번째 실패는 원시 실수 취득 시각과 호환용 ROS header의 정수 나노초 반올림 시각을 exact 비교한 코드 문제였다. 예를 들어 `0.5000000000000001`과 header 복원 `0.5`는 같은 입력에서 만들어졌지만 서로 다르다. 허용 오차를 넓히는 대신 r67에서 원시 최초시각을 입력/부분관측/기억 비교에 일관되게 사용한다. 기존 균일 LaserScan 경로의 계산식은 유지한다. native trace의 비용 계측도 `sec/nanosec` 키를 가정하지 않도록 보완했다. 새 검사에는 이 반올림 차이가 있어도 기존 경계 확인과 출발 대기 단계를 거친 세 관측 후 **양수 진행 명령**이 나오는 조건을 포함한다.

`/scan/native` 그래프 단일 수집에서는 `lidar_safety` 구독을 확인했지만 같은 snapshot의 제어기 구독까지 확인하지 못했다. 양 소비자가 같은 순간 구독했다는 근거로 쓰지 않는다. 제어기 motion/status와 보호/종료 결과는 별도 원본 근거다. `run_time_fix.py`는 r67검사 뒤 새 결과 경로에 실행했으며, 앞의 실패 결과를 덮어쓰지 않았다.

r67후속314검사 중313통과·1실패는 새 fixture가 기존 `follow_release_wait` 한 단계를 빠뜨리고 두 번째 스캔에 출발을 기대했기 때문이다. 실제 두 번째는 경계확인 후 출발대기, 세 번째는양수1.0m/s였으며 이 순서를 명시하는 검사로 고쳤다. 대기 기준 자체는 변경하지 않았다.

## r67 새 입력 주행 결과와 정체 원인

`solo_time_fix`는42.060m/0랩·최고2.874658m/s·속도중앙1.165m/s·접촉0이었다. 코스44.64m의 기존 종료 목표46.64m에는 도달하지 못했다. 횡오차 RMSE0.0451m·p95 0.090m이며 부분 주행 범위의 결과다. 원천 취득504/508/512점·10Hz·첫점~마지막점0.099803초, 순차 취득 감사는 통과했다. 이 시간은 합성 근사이고 `hardware_timing_verified=false`다.

cleanup은 소프트웨어 STOP 응답·MCU `ESTOP_LATCHED/software_stop`·목표0·Gazebo 정상종료와잔류0을 확인했다. 입력551개 해시가 불변이다. 관련 native18검사·출처164검사, `arena_autonomy` 재빌드 및17console entrypoint 로드를 통과했다. 그래프 수집 한계는 위와 동일하다.

마지막42.62/42.82초에는 경계·약0.8m swept clearance가 계산되고 측정속도는0이었다. 경로 요청 약0.994m/s를 그대로 부분 관측 검사에 넣자, 약5° 결측의 예상 숨은 폭이92mm로50mm 범위를 초과했다. 정책이 거절할 때 대기 상태가 초기화되어, 요청0인 대기 호출에서는 관측이 통과하고 다음 양수 요청에서는 다시 거절하는 순환이 생겼다. 독립 보호층은 clear였다. 따라서 **요청만 기존0.2m/s 운용 상한으로 먼저 낮추고, 측정속도는 자르지 않은 채 같은 조건으로 평가**하는 저장 입력 후보를 대조한다. 빈 공간 생성·물성/보호 기준 완화가 아니며, 아직 후보의 실제 궤적 성공을 확인한 것은 아니다.

### 재개 환경

ROS 실행에서는 `source /opt/ros/jazzy/setup.bash`와 `source install/setup.bash` 뒤 기존 `PYTHONPATH`를 보존한다. 소스 경로를 앞에 추가할 때에는 `export PYTHONPATH="src/arena_autonomy:src/arena_vehicle_interface:scripts:tests:${PYTHONPATH:-}"` 형태를 사용한다. 소스 import만 되는 것은 ROS console entrypoint의 배포 metadata를 확인한 것이 아니다. 이번 수정 환경에서는 두 패키지의 console entrypoint17개 `.load()`까지 통과했다. 함수 자체를 실행한 사전 주행 시험은 아니다.
