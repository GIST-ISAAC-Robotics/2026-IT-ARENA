# Jetson 처리 주기 구조 자문 원문

2026-11-11 14:52–14:58 KST. Claude Fable 5.2/high 읽기 전용 자문. 첫 인사만 제외했다. 아래는 자문 의견이며, 독립적으로 검증된 결과나 구현 채택 기록이 아니다. 특히 r91 run3의 출발 실패를 받기 전 작성됐다.

## 핵심 판단

**추천 순서는 A → C(표적 한정) → B-lite(조건부)입니다.** A는 선택이 아니라 실시간 운용의 전제이고, A를 적용하면 C의 목표가 20ms에서 약 90ms로 바뀝니다.

- **입력 수신 분리는 필수입니다.** 판단이 56~161ms 동안 executor를 점유하는데, 운동 이력은 입력 공백 `.05s`·외삽 `.03s`를 넘으면 `motion_gap`/`motion_stale`로 정지합니다(`lidar_motion.py:30-31`). IMU 구독은 `qos_profile_sensor_data`입니다(`lidar_motion_ros.py:89`).
  - 추론: 이 QoS의 깊이는 5(약 25ms분)이고 rclpy 단일 executor는 대기 1회당 구독별 1건만 꺼내므로, 실시간에서는 IMU 유실로 정지가 반복될 가능성이 큽니다. 시뮬은 느린 시계라 드러나지 않았을 것입니다.
- **r90의 상태 변화는 스캔 누락과 지연 쪽일 가능성이 높습니다.** 확인 계수는 새 스캔(`fresh`)에서만 오릅니다(`local_follow.py:747,1053,1135`, `parallel_lane_trial.py:165,178`). 반면 경로 기억 TTL `.30s`, 장면 노화 `.3s`, 서로 일치하는 새 스캔 2회 확인은 매 스캔을 제때 처리한다는 전제입니다(`local_follow.py:75,87,732,1052`).
  - 추론: 75개 스캔 미처리와 .06~.16s 간격이 기억 만료 → `follow_boundary_unconfirmed` → `parallel_hold_baseline_unavailable`(기준 사유가 허용 목록 밖, `parallel_lane_trial.py:46`) → 재개 대기로 이어졌을 것입니다. r90은 반복 틱 생략과 스캔 누락을 분리하지 않았습니다.
- **스캔당 1회 판단이면 지연 예산은 약 100ms입니다.** 스캔 k의 계획이 k+1의 결과가 나올 때까지 `.3s` 계약 안에 있으려면 판단 지연이 대략 `.1s`에서 드라이버 지연을 뺀 값보다 짧아야 합니다. r90의 새 원천 비용(평균 103.65ms, p95 186.77ms)은 이를 넘습니다. C의 목표는 p95 약 2배 감소입니다.

## 단순 캐시가 위험한 이유 (소스 확인)

- 장면은 매 틱 현재 기준시각의 차체 좌표로 다시 만들어집니다(`local_pursuit.py:430`). 틱 간 캐시는 v·Δt만큼 어긋난 기하입니다(2.8m/s에서 100ms당 28cm).
- 광선별 팽창과 `braking_speed`는 노화 시간에 따라 커집니다(`occupancy_timing.py:17`, `local_path.py:456`). 캐시는 이를 낙관적인 값으로 고정합니다.
- 점유 검사는 실제 발행될 조향 `previous±3·dt`와 직전 조향의 두 원호에 대해 수행됩니다(`local_follow.py:1100-1110`). 캐시된 결과는 다른 조향 쌍을 검사한 것입니다.
- 정지 상태 초기화는 새 스캔이 아닌 틱에서도 일어납니다(`local_follow.py:1133`, `_hold`).
- 안전한 캐시는 한 호출 안에서 같은 장면·같은 인자의 순수 계산을 재사용하는 것뿐입니다. 예: `per_ray_padding`이 `local_follow.py:698,1103`과 `parallel_lane_trial.py:113`에서 호출됩니다.

## 대안 tradeoff

| 안 | 장점 | 한계 |
|---|---|---|
| A 저주기 판단 + 수신 분리 | 판단 코드와 호출당 출력을 보존하고 변경이 가장 작음 | 조향이 지연+0.1초 동안 고정되고, 스캔당 지연이 100ms 미만이어야 함 |
| B 느린 기하 + 빠른 추종 | 2.8m/s 조향 지연을 해소 | 완전판은 `_baseline_command`와 선택기를 분할해야 해 r87 검증 대상이 바뀜. 경로 운송+추종만 하는 B-lite만 작음 |
| C 동등 계산 축소 | 출력 동일성 도구로 검증 가능 | r89에서 p95가 3%만 줄었고 비용이 분산되어 20ms(약 9배)는 비현실적. 약 2배는 표적 작업으로 시도할 만함 |

## 먼저 할 최소 단계

1. **판단을 별도 process로 분리합니다 (A).** `VisionProcess`의 epoch/sequence/폐기 통계 방식과 `follow_trace.snapshot_call`/`restore_call`(Jetson 복원 1.95ms)을 재사용합니다.
   - **snapshot:** 기존 `record_call` 인자(스캔, 운동 이력, 기준시각, 운동 epoch, 엔코더 속도, side, 실제 발행된 직전 조향, dt)에 `seq`, `generation`, 스캔 수신 monotonic을 더합니다.
   - **제출:** 새 스캔이 왔고 워커가 비었을 때만 보냅니다. 대기열은 최신 1건이며 누락 스캔 수를 기록합니다.
   - **결과:** `(speed, steering, detail)`에 `seq`, `generation`, `t_ref`, `source_first_s`, 완료 시각을 붙입니다.
   - **채택:** generation이 일치하고 seq가 증가하며, 적용 시각 기준으로 `now − source_first_s < .3`일 때만 씁니다. 기존 `follow_scene_stale` 수치를 적용 시각으로 옮긴 것이어서 새 게이트가 아닙니다. 만료되면 속도 0, 조향 유지입니다.
   - **STOP/reset/입력 경계/정지 상태:** 같은 콜백에서 generation을 올리고 계획을 버리며 기존 `stop()`을 호출합니다. 워커는 generation이 바뀌면 `follow.reset()`합니다.
   - **출력:** 50Hz 타이머는 기존 허가 판정과 가속/조향 변화율 제한만 수행합니다. `/drive` stamp는 발행 시각을 유지하되, 만료된 계획은 재발행하지 않습니다.
   - **dt:** `.1` 고정을 권합니다. 코드에서 dt는 경과 시간이 아니라 다음 명령까지의 조향 도달 창과 외곽 거리입니다(`local_follow.py:1100`, `parallel_lane_trial.py:23,85`). r90의 경과 dt 방식은 맞지 않습니다.
   - trace 기록(`local_pursuit.py:441`)도 워커로 옮겨 제어 경로에서 빠집니다.
2. **C를 표적 한정으로 진행합니다.** 순서는 GC 조정(r88 기록: 판단 중 수집 3,112회), 호출 내 동일 인자 재사용, 자체 비용 상위 1~2개(광선 깊이 지지, `swept_limit`의 Python 삼각함수 루프)의 native화입니다. 매번 3,060 출력 동일성으로 확인합니다.
3. **B-lite는 증거가 있을 때만 추가합니다.** 채택된 계획의 `path_points`를 `transport_points`로 현재 자세에 옮겨 `pursue_path`로 조향만 갱신하고, 속도는 계획값 이하로 둡니다. 실제 조향의 점유 검사는 독립 보호층이 50Hz로 수행합니다(`lidar_safety.py:215-219`).

## 검증

1. **오프라인 분리 시험(기존 r90 도구):** "모든 스캔을 정확히 1회, 누락 0, dt=.1" 조건으로 새 0명령 수를 봅니다. 0에 가까우면 r90의 변화는 스캔 누락·지연 탓으로 분리됩니다.
2. **지연 주입 폐루프 1회:** 1단계 구조에 r89의 Jetson 비용 분포(또는 고정 약 170ms)를 시뮬 시간 지연으로 넣습니다. r91이 제외한 가변 지연을 보는 시험입니다.

1단계 수용 기준으로는 Jetson 실물 센서에서 IMU 공백 초과 횟수, `motion_gap`/`motion_stale` 횟수, STOP에서 0명령까지의 지연을 계측하시기를 권합니다.

## r91 run3 결과별 결정

- **성공:** 스캔당 1회, dt=.1 판단이 지연 0 조건의 명목 교통에서 성립한 것입니다. A를 최종 골격으로 두고 B-lite는 보류하며, 남는 위험은 지연뿐이므로 검증 2와 C로 갑니다.
- **실패, 추종 문제(경로 이탈·접촉·진동):** B-lite를 C보다 먼저 합니다.
- **실패, 정지 연쇄:** 지배 사유를 먼저 확인합니다. dt=.1로 넓어진 외곽 때문이라면(`lateral_motion_not_small` 등) 10Hz 판단의 실제 비용이므로 B 또는 판단 주기 단축이 필요합니다. 기억·확인 계약 때문이라면 검증 1로 분리합니다.
- **어느 경우든:** run3에는 계산 지연이 없으므로 Jetson 운용 승인 근거가 아니며, 1단계는 그대로 필요합니다.

## 미확인·가정

- rclpy의 구독별 1건 처리와 QoS 깊이 5는 저장소 밖 일반 동작에 근거한 추론입니다.
- r90 `report.json` 원문은 열지 않았고, 사유 연쇄는 README와 소스 대조에 의한 추론입니다.
- 단독 2.8m/s 구성의 Jetson 비용은 받은 근거에 없습니다. `solo_route_only`는 측방 선택기를 생성하지 않으므로(`local_follow.py:485,494`) 더 가벼울 수 있어, 같은 도구로 1회 계측하시기를 권합니다.
- process 대신 thread를 쓰는 안은 GIL 경합 우려로 권하지 않았으나 실측한 것은 아닙니다.
- 5시간 사용량 경고는 없었습니다.
