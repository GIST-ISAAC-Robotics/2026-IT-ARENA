# 판단 처리 간격을 바꾼 저장 입력 비교

2026-11-11 실행 전 기록.

## 질문과 범위

r89는 최신 완주 입력에서 판단 비용을 줄였으나 Jetson 전체 중앙65.37ms·p95 170.05ms로20ms를 넘는다. 현재 노드는 단일 executor에서 `MotionInput.project → motion_scene → follow.command → 출력`을 수행하며, 판단과 출력의 `dt`도 고정 `1/control_rate_hz`다. 느린 판단이 끝나야 같은 노드의 센서/운영 콜백이 처리될 수 있다. 이 코드 사실과 실제 ROS에서 발생할 적체량은 구분한다.

이번에는 `scripts/probe_follow_cadence.py`로 다음 세 조건을 동일한 r87 저장 입력·r89 동결 코드에서 비교한다.

1. 모든 호출을 유지해 원래3,060출력과 전체 동일성 확인.
2. r89에서 계측한 `motion_scene + follow_command` 시간 동안의 틱을 생략하고, 다음 기록 틱에서 최신 입력으로 시작. `dt`는 현행20ms 유지.
3. 같은 호출 생략에서 `dt`만 실제 선택된 시작 시각 차이로 변경. .2초 상한을 넘으면 기존 거절을 그대로 기록하며 임의로 clamp하지 않음.

실시간에서 필요 없는 기록 복원 비용은 가상 busy 시간에 넣지 않는다. reset은 상태와 busy 경계 모두를 초기화한다. 운영 제어기·ROS 토픽·보호·물성·TTL은 변경하지 않는다. 성공 판정선을 새로 만드는 시험이 아니며, 상태/명령 변화와 오래된 입력·고정dt의 영향을 분리하는 진단이다.

## 해석 한계

- 원래 입력의 차체 속도·이전 조향·센서 궤적을 그대로 사용한다. 선택한 새 출력이 다음 관측을 바꾸지 않으므로 **개방 루프 분석이며 주행/완주 증거가 아니다**.
- 비용도 원래 전체 호출 순서의 같은 seq에서 얻은 값을 지정한다. 호출 생략으로 상태가 달라지면 실제 비용 역시 달라질 수 있다. ROS·선행 투영·독립 보호·영상·직렬 통신 비용은 포함하지 않는다.
- reset의 실제 전송·STOP 지연, 비동기 결과 폐기, 빠른 출력부는 구현하지 않는다. 결과가 오래됐는데 새 시각으로 재발행하는 운용안을 승인하는 자료가 아니다.
- 현재 독립 보호층과 명시 STOP은 그대로 유지한다. 이 결과 하나로50Hz를10Hz로 바꾸거나 캐시된 명령을 반복 발행하지 않는다.

## 재개와 실행

도구의 admission/부호·비유한시간/시계 reset/비용 완전성 검사를 먼저 수행한 뒤 GPT-6 Luna가 위 세 조건을 순서대로 실행한다. 첫 전체 동일성이 실패하면 뒤 두 조건을 실행하지 않고 원인을 회수한다. 원 입력/비용/동결 소스의 전후 SHA-256을 확인한다. 상세 입력은 기존 Git 제외 정책을 유지하고, 결과의 선택 seq·요약 명령·기간만 기록한다.

## 첫 비교 결과

관련17검사가 통과했다. 최초에는 테스트의 소수 덧셈 결과를 완전 일치로 비교한1건이 실패해 테스트 비교를 `pytest.approx`로 수정했다. 실행 전 WSL 일반/root 명령의 `E_UNEXPECTED`를 확인해 기존 허용 범위에서 Ubuntu-24.04만 재시작했다. 운영 코드나 Jetson 전력/환경은 바꾸지 않았다.

| 조건 | 처리 / 생략 | 전체 출력 차이 | 속도·조향 차이 | 원 진행→새0명령 | dt>.2초 |
|---|---:|---:|---:|---:|---:|
| [전체 유지](all_recorded/report.json) | 3,060 / 0 | 0 | 0 | 0 | 0 |
| [busy 생략·기존dt](busy_recorded/report.json) | 721 / 2,339 | 704 | 494 | 145 | 0 |
| [busy 생략·경과dt](busy_elapsed/report.json) | 721 / 2,339 | 631 | 499 | 150 | 9 |

입력·동결 소스는 세 조건 모두 불변이다. busy 두 조건의 선택된 판단 간격은 중앙.060초·p95 .160초, 가상 완료 시점의 첫 광선 나이는 중앙.225초·p95 .311초·최대.415초다. 원 장면/속도는 유지되므로 이 숫자를 실제 정지 횟수나 랩 손실로 바꾸어 쓰지 않는다. 경과dt에서9회는 현행 `.2초` 입력 한계를 넘으며 그 조건을 완화하지 않았다.

기존dt 조건의 새0명령145개 중100개는 `baseline_not_normal`,21개는 `released_hold_keep_steering`,16개는 `side_threat_not_passed`,7개는 `large_motion_region_unobserved`,1개는 `no_side_threat_seen`였다. 이는 최상위 선택 사유여서 기본 경로·결측 정책의 하위 원인을 추가 회수한다. 첫 도구는 [원본](probe_at_first_run.py)으로 보존했으며 진단 필드만 추가한 조건1회에서 기존 선택 seq/필드 동일성을 대조한다.

**현재 판단:** 단순 호출 생략이나 `dt`만 바꾼10Hz 운용은 채택하지 않는다. 빠른 출력/보호와 느린 계획을 나눌 가능성은 남기되, 이 실험은 그 구현이나 효과의 증거가 아니다. 우선 반복 호출이 실제로 어떤 상태 이력을 유지했는지 확인한다.

## 원인 범위와 후속 비교

[하위 사유 회수](busy_reason_detail/report.json)는 선택721seq와 기존15개 행 필드가 모두 기존 결과와 같았다. 새0명령은 `parallel_hold_baseline_unavailable`98·`follow_release_wait`22·`parallel_hold_lateral_motion_not_small`8·`parallel_hold_reference_not_straight`7·`parallel_hold_release_wait`5·`parallel_hold_partial_observation_outside_trial`3·`follow_boundary_unconfirmed`2였다. 그때 결측 정책 사유는140회 `fully_observed`,5회 `bounded_side_missing`이었다. 이를 전부 LiDAR 무반환 탓으로 설명하지 않는다. 최초 차이는10.04/10.10초 경계미확정과10.16초 재개대기였다.

[기록 기반 원천별 비용](cost_by_source.json)에서 전체613개 scan 중 busy 조건은538개만 처리했고75개는 한 번도 처리하지 않았다. 새 원천의 계산 비용은 평균103.65ms·중앙73.28ms·p95 186.77ms, 같은 원천의 후속 판단은 평균83.58ms·중앙53.25ms였다. 원천 처리 자체도100ms를 넘는 경우가 있어, 단순 중복 틱 생략만으로10Hz 실시간을 보장할 수 없다. 프로파일/별도 함수 시계가 아니라 r89에 이미 저장된 두 단계의 합을 원천별로 나눈 것이다.

원 궤적이 새0명령을 무시하고 계속 움직이는 진단의 한계를 분리하기 위해, [r91의 주기적10Hz 폐루프1회](../control_10hz_r91_v1/README.md)로 이어간다. 실제 명령이 다음 관측을 바꾸는 경우를 보되, 가변 계산 지연·Jetson/ROS 실시간 검증과 섞지 않는다. 이 단계에서 운영 주기나 보호 상수를 바꾸지 않았다.
