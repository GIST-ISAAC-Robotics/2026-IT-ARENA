# PC/Jetson 경로 재표본 점 개수 일관성

상태: 구현·관련96검사와 소스 계보177검사 완료. Jetson 전체3,072판단의 속도·조향 명령은 기존 비교 기준으로 모두 일치했다. 세부 질의점 개수 차이는544판단에 남았으며 전체 출력 일치·비용 측정 통과로 확대하지 않는다. 대표 주행은20.01m에서 정체해 실패했다.

## 재현된 원인

r79 원 판단3072회는 PC(x86_64/Python3.12.3/NumPy1.26.4)에서 모두 일치했다. 같은 소스·입력의 Jetson(aarch64/Python3.10.12/NumPy1.21.5)은 4번째 판단 seq384부터 내부 경로 좌표가 약2–3mm 달랐다. 첫3불일치의 명령은 같았으나 전체 명령 동일성은 확인되지 않았다. 기존 비용 시험은 동일성 관문에서 실패해 비용값이 없다.

최초4판단의 `local_path` 중간값을 대조했다. 호길이 끝점은 약1e-15 수준 차이였으나 `int((last-first)/.025)+1`에서 정수 경계의 아래/위로 갈리며 **82개 또는83개**로 재표본화됐다. 이후 적합에 쓰는 점 위치가 달라져 경로 차이로 증폭됐다. [PC 중간값](../jetson_traffic_r79_v1/pc_path_sampling.json), [Jetson 중간값](../jetson_traffic_r79_v1/jetson_path_sampling.json).

## 수정과 보존

`_sample_count`는 차감·나눗셈의 기계 정밀도 범위에서만 격자 정수에 맞춘다. 원 관측 끝점·.025m 표본 간격·최소12점·주행 간격·TTL·충돌/노면 판정은 유지한다. 일반 벽과 확장 코너의 두 표본수 계산에 적용했다. 실제로1nm 짧은 구간은 여전히 아래 개수를 사용한다. 단순히 출력 비교 허용 오차를 키운 변경이 아니다.

별도로 평가 로그에서 `+inf`를 null로 합치던 부분을 수정해 송수신의 구분을 기록에도 유지했다. 과거 로그는 원래 바이트로 보존한다. 이전 제어/평가 소스는 [before_r82.zip](before_r82.zip), 출처는 [계보](../../../../config/tests/path_sampling_r82_sha256.json)에 남겼다.

## 검증 경계

- WSL 관련96검사 통과. Windows 보조 환경에서 먼저 시도한 묶음은 `shapely` 미설치로 수집 단계 실패했고, 기존 의존성이 있는 WSL에서 실행했다.
- 고정 r79 입력으로 r82 예상 출력 사본을 만들되 원 실제 출력은 덮어쓰지 않는다. 바뀐 판단/명령 수와 입력 불변성을 별도 기록한다.
- 그 사본과 Jetson 출력을 대조해야 플랫폼 일관성 개선을 판단할 수 있다. 이전 실패를 성공으로 바꾸거나 재생을 새 폐루프 성공으로 세지 않는다.

고정3,072판단 중871개 세부 출력·559개 명령이 바뀌었다. [명령 차이](command_change_audit.json)는 속도34회·조향558회이며 0↔양수 전환은0회다. 최대 속도 차이는0.566m/s, 조향 차이는0.0502rad 미만이므로 단순 표시 정밀도 수정으로 축소하지 않는다. 재표본 점 하나의 차이가 경로 적합과 속도 분기까지 영향을 준다. [새 출력 사본](derived_expected.json)은 원 입력 해시를 유지했고 원 r79 기록은 보존한다. 출력 일관성 확인 뒤 현재 설정의 대표 주행으로 실제 영향을 확인해야 한다.

Jetson은 새 `/home/q/it_arena_traffic_r82_20261111`만 사용한다. [107파일 묶음 검사](jetson_bundle_check.json)와 정적 의존성 확인을 마쳤으며 원 r79 원격 결과를 덮어쓰지 않는다. 묶음 생성은 Windows 기본 인코딩 때문에 원격 실행 스크립트 생성 단계에서 한 번 실패했고, 이미 생성된 archive/manifest는 보존해 검증한 뒤 UTF-8로 스크립트만 완성했다.

[Jetson 결과](jetson_summary.json)는 `recorded outputs do not match current source`로 실패했다. 입력·소스 불변과 snapshot 완전성은 확인했으나 비용값은 없다. 첫 원인의 수정만으로 전체 플랫폼 동일성이 확보됐다고 하지 않는다. 최초3불일치 진단으로 다음 차이를 분리하며, 같은 전체 비용 시험을 무변경 반복하지 않는다. 대표 주행의 최초 실행 wrapper는 CRLF 때문에 빌드·시뮬 시작 전에 실패했고, 원 로그를 보존한 뒤 LF로 고쳐 실행했다.

## 새 실제 주행과 남은 플랫폼 차이

[동일 조건 실제 주행](two_actor_run1/combined_assessment.json)은 **20.01m·최장 저속25.58초**로 완주·정체·최종간격 기준에 실패했다. 접촉/차체 겹침0,34161노면 표본의 바퀴 이탈·차체/조향 외곽 이탈0, STOP과14/14프로세스 정상 종료를 확인했다. 선택형native682스캔·504/508/512점·지연32–70ms·거리오차±3cm와 소스 불변을 확인했다. 실제3038판단의0→양수/양수→0 전환은 각각15회이며, 위 고정r79 입력의0회와 다른 집계다. 수치 일관성 수정이 정체를 해결했다고 하지 않는다.

[PC](pc_first_region.json)·[Jetson](jetson_first_region.json)의 첫 잔여 차이는 이동 외곽 질의3381/3380개와 그중 가림 질의246/245개다. 두 질의점 집합의 최근접 차이는 최대 약1.71e-15m이며 두 조향각 중 한쪽만 차이가 났다. 최초3불일치의 속도/조향 명령은 같았지만 전체 명령 동일성과 비용 시험은 아직 통과하지 못했다. 중복점 수치 차이 가능성을 남기고 주행 정체 개선을 우선한다. 비교 허용량을 넓혀 성공으로 바꾸지 않았다.

## 전체 플랫폼 출력 감사 완료

[전체 감사](jetson_full_platform_audit.json)는 원격107파일과 입력 해시를 유지한 채 **3,072회 중 명령3,072회 일치**, 전체 출력2,528회 일치를 확인했다. 원래 `equal_output` 기준을 바꾸지 않았으며 명령 차이는0회다. 나머지544판단은 질의점·가림점·미관측점 개수의 차이였다. 예를 들어 첫 미관측점 차이는480/481개였고 이 입력에서 진행/정지 명령을 바꾸지는 않았다. 모든 차이를 원소별로 비교한 [감사 코드](audit_platform_outputs.py)와 결과를 보존했다.

첫 구간의1e-15m 중복점 원인은 직접 대조했지만 전체544판단의 점집합까지 같은 원인이라고 증명한 것은 아니다. 미관측점 개수는 정책에 사용될 수 있으므로 이 차이를 무조건 표시 전용으로 선언하거나 전체 출력 실패를 지우지 않는다. 현재 고정 입력에서 명령이 달라지지 않는다는 범위로 정리하고 시설·교통 정체 개선을 우선한다. 이후 최신 제어기 이관 시 같은 검사를 사용한다. 이번576초는 상세 비교까지 포함한 전체 감사 소요시간이며 제어 비용·ROS 마감 성능 수치가 아니다. 원 비용 시험의 실패 판정과 원 r79 결과는 유지한다.

## 별도 비용 관측

전체 출력 실패를 유지한 채 [별도 계측](jetson_cost_observation.json)으로 같은 동결r82·3,072판단의 입력 복원/운동 장면/명령 비용만 측정했다. JSON 읽기·출력 비교는 시간 창 밖이며 명령 일치3,072·전체일치2,528·입력/107파일 불변을 다시 구분해 기록했다. wall 중앙193.33ms·p95 265.18ms, threadCPU 중앙192.76ms·p95 264.12ms였다. 모든 호출이20ms를 넘었다. `no_side_threat_seen` 중앙49.41ms에 비해 `large_motion_region_unobserved`는200.80ms였다.

이것은 **오프라인 순수 판단 비용 관측**이며 전체ROS 실시간 통과나 현재r84의 비용이 아니다. 이전 단독r72와는 입력/정책이 달라 직접적인 최적화 회귀율로 계산하지 않는다. 다만 실물 운용을 막을 규모이므로 [교통 CPU 후속](../traffic_cpu_r85_v1/README.md)에서 함수 비용을 우선 계측한다. 최초 원격 호출은 필수 옵션 대신 위치 인자를 전달해 argparse 단계에서 실패했고, 새 로그로 올바른 옵션을 사용했다. 운영 소스·전원·센서는 변경하지 않았다.
