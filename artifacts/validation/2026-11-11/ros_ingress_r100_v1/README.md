# ROS 입력 수신과 판단 계산의 경합 대조

2026-11-11 실행 전 등록. r99 별도 프로세스는610판단 동일·합성 부모 응답을 확인했다. 이번에는 **실제 ROS 구독**에 합성200Hz IMU 메시지를 보내면서 같은 r91 저장 판단610개를 부모 단일 executor/별도 프로세스에서 각각 처리한다. 기록 궤적·원래 단위·판단은 그대로이고 차량 명령은 발행하지 않는다.

진단 전용 localhost DDS domain199·`/arena_probe_r100/imu`를 사용한다. 현재 IMU 구독과 같은 sensor_data QoS를 사용하며 순번·취득/수신 시각으로 누락·지연·50ms 이상 원천 간격을 비교한다. 새 메시지 값은 실측 IMU가 아닌 진단 순번이고, 판단 입력은 저장 기록이다. 따라서 **실제 센서/운동 보정/전체 제어기 동시 실행 증명은 아니다.** publisher의 실제 송신 수·주기와 모든 프로세스 종료도 확인한다.

두 조건은 각각610개를 끝까지 처리하므로 경과시간/송신 수가 달라질 수 있다. 누락률과 지연을 비교하고 완벽히 같은 부하 시계라고 부르지 않는다. 운영 QoS·TTL·속도·물성·전원 설정을 바꾸지 않는다. 이 결과 뒤 입력 분리의 운영 연결 범위를 정하고, 해당 문제가 해소되면 기존 미완성 주행 기능으로 돌아간다.

각610판단의 명령·전체 출력이 원 기록과 같고 입력/소스도 불변이다. publisher와 판단 worker는 강제 종료 없이 exit0으로 끝났다. 실제 센서 표본이 아닌 진단 메시지이지만, **같은 단일 executor에서 긴 판단을 수행하면 고주기 구독이 누락되는 현상**을 재현했고 프로세스 분리로 이 장면의 누락을 제거했다. 기존 실제 IMU 결측 전체의 원인이나 모든 부하에서의 무손실 보장으로 확대하지 않는다.

원시 sent/received CSV는 로컬에 보존하며 Git에서 제외한다. Jetson 대조와 지연 결과의 실제 적용 계약은 후속이다. 늦게 끝난 조향을 현재시각 명령으로 재발행하는 운영 연결은 아직 없다.

두 조건610명령은 모두 원 기록과 같고 소스/입력 불변이다. 전체 출력69개 불일치의 **순번**은 두 조건과r98에서 같지만 r100은 상세 출력을 다시 저장하지 않았으므로 이 기록만으로 모든 필드 차이를 재분류하지 않는다. r98에서 확인한 플랫폼 진단 차이는 별도 근거로 보존한다. 계산 프로세스의 중앙/p95/최대는 약87/193/407ms로, **수신 개선이 계산 마감 통과를 뜻하지 않는다.** 부모와 모든 자식은 강제 종료 없이exit0, 회수한6개파일은 원격 해시와 일치했고 잔류 진단 프로세스가 없다.

첫 Jetson 호출은 Humble 환경 누락으로 시작 전 실패했고, 다음 준비 과정에서는 `set -u`의 ROS setup 변수와 PYTHONPATH 덮어쓰기를 확인했다. `source /opt/ros/humble/setup.bash` 뒤 기존 PYTHONPATH를 유지하며 격리 묶음 경로를 앞에 추가해 해결했다. 초기 로그·빈 출력 경로는 남겼다. 패키지 설치나 센서/OS/전원 변경은 하지 않았다.

이번 대표에서는 입력 수신을 계산과 분리할 근거가 확보됐다. 실제 IMU/C1/영상/모터의 전체 운영 부하나 결과 적용은 아직 연결하지 않았으며, 이후 [r101 시점 분석](../decision_age_r101_v1/README.md)의 불필요한 스캔 대기와 긴 계산을 분리해 다룬다.
