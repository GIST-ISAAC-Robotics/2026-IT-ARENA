# 10Hz 시작 정지와 영상 결과 회수 진단

2026-11-11. r91 run3의 실제10Hz에서 경로 판단0회·SENSOR_STOP이 반복됐다. 원status에서는 영상 통계가 제외되어 원인 확정이 불가능했다. 운영 제어기를 바꾸기 전 평가측에서 전체status를 보존한다.

가설은 `VisionPipeline.pump`가 제어 타이머에서만 호출되어, 느린 Gazebo의0.1초가 실제1초 이상이 되면 이미 끝난 영상 결과도 submission→poll 시간 때문에 폐기된다는 것이다. **아직 실측 확정 전**이다. work timeout·센서 freshness·보호 조건을 늘리지 않는다.

- 진단run1: case만4초로 줄여 추가 actor의60초 일정 검사에서 거부. 실제시뮬0회.
- 진단run2: 두 actor일정도4초로 줄였으나 full-course의1랩 이동 조건에서 거부. 실제시뮬0회.
- 이를 위해 원 일정/기하 검증을 낮추지 않았다. 평가기에 명시 `--diagnostic-stop-after-green-s`를 추가해 원60초설정을 유지하고 관측만4초 뒤 끝내며 기존 명시STOP/종료를 수행한다. 옵션을 쓴 결과는 전체시험 `passed=false`로 남긴다. 기본무옵션과 운영 제어기는 같다. 변경전ZIP·[소스계보](../../../../config/tests/diagnostic_window_r95_sha256.json), 문법검사·신규계보1검사를 보존했다.
- run3: 전체 status 49개가 모두 SENSOR_STOP이었다. 영상 756장 수신·121작업 제출·120완료·120 stale 거절·채택0·fault 없음, 처리 총691.3ms·최대33.64ms였다. 실제 계산은 빠른데 결과 회수 시각까지의1초 작업 제한으로 거절되는 구조와 일치한다. STOP 정착·5자식 정상 종료·잔류PID0·203소스 불변·원 `passed=false`를 확인했다. 원자료는 [run3](run3/)에 보존했다.

## r96: 계산 완료와 결과 회수 시각 구분

worker가 같은 호스트의 monotonic 완료 시각을 결과에 담고, 부모는 기존1초 작업 예산을 `completed − submitted`로 검사한다. 결과를 안 읽고 기다린 시간은 별도 `completion_wait_ms`로 남긴다. **원천 영상 나이·수신 후 벽시계 나이·미완료 작업 watchdog·epoch/seq/신호 mode 검사는 그대로**다. 시간 상수나 검출기·출발 조건은 변경하지 않았다. 완료 시각이 없으면 기존 엄격한 poll 시각을 사용하고 NaN/무한/미래/제출 전 시각은 거절한다. poll 도중 끝난 결과를 미래 시각으로 오인하지 않도록 실제 시계는 poll 뒤 다시 읽는다.

첫 회귀는 실행 명령의 PYTHONPATH가 ROS 경로를 덮어써9 import 실패·101통과·1skip이었다. 테스트나 운영 코드를 그 오류에 맞춰 바꾸지 않고 기존 bash 방식의 환경 누적을 복구해117검사를 통과했다. 이어 동시 완료 경계1검사와 소스 계보1검사를 통과했다. 변경 전 코드와 [계보](../../../../config/tests/vision_completion_r96_sha256.json)를 보존했다. run4는 빌드 뒤 동일4초 진단을 수행하며 전체 주행이나10Hz 성능 통과로 해석하지 않는다.

빌드와 설치/소스 hash 일치 뒤 같은 진단에서 영상124개를 모두 채택했고 stale 거절/fault는0이었다. 상태는 WAIT_GREEN31·RUNNING19·HANDOFF_FOLLOW1·초기SENSOR_STOP1개였다. 신호 후 주행을 시작해3.29m 진행했다. 수집된 서로 다른51개 완료 결과의 **계산 중앙4.832ms와 회수 대기 중앙1,152.689ms**를 구별했다(회수 대기 p95 1,219.555ms, 최대1,250.545ms). 이는 느린 시뮬레이션의0.1초 타이머가 벽시계로1초 이상 걸린 조건이다. 실제 영상 계산 지연이나 실차10Hz 성능으로 바꾸어 쓰지 않는다.

STOP 정착·5자식 종료코드0·잔류PID0·203소스 불변·native126스캔/10Hz를 확인했다. `diagnostic_window_complete`와 전체 `passed=false`는 그대로다. 처음 실행 wrapper 두 건의 경로 실패는 시뮬 시작 전이었고 실제 run4는1회다. [run4](run4/)와 `build/r95_diag4_v2.log`에 보존했다. 이 대표로 수정 범위를 닫고, r91의 실제10Hz 전체 조건 비교로 돌아간다.
