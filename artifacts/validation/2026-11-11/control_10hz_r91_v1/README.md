# 제어 주기10Hz의 시설·교통 폐루프 비교

2026-11-11 실행 전 등록. r89의 계산 변경은 원/후3,060출력 동일을 확인했다. r90의 busy 저장 입력 분석은 원 궤적을 유지하므로, 여기서는 명령에 따라 차체와 다음 센서 입력도 바뀌는 제한 폐루프1회를 수행한다.

- r87의 공식 코스·시설 지주·두 상대/오목 차체·ID20/30 누락·native10Hz·81T·실측 IMU 가정·원 속도·물성을 유지한다. 추가 거리/지연 주입은 r87과 같이 없다.
- 바꾸는 시험 설정은 `launch.control_rate_hz: 50 → 10` 하나다. 이에 따라 기존 코드가 사용하는 `dt`도 `.02 → .1 s`가 된다. 독립 보호층은50Hz를 유지한다. 새 상태 필터·타임아웃 연장·느린 명령의 새 시각 반복 발행은 추가하지 않는다.
- 진행44.64m·최장저속2.5초·상대간격8cm·접촉/시설겹침0·최대두바퀴도로밖·STOP/정상종료·원천 입력 및 소스 불변의 기존 판정을 유지한다. 원 `final_gap` 판정은 별도로 보존한다.
- 실행 직전 `src/scripts/config`와 평가기·각본을 보존하고 실행 중 변경하지 않는다. 원 r87/r89/r90 자료를 덮어쓰지 않는다.
- 성공할 때까지 반복하지 않는다. 이번1회 뒤 실제 경로 유지/진행 손실과 판단 입력의 `.1s` 계약을 확인한다.

**이 시험은 Jetson 계산 지연을 재현하지 않는다.** 느린 Gazebo 시계에서도 주기적인10Hz 판단의 차량 반응을 보는 것이다. r90과 달리 무작위처럼 생략된 호출/가변 busy 시간도 아니다.10Hz 기본 채택, 실물 동작, 전체 ROS 처리율, 비동기 구조의 타당성은 이 한 번으로 결론 내리지 않는다.

## 실행 전 도구 오류와 수정

첫 등록 `two_actor_run1`은 Gazebo 시작 전 `g1_handoff_eval.launch_arguments`의 기존50Hz 고정 조건에서 거부됐다. 실제 주행0회이며 원 등록·소스·`build/r91_trial.log`를 보존했다. 빌드 두 패키지는 성공했다. 이는 주행 실패나10Hz 불안정성의 증거가 아니다.

시험 도구에 `--handoff-control-rate-hz 10`을 추가했다. 기본50Hz는 유지하고 G1/G2에서만10/50Hz를 명시 선택하며 설정 파일과 다르면 거부한다. 다른 센서·속도·기록 조건과 반환되는 제어 옵션은 같다. 변경 전 파일과 [출처 계약](../../../../config/tests/control_cadence_r91_sha256.json)을 보존했다. 관련12검사·출처계보183검사를 통과했다. 새 등록 `two_actor_run2`에서 실제 주행1회를 수행하며, `.1s` 판단 입력은 별도 사후검사한다.

## run2: 10Hz 설정 전달 실패

실제 run2는47.84m 한 랩·최장저속.10초·접촉/노면이탈0이었다. STOP·자식5개 정상 종료·잔류PID0과 원천687스캔/203소스·snapshot 불변을 확인했다. 원report의 `final_gap` 실패는 보존했다. 그러나 **판단3,057회가 모두 dt=.02초이고 기준시각 간격 중앙도.02초**여서 등록10Hz 조건은 실패했다. [결합 판정](two_actor_run2/combined_assessment.json). 이 결과는10Hz 주행 증거가 아니다.

`local_pursuit.launch.py`가 상위에서 받은 `autonomy_control_rate_hz`를 demo include에서 상수50으로 덮어썼다. 실행기 인자 검사는 통과했지만 실제 중첩 launch가 달랐다. 실제 ROS launch 치환을 G1→pursuit→demo→simulation 경계까지만 실행한 [변경 전 재현](launch_resolution_before.json)에서도 명시10이50으로 바뀌었다. 최초 확인은 overlay 미설정으로 패키지 조회에 실패했으며 설정 후 위 재현을 얻었다. Gazebo/Node는 실행하지 않았다.

기본50은 유지하고 명시값을 그대로 넘기도록 수정한 [변경 후 대조](launch_resolution_after.json)에서는 제어주기만50→10으로 달랐다. [소스 계약](../../../../config/tests/control_rate_launch_r93_sha256.json)·변경 전ZIP을 보존했고, 실제launch 치환·기존 실행기 관련54검사와 새 출처계약1검사를 통과했다. 동일 조건의 `two_actor_run3`에서 실제10Hz1회를 다시 확인한다. 원 run2를 덮거나 그 완주를10Hz 성공으로 소급하지 않는다.

## run3: 실제10Hz 연결, 경로 판단 전 정지

설치/소스 launch 해시가 같고 실행 중 `/local_pursuit control_rate_hz`가10.0인 것을 확인했다. 그러나 시작부터 `SENSOR_STOP`이어서 **진행0m·경로 판단0회·동일 사유 reset683회**였다. 판단이 실행되지 않아 `.1s dt`의 차량 반응은 확인하지 못했다. [실패 요약](two_actor_run3/failure_summary.json)·[원 판정](two_actor_run3/assessment.json)을 보존한다.

정지한 자차에 각본 상대가 코스를 돌아오면서60.961초부터접촉500건이 기록됐다. 진행·정체·간격·접촉 판정은 실패다. STOP 정착·자식5개 정상 종료·잔류PID0, 등록203소스/스냅샷불변, native683스캔(504/508/512점), 노면이탈0은 확인했다. 상대차는 물리 주행차가 아니라 각본 이동 모델이다.

기존 외곽 분석은 진행 창에 광선이 없어 `ValueError: 창 안 광선 없음`으로 중단됐다. 따라서 `combined_assessment.json`은 생성되지 않았으며 성공으로 대체하지 않는다. 원status 수집기가 `vision`을 제외했으므로 영상 미수신·결과 폐기 중 어느 쪽인지는 원기록만으로 확정할 수 없다. 후속[r95](../vision_poll_r95_v1/README.md)에서 운영 코드를 바꾸기 전 전체status를 짧게 수집한다. 이 결과는10Hz 조향 실패나 Jetson 처리 성능의 증거가 아니다.

## run4: 영상 완료 시각 분리 후 실제10Hz 주행

[r95/r96](../vision_poll_r95_v1/README.md)에서 영상 계산 완료 시각과 부모의 늦은 결과 회수 시각을 구별했다. 실제 계산·원천/수신 freshness 제한은 그대로 유지했다. 짧은 진단 뒤 동일 시설·교통60초 조건을 한 번 실행했다.

- [등록 판정](two_actor_run4/combined_assessment.json)은 통과했다. **47.90m·1랩, 출발 후 최장저속0.100초, 최고1.551m/s**, 접촉·도로 이탈 표본0이다.610판단 모두 `dt=.1s`, 기준시각 간격 중앙/최대.1s로 실제10Hz를 확인했다.
- 원report는 `final_gap` 때문에 실패이며 그 판정을 보존했다. 이는 기존 시설·교통 기능 수용 기준과 구별한다. 최소 표본/이동 중 검사 간격은 각각0.78555/0.78413m다.
- 사례 창598판단은598개 원천 스캔을 사용했고 첫 광선의 나이는 모두 약.197s였다. 전체 native686스캔의 입력 계약,203소스와 스냅샷 불변, STOP 정착·자식5개 정상 종료·잔류PID0을 확인했다.
- 시뮬68.603초에 실제783.99초가 걸렸다. 따라서 **이번 결과는 계산 지연이 사실상 숨겨진10Hz 차량 반응**이며 Jetson 실시간 처리나10Hz 기본 채택의 근거가 아니다.2.8m/s 단독 고속도 별도다.

다음은 [r97 모든 스캔 한 번씩 처리](../scan_once_r97_v1/README.md)로 r90의 누락 영향과 반복 호출 감소를 분리하고, [r98](../control_10hz_cost_r98_v1/README.md)에서 이번610판단 자체의 Jetson 비용을 측정한다. 의미 없는 동일 주행 반복은 하지 않는다.
