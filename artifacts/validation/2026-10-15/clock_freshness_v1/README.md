# 시각 구간과 입력 신선도 — 실물 이관 전 오프라인 준비

기존 MCU↔호스트 왕복 시각 적합을 그대로 사용하고, 그 결과의 하한/상한 전체를 명시된 호스트 결정 시각 구간과 대조한다. 시계나 ROS 헤더를 변경하지 않으며, 운영 노드가 이 모듈을 import하지 않는 것도 회귀로 확인했다.

관련 회귀 **79개**, CLI 합성 **12조건**이 기대한 분류/거절을 통과했다. [합성 결과](probe/report.json), 각 입력/검토 조건/보고서·소스 snapshot·회귀 로그를 보존한다. 올바르게 구성된 오래된 입력의 진단은 도구 실행 성공이지 입력 채택이나 주행 성공이 아니다.

예시의 1 ms/9 ms 비대칭 왕복에서 취득 나이 범위가 **21.95~31.95 ms**였다. 중간값은 26.95 ms로 30 ms 아래이지만 전체 범위는 문턱을 넘으므로 `uncertain_age`다. 30 ms는 합성 진단 예시이며 실제 timeout을 바꾸거나 모든 센서에 같은 한도를 적용하지 않는다.

분류는 `fresh_under_assumptions`, `stale_under_assumptions`, `future_under_assumptions`, `uncertain_age` 네 가지다. 정확한 문턱 포함/미포함 정책, 결정 시각 읽기 불확실성, 큰 uptime의 정수 ns, 호스트/MCU 세대 불일치·다른 원문 해시·합성값의 실측 재표기 거절을 검사했다.

`ready_to_drive=false`, `ros_stamp_verified=false`, `clock_mapping_applied=false`다. 실물 시계 오차 상한·timestamp 취득 위치·동일 host 세대가 맞다는 사실을 코드가 자동 검증하지 않는다. 원본 시각을 수신 시각이나 중간 추정값으로 바꿔 붙이지 않으며, host monotonic↔ROS 연결·실물 취득/전송·모터 제동은 남는다.

최종 검토에서는 원문 불변 해시를 파일 전체 일괄 읽기 대신 1 MiB씩 계산하도록 바꾸고 회귀 1개를 추가했다. 위 79개/합성 12조건은 당시 snapshot 그대로 보존한다. 이후 전체 2,075개 회귀에는 추가 검사까지 포함되며, 이 변경으로 운영 시간 계약을 적용하거나 실물 입력을 검증한 것은 아니다.
