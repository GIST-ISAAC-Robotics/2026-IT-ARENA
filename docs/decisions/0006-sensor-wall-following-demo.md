# 결정 0006: 픽셀 출발 신호와 라이다 벽 추종 데모

- 날짜: 2026-08-31
- 상태: 채택·구현·최종 단일차 통합 검사 통과. 공식 대회용 알고리즘이나 하드웨어 확정 아님.

## 요청과 선택

사용자는 움직이는 신호등, 임시 RPLIDAR C1급 2D 라이다, 지름길을 이용하지 않고 계속 본선을 도는 가장 기초적인 자율주행을 요청했습니다. 기존 계획의 정답 위치 기반 중심선 추종과 별개로, 이번 요청에서는 실제 센서 토픽만으로 작동하는 설명 가능한 벽 추종 데모를 구현합니다.

1. 신호등 제어기는 시뮬레이터 전용으로 분리합니다. 실제 렌즈 재질을 빨강→노랑→초록으로 바꾸고 초록 상태를 유지합니다. 진단 상태 토픽을 자율주행 입력으로 연결하지 않습니다.
2. 자율주행 노드는 카메라 픽셀에서 빨간 렌즈를 먼저 확인하고, 같은 신호등의 녹색 렌즈를 연속 확인한 뒤 출발을 허용합니다. 녹색 노면을 신호로 인정하지 않도록 위치 관계를 제한합니다.
3. 조향은 `/scan`의 한쪽 벽 표본으로 계산합니다. 좁은 기둥을 제외하며 가까운 벽을 2차 곡선으로 근사하고, 벽과의 거리·방향·곡률을 이용합니다.
4. ID 20에서 왼쪽 벽, ID 30에서 오른쪽 벽을 따릅니다. ID 0·45에서는 기본 왼쪽 벽으로 돌아갑니다. 현재 두 분기의 방향을 미리 아는 단순 규칙이며, 좌표 지도나 시뮬레이터 정답 위치를 읽는 방식은 아닙니다.
5. 출발 허용은 신호등을 통과한 뒤에도 유지합니다. 랩 수가 1이 되면 멈추는 조건은 넣지 않습니다. 사용자 정지, 센서 누락, 가까운 장애물, 벽 추정 실패는 정지 조건입니다.
6. 라이다는 C1의 공개 대표값인 360°·10 Hz·500점·0.05~12 m를 사용합니다. 반사율·회전 왜곡·잡음은 재현하지 않는 기초 모델입니다.
7. 데모는 RGB 30 Hz와 라이다를 사용하고 사용하지 않는 깊이 센서를 끕니다. 일반 실행의 RGB 60·깊이 90 기본값은 유지하며 데모에서도 `depth_camera:=true`로 깊이를 켤 수 있습니다.

## 제어기 수정 근거

기존 Gazebo 설정은 속도 ±2 m/s·가속도 ±4 m/s²·jerk ±20 m/s³를 함께 제한했습니다. 설치된 Gazebo Math 7.6.0 제한기만 호출하는 `scripts/check_speed_limiter.cpp`에서도 0.16 m/s 명령 7초 후 0 명령을 6초 유지하면, 마지막 2초 출력이 약 -0.0631~+0.0676 m/s로 흔들립니다. 물리 접촉·방지턱·ROS 없이 재현된 결과입니다.

jerk 제한만 제외하고 속도·가속도 제한을 유지하면 같은 시험의 마지막 2초 출력이 정확히 0입니다. 따라서 이번 모델은 해당 jerk 제한을 제외합니다. [Gazebo 제한기 구현](https://github.com/gazebosim/gz-math/blob/gz-math7/src/SpeedLimiter.cc)과 [Ackermann 명령 처리](https://github.com/gazebosim/gz-sim/blob/gz-sim8/src/systems/ackermann_steering/AckermannSteering.cc)를 대조했습니다. 실제 차량의 제동 성능이 입증된 것은 아닙니다.

조향 비례 이득은 기본 1에서 임시 12로 설정합니다. 현재 시뮬레이터의 조향 관절 응답을 위한 값이며 실물 서보 응답·PID 보정값이 아닙니다. 실제 주행·정지 검사는 별도로 기록합니다.

수정 후 같은 시설 검사에서 가시성 18/18·방지턱 통과·지속 정지·정상 종료가 모두 통과했습니다. 정지 기준인 속도 절댓값 0.01 m/s 미만을 0.5초 유지하는 데 약 0.54초가 걸렸고 최종 속도는 0이었습니다. 기존 실패 보고서는 유지합니다.

## 검증 원칙

- 정답 세계 위치와 중심선은 검사기의 랩 진행·이탈·벽 간섭 판정에만 사용합니다.
- 최소 두 바퀴와 추가 전진을 확인해 한 번만 완주한 결과와 구분합니다.
- 빨강·노랑 대기와 실제 초록 렌즈 이후 출발, 마커 양쪽 분기 통과, 센서 사양·수신, 사용자 정지를 각각 확인합니다.
- 동적 상대 차량 회피, 고속 주행, 실물 센서 결측과 마커 누락에 대한 보장은 하지 않습니다.

## 2026-08-31 중간 검증과 종료 경로 보완

최종 구동 코드로 95.2856 m를 진행해 두 바퀴와 추가 약 2 m를 확인했습니다. 조기 출발 없음, 벽과의 외형 겹침 0회, 마커 0·20·30·45와 양쪽 벽 선택, 약 0.587초의 지속 정지 판정을 확인했습니다. 최대 중심선 오차는 약 0.1505 m이며 노면 경계 준수를 보장하는 수치로 해석하지 않습니다. 실제 라이다 수신은 시뮬레이션 시간 기준 약 10.00006 Hz·500점이었습니다.

검사기가 `ros2 launch` 부모에게만 SIGINT를 보냈지만 WSL에서 터미널 입력이 상속되면 실행기가 대화형 모드로 판단할 수 있었습니다. 설치된 `ros2launch/command/launch.py`는 `not sys.stdin.isatty()`를 기본값으로 사용하고, `launch/actions/execute_local.py`는 SIGINT 종료가 대화형이면 자식에게 다시 SIGINT를 보내지 않습니다. 실패 로그에서 모든 자식의 5초 대기 후 SIGTERM 에스컬레이션과 RGB 브리지 종료 코드 -11을 확인했습니다.

검사 실행 함수에 `--noninteractive`와 `stdin=DEVNULL`을 명시해 부모에게 보낸 종료 신호가 자식에게도 전달되게 했습니다. 센서가 실제 활성화된 짧은 실행 3회에서 신호 전달·약 1.18~1.63초 내 정상 종료·남은 자식 프로세스 없음이 확인됐습니다. 회귀 검사도 추가해 총 57개가 통과했습니다. 이 수정은 검사기의 실행·종료 방식에 한정하며 구동 코드 9개 입력의 해시는 긴 주행 당시와 모두 같았습니다.

긴 주행 보고서의 종합 `passed: false`는 보존합니다. 별도 종료 검사 통과를 같은 실행의 장거리 통합 성공으로 합치지 않습니다. 사용자의 중간보고 요청으로 보완 후 장거리 재검사는 다음 지시 이후로 남겼습니다.

## 2026-08-31 최종 통합 검증

사용자의 후속 지시 뒤 새 통신 영역에서 처음부터 다시 검사했습니다. 생산 입력 9개의 해시를 고정한 같은 실행에서 95.2856 m(두 바퀴+약 2 m), 고정 20×15 cm 외형과 정적 벽의 겹침 표본 0, 최대 중심선 거리 약 0.1504 m, 마커 0·20·30·45와 좌·우 벽 선택을 확인했습니다. 제어 노드의 구독은 RGB·`/scan`·`/clock`뿐이었습니다.

정지 요청 뒤 약 0.592초에 지속 정지하고 약 16.1 mm를 이동했으며 최종 오도메트리 속도는 0이었습니다. 부모 프로세스 종료 코드 0/0, 오류 목록 없음, `shutdown_clean: true`로 종합 `passed: true`입니다. 앞 절의 실패 보고서는 원인 분리 근거로 그대로 보존합니다.

독립 검토에서 기존 조기 출발 판정이 `run_started` 뒤에는 빨강/노랑 비영 명령을 검사하지 않는 사각을 발견했습니다. 최종 실행의 초록 전 107개 궤적 표본을 별도로 대조해 출발 허가 없음·자율주행 상태의 속도 명령 0, 최대 절대 오도메트리 속도 약 `1.60e-18 m/s`, 최대 XY 변위 약 `9.20e-14 m`임을 확인했습니다. 검증기는 `run_started`와 무관하게 초록 전 `started`·자율주행 속도·`/drive` 속도를 확인하도록 보강했습니다. 최종 실행 도중 소스만 수정했으므로 실행 중 검사기에는 소급 적용되지 않았고, 해당 실행의 출발은 원시 기록 감사로 보강했습니다. 새 로직의 회귀 검사를 포함한 전체 자동 검사 62개가 통과했습니다. 이 변경은 생산 제어 노드를 바꾸지 않습니다.

같은 실행을 Gazebo 3D 카메라의 고정 사선 조감도로 녹화했습니다. 녹화 중 두 체크포인트 사이에만 약 47.57 m를 진행해 한 바퀴 46.6329 m 이상을 포함합니다. 영상 재생 길이 165.88초는 시뮬레이션 시간 기준이며 실제 PC 녹화 시간과 다릅니다. 검사·GUI 종료 후 남은 관련 프로세스가 없음을 확인했습니다.
