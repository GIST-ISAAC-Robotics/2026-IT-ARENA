# 현행 개발 계획: 첫 완주와 실물 통합

갱신: **2026-10-27 (KST)**. 사용자 결정은 [ADR 0027](decisions/0027-completion-first-policy-and-placement.md), 완료 범위는 [현재 현황](PROJECT_CONTEXT.md)을 기준으로 한다. 아래 구현 순서·검증 설계는 개발 권고이며, 세부 수치나 모든 시험 조건이 사용자에게 승인된 것으로 쓰지 않는다.

[10/23 계획](reports/DEVELOPMENT_PLAN_2026_10_23.md)은 당시 선택과 10/24–26 실행 이력으로 보존한다. 날짜별 계획을 새로 누적하지 않고 앞으로의 작업 순서는 이 문서에서 교체한다.

## 목표와 고정 범위

**먼저 현재 구매 구성으로 출발부터 한 바퀴, 정지까지 이어지는 주행을 만든다.** 이후 추종·피추월·밀집 출발·방지턱·5랩·실물 운용을 같은 실행 구성에서 확인한다. 조각 시험·회귀 개수를 완주 성과로 대신하지 않는다.

- 구매 센서·구동 방식은 고정, 장착 위치·높이·방향은 변경 가능하다.
- Pure Pursuit는 현재 수단이다. 관측·행동 정책 때문에 멈추는 문제부터 고치고, 실제 추종 오차가 주된 한계일 때 다른 추종기를 비교한다.
- 두 바퀴 잔디를 활용하며 충돌 임박 시 세 바퀴 이상 이탈 페널티를 감수하는 방향이다. 무벌점 진행이 우선이고 잔디 회피의 벽·전복·복귀 위험을 함께 평가한다.
- 약 15 km/h는 목표 상한이다. 현재 `local_fast`의 9 km/h 설정 및 구동·제동·시야·처리율로 검증된 운용 속도는 별도로 관리한다. G1/R0+ 운영 연결은 현재 1.0 m/s, M3 측방 후보 활성 구간은 0.35 m/s, 최근 관측 보완 선택 구간은 0.2 m/s 상한을 쓴다. M3가 BASELINE으로 돌아오면 기본 G1 출력을 사용한다.
- `/drive` → 독립 보호층 → `/drive/safe`, 명시 STOP·입력 만료 처리를 유지한다. 부분 관측으로 진행을 허용할 때 남는 위험을 명시하며 `unknown`을 측정된 자유 공간으로 바꾸지 않는다.

## 1. 가장 먼저 바꿀 것

| 묶음 | 구체적인 작업 | 확인할 결과 |
|---|---|---|
| 관측 정책 | 계획기와 보호층의 단일 결측 정지를 찾아 소수 결측·연속 공백·위치·시간·이미 관측한 장애물을 구분한다. 기존 최근 광선 후보의 실패를 재사용한다 | 43 m 정적 교착에서 진행을 허용하는 이유와 잔여 위험이 명확하고, 알려진 가까운 장애물·스캔 전체 고장을 누락시키지 않음 |
| 노면·간격 | 경로 생성·선택·평가기의 `road_only`/두 바퀴 정책을 맞춘다. 세 바퀴 이상 긴급 회피와 복귀를 추가 검토한다. 일률 15 cm 및 97/115 mm 예산을 사용자 고정 제약으로 쓰지 않는다 | 차체가 도로 밖으로 일부 나간 것과 충돌·세 바퀴 이탈을 구분하며, 실제 회피 가능한 공간을 사용하는 후보가 생김 |
| 후방·복귀 | 정상 전진·작은 복귀의 후방 조건 완화와 불필요한 중앙 복귀 생략을 시험 가설로 구체화한다. 큰 횡이동·보이는 옆차·최근 위협·뒤 모서리 이동은 별도로 판단한다 | 진행과 접촉·정체·복귀를 비교한다. 구체값은 개발자가 시험으로 제안하며, 기존 합의 범위를 넘는 위험 수용 변경이 필요할 때 사용자와 결정 |
| 출발·카메라 | 고정 마운트 후보와 ROI를 비교한다. 빨강이 가린 뒤 초록만 보이는 출발과 코스 전환 마커를 통째로 놓치는 경우를 포함한다. 코스 마커 의존도 완화도 비교한다 | 공식 6그리드의 영상 출발과 분기·합류의 본선 유지 확인. 실제 시설 미확정치는 가정으로 표시 |
| 실행 통합 | G1/최근 관측/M3/M5/B3의 연결 여부·상호 배제·기본값을 정리해 경기용 후보 한 구성을 명시한다 | 신호→단독 1랩→명시 STOP, 해당 소스·설정·입력으로 재현 가능한 결과 |

첫 완주에 필요하지 않은 새 센서·전면 제어 스택 교체·범용 도구 확장은 우선순위를 낮춘다. 이동 추월(G3)은 첫 완주·추종·피추월 대응 이후 검토하는 기능이며 영구 금지 결정이 아니다. G2는 두 바퀴 및 긴급 잔디 회피 정책과 연결해 실제 우회·복귀가 가능한 범위만 다룬다.

## 2. 시험 순서와 판정

1. **저장 근거를 먼저 재사용한다.** R0 43 m, M3 좌우 가림·후방 재접근, M5 초기 좁은 간격에서 새 정책의 판단 차이를 설명한다. 같은 엄격 관측 계약을 다른 이름으로 반복하지 않는다.
2. **원인이 바뀐 후보로 전체 1랩을 확인한다.** 작은 사례만 늘리지 말고 정지·재개와 명시 STOP·프로세스 종료까지 확인한다. 센서 기반 제어와 평가용 정답은 구별한다.
3. **필수 교통 상황을 연결한다.** 앞차 추종/정지/재개, 옆차 통과와 불필요한 중앙 복귀, 공식 신호와 2/3/5대 그리드, 가림 회복을 선택 구성으로 확인한다. 단순 스크립트 actor 결과를 여러 독립 자율 차량의 결과로 확대하지 않는다.
4. **방지턱과 다랩을 포함한다.** 공개 50 mm 형상으로 기구 간섭·저속 동적 통과·센서/경로 복구를 확인한다. 카메라로 턱을 인식하지 않는 방안부터 검토하되 턱 영향을 무시하지 않는다. 높은 속도를 원할 때 선행 감속 수단이 필요한지 판단한다.
5. **Jetson·실물로 이어간다.** 실제 선택 코드의 처리 지연과 입력 나이, MCU 피드백·제동·원격/물리 STOP을 확인한다. PC 오프라인 함수 비용을 차량 전체 지연 측정값으로 쓰지 않는다.

새 판정은 완주 여부/시간, 접촉 횟수와 결과, 세 바퀴 이상 잔디 사건, 장시간 정체, 개입 횟수, 실제 정지·정상 종료를 구분한다. 접촉이 있어도 완주 성과는 기록할 수 있으나 무접촉 성공으로 표시하지 않는다. 기존 69.8 mm 간격 미달·R0+ 접촉·M1 실패는 당시 판정 그대로 남긴다.

입력/출력 기록 오류나 정상 종료 실패를 없었던 것으로 처리하지 않는다. 새 원인이나 조건 변화 없이 같은 실패 주행을 반복하지 않는다. 반대로 과거 작업에서의 임시 실행 금지·승인 대기를 새 작업의 영구 제한으로 승계하지 않는다.

### 직접 시험할 최소 장면

아래는 **후속 구현·시험 계획**이며 이번 문서 변경에서 통과한 결과가 아니다. 대표 사례를 기존 입력·시험기에서 골라 사용하고 모든 수치의 조합 시험으로 늘리지 않는다. 필수 교통 장면 전부를 첫 단독 1랩 시도 전의 새 관문으로 만들지 않는다.

| 묶음 | 대표 장면 | 확인할 결과 |
|---|---|---|
| 부분 무반환 | 기존 43 m 장면과 가까운 관측 장애물·넓은 관측 공백·스캔 중단 대조 | 작고 국소적인 결측에서 달라진 판단·잔여 위험을 설명하고, 가까운 장애물이나 입력 고장을 함께 무시하지 않음 |
| 좌·우 피추월 | 옆차가 뒤→옆→앞으로 통과. 자차는 현재 위치 유지 또는 필요한 작은 복귀 | 순수 후방 미관측 때문에 생긴 무기한 HOLD와 불필요한 중앙 복귀를 줄이는지, 실제 진행·접촉·복귀로 확인 |
| 곡선·횡이동·잔디 | 곡선의 뒤 모서리 이동, 보이는 옆차 쪽 횡이동, 두 바퀴로 회피 가능한 경우와 세 바퀴 이상이 필요한 경우. 잔디 쪽도 벽으로 막힌 대조 | 작은 조향각만으로 작은 복귀를 판정하지 않음. 바퀴별 노면·접촉·벽 간섭·복귀를 구분하고 차체 일부 도로 밖을 일률 실패로 쓰지 않음 |
| 가림·재접근·모드 전환 | 옆차가 가려지거나 같은 측면에 다른 물체가 남음. 복귀/모드 해제 뒤 차량이 다시 접근 | 안 보임을 통과 완료로 처리하지 않음. 해제 순간뿐 아니라 이후 기본 G1 출력까지 최근 위협·측방 대응이 어떻게 이어지는지 확인 |
| 코스 마커 의존도 | 처음부터 코스 ID 없음, ID 30 누락, ID 30 관측 뒤 0/20/45 누락·재검출. 해당 분기·합류 포함 | 단순 양수 출력이 아니라 본선 유지·경로 연속성·잘못된 전환 여부를 확인. 유망 후보로 본선 1랩 연결 |
| 출발 가림 | 빨강 가림→앞차 이동→초록 노출, 초록이 보이지 않는 대조 | 앞차 이동만으로 출발하지 않으면서 출발등 영상 근거로 출발하는 조건 확인 |

작은 복귀의 분류에는 속도·목표/누적 횡변위·곡률·자세, 이전/현재 조향에서 이어질 이동·감속 중 차체 영역, 알려진 옆차와의 접근 방향을 함께 쓴다. 정확한 경계값은 후보별로 기록한다. 이를 모든 후방 미관측점의 부재를 증명해야 하는 조건으로 다시 만들지는 않는다.

코스 마커 누락 시험에서도 출발 신호 영상과 정상 프레임 취득은 유지한다. 검출 결과 억제·영상 마스킹·실제 앞차 가림 렌더링은 각각 어떤 현상을 재현하는지 기록한다. 현재 코드도 미검출 시 이전 벽 선택을 유지하므로, 단순히 멈추지 않았다는 결과만으로 의존도 문제가 해결됐다고 판정하지 않는다.

### 시험 단계와 증거 범위

- **순수 함수·저장 입력:** 정책 분류·출력의 차이를 확인한다. 새 출력대로 차량이 움직인 결과가 아니다.
- **센서 기반 폐루프 시뮬레이션:** 하나의 실제 실행 구성으로 진행·본선 유지·복귀·출발·정지를 확인한다. 평가기만 정답 위치·actor 상태를 사용하며, 제어기에 지도·정답 자세·심판 신호·시험기의 가림 상태를 넣지 않는다. 방지턱 활성 여부와 입력/모델 버전을 결과에 명시한다.
- **실물:** 실제 가림·시각·구동·제동을 확인한다. 저장 입력·정적 기하·Gazebo의 성공을 실물 성공으로 확대하지 않는다. 차체 전 벤치는 앞 단계의 완료를 기다리지 않는다.

현재 M3와 최근 관측 옵션은 동시에 선택할 수 없다. 함께 켠 가상 조합을 시험 구성으로 쓰지 않으며, 운영 미연결 시제품과 실제 노드에서 사용한 기능을 구분한다. 판단 지연과 입력/출력 나이도 함께 기록한다. 과거 반례는 새 정책이 바꾸는 기대값과 계속 유지할 고장 처리를 나눠 사용한다.

## 3. 하드웨어 설계와 병행할 일

[하드웨어 전달 목록](HARDWARE_AND_RULE_QUESTIONS.md)에 요구사항을 모은다. 상대팀 모든 차량 도면 확보나 완전한 360° 시야 증명을 새 선행 조건으로 만들지 않는다.

- C1 측정 높이에 걸리는 우리 부품·기둥·배선의 배치를 확인한다. 전방·측면과 뒤 양 모서리 시선을 우선 보고, 후방 마커판은 위로 옮겨 측정 높이를 비우는 안을 검토한다.
- 카메라는 시뮬레이션에서 고정 브래킷을 결정할 후보를 고른다. 신호·코스 마커·앞차/자차 가림·차체 기울기를 함께 본다. 실제 CSI 촬영 모드의 화각·크롭과 시설 사진이 확보되면 해당 가정만 갱신한다.
- 최저 지상고, 조향 중 외형·회전 영역, 타이어·축거·질량, 배선·PDB·서보 전원, HW/SW 정지를 구매 부품에 맞춰 정한다.
- C1 원시 점/시각, B0183 RGB/PTS, IMU 축/단위/시계, 모터축 카운트와 MCU 콘솔 충돌은 장비 연결 즉시 벤치에서 확인한다. 차체 완성을 기다리지 않는다.

실차 이관은 정지 기능·배선 확인 → 기구/센서/시간 → 저속 단독 → 추종·가림 → 출발·재개·방지턱·다랩 순서로 진행한다. 전체 단계를 하루에 마친다는 일정이 아니며 장비·차체 수령 시점에 맞춰 진행한다. 구동 모델의 이상적 관절 피드백과 실제 엔코더 PI, 모터축 저속과 차체 정지, 설정 상한과 실제 속도를 구분한다.

## 4. 일정과 점검일

대회일은 **11/14**, 기존 계획의 설정 동결 목표 **10/31**, 모드 선택 **11/1**, 고정 회귀 마감 **11/7**, 결산 **11/13**을 점검일로 유지한다. 장비 수령·제작 완료일은 확정되지 않았고 사용자 설명으로 기구 설계도 아직 본격 확정 전이다. 구체적인 담당·납기·당일 작업량은 팀과 맞춘다.

| 순서 | 지금 할 일 | 다음으로 넘어가는 근거 |
|---|---|---|
| 즉시 | 새 정책·고정 배치 후보·앞차 가림 사례를 구체화하고 하드웨어팀 설계 입력 준비 | 변경할 조건과 남길 조건이 코드/시험별로 식별됨 |
| 그다음 | 관측·노면·간격의 일관된 후보로 첫 1랩 | 실제 진행·정지·실패 원인으로 다음 변경 선택 |
| 선택 구성 확보 뒤 | 필수 교통·공식 출발·방지턱·5랩·Jetson 연결 | 부가기능 수가 아니라 전체 운용 결과 |
| 장비 연결 즉시 병행 | 센서·MCU 벤치와 실차 준비 | 실제 입력·출력·정지·제동의 근거 |

첫 완주가 안 되는 상태에서 주변 시제품 최적화만 계속하지 않는다. 남은 실패를 보고하고 한 번에 바꿀 원인을 좁힌다. 차량이 늦으면 기능과 운용 속도를 줄이되, 시뮬레이션을 실차 검증으로 대신하지 않는다.

## 5. 개발자가 구체화할 일과 팀에서 정할 일

| 구분 | 다룰 내용 |
|---|---|
| 개발자가 구체화·시험 | 결측·시간·속도 임계값 후보, 작은 복귀/큰 횡이동의 구분, 마커 누락 후 본선 유지, 빨강을 놓친 출발 판정, 구동·방지턱의 운용 속도. 기존 기록으로 후보와 비교 근거를 만들며 숫자 하나마다 사용자 결정을 기다리지 않음 |
| 하드웨어팀과 설계 | C1 위치와 비워 둘 높이, 후방 마커 높이, 고정 카메라 배치, 실제 부품·배선·BOM, 도면·조립·벤치 담당과 납기 |
| 새로운 전략 결정이 필요할 때 사용자와 논의 | 구매/구동 범위 변경, 기존 합의를 넘는 경기 위험 수용, 후보가 실패해 목표나 운용 범위를 바꿔야 하는 경우. 구체적인 결과·선택지·영향을 먼저 제시 |

미정인 구현값·장착 치수와 실제 시험의 필요성은 문서 계획 반영을 막는 조건이 아니다. 문서 반영을 미검증 주행 정책의 기본 활성화로 해석하지 않는다. 결정 내용을 시험 결과로 쓰지 않으며 개발 권고의 구체값을 사용자 결정으로 승격하지 않는다. 공식 질문 초안과 외부 게시·팀원 메시지는 구별한다.
