# 프로젝트 현황과 인수인계

최종 갱신: 2026-09-24

## 최신: A2 기록·재생 기반/1차 진단 종료, 1배속 제어는 미통과

- 사용자 재개 후 **기록·재생 검증까지만 마무리**하라는 범위를 확인했다. [A2 결과](simulation/RECORD_REPLAY_2026_09_24.md)·[ADR 0024](decisions/0024-isolated-sensor-record-replay.md)를 우선한다. 센서 이상치 시험·제어기 성능 개선은 시작하지 않았다.
- `capture_v2`는 GPU 렌더링·12.11848 m·최고 8.16 km/h·실제 정지·주행/정지 벽 겹침 표본 0·자식 14/14 정상 종료다. 20.968초 원시 자료의 파일/CDR 무결성을 확인했다. 기록기 RGB 1,298개와 평가기 1,310개 차이가 있으므로 upstream 완전 무손실은 미확인이다. 전체 코스/별도 노면 감사/실차 시험이 아니다.
- 최종 원시 CDR 재생 `replay_half_raw_v1`은 0.5배속 기능/스케줄 통과, 지역 제어기 IMU 15개·RGB 1개 부족이다. `replay_1x_raw_v1`은 **1배속 스케줄 통과·제어 기능 실패**다. 발행 지연 p99 7.06 ms·최대 17.07 ms지만 지역 제어기 IMU 1,563/5,242개·RGB 245/1,298개 부족, 제어 콜백 p99 43.97 ms·최대 49.90 ms, `RUNNING/MOTION_STOP` 반복·최고 안전 명령 0.03 m/s다. 보호층은 LiDAR/IMU/후륜을 모두 받았다. 두 재생 모두 EOF 0명령·자식 2/2 정상 종료이며 완전 무누락/실시간 대응 완료로 표현하지 않는다.
- 선택형 계측 snapshot 서비스로 실제 콜백 완료 횟수와 진단 로그 수를 구분한다. 최종 두 실행은 수가 일치하며 `delivery_audit.json`에 누락 헤더 구간을 남겼다. 초기 그래프 조회 실패·19.97초 지연·회귀와 부하가 겹친 1배속 실패도 보존했다. 최종 회귀 **395개(36.63초)**, 미완료 기록 거절 **7조건** 통과다.
- 다음 권고는 같은 bag로 **지역 제어기 내부 시간 분해 → 1배속 적체/운동 입력 보호 정지 개선**, A3 Jetson 시험 병행, 이후 A4 이상치/고착 시험이다. 원인 함수별 비용은 아직 미계측이다. 이번에는 기록·재생까지만 종료한다. 코드/원시 자료는 로컬 보존이며 GitHub 게시·컴퓨터 종료는 하지 않았다. 사용자 지정 GPT-6 Luna가 단순 실행/결과 수집을 맡았고 승인 서비스 장애가 있는 실행은 root의 정식 권한 요청을 사용했다.

### 이전 사용량 중단 이력

아래는 최초 중단 시점의 상태이며 위 재개 결과가 현재 기준이다.

- 사용량 확보를 위한 사용자 요청으로 중단한다. [A2 안내/재개 순서](simulation/RECORD_REPLAY_2026_09_24.md)·[ADR 0024](decisions/0024-isolated-sensor-record-replay.md)를 우선한다. 원시 MCAP·무결성 감사·실행 매개변수·선택형 계측·구동부 없는 격리 재생 코드를 작성했지만 **A2 완료/재생 성공은 아직 검증하지 않았다.**
- 3패키지 빌드와 당시 회귀 **391개(41.02초)**는 통과했다. `artifacts/validation/2026-09-24/record_replay/capture_v1`은 출발 신호 대기·진행 0 m에서 중단 요청을 받았다. 주행/재생 통과가 아니며 부분 자료/종료 로그를 보존한다. 이후 추가한 최종 소스의 회귀 재확인이 필요하다.
- 재개는 종료 기록/잔존 확인 → 미완료 기록 거절 시험 → 새 폴더의 짧은 기록 주행 → 무결성 감사 → 0.5/1배속 격리 재생·콜백 전달량/EOF 0명령/정상 종료 → 결과 문서 갱신 순서다. 기존 폴더는 덮어쓰지 않는다. Jetson/A4는 후속이다.
- 다음 단순 실행/대기는 사용자 지정 **GPT-6 Luna**를 사용한다. 설계·수정·판정은 주 에이전트가 맡고 중복 감시를 최소화한다. 원시 RGB bag/수신 로그는 로컬 보존·Git 기본 제외, 기본 계측 비활성·제어/속도/트랙 유지다. GitHub 게시·컴퓨터 종료는 하지 않는다.
- 중단 정리는 완료했다. `capture_v1`은 중단 사유로 `passed=false`·0 m, 자식 14/14 정상 종료·잔존/강제 종료 없음이다. 기록기 내부 완료·반환 0과 약 33 MB MCAP 보존을 확인했지만 사후 무결성/재생 검증은 남는다.

## 최신 완료: A1-2 ROS 경로·별도 가상 MCU

- 사용자의 다음 작업 승인으로 [ROS 구동 연결](hardware/ACTUATION_ROS_2026_09_22.md)을 구현·검증했다. `actuation_mode:=virtual_mcu`에서 `/drive/safe` 뒤 호스트 → CRC 프레임 → 별도 가상 MCU → 최종 출력 감시를 둔다. 기본 `legacy`·기존 지역 Pure Pursuit/속도/보호층·차량/트랙을 유지한다.
- 명시 ARM, STOP/CLEAR 분리, 명령/엔코더 만료 고정 정지, 호스트/MCU 재시작과 시계 정지/역전, 출력부 준비 확인을 시험한다. ROS 서비스는 수신기 ACK를 기다린다. Gazebo 내부 속도 PI는 여전히 이상적인 관절 피드백이며 새 MCU PI/실물 ESC를 검증한 것이 아니다.
- 초기 `ros_v1` 부팅 시계 미수신 오인과 `ros_v2` 출력부 재연결/허가 경계 실패를 보존하고 수정했다. 최종 `ros_final` **14/14조건·6프로세스 정상 종료/잔존 없음**, 전체 회귀 **365개 통과**다. Gazebo STOP/호스트 종료 두 경우 각각 **12.21847/12.15847 m·최고 8.15/8.17 km/h**, 실제 모형 정지·주행/정지 벽 겹침 표본 0·자식 14/14 정상 종료를 확인했다. 최종판 호스트 종료 주행 및 ROS 입력 해시 일치도 확인했다. STOP 첫 실행 후의 경계 보완과 소스 스냅샷은 보고서에 구분한다. 단순 실행/대기는 Luna, 설계·수정·판정은 주 에이전트가 수행했다.
- 약 12 m 부분 주행이지 새 구성의 전체 코스 완주/실차 제동 검증이 아니다. 정지 요청 후 위치 변위는 0.774/0.966 m, 안정 정지 0.5초를 포함한 확인 시간은 1.348/1.448초다. 실차 제동거리로 사용하지 않으며 별도 노면 전수 감사도 이번에는 하지 않았다. 다음은 A2 원시 입력·명령·상태의 기록/재생 및 Jetson 부하 검증 인계다.
- MCU 계약 고장과 상위 센서 일시 누락에 따른 신선한 0명령은 구분한다. 후자는 기존 자동 복구 정책을 유지하며 경기/자율주행 상위 재출발 정책 전체가 완성된 것은 아니다. ESC·엔코더 사양은 계속 미정이고 외부 게시·구매·실물 연결·컴퓨터 종료는 하지 않는다.

## 최신 구현: A1-1 MCU 구동/정지 계약의 PC 참조

- 사용자가 전체 계획의 첫 작업 착수를 승인했다. **ESP32-S3 우선 후보**, 적어도 Arduino/ESP32 계열 보드이며 **Jetson 목표 속도 → MCU 좌우 엔코더 피드백의 단일 모터 속도 제어** 분담을 다시 확인했다. 추가 질문에 ESC 모델/명령 방식은 **미정**이라고 답했다. PWM/UART/CAN·핀·제동/서보 매핑을 확정하지 않는다.
- [ADR 0023](decisions/0023-mcu-actuation-contract-reference.md)과 [구동 계약 보고서](hardware/ACTUATION_CONTRACT_2026_09_22.md)를 우선한다. 부팅 구동 금지·명시적 ARM·정지 고정/CLEAR·명령/엔코더/제어 주기 감시·세션/순번/짧은 수명 토큰·CRC 프레이밍·평균 속도 PI를 PC 참조로 구현했다. 통신 복구/버튼 해제/재부팅만으로 재주행하지 않는다. 실제 MCU 펌웨어·전자식 차동 구현이 아니다.
- 단순 종방향 모형과 별도 가상 MCU 프로세스에서 검증하며, Gazebo/실차 속도·제동/안전 결과로 표현하지 않는다. `/drive/safe` 뒤 ROS 어댑터 연결은 **다음 A1-2**다. 기존 지역 Pure Pursuit/보호층·차량/코스·물성/속도·기존 실패/활동 자료를 그대로 유지했다.
- 최종 `windows_v3`는 단위 38개·고정 시간 10조건+독립 프로세스 1조건 **11/11**·WSL 전체 회귀 **340개(17.06초)**를 통과했다. 독립 자식 프로세스 정상 종료·강제 종료/잔존 없음, 5개 소스 해시 일치를 확인했다. 초기 IPC `WinError 5` 미완료와 v2의 37/339개 통과, 최종 큰 정수 `OverflowError` 거절 보완을 구분해 보존한다. Luna가 실행/수집을 맡았고 설계/수정/판정은 주 에이전트가 수행했다.
- 다음은 A1-2 ROS 경로의 명령/프로세스 종료·재시작/재허가 및 시계 경계 → A2 원시 기록/재생 → 제한된 A4 이상치/내부 엔코더 피드백 검증이다. Jetson 실제 성능·부품 후 교정/제동·무선 STOP/독립 차단은 별도 미완료로 남는다. 이번 작업에서 구매·외부 게시·GitHub 반영·컴퓨터 종료를 하지 않는다.

## 최신 계획: 실차 이전 필수 준비와 조건부 보완

- [전체 개발 계획](reports/DEVELOPMENT_PLAN_2026_09_22.md)을 향후 작업의 권고 순서로 사용한다. 사용자 요청에 따라 코드·규정·센서/구동 구조를 대조했으며, 팀 설계 확정이나 새 구현 승인은 아니다. 아래 센서 내성/Jetson 계획은 선행 논의와 완료 이력으로 보존한다.
- 지금 사용할 수 있는 하드웨어는 **Jetson Orin Nano뿐**이고, 센서/모터 도착은 미정이며 **하드웨어팀 설계 시작까지 약 1~2주** 남았다. 이전의 ‘실물 시험 기간 약 1~2주’ 추정과 구분한다. 고정 주차 일정 대신 선행 조건/완료 기준을 둔다.
- 권고는 정지/복구·입력/명령 계약과 기록/재생 기반 → 제한된 잡음·이상치/고착 및 남은 고장 검증 → 벽 가림/다중 차량 추종·정지 → 정지 차량 저속 우회다. Jetson 이식/실시간 부하는 병행 과제다. **필터 검증은 필요하지만 평활화 필터 구현은 효과/추가 지연을 확인한 경우에 한한다.** 기존 11조건 통과를 모든 실제 잡음·MCU 제어 검증으로 확대하지 않는다.
- 공식 LED 시퀀스와 현재 임시 빨강→초록 검출기의 차이, 비상정지 유지/재허가 및 중도 재출발, 낮은 상대차/C1 가림, 실차 시간 계약/구동/제동, 5랩 운용과 방지턱 복귀를 필수 공백으로 구분했다. 장착·방지턱 구현과 속도 향상/추월 보류는 유지하며, 설계 전 요구사항만 미리 준비한다.
- 계획용 공식 자료는 `main` 커밋 **`3a9ada035f77305390217795edaa73c495687b6e`**의 MANUAL·트랙 README·전원 자료 및 #14 최종 답변을 직접 확인했다. 9/22 후방 마커 규칙은 모양 자유, `DICT_4X4_50` 사용 시 코스 ID 0/20/30/45 금지·사전/ID 공유·중복 조정이다. 임시 ID 10의 팀 등록/중복 확인은 별도다. 아래 사전/ID 정책 ‘미명시’는 이전 기록이다. 실행 입력/ZIP/차량/트랙은 교체·재감사하지 않았다.
- 이번에는 계획 문서·인수인계·활동 기록만 수정했다. 주행/Jetson 시험·외부 게시·GitHub 반영은 하지 않았다.

## 최신 완료: IMU·엔코더·시간 정렬 내성 1차 구현·11조건

- 사용자 승인으로 [운동 센서 내성 시험](autonomy/MOTION_SENSOR_ROBUSTNESS_2026_09_22.md)을 완료했다. 시험 전용 중계기·주입 감사·주행 중 고장/복구 판정을 추가했고 최종 회귀 302개를 통과했다. 기본 7조건 각 12 m, 주행 중 IMU/휠 2초 누락·IMU 80 ms 일시 지연 3조건, 복합 한 바퀴 총 11/11회 통과다.
- 복합은 C1 ±3 cm·자이로 +1°/s·후륜 −5%·각 10±3 ms 지연·IMU 시각 −5 ms에서 48.6527 m, 최고 8.26·코너 중앙값 4.37 km/h다. 실제 정지·정상 종료·잔존 없음·벽/노면 이탈 표본 0, 노면 감사 345/433표본을 확인했다. `PATH_TOO_SHORT`/`front_unobserved` 각각 1표본은 보존한다.
- 주행 중 고장 세 조건은 보호층 0 명령 약 0.09초 후 관측, 실제 정지 약 0.70~1.00초 후, 복구 후 재주행을 확인했다. 직전 속도와 표본 간격이 달라 제동거리를 직접 비교하지 않는다. 약 8 km/h 누락 조건의 표본 이동거리 약 0.9 m는 가상 구동계 기준이며 실차 보장이 아니다. 실제 MCU 내부 피드백·자동 교정·온도/장기 드리프트·값 고착·좌우 개별 펄스 손실은 미검증이다.
- 엔코더 분해능과 통신 주기는 **미정**이라는 사용자 답변을 받았다. 자이로 ±1°/s·후륜 ±5%·시각 ±5 ms와 지연/누락은 민감도 시험값이지 실물 사양이 아니다. v8 제어기·속도·안전 한도·차량/코스를 유지한다. 아래 문서 정리 단계의 ‘아직 구현하지 않았다’는 이 착수 전의 기록이다.
- 설계·수정·판정은 주 에이전트, 실행 결과 감시는 Luna가 담당했다. 모든 결과는 로컬에 보존했고 GitHub 게시·녹화·컴퓨터 종료는 하지 않았다. Jetson 시험은 아래 별도 과제로 남는다.

## 최신 우선순위: 센서 내성·Jetson 검증 → 다중 차량 추종·정지 차량 우회

- 사용자는 실제 차량/센서 시험 시간이 **약 1~2주일일 수 있다**고 설명했다. 미확정 추정이며 확정 일정으로 만들지 않는다. [센서 내성·Jetson 인수인계 계획](reports/SENSOR_ROBUSTNESS_AND_JETSON_PLAN_2026_09_22.md)을 다음 작업의 우선 기준으로 삼는다.
- 9/22 코스 비교에서 바꾼 것은 LiDAR 거리 오차/추가 지연이다. 기존 IMU 임의 백색잡음과 엔코더 2048틱·100 Hz·2 ms 지연은 고정했다. 9/8의 IMU/엔코더/시각 오차 합성 기하 검사도 보존하되 코스 폐루프 내성 검증과 구분한다. 다음은 자이로 편향·엔코더 환산 오차·개별 지연/누락·센서 간 시각 차이와 주행 중 고장/복구를 우선한다.
- Jetson 실제 연산량/지연 측정·최적화는 **다른 세션의 병행 과제**다. 원시 센서 bag을 목표 속도로 재생 → 필요 시 PC Gazebo와 Jetson 제어기의 폐루프 연결을 제안했다. 가상 고장 중계기/MCU/계측기는 필요한 부분만 추가하며 아직 구현·실행하지 않았다. 느린 PC 시뮬레이션이나 재생 성공을 실시간 Jetson 성능·완주로 승격하지 않는다.
- 이후 상대차 가림에도 경로 유지 → 앞차 추종·정지 → 충분한 공간이 확인된 **완전 정지 차량의 저속 우회**를 진행한다. 이동 차량 추월은 후순위다. 현재 속도는 우선 유지하고 고속화는 실제 차 제작 후 가속력·제동/조향 응답 확인 뒤 검토한다. 장착/방지턱도 보류한다.
- 이번 갱신은 코드/기존 검증 대조와 문서 정리다. 새 오차 시험·가상 노드 구현·Jetson 접속·원격 작업 생성·GitHub 게시를 하지 않았다.

## 최신 검증: C1 거리 오차·입력 지연 내성 — 재개 검증 완료

- 사용자 요청으로 [9/22 시험](autonomy/LIDAR_ROBUSTNESS_2026_09_22.md)을 시작했다. ±3 cm 거리 오차를 우선하고 전송 지연을 분리/결합 검증한다. 제조사 ±30 mm는 σ=30 mm라는 뜻으로 해석하지 않는다. 장착·방지턱·회피/추월은 이번에 변경하지 않는다.
- `lidar_test_profile`을 명시한 순차 취득에서만 합성 거리오차/전송지연을 적용하며, 취득 시각과 결측을 보존한다. 제어기/독립 보호층 모두 오차 스캔을 받는다. 기존 기록·기본 무주입 실행은 보존하고 실행별 실제 주입 통계·주행/정지/종료를 함께 판정한다.
- v7에 균일 ±3 cm를 넣으면 벽 호길이가 잡음의 지그재그로 부풀어 관측 경로를 짧게 계산했다. v8은 거친 연결 구간의 호길이 측정 좌표만 7점 평균하고 원시 적합/보호층·깨끗한 모서리는 보존한다. 첫 무조건 평활화 안의 과거 커브 회귀 2개 실패도 기록했다. 속도/안전 한도를 완화하지 않았다.
- 같은 오차의 한 바퀴는 수정 전 최고/코너 중앙값 6.03/2.77→수정 후 **8.07/4.44 km/h**, 48.7127 m·실제 정지·정상 종료·벽/노면 이탈 표본 0이었다. v8 오차+50±20 ms 추가 지연(seed 23) **두 바퀴 95.3056 m**, 최고 8.06·코너 중앙값 4.26 km/h, 벽 겹침 0·실제 정지·정상 종료로 평가기 `passed=true`다. 일시 경로 거부 상태 표본은 각각 1개/9개 남는다. 20 km/h·실차 안전을 검증한 결과가 아니다.
- 승인 서비스 장애로 한 차례 보류했으나 사용자 요청으로 **남은 검증을 완료**했다. 결합 두 바퀴의 노면 감사는 주행 726/정지 530표본 모두 이탈 면적 0이다. 고정 +3/−3 cm·추가 80 ms·무주입은 각각 12 m 구간에서 주행·실제 정지·정상 종료·벽/노면 이탈 표본 0을 확인했다. 최고 속도는 각각 8.07/8.11/7.68/8.16 km/h다. 짧은 구간 결과를 전체 코스 완주로 승계하지 않는다.
- 추가 300 ms 지연은 초록 신호 인지 후 7.074초·71표본에서 보호층이 `stale_input`으로 안전 명령 0을 유지했고 실제 차량도 출발하지 않았다. 보호층 출발 거부 판정만 통과이며 원래 완주 판정 `passed=false`는 보존한다. 경로 제어기 450 ms/보호층 300 ms의 기존 입력 나이 제한 차이로 `RUNNING` 상태 표본도 22개 있었다. 두 계층 모두 항상 정지했다고 표현하거나 보호층을 생략하지 않는다. 주행 중 지연 급증 후 제동은 다음 시험이다.
- 빈 시험 프로필을 ROS CLI로 전달해 무주입 대조가 시작되지 않는 검사기 오류를 수정했고 실패 기록은 남겼다. 수정 후 **전체 Python/ROS 회귀 277개 통과**다. 기본 실행은 오차 무주입이며 시험 JSON을 명시해야 한다. 설계·수정·최종 판정은 주 에이전트, 실행 대기·수집은 Luna가 맡았다. 코드·자료는 로컬에 보존했고 GitHub 게시·새 녹화·컴퓨터 종료는 하지 않았다.

## 선행 결정: 지역 경로 생성 + Pure Pursuit

- 사용자 결정으로 **주변 관측에서 지역 경로를 계속 생성하고 Pure Pursuit로 추종하는 방식부터 개발**합니다. 다른 제어기·지도 기반 경주선·전역 위치 추정은 여유가 있을 때의 후속 후보입니다. 기존 알고리즘 문서의 ‘단계 2→3’은 필수 순서가 아닙니다. [현재 설계](autonomy/ALGORITHM_OPTIONS.md), [ADR 0021](decisions/0021-local-path-pure-pursuit.md)을 우선합니다.
- 차량 기준으로 매번 경로를 생성하므로 전역 자기 위치 추정은 필수가 아닙니다. 엔코더·자이로의 짧은 이동량·회전량 계산은 기존 LiDAR 운동 보정과 연결하며 별도 SLAM 도입으로 해석하지 않습니다. 동적 장애물 회피·추월은 경로 선택·상대차 추적을 추가해야 하는 후속 기능입니다.
- 실차 센서는 **일반 RGB + C1 사용이 거의 확정, ToF는 아마 미사용**이라는 최신 사용자 설명을 적용합니다. 엔코더는 있으나 구체 사양·선정은 미정이고, IMU는 후보 모델을 검토한 6축 장착안으로 아직 미확정입니다. 9/19 B0183 견적 이력은 유지하며 새 모델·구매 완료를 임의 확정하지 않습니다.
- C1은 낮게 달아 후방 일부가 가려지고 전방에 얇은 기둥/지지물이 있을 가능성이 있으나, 높이·배치·가림 범위는 전부 미확정입니다. 앞으로 구현할 때 자기 반사 제거와 미관측 영역을 구분하고 가려진 공간을 빈 공간으로 취급하지 않습니다. 낮은 설치가 상대차 검출을 보장하지는 않습니다.
- 신규 실차 주행은 ToF 없는 조건에서 성립하도록 설계합니다. 기존 ToF 안전층·시뮬레이션·시험은 보존하고, C1 관측/가림·입력 만료·제동거리를 반영한 독립 감속·정지층을 별도로 구현·검증해야 합니다. `/drive/safe` 직접 발행으로 우회하지 않습니다. 실물 C1 시간 계약과 엔코더·IMU 연동 확인은 남습니다.
- 이 절은 구현 요청 이전의 문서·결정 기록 갱신입니다. 이후 실행 구현은 위 최신 절과 ADR 0022를 따릅니다. 사용자 요청에 따라 주차별 일정·6주 우선순위는 작성하지 않습니다.

## 최신 센서 선택: B0183·C1 기준, 별도 IMU 검토

- 독립 주행 20회를 완료했다. 15 km/h에서는 순간/내부/이후/결합 통과·순차 무보정 실패, 20 km/h에서는 결합만 주행·제동 통과였다. 결합의 20 km/h 재시험도 통과해 2/2회다. 반경 1 m의 8 km/h 다섯 모드는 모두 통과, 결합의 직선 5/10 및 커브 5/10도 통과했다. 전체 취득·정지·하위 프로세스 종료는 정상이며 실패 주행 원문은 보존한다. 과거 순간 스캔 20 km/h 통과와 이번 순간 대조군 실패를 구분한다. 적은 반복·이상화 센서·임시 물성이므로 실물 최대속도를 확정하지 않는다.
- 공식 코스 500 Hz 원시 광선의 높은 부하에서 벽시계 3초 감시로 SENSOR_STOP/TOF_STALE_STOP이 반복됐다. 최초 짧은 실행은 진단을 위해 정상 중단하고 실패/중단 원문을 보존했다. `sensor_wall_timeout_s` 기본 3초는 유지하고 오프라인 재검사만 30초로 명시했다. 측정 시각 기준 scan/IMU/엔코더/ToF 제한과 물리는 바꾸지 않았다. 재검사 demo_short_v2는 ToF 보호 상태에서 1.01989 m·실제 정지·정상 종료를 통과했다. 아래 9월 6일의 '보정 미구현' 설명은 당시 조사/시험 이력이다.
- 공식 코스 촬영은 한 바퀴+약 2 m(48.6727 m)를 완료했지만 최고 실제 속도는 12.3775 km/h로 20 km/h에 미달했다. 60.5초 3인칭 영상의 1,210프레임을 확인하고 원본/취득 시각/1배속 사본을 보존했다. 코스 마커 네 ID·조기 출발 없음·평면 벽 겹침 표본 0을 확인했으나 방지턱에서 최대 피치 42.67°로 크게 들렸다. 로그에 짧은 WALL_LOST 두 번도 있다. 고속 안전·3차원 보정이 검증된 것은 아니다.
- 공식 촬영 실행은 목표 이후 정지 확인의 벽시계 60초 제한 초과와 GPU Gazebo 강제 종료(-9)로 종합 미통과다. 느린 계산 대비 정지 검사 시간이 부족한 정황은 있으나 최종 제동 trace가 없어 실제 정지는 미확인이다. 독립 시험 성공으로 이 실패를 덮지 않는다. [최종 산출물 색인](../artifacts/validation/2026-09-08/lidar_motion/README.md)에 영상·속도 그래프·실패 원문을 모았다.
- 최종 전체 Python/ROS 검사 208개 통과, 실행 23개 소스 ZIP 해시 일치를 확인했다. 시뮬레이션 프로세스는 종료했다. 다음은 카메라 기반 방지턱 인식/사전 감속 검토, 시뮬레이션 시간 기준 정지 검사와 제동 trace 보강, 실물 C1 시각·엔코더/자이로 교정이다. GPU 종료는 별도 미해결 과제이며 GitHub 게시·컴퓨터 종료는 하지 않았다.

## GPU 마지막 추가 진단: 순차 LiDAR에서 선택형 이득 확인

- 사용자 요청으로 시뮬레이터만 최종 확인했다. RGB·깊이·C1/ToF의 광선 계산은 이미 같은 GPU 렌더러 선택 대상이며, 로봇 영상 인식·DART 물리 계산은 별도다. 누락된 센서 전체를 새 CUDA 코드로 이식한 것은 아니다.
- 센서 단독 CPU/GPU 2회씩 비교에서 RGB-D 시간 약 24%, 500 Hz 원시 LiDAR 약 39%, ToF6 약 24% 감소했다. 화면 연결을 생략하는 EGL은 GPU GLX 대비 추가 속도 이득이 없었다.
- 실제 5 km/h 직선·10 Hz 순차 취득·500 Hz 원시 광선·8초 주행/정지 시험은 CPU 161.701초→GPU 108.582초로 전체 시간이 약 33% 줄었다. 양쪽 취득·주행·정지·21개 자식 정상 종료를 통과했고 시간 근사 오차 최대 약 1.8 ms를 유지했다. 각 1회·준비/종료 포함 실행 시간이며 공식 코스의 순간 스캔 시험과 구분한다.
- `validate_lidar_control_lab.py`에 `--render-backend` 선택을 연결했다. GPU는 고부하 순차 시험에 활용할 근거가 생겼으나 과거 간헐적 종료 실패가 해결된 것은 아니므로 전역 기본 `system`은 유지한다. 관련 검사 19개 통과. [최종 진단](simulation/GPU_FINAL_DIAGNOSTIC_2026_09_08.md)을 확인한다.
- 이번 추가 진단은 완료했다. 아래 이전 'GPU 성능 이득 없음'은 당시 일반 코스/순간 스캔의 결과이며 모든 부하로 일반화하지 않는다. 추가 GPU 엔진 이식보다 확보된 선택형 경로를 이용한 자율주행 알고리즘·보정 실험을 우선한다.

## 실행 속도 병목 분리와 선택형 개선

- 9월 8일에는 차량·카메라·ROS 없이도 공식 코스 물리 계산에 1 sim초당 약 5.47초가 걸림을 확인했다. 같은 정적 코스 전체는 6.60초, 물리 제외는 1.225초였다. 3,740개 충돌 형상의 계산 비용이 큰 부분이며 GPU 미사용만의 문제가 아니다.
- 같은 DART 엔진에서 충돌 검출만 ODE/Bullet로 비교하면 5.16/2.34초였다. 실제 RGB-D 30 Hz·ToF6·공식 코스·짧은 주행은 기본 0.10953→Bullet 0.14302 RTF(약 31% 개선)이고 센서·직진·조향·실제 정지·정상 종료를 모두 통과했다. SceneBroadcaster 해제는 0.13937 RTF로 추가 개선을 확인하지 못했다.
- `collision_detector:=bullet`과 headless 전용 `scene_broadcaster:=false`를 선택형으로 추가했다. 기본 검출기·상태 발행은 그대로이며 원본/운영 SDF를 바꾸지 않고 임시 사본에만 설정한다. 검출기에 따라 직진 거리·회전량이 달라 기존 동역학·본선 완주 결과를 승계하지 않는다. [ADR 0017](decisions/0017-optional-collision-detector-performance.md)과 [성능 분석](simulation/PERFORMANCE_2026_09_08.md)을 확인한다.
- GPU를 같은 경량 조건에 더한 실행은 0.14222 RTF로 추가 이득이 없었고 종료 실패였다. 종료 직후 스택은 Ogre 장면 노드 해제 중이었으며 D3D12 core는 아직 로드되어 있었다. 따라서 이전 core 조기 해제 추론만으로 모든 종료 대기를 설명하지 않는다. 종료 시간 진단·원문 실패는 당일 활동에 기록한다. `render_backend:=system` 기본은 유지한다.
- SIGINT 유예 60초 진단은 1회 약 2초 정상 종료, 반복은 약 65.28초 후 강제 종료였다. GPU 종료와 실시간 1배 달성은 미해결이다. Python 58개·원본/형상 보존 검사를 통과했고 잔존 시험 프로세스가 없다. [9월 8일 활동](activity/2026-09-08.md)을 확인한다.

## GPU 사용 여부 점검

- **최종 상태:** GPU 렌더러 선택은 구현·확인했으나 속도 개선은 없고, 수명 보조 후에도 두 번째 시험에서 Gazebo 종료가 실패했다. `render_backend` 기본값은 기존 환경을 따르는 `system`으로 유지하고 `auto`·`wsl_nvidia`는 선택형 진단 경로로 남겼다. 아래 첫 성공은 이력이며 안정성 해결로 승격하지 않는다. 다음은 종료 중 스레드/라이브러리 수명 심층 추적과 물리·전송 부하 분리다.

- 9월 7일 확인한 기존 Gazebo Ogre2 로그(수정 시각 9월 6일 00:55:47 KST)는 `GL_RENDERER = llvmpipe (LLVM 20.1.2, 256 bits)`와 소프트웨어 EGL 장치 선택을 기록한다. 해당 실행은 하드웨어 GPU 렌더링이 아니었다. 모든 과거 실행에 일반화하지 않는다.
- Windows는 RTX 5070 Laptop GPU와 AMD Radeon 610M을 인식하고 WSL에는 `/dev/dxg`가 존재한다. 조회 전 WSL은 정지 상태였으며, 이번에는 조회를 위해 시작했지만 시뮬레이션은 실행하지 않았다. GPU 렌더링 경로 복구와 같은 조건 성능 비교는 미완료다. [점검 기록](activity/2026-09-07.md)을 확인한다.
- 후속 사용자 승인으로 D3D12/NVIDIA 선택을 실행 파일에 구현했다. `render_backend:=auto|system|wsl_nvidia|software`로 선택하며 기본 auto는 WSL에서 GPU 경로를 요청한다. 첫 GPU 실행은 종료 실패였고 기본 Gazebo 예제에서도 렌더 스레드 종료 충돌을 재현했다. D3D12 core의 조기 해제만 막는 프로세스 한정 보조 라이브러리를 추가했고 최종 첫 실행은 센서·직진·조향·실제 정지·정상 종료를 통과했다. 위 미실행·미완료 표현은 최초 조회 단계의 이력이다.
- 같은 RGB-D 30 Hz·ToF6·공식 코스 짧은 비교에서 CPU RTF 0.11843, 최초 GPU 0.11743, 종료 수정 후 GPU 0.11231로 속도 개선은 확인하지 못했다. GPU 미사용만으로 느림을 설명하지 않는다. 설정·한계·후속 검증은 [GPU 렌더링](simulation/GPU_RENDERING.md)과 당일 활동을 확인한다. 기존 장시간 스테레오 실패·순차 LiDAR 결과는 재판정하지 않는다.

## 병행 작업: C1급 순차 회전 취득 속도 시험

- `lidar_acquisition:=sequential`을 추가했다. 10 Hz·500점을 회전 중 각 시각의 실제 Gazebo 광선 프레임에서 모으며, 기본 500 Hz 원시 계산의 점별 시간 근사는 약 2 ms 이내다. 기존 `snapshot` 기본값과 이전 결과는 보존한다. `snapshot_matched`는 동일 원시 부하의 순간 스캔 대조군이다.
- 운동 보정·스캔 사이 예측·실물 통신/반사율/결측 모델은 미구현이다. 한 바퀴를 모아 전달하는 드라이버와 임시 회전 위상 가정이며 실물 C1 전체 재현으로 표현하지 않는다.
- [구현과 속도 시험](sensors/C1_SEQUENTIAL_SPEED_EXPERIMENT.md), [ADR 0016](decisions/0016-sequential-c1-acquisition.md), [활동](activity/2026-09-06.md)을 확인한다. 결과는 `artifacts/validation/2026-09-06/rotating_lidar/matched_matrix_v1/`에 저장한다. 독립 시험의 고정속도·100 Hz 제어·ToF 해제를 일반 데모로 승계하지 않는다.
- 이 작업은 공식 코스나 센서 예산 후보·시뮬레이션 기본 센서 배치를 바꾸지 않는다. 아래 예산 협의 기록은 별도 작업으로 보존한다.
- 실험 완료: 본 비교 14회와 직선 15 km/h 추가 한 쌍을 마쳤다. 순간 스캔은 직선 5/10/15/20·반경 1 m 커브 5/8/10을 통과했고, 순차는 직선 5/10·커브 5/8/10 통과, 직선 15/20 실패였다. 15 km/h는 순간 2/2 통과·순차 0/2 통과로 재현했다. 16회 센서 취득·실제 정지·정상 종료, 자동 검사 165개를 확인했다. 정확한 최대속도·실차 안전은 미확정이다. 다음은 같은 조건의 엔코더/IMU deskew·스캔 사이 예측 비교이며 아직 구현하지 않았다.

## 후속 준비: 회전식 라이다 보정 자료 조사

- 2026-09-06 사용자 요청으로 [보정 구현 조사](sensors/ROTATING_LIDAR_COMPENSATION_RESEARCH.md)를 작성했다. 공식 메시지·SLAMTEC 드라이버/SDK·ROS 보정/추정 구현과 저자 LIO 자료를 읽고 소스 커밋을 고정했다. 연구·제안만 완료했으며 보정 코드·새 주행·GitHub 게시·센서 설계 변경은 하지 않았다.
- 내부 deskew와 스캔 이후 이동 보정은 서로 다른 시간 구간의 상대 좌표 변환이다. 하나의 센서 기반 이동 이력으로 무보정/내부만/이후만/둘 다를 비교한다는 제안이며, 성능 순위나 보정 후 최대속도는 미확정이다. SLAM은 첫 구현의 전제 조건이 아니다.
- 실물 C1의 점별 시각·취득 순서가 먼저다. 공식 `angle_compensate`는 각도 격자 정리이며 운동 보정이 아니다. 정렬·반전·복제 이후 `LaserScan` 인덱스를 곧 취득 시각으로 가정하지 않는다. SDK timestamp API는 있으나 C1 하드웨어 지원·정확도·실제 포함 SDK 버전은 확인해야 한다.
- 다음 후보는 양자화 `/wheel_states`와 IMU 자이로의 이동 버퍼다. 현재 `/odom`은 정답 pose 자체가 아니라 Gazebo 플러그인의 이상적 바퀴·조향 적분값이며, 실제 센서 지연·양자화 경로를 우회하므로 자동 재사용하지 않는다. `/wheel_encoder_ticks`에는 시각 헤더가 없다. D435i 제거 후보에서는 별도 IMU 유지 여부도 확인한다.
- 좌표를 현재 기준으로 옮겨도 관측은 새로워지지 않으며 상대차 운동·가림은 해결되지 않는다. 원래 관측 나이·시간 오류·슬립·방지턱의 평면 가정 한계와 입력 지연을 별도 검사한다. 기존 16회 무보정 결과와 활동 기록은 보존한다.

## 최근 작업: 2026-09-03 LiDAR 갱신률 실험

- 공식 코스의 짧은 출발~커브 진입 비교와 별도 고정 속도 시험장을 구현했습니다.
  기본 차량·트랙·10 Hz·ToF 안전층·일반 20 Hz 조향기는 그대로 유지합니다.
  실험용 `lidar_rate_hz`와 명시적인 안전층 해제 옵션은 기본값과 구분합니다.
- 독립 시험은 동일 2 kg 차량·500점 snapshot LiDAR·100 Hz 조향을 사용합니다.
  반경 1 m 원형에서 5·8 km/h의 10/20/30/40 Hz 여덟 조건이 추종·정지를
  통과했지만 약 7.5~8.4 cm의 안쪽 치우침이 남았습니다. 공식 급커브 검증은 아닙니다.
- 20 km/h 직선은 각 주기를 세 번씩 반복했습니다. 실제 최고 약 20.56 km/h,
  추종·정지 통과는 10 Hz 0/3, 20 Hz 3/3, 30 Hz 0/3, 40 Hz 3/3입니다.
  30 Hz는 제동 중 노면 이탈이 있었고, 평균 스캔 나이도 20 Hz보다 컸습니다.
  이 소프트웨어 경로의 결과를 실제 제품의 단순 Hz 순위로 해석하지 않습니다.
- 최초 검사기에는 그룹 SIGINT와 실행 부모의 자식 신호 전달이 중복되는
  오류가 있었습니다. 첫 20회는 주행·정지 측정 뒤 종료 단계에서 모두 문제가
  있었으므로, v1 원문의 `passed`·`shutdown_clean` 대신 `shutdown_audit.json`을
  확인합니다. 부모에만 한 번 전달하고 자식 로그까지 검사하는 v2로 보완했으며,
  후속 20/30 Hz 두 실행의 부모·자식 20개 정상 종료를 확인했습니다.
  중단·원시 로그·v1 검사기 사본도 보존했습니다. 추종·정지 지표와 종료는 별개입니다.
- 센서의 순차 회전 취득·운동 보상·노이즈·이동 차량은 아직 미구현/미검증입니다.
  고속 구매 최소 Hz나 실차 안전 속도를 확정하지 않았습니다. 엔코더 100 Hz·
  IMU 200 Hz를 확인했으며 보정기에는 시뮬레이션 정답값을 입력하지 않습니다.
- 세션 복구 뒤 사용자 지시에 따라 컴퓨터 종료는 취소했습니다.

## 최신 작업: C1·D435i 선택형 단독 주행과 완주 영상

2026-09-04 재개 현황은 [당일 활동 기록](activity/2026-09-04.md)을 먼저 확인합니다.

- C1+ToF6는 `lidar_brisk_one_lap_video_01`에서 48.6527 m·한 바퀴+약 2 m,
  최대 중심선 거리 0.129494 m·벽 겹침 0개·정상 정지/종료를 통과했습니다.
  [86.65초 3인칭 영상](../artifacts/videos/2026-09-04/c1_tof6_third_person_one_lap.mp4)을
  저장하고 1,733프레임을 모두 디코드했습니다. 마지막 신호등 통과 순간에는
  관찰 카메라가 시설물에 잠깐 가려집니다.
- 이전 스테레오의 깊이 통로·벽 거리·RGB 보조 합산 방식은 25.016 m 단기
  시험 통과 뒤 완주 녹화에서 24.196 m에 한쪽 뒷바퀴 헛돎으로 실패했습니다.
  실패 영상·보고서는 보존합니다. 현재는 가까운 RGB-D 노면 목표점을 Pure
  Pursuit로 추종하고 목표점이 없을 때만 깊이 조향을 최저속도로 선택합니다.
  새 `stereo_rgbd_target_one_lap_video_01`은 48.6527 m·벽 겹침 0개·최대 중심선
  거리 0.090293 m·마커 네 종류·실제 정지와 [130.1초 영상](../artifacts/videos/2026-09-04/d435i_tof4_third_person_one_lap.mp4)을
  확인했습니다. 단, 깊이 수신 약 23.975 Hz와 Gazebo 종료 실패 때문에 종합
  `passed`는 `false`입니다. 한 바퀴 성공과 전체 검사 성공을 구분합니다.
- 같은 소스의 녹화 없는 2.0598 m 분리 시험은 깊이 27.56176 Hz·실제 정지·
  자식 18개 정상 종료까지 통과했습니다. 짧은 실행 성공으로 장시간 녹화 실패를
  해소했다고 보지 않습니다. 남은 일은 수신률의 렌더/전송/검사 부하 분리와
  Gazebo 종료 대기의 재현·해결입니다. 두 완주 영상과 원 실패 근거는
  [고정 검증 문서](../artifacts/validation/2026-09-04/selectable_autonomy/README.md)에 연결했습니다.
- Python/ROS 160개·C++ 차동 1개·패키지 5개 빌드와 공식/실험 해시 검사를
  통과했습니다. 센서 설정 변경에 따른 공식 생성 이력 누락은 별도 재생성에서
  29개 출력이 동일함을 확인한 뒤 입력 해시만 갱신했습니다. 트랙은 바꾸지 않았습니다.
- 센서 제거 질량은 A/B 시험용 차체 보정으로 총 2.000 kg을 맞췄지만
  질량 중심·관성 분포까지 동일하지는 않습니다. 녹화 카메라는 별도 1 mg입니다.

- 이 구성은 사용자의 **개인 임시 제안**이며 하드웨어팀을 포함한 다른 팀원과
  아직 협의하지 않았습니다. 팀 합의·구매 결정으로 취급하지 않습니다.
- `autonomy_mode:=lidar`는 기존 상부 C1급 LiDAR와 ToF 여섯 개,
  `autonomy_mode:=stereo`는 전방 D435i급 RGB-D와 좌우 전·후측 ToF 네 개를
  선택합니다. 후자는 양쪽 측면의 명목 시야를 우선하고 정후방 약 60°를
  포기합니다. 실제 근접 무사각을 보장하지 않습니다.
- 두 모드 모두 RGB 신호·ArUco, 단일 모터·기계식 차동과 독립 ToF 안전층을

  쓰며 `/scan`, 지도와 정답 위치를 읽지 않습니다. 녹화 전용 추적 카메라도
  제어 입력에서 제외했습니다.
- 9월 3일의 핵심 검사 43개·초기 2 m 실패와 중단 경위는
  [결정 0015](decisions/0015-selectable-lidar-stereo-autonomy-prototypes.md)와 당시 활동 기록에 보존했습니다.
- 현재 시험 프로세스는 모두 종료했습니다. 직전 재개 작업은 로컬 보관으로

## 차량 치수의 확정 범위

- 전체 평면 외형: 길이 0.20 m·폭 0.15 m는 팀이 확정한 설계 목표입니다. 시뮬레이션의 기본 자세에서는 바퀴·센서·범퍼를 포함한 전체 외형으로 해석하며, 실제 검차의 측정 방식과 제작 공차는 별도 확인이 필요합니다.
- 검차 시 조향 상태: 사용자는 조향 중 바퀴 돌출은 검사하지 않을 것으로 예상하지만, 공식 조건은 아직 확인되지 않았습니다. 조향 중 전체 점유 영역이 20 cm x 15 cm 안에 있어야 한다는 규정을 추가로 가정하지 않습니다. 실차의 벽·주변 차량 충돌 판단에서는 조향 중 점유 영역을 고려해야 하며, 현재 주행 검사기의 고정 외형과 구분합니다.
- 임시 주행 치수: 사용자의 긴 축거·넓은 윤거 선호를 반영해 축거 0.145 m, 윤거 0.135 m로 늘렸습니다. 바퀴 반지름 0.025 m(지름 5 cm), 바퀴 폭 0.012 m는 유지합니다. 직진 상태의 바퀴 바깥 치수는 0.195 m x 0.147 m이며, 전체 목표 외형 안에 있습니다. 너클·허브·링크 등 실물 장착성은 미검증입니다.
- 조향 관절 한계 ±0.45 rad에서 바퀴의 보수적인 점유 폭은 약 0.1676 m입니다. 실차 충돌 판단에서 고려할 기하 계산값이지 현재 주행 검사의 외형 설정값이 아닙니다. 이번 주행 검사는 고정 20×15 cm 직사각형을 사용했습니다. 축거 증가에 따른 실제 최소 회전 반경·지름길 진입 궤적은 추가 검증해야 합니다.
- 높이 0.06 m와 통합 차체 질량 1.635 kg(나머지 링크 포함 총 2.000 kg), 조향 범위, 센서 위치·자세도 임시값입니다. 설정의 `footprint`는 전체 외형 목표이고, `body`는 그 평면 외형을 보수적으로 근사한 단순 충돌체이지 확정된 섀시 판 형상이 아닙니다.
- 지름길에 맞추기 위해 차량을 축소하지 않습니다. 주최 측 트랙의 기존 15 cm x 10 cm 차량 가정과 우리 차량의 확정 외형을 구분합니다.

## 아키텍처 결정

- PC 시뮬레이션: Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonic
- Jetson 배포: JetPack 6.2.1 / Ubuntu 22.04를 유지합니다. 시뮬레이터와 운영체제 버전을 맞추기 위한 목적만으로 재설치하지 않습니다.
- 가능한 범위에서 알고리즘 패키지가 ROS 2 Humble과 Jazzy 양쪽에서 소스 수준으로 호환되도록 유지합니다. 시뮬레이터 연동은 전용 패키지로 한정합니다.
- 환경이 달라져도 차량 제어·피드백 인터페이스는 유지하고, 이를 연결하는 어댑터만 교체합니다.
- 제어기 검증에는 Gazebo의 정답 위치·자세(ground-truth pose)를 사용할 수 있지만, 대회용 자율주행은 이에 의존해서는 안 됩니다.

선택 근거는 `docs/decisions/0001-simulation-platform.md`에 기록했습니다.

실제 차량의 잠정적인 역할 분담은 Jetson이 인지·계획을 담당하고, ESP32가 구동 장치의 동작 타이밍, 명령 수신 시간 초과 처리, ESC·서보 출력과 엔코더 신호 수집을 담당하는 구조입니다. `docs/decisions/0002-jetson-esp32-actuation-boundary.md`를 참고하십시오.

RGB와 깊이는 독립적인 Gazebo 카메라로 구성합니다. 기본 프로필은 각각 848×480의 60/90 FPS이고, 동일 주기 60/60·저부하 30/30도 지원합니다. 실제 장치와 공통으로 사용할 토픽은 유지하되, 영상 표현·정렬·점군 색상과 IMU의 차이는 어댑터 단계에서 처리합니다. 선택 근거는 `docs/decisions/0004-d435i-simulation-profile.md`에 있습니다.

사용자의 후속 요청으로 `demo.launch.py`에 RGB 신호 출발·ArUco 분기 선택·라이다 벽 추종을 추가했습니다. 기존 정답 위치 기반 중심선 추종 이정표와 별개인, 설명 가능한 센서 기반 시연입니다. 자율주행 입력은 `/scan`과 RGB뿐이며 지도·정답 위치·신호 제어 상태를 읽지 않습니다. 이 데모만 RGB 30 Hz·깊이 꺼짐을 기본으로 하며 일반 실행의 고속 설정은 유지합니다.

별도 `tof_safety`는 `/drive`·여섯 ToF 점군·`/wheel_states`·시계만 읽어 속도를 제한합니다. `/sim/drivetrain`의 `truth_*`와 정답 위치는 검사기에만 쓰며 두 제어 노드의 입력이 아닙니다. `/odom`은 바퀴/조향 관절 적분값이므로 슬립 상황의 실제 위치나 정지를 보증하지 않습니다.

임시 RPLIDAR C1 기준 라이다는 360°·10 Hz·500점·0.05~12 m입니다. 스캔 중심 XYZ=(-0.03, 0, 0.125) m이며 차체를 피한 높은 위치의 벽 추종용 가정입니다. 저상 상대 차량 감지는 보장하지 않습니다. 실물 오차·반사율·회전 왜곡·거리 양자화는 미구현입니다.

## 계획한 소프트웨어 역할 분리

```text
Gazebo 월드·시뮬레이션 센서
              |
              v
시뮬레이션 어댑터 -> 공통 ROS 토픽 <- 실제 하드웨어 어댑터
                              |
                              v
       인지 -> 위치 추정 -> 경로·경주 상태 -> 계획 -> 제어
                                                      |
                                                      v
                                                 /drive 명령
```

Gazebo의 휠 관절 정답값은 `/sim/joint_states_raw`로만 노출합니다. 시뮬레이션 엔코더 어댑터는 정해진 엔코더 분해능에 맞춰 양자화한 `/wheel_states`와 `/wheel_encoder_ticks`를 발행하며, 이는 실제 ESP32에서 받을 피드백 인터페이스와 맞춥니다.

신호등·ArUco 인식 알고리즘은 렌더링된 RGB 영상을 입력으로 사용해야 합니다. 시뮬레이터 내부 상태의 직접 사용은 테스트의 정답 판정과 시각화에만 허용합니다.

## 단계별 이정표

1. 환경 점검과 의존성 설치를 반복 가능한 형태로 준비합니다.
2. 제공된 트랙을 창 없이 실행하고, Gazebo GUI에서도 불러옵니다.
3. 매개변수 기반 Ackermann 차량을 생성하고 수동 전진·조향 제어를 검증합니다.
4. 시뮬레이터의 정답 위치·자세를 이용해 제공된 중심선을 추종합니다.
5. 곡률 기반 속도 제어를 추가하고 단독으로 한 바퀴를 완주합니다.
6. 공통 인터페이스를 유지하면서 카메라·IMU·2D LiDAR와 하부 ToF 여섯 개 모델을 추가합니다. **기초 인터페이스 구현 완료**이며 실물 오차·간섭 모델은 후속입니다.
7. 신호등과 ArUco 마커를 렌더링하고 카메라 영상의 픽셀에서 인식합니다.
8. 정답값 입력을 실제 환경에 맞는 위치 추정 입력으로 교체합니다.
9. 다른 차량을 추가하고, 안전한 추종·정지와 제어 가능한 회피를 구현합니다.
10. 다중 차량, 잡음, 지연, 데이터 누락과 매개변수 범위별 반복 실험을 수행합니다.
11. 실제 센서·구동 장치 어댑터를 통해 동일한 자율주행 노드를 Jetson에서 실행합니다.

## 현재 미해결 사항과 위험 요소

- 최종 차량의 축거(wheelbase), 윤거(track width), 바퀴 반지름, 조향 범위, 질량, 무게중심(CG), 모터·ESC 응답 특성과 센서 장착 위치·자세를 아직 모릅니다.
- 토크 기반 모델도 실측 보정 전입니다. 오픈 차동·편측 저마찰 시험에서 명령 중단 뒤 바퀴 평균이 거의 0이어도 차체는 미끄러졌습니다. 현재 ToF 안전층의 엔코더 기반 정지 예측에는 이 한계가 있으며 실차 IMU/자기 운동 추정·제동 시험이 필요합니다. 평지 마스크를 쓰므로 경사·들림·전복 상태의 감지 안정성도 보장하지 않습니다.
- 초기 전달본의 분기 경로 폭 12 cm는 우리 차량의 확정 목표 폭 15 cm보다 좁습니다. 해당 보존본은 15 cm x 10 cm 차량을 가정합니다. 당시의 이전 규격 잔존 가능성에 대한 미확정 이력은 보존하며, 현재 기본 `official`은 공식 배포본의 20 cm 지름길·20×15 cm 차량 기준을 적용했습니다. 폭 정정 자체가 지름길 연속 진입 성공을 보증하지는 않습니다.
- 초기 전달본의 본선 35 cm와 6월 30일 회의록의 본선 45 cm·차량 20 cm x 15 cm는 불일치했습니다. 당시 확인 한계와 그 때문에 만든 별도 폭 실험 이력은 유지하며, 새 공식 자료의 수치·구현 상태와 혼합하지 않습니다.
- 초기 전달본의 일반 구간 최소 곡률 반경 검사는 실패 상태였습니다. 값은 `0.2987 m`이고 동봉 README에는 `0.45 m`로 적혀 있었습니다. 새 공식 배포본도 별도로 대조한 결과 이 급커브를 의도적으로 유지하며 반경 검사는 여전히 실패입니다. 이 원본 정책과 실제 차량의 조향 가능성·주행 실패 여부를 분리합니다.
- 초기 전달본의 README와 `output_final`은 한 바퀴 길이·벽 높이·마커·분기 형상·기준 파일 설명이 달랐습니다. 이 원본 감사 결과를 새 공식 `track/README.md`도 읽을 필요 없다는 의미로 해석하지 않습니다.
- 원본 신호등은 세 등 모두 발광하며 UDP 스크립트가 화면을 바꾸지 않는 상태로 보존됩니다. 동봉 설명은 화면 연동을 팀별 bridge의 책임으로 명시하므로 미연동 자체를 배포 버그로 규정하지 않습니다. 가로대·등 배열의 진행방향 배치는 횡단 배치 의도인지 별도로 확인합니다. 실험본 파일의 초기 상태는 등 중심 30 cm의 빨강 단독 점등입니다. `traffic_light:=true` 또는 데모 실행에서는 실제 렌즈 재질이 빨강→노랑→초록으로 바뀌며 RGB 인식으로 출발합니다. 대회 신호 주기·형상의 공식 확정값은 아닙니다.
- 실험 신호등은 현재 카메라로 6개 출발 위치에서 보이는 것을 확인했습니다. 실제 대회 신호등 높이·방향과 D435i 브래킷은 미확정이며, 원본의 약 1.08 m 높이 배치가 해결된 것으로 해석하지 않습니다.
- 이전 정지 속도 흔들림은 설치된 Gazebo Math의 jerk ±20 제한만으로도 재현했습니다. 속도 ±2·가속도 ±4 제한은 유지하고 jerk 제한만 제외했습니다. 후속 시설 재검사에서는 18/18 가시성·방지턱 통과와 함께 약 0.54초 안에 지속 정지 조건을 통과하고 최종 속도 0을 확인했습니다. 과거 실패 보고서는 덮어쓰지 않으며, 수정 근거는 결정 0006에 기록합니다.
- 2D LiDAR의 단일 스캔 평면보다 낮은 차량을 보완하기 위해 하부 ToF 여섯 개를 추가했지만 광학 중심이 달라 근접 경계 사각이 있습니다. 중심 광선 모델은 영역의 부분 점유·반사율·외광·간섭·invalid도 재현하지 않습니다. 실제 가림·경계 결측 시험, 여덟 개 중첩 배치 비교와 상대 차량 높이 자료가 필요합니다.
- VL53L7CX급 여섯 캐리어의 대표 전류 단순합은 약 600 mA, 피크 단순합은 약 900 mA입니다. 같은 초기 I²C 주소, 버스 점유·MCU 메모리·다중 능동 IR 간섭과 전원 레일을 실물에서 검증해야 합니다.
- D435i 모델은 RGB 69.4°×42.5°·깊이 87°×58°의 명목 시야각과 별도 내부 파라미터를 사용합니다. 실제 보유 장치의 보정값은 아니며, 두 렌즈의 위치 차이·왜곡·깊이 결측·조명 민감도·롤링 셔터와 IMU 잡음은 미반영입니다.
- 848×480 깊이의 최소 거리는 0.195 m로 설정하고 기본 최대 절단 거리는 3 m로 둡니다. 4 m는 선택적인 확장 실험값이지 정확도 보장 거리가 아닙니다. RGB 렌더링 경계 20 m는 깊이 유효 거리·마커 인식 가능 거리와 다릅니다.
- 깊이 영상은 `32FC1`의 m 단위이며 실제 RealSense Z16 경로의 표현·스케일과 구분해야 합니다. RGB·깊이는 정렬되지 않았고, 기존 `/camera/depth/color/points`의 `rgb`는 실제 컬러 영상이 아닌 깊이 시각화 회색조입니다. Gazebo의 이상적 IMU 자세도 실제 센서의 직접 관측으로 취급하지 않습니다.
- 60/90 설정은 시뮬레이션 시간 기준입니다. 현재 PC에서 실시간보다 느리게 진행되고 일부 진단 실행에서는 영상 누락도 관측됐습니다. Gazebo의 정수 ms 주기 처리로 명목 60 Hz가 약 62.5 Hz로 생성되는 한계도 있습니다. 실행별 처리율·종료 결과는 2026-08-31 활동 기록과 검사 산출물에서 확인하며 실물 성능 보장으로 사용하지 않습니다.

## 초기 전달본을 기반으로 한 폭 실험 지도 — 기존 기준선과 검증 기록

- [2026-06-30 미팅](https://maddening-cause-ce7.notion.site/2026-06-30-38f99fd42e3080f6956fe5a5b90d0824)의 A-1·A-2에서 본선 노면 폭 0.45 m, 차량 0.20 m x 0.15 m 기준의 3대 폭과 지름길에 한정한 협소 구간을 확인했습니다. 지름길의 정확한 폭과 조향 시 검차 조건은 조회한 본문에 명시되어 있지 않습니다. 6월 당시 기록이며 최신 규정으로 확정한 것은 아닙니다.
- 사용자 승인에 따라 `config/tracks/experimental.yaml`에서 본선 0.45 m·지름길 각각 0.25 m를 관리하는 별도 실험 지도를 생성했습니다. 0.25 m는 공식 폭이 아닌 임시값입니다. `scripts/build_experimental_track.py`가 원본 생성기를 메모리에서 재사용하며, 원본 파일은 수정하지 않습니다.
- 당시 실행 기본값은 `track:=experimental`이었으며, 현재는 `track:=official`로 전환했습니다. 기존 실험은 `track:=experimental`, 초기 0.35 m·0.12 m 원본 재현은 `track:=original`로 선택합니다. `src/arena_gazebo/worlds/it_arena_experimental/`의 SDF·지도·CSV·설계 사본·출처 및 검증 기록도 유지합니다. 출발 위치는 선택한 월드의 `scene.json`에서 읽습니다.
- 두 번째 지름길 입구의 ID 30은 간섭을 피해 실험 사본에서만 반대편으로 옮겼고, ID·경로상의 위치 `s`를 유지합니다. 후속 시설 수정에서 검은 코드 10 cm·흰 여백 포함 판 13 cm로 크기 기준을 명시했으므로 원본과 물리적 인쇄 크기까지 같다고 표현하지 않습니다. 마커의 정지 영상 가시성은 확인했지만 지름길의 연속 진입·합류 궤적은 미검증입니다.
- 차량 축소와 지도 전체 확대는 기본안으로 권장하지 않습니다. 차량 축소는 실제 충돌 여유·센서 위치·주행 특성을, 지도 전체 확대는 주 경로 폭·곡률·거리·마커 배치를 함께 바꿉니다.
- 본선 2,332개·지름길 155개와 141개 표본 및 출발 위치 6개에서 실제 SDF의 벽·저층 시설 661개와 차량 평면 외형 간 겹침이 없는 것을 확인했습니다. 이 정적 검사와 짧은 실행 검사는 완주·추월·다중 차량 안전성을 보장하지 않습니다. 결정 근거와 재생성 방법은 `docs/decisions/0003-track-variants.md`, `docs/track/EXPERIMENTAL_TRACK.md`에 있습니다.

기존 자료 확인·하드웨어 연동·확장 과제는 아래와 같이 유지합니다.

1. 공식 `v2026.09.02` 적용 상태를 기준선으로 유지하고, #12 운영 회의의 마커 방향 결론, 후속 신호등·방지턱 제작 자료, 후방 마커 상세·검차 조건·상황별 패널티와 PDB 실물 핀아웃·정격을 확인합니다. 도로·잔디·타이어 마찰은 재질명만으로 추정해 넣지 않고 공식 수치 또는 실물 측정을 기다립니다. 이미 확인한 행사·지원 모델·높이 제한·후방 마커 의무를 다시 미확정으로 되돌리지 않으며, 남은 질문은 `docs/HARDWARE_AND_RULE_QUESTIONS.md`에서 관리합니다.
2. 하드웨어팀에서 실제 축거·윤거·안/바깥 최대 바퀴각·조향 중 점유 영역·질량/CG·서보/ESC/엔코더 응답을 측정합니다. 현재 차량 설정은 그 결과로 교체합니다.
3. 순간 스캔의 1차 갱신률 비교는 완료했습니다. 다음은 30 Hz 경로의 스캔 나이·제동 이탈 원인을 분리 계측하고, 순차 취득·엔코더/IMU 운동 보상·지연·결측을 같은 조건에서 비교하는 작업입니다. 공식 코스의 5~8 km/h 구간별 주행과 정지 차량/느린 앞차/cut-in의 TTC 검증은 별도입니다. 상부 C1과 낮은 전방 C1의 자기 가림·상대차 단면, ToF 한 개의 4×4·60 Hz/8×8·15 Hz를 실측합니다. 예산안 전에는 D435i·상부 C1·ToF 여섯 개 기준선을 유지하고, 이후 전방 스테레오+D435i 기준 `±65°` ToF 두 개부터 3·4·5개 배치를 같은 상대차 시나리오에서 비교합니다.
4. 공식 크기·벽 부착 ArUco를 기준으로 신호등·마커 인식을 다른 출발 위치·표지판 누락·다른 차량의 가림·노출·잡음 조건으로 확장합니다. 현재 데모는 임시 신호등 모양과 마커 ID별 벽 선택에 맞춘 최소 규칙이며, 고정 데모 순서와 실제 무작위 출발 절차를 구분합니다. 지름길의 연속 진입·합류도 별도로 검증합니다.
5. 현재 ToF의 정적 저상 표적 감속·정지를 실측 제동/지연·슬립 추정·상대속도 TTC로 보완하고, 느린 앞차 추종→cut-in·측면 접근 순으로 상대차 시나리오를 추가합니다. 경주선+Pure Pursuit/Stanley와 FTG는 같은 조건에서 비교합니다. 20 km/h 도달과 대회 트랙의 해당 속도 완주/안전은 별도 이정표입니다.
6. ESC, 엔코더, 정확한 ESP32 보드와 Jetson 통신 방식을 선택한 뒤, 기존 토픽 인터페이스에 맞는 실제 하드웨어 어댑터를 구현합니다.
   - 단일 모터·기계식 차동장치 방침에 맞춰 전원 보드/ESC 연결, 전체 감속비·허용 토크·차동기 종류를 확인합니다. 엔코더는 좌우 뒷바퀴 두 개 방향을 유지하고 허브/반축 상세와 분해능을 정합니다. 토크 기반 모델은 구현됐지만 실제 부품 응답·반사 관성·백래시·타이어 보정은 후속입니다.
7. 보유 D435i의 실제 스트림 조합·USB 연결·보정값·IMU 리비전을 조회하고, 노출·거리별 오차·지연을 측정합니다. 시뮬레이션의 지속적인 RGB-D·점군 처리율과 실물의 고속 처리 성능도 별도로 검증합니다.

## 문서 운영 원칙

- 프로젝트 설명과 인수인계 문서, 활동 내역, 결정 기록은 한국어를 기본으로 작성합니다. 필요한 전문 용어는 영문을 병기하되, 실행 명령어·코드 식별자·경로·ROS 토픽·메시지 형식·설정 키는 유지합니다.
- 이번 한국어판은 복구된 영문 문서에서 새로 번역했습니다. 앞서 작성된 번역본이나 그 백업은 참고하지 않았습니다.
- 번역과 문서 운영 원칙 추가는 별개의 작업입니다. 기존 기술 결정, 수치, 검증 결과와 미확정 사항은 번역 과정에서 바꾸지 않습니다.
- 주최 측 원본 트랙 자료는 번역 대상에서 제외하며, 한국어 문서와 같은 내용의 영문 문서를 별도로 중복 관리하지 않습니다.
