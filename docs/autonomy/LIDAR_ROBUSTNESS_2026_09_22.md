# C1 거리 오차·입력 지연과 지역 Pure Pursuit 내성

날짜: 2026-09-22. 상태: **재개 검증 완료.** 결합 두 바퀴의 노면 감사, 고정 ±3 cm·80 ms 지연·무주입 각 12 m, 300 ms 지연의 보호층 출발 거부, 전체 회귀 277개를 확인했다. 아래 장애·초기화 실패 기록은 보존한다.

## 범위

사용자 요청에 따라 현재 B0183+C1·별도 6축 IMU·후륜 엔코더의 지역 Pure Pursuit 제어기를 유지한 채 거리 오차와 입력 지연을 우선 검증한다. 장착 위치·방지턱·상대 차량 회피/추월은 이번 범위 밖이다. 회피·추월은 주말에 검토하고 싶다는 사용자 의향만 기록하며 예약 실행을 만들지는 않는다. 기존 원본·다른 센서 모드·과거 실패 기록·다른 작업의 수정은 보존한다.

후속 사용자 요청으로 우선순위가 갱신됐다. [센서 내성·Jetson 계획](../reports/SENSOR_ROBUSTNESS_AND_JETSON_PLAN_2026_09_22.md)에 따라 IMU·엔코더·시간 정렬의 내성을 먼저 검사하고 Jetson 검증을 병행한다. 다중 차량 추종·정지 차량 우회는 이후, 이동 차량 추월·고속화는 후순위다. 위 주말 의향은 이전 대화 이력이다.

이번 비교에서 바꾼 오차는 LiDAR뿐이다. IMU의 기존 임의 백색잡음(각속도 표준편차 0.001 rad/s·가속도 0.01 m/s²), 엔코더의 2048틱/회전·100 Hz·설정 지연 2 ms·누락 0은 고정했다. 9/8에 자이로 편향·바퀴 배율·시각 오차의 합성 기하 검사를 수행한 이력은 있으나, 해당 조건의 코스 폐루프 검증과는 다르다.

## 제조사 수치와 시험 가정

[SLAMTEC 공식 한국어 사양](https://www.slamtec.com/ko/c1/spec)을 9/22 확인했다. 측정거리오차는 **±30 mm**, 거리측정 분별력은 15 mm이며 둘은 다른 항목이다. 공개 사양표만으로 오차의 확률분포·표준편차·각도/시간 상관·개별 센서 바이어스를 확정할 수 없다. 따라서 ±30 mm를 Gaussian 표준편차 30 mm로 바꾸거나 15 mm를 UART 출력의 반올림 간격이라고 가정하지 않는다. 제조사 PDF 링크의 열람은 시간 초과/접근 거부로 끝났으며 PDF 각주 조건을 확인했다고 표현하지 않는다.

시험용 가정은 다음과 같이 구분한다. 지연값은 실측 C1 통신 지연이 아니라 제어기 스트레스 조건이다.

| 조건 | 목적 |
|---|---|
| 점별 균일분포 −3~+3 cm | 명시 범위 안에서 점마다 흔들리는 경우 |
| 전체 거리 +3 cm / −3 cm | 평균을 내도 사라지지 않는 편향 |
| 추가 지연 80 ms | 원래 회전 취득 100 ms 외 전송 지연 |
| ±3 cm + 50±20 ms 지연 | 다른 난수 seed에서 오차/지연 결합 |
| 추가 지연 300 ms | 오래된 입력이 들어오면 주행을 거부하는 보호 조건 |
| 표준편차 3 cm Gaussian | ±3 cm를 초과할 수 있는 별도 강한 진단 조건; 제품 사양 모델 아님 |

## 주입 방식과 판정

`config/tests/lidar_*.json`을 명시한 순차 취득 실행에만 적용한다. 원래 시간·각도별로 취득한 거리값에 **센서 원점 기준 방사 방향 오차**를 더하고, 회전 완료 후 스캔 발행을 지연한다. 취득 header/점별 간격을 현재 시각으로 고쳐 쓰지 않는다. 제어기와 독립 보호층 모두 같은 오차 스캔을 받으며 깨끗한 입력을 몰래 따로 쓰지 않는다. 후방 마스킹·기존 NaN/Inf 결측은 유지하고, 오차 때문에 유효 거리 밖으로 나간 점은 미관측 NaN으로 처리한다.

오차/지연 RNG는 명시 seed를 사용하나 Gazebo/ROS 전체 실행의 결정성을 보장하지 않는다. 시험 JSON·코드 ZIP·실제 주입 통계/지연·원래 순차 취득 감사·주행/정지/종료 보고서를 보존한다. ROS 추가 수신 지연은 주입한 지연보다 클 수 있으며 보정에는 실제 취득 시각을 사용한다. 기본 실행에서 JSON을 생략하면 기존 동작을 유지한다.

완주는 실제 정지·정상 종료와 분리해서 읽으며, 벽 겹침 외에도 노면 합집합과 차체 외형의 표본 감사를 수행한다. 과도한 지연 조건은 완주가 아니라 정지/비영 명령 억제가 기대 결과다. 정지 성공과 완주 실패를 구분하며 성공 기준을 사후에 완화하지 않는다.

300 ms 추가 지연은 첫 점 기준으로 한 바퀴 취득 100 ms까지 합쳐 최소 약 400 ms인 입력을 만든다. `summarize_lidar_robustness.py`의 별도 보호 판정은 초록 신호 인지 후 5초 이상 모든 표본에서 안전 명령 0·`stale_input`·실제 평면 속도 1 cm/s 미만·벽 겹침 없음과 주입/순차 취득/정상 종료를 요구한다. 기존 `report.json`의 완주 실패는 바꾸지 않는다. 시작부터 지연된 조건의 **출발 거부**이며, 달리던 차가 새 지연에 대응해 제동하는 동적 시험으로 표현하지 않는다. 별도 단위 검사에서는 주행 명령이 있던 보호층에 오래된 패킷이 새로 도착해도 명령을 0으로 바꾸는 것을 검사한다.

## 사전 계산

[v7 직선 벽 진단](../../artifacts/validation/2026-09-22/lidar_robustness/probe_v7/report.json)은 조건별 50개 seed를 사용했다. 무오차·균일 ±3 cm·고정 ±3 cm에서는 정지 0/50이었다. 균일 오차의 절대 조향 95백분위는 약 0.00609 rad, +3/−3 cm 편향은 약 0.03089/0.03202 rad였다. Gaussian σ=3 cm는 7/50 정지, 절대 조향 95백분위 약 0.1965 rad였다. 합성 정지 직선만으로 실제 급커브/폐루프 성공을 판단하지 않는다.

## 실행 결과

### 수정 전 재현

`uniform30_v7`은 48.6927 m 한 바퀴·실제 정지·정상 종료를 통과했다. 벽 겹침과 노면 밖 차체 면적 표본은 0이었으나 최고 6.03 km/h·코너 중앙값 2.77 km/h로 무오차 v7의 약 8.08/4.78 km/h보다 낮았다. 고유 제어 상태 표본에 `PATH_TOO_SHORT` 5개·`OFFSET_PATH_FOLDED` 3개·`WALL_SEGMENT_SHORT` 4개가 있었다. 이는 정지 사건 12회 또는 12회의 제어 주기를 뜻하지 않는다.

합성 직선에서 오차 점 사이의 지그재그 거리를 그대로 합치면 벽의 호길이가 부풀었다. 균일 ±3 cm 조건의 실제 관측 경로 길이 평균은 0.627 m, 목표 속도 평균은 1.02 m/s로, 무오차의 1.874 m/2.16 m/s보다 줄었다. 관측 벽 1.8 m 예산을 너무 일찍 소진하는 현상이다.

### 수정 과정과 보존한 실패

1. 연결된 벽 안에서 호길이 계산용 좌표에만 7점 이동평균을 적용했다. 원시 관측으로 벽을 적합하고 안전층은 원시 오차 점을 그대로 사용한다.
2. 첫 안은 **73개 회귀 통과·2개 실패**였다. 과거 코너를 지나친 정지 자세에서 전진 명령이 생겼고, 기둥 옆 반대 벽 대체 판단도 바뀌었다. 이 안으로 Gazebo 주행은 하지 않았다.
3. 모든 벽을 평활화하지 않도록 수정했다. 중간점에서 양옆 점을 잇는 현까지 수직 잔차의 중앙값이 3 mm를 넘는 연결 구간만 호길이 측정 좌표를 평활화한다. 깨끗한 벽과 소수의 실제 모서리는 원래 호길이를 유지한다. 3 mm·7점은 이번 제어기 설계값이며 C1 제조사 사양이 아니다.
4. 관측 밖 외삽·벽 사이 연결·실제 점 삭제는 하지 않으며, 경로 접힘 검사·최대 입력 나이·독립 보호층·속도/제동 상한은 완화하지 않았다.

### 후속 배치 범위

수정안을 고정하고 균일 ±3 cm+50±20 ms 추가 지연(seed 23)은 공식 코스 두 바퀴, 일정한 ±3 cm 편향·추가 80 ms 지연·무주입 대조군은 각각 12 m 구간, 300 ms 지연은 출발 거부를 검사한다. **12 m 결과를 본선 완주나 모든 코너 검증으로 승격하지 않는다.** 실패 시 뒤 조건을 자동으로 밀어붙이지 않고 원인을 검토한다. 결과는 각 실행의 `report.json`·`road_audit.json`·`robustness_summary.json`에 보존한다.

결합 두 바퀴에는 고유 상태 표본 `PATH_TOO_SHORT` 7개·`WALL_SEGMENT_SHORT` 1개·`OFFSET_PATH_FOLDED` 1개가 남았다. 위험한 관측을 억지로 경로로 만들지 않고 일시 감속/정지하는 동작이며, 모든 순간의 경로 생성이 안정화됐다고 표현하지 않는다. 보호층 표본은 `clear` 630·`lidar_braking` 96개였다. 실행 전체에서 발행된 781개 스캔의 실제 추가 지연은 **32~70 ms**, 오차 RMS 1.734 cm·최대 절대값 3 cm 이내였다. 지연 주입 및 순차 취득 감사는 통과했다. 제어 상태의 유효 관측 나이 최댓값은 258 ms였다.

고정 편향 두 실행의 고유 제어 상태는 각각 `RUNNING` 42/44표본이었다. 80 ms 지연에서는 `RUNNING` 49·`WALL_SEGMENT_SHORT` 1표본이며 유효 관측 나이는 최대 277 ms였다. 무추가 지연의 약 198 ms, 결합 지연의 258 ms와 구분한다. 이 값은 **운동 보정이 유효하다고 판정한 상태 표본에서 첫 점 취득 이후 지난 시간**으로, 제품의 전송 지연 자체나 모든 제어 주기의 최대 지연은 아니다. 회전 취득 시간과 다음 스캔을 기다린 시간도 포함한다.

### 과도한 지연: 경로 계산과 구동 허용의 구분

기존 경로 제어기/운동 보정의 입력 나이 제한은 **450 ms**, 독립 LiDAR 보호층의 제한은 **300 ms**다. 이번에 어느 쪽도 늘리지 않았다. 300 ms 추가 지연 시험에서는 이미 약 400 ms 지난 스캔이 들어오기 때문에 보호층은 항상 차단하지만, 경로 제어기는 일부 스캔으로 명령을 계산할 수 있다. 실제 고유 제어 상태는 `RUNNING` 22·`SENSOR_STOP` 49표본, 운동 보정이 받아들인 관측 나이는 최대 417 ms였다. 따라서 제어기까지 7.074초 내내 `SENSOR_STOP`이었다고 표현하지 않는다.

이 시험에서 확인한 것은 **경로 제어기의 명령이 있어도 독립 보호층이 오래된 관측을 차단한다는 것**이다. 최종 `/drive/safe`는 71표본 모두 0이고 실제 차량도 출발하지 않았다. 이는 두 계층이 동일한 신선도 판단을 한다는 검증이 아니며, 이 구성에서 보호층을 생략하거나 `/drive/safe`에 직접 명령을 보내면 안 된다. 시작부터 지연을 적용했으므로 주행 중 지연 급증 시의 정지거리도 아직 확인하지 않았다. 다음 지연 시험은 정상 주행 중 지연/패킷 손실을 시작하고 실제 정지거리와 재출발을 확인하는 것이 적절하다.

### 실행 환경 장애와 재개 경위

두 바퀴 종료 후 WSL 감사 명령을 요청했으나 승인 서비스가 `502 Bad Gateway`를 반환해 명령 자체가 시작되지 않았다. 같은 승인 경로로 한 번 더 요청해 동일 오류를 확인하고 추가 WSL 실행을 멈췄다. 승인을 우회하거나 기존 프로세스를 다시 띄우지 않았다. 완료한 주행 결과는 유지한다.

허용된 Windows 로컬 Python으로 `robustness_summary.json`은 생성했지만 `shapely`가 없어 기존 노면 감사는 실행하지 못했다. 작업 공간의 무시되는 시험 의존성 폴더에 Shapely 설치도 시도했으나 배포본을 구하지 못했다. Windows에는 `pytest`도 없어 전체 회귀 실행을 대체하지 않았으며, 결과 집계의 독립 assert 두 건만 직접 실행해 통과했다. 일부 pip 임시 폴더 정리 경고가 있었으며 사용자 데이터나 기존 산출물을 삭제하지 않았다.

중단 당시 재개 순서는 기존 두 바퀴의 노면 감사 → 미실행 조건 → 전체 회귀였다. 당시 관련 회귀 89개만 통과한 상태였고, 추가한 두 과주행 잡음 회귀는 정지 스캔 50 seed 진단으로 같은 조건만 검사했다. 이전 전체 252개를 이번 전체 회귀 통과로 승계하지 않았다.

사용자 재개 요청 후 주 에이전트의 **정식 추가 승인 경로**로 실행 확인과 노면 감사가 통과했다. Luna 측 검토 서비스 연결은 계속 실패해, 주 에이전트가 한 번의 승인으로 순차 배치를 시작하고 Luna가 실행 대기·결과 수집을 맡았다. 승인 검사를 우회하거나 권한 정책을 변경하지 않았다. `resume_v8` 시작 전 전체 Python/ROS 회귀 **276개**를 새로 통과했다.

세 조건(+3 cm·−3 cm·80 ms) 통과 뒤 무주입 대조 `resume_v8_clean`은 `malformed launch argument 'lidar_test_profile:='`로 시뮬레이터 시작 전 실패했다. 선택 인자의 빈값을 ROS CLI로 넘긴 검사기 오류다. 주행/센서 표본이 없고, 정상 종료 감사도 실패한 초기화 실패를 그대로 보존한다. `start_demo_process`가 빈 `lidar_test_profile`/`runtime_artifacts`를 생략하도록 수정하고 빈값·공백 포함 경로 회귀를 추가했다. `resume_v8_remaining`에서 전체 **277개 회귀 통과** 후 clean/300 ms만 새 출력 폴더에서 검증했다. clean은 주행·정지·종료를, 300 ms는 별도 출발 거부·정상 종료를 통과했다. 이미 통과한 편향·80 ms 주행은 반복하지 않았다.

이후 모든 실행 프로세스의 종료를 확인했다. 설계·수정·판정은 주 에이전트가, 배치 실행 대기·결과 수집은 Luna가 맡았다. GitHub 게시·새 영상·컴퓨터 종료는 이번에 수행하지 않았다.

주행 알고리즘 자체는 `uniform30_v8`·`combined_v8_two_laps`에서 사용한 `local_path.py` SHA-256 `96c270c0a58f2ae517e17ea5d9f3c624402ee57f3c94423abdcd7dc42595c24e` 그대로다.

### 저장된 커브 스캔의 오차 검사

`recorded_corner_noise_v8_verified`는 이전 네 정지 스캔에 균일 ±3 cm를 더한 50 seed씩의 비교다. v7/v8 모두 도달 가능한 `v2` 커브는 50/50 경로를 생성하고, 이미 과주행한 `v3`/`v5` 자세는 각각 50/50 정지했다. 기둥 옆 `v6_repeat2`도 두 버전 모두 50/50 경로를 생성했다. 정지 스캔의 명령 계산일 뿐 실제 궤적·제동·충돌 검증은 아니다.

초기 임시 계산에서 유효 거리 밖의 점을 걸러내지 않아 `v5`에 잡음이 있으면 전진한다고 오해할 수 있는 결과가 나왔다. 실제 입력 처리와 같은 최소/최대 유효 거리를 적용해 재검사하니 두 버전 모두 정지했다. 이 임시 결과를 실주행 실패로 사용하지 않는다. 감사 도구 첫 저장은 상대 경로 처리 오류로 실패했으며 절대 경로로 고친 뒤 위 별도 출력에 코드·입력·결과를 보존했다.

## 남는 제한과 실행 기본값

- 이번 개선은 **거리 오차 때문에 과장된 벽 길이 계산**을 완화한다. 편향을 자동으로 교정하거나 원래 측정하지 못한 공간을 복원하는 기능이 아니다. 고정 ±3 cm 직선 진단의 조향 변화가 남는 것도 정상이다.
- 공식 제조사 수치의 전체 실험 조건·확률분포를 재현한 센서 모델이 아니다. 검은/반사 표면, 유리, 모서리 혼합 반사, 각도별/시간별 상관 잡음, 패킷 손실, Jetson 처리시간, 시계 오프셋, 실제 서보/엔코더 오차는 이 테스트 결과로 해결됐다고 보지 않는다.
- 거리 오차와 원래 순차 취득에 추가한 지연만 바꿨다. IMU·엔코더·타이어·제동·질량은 기존 가정이다. 동일 seed도 실제 이동 위치가 달라지면 같은 실제 장면의 반복 측정은 아니다.
- `local_pursuit`는 개선된 경로 계산을 쓰지만 기본 실행의 `lidar_test_profile`은 빈 값으로 유지한다. 오차 조건을 시험하려면 JSON을 명시한다. 기존 단순 LiDAR/스테레오 모드의 제어기는 교체하지 않았다.
- 9 km/h 명령 상한을 유지한다. 이번 시험으로 20 km/h, 모든 출발 슬롯, 전후방 저상 상대차, 회피/추월, 방지턱, 실물 안전을 검증한 것은 아니다.
- 다음 실제 센서 연동에서는 벽에 정지한 거리값의 평균/흩어짐과 측정 시각부터 확인해야 한다. 이번에는 하드웨어 설치나 현장 시험을 요구하지 않고 제어기 측 검증만 수행한다.
