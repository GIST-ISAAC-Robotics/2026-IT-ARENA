# B3 출발 신호·정지·재개 계약 후보

2026-10-13. **기본 미전환인 선택형 시험 후보**다. 픽셀 후보의 제한 ROS 연결과 진단 좌표의 정적 렌더링 검출은 확인했다. 공식 원위치 시야 부적합·실물 영상·동적 점등·경기 운영 재개 절차는 남으며, 렌더링 시험은 Gazebo 종료 실패 때문에 전체 실패다. G1 왼쪽 실패와 종료 오류를 이 작업으로 해결한 것으로 표시하지 않는다.

## 1. 출처와 확인한 차이

10/12 [공식 자료 보고서](../reports/OFFICIAL_UPDATE_2026_10_12.md)의 고정 커밋 `b27f94730b869837a804a3088447103d6b35b87e`에서 [traffic_light.py](https://github.com/MOSW626/istech-it-arena/blob/b27f94730b869837a804a3088447103d6b35b87e/track/output_final/traffic_light.py), [제작 사양 댓글](https://github.com/MOSW626/istech-it-arena/issues/3#issuecomment-6077787556), [Arduino 원문](https://github.com/MOSW626/istech-it-arena/issues/3#issuecomment-6077789894)을 10/13 읽기 전용으로 다시 대조했다. 댓글 수정 시각은 각각 10/9 18:07:07·18:00:29 KST다. 이후 main 전체 변경을 다시 감사한 것은 아니다.

공식은 왼쪽부터 빨강 네 세트·초록 한 세트다. 각 세트는 위아래 두 광원이며 발광면 15 mm 표현의 단위와 실물 설치 높이/방향은 여전히 미확정이다. 출발 때 빨강이 꺼지며 초록이 켜지고 5초 후 초록도 꺼진다. 랜덤 대기시간은 시험 입력 생성에만 쓰고 검출기에 출발 시각·UDP·신호 상태를 공급하지 않는다.

기존 `StartSignal`은 팀 임시 빨강–노랑–초록 모델의 지름 52 mm·빨강에서 초록까지 210 mm 비를 하드코딩한다. 공식 4열 빨강의 마지막/가장 큰 후보를 잡으면 예상 초록 위치가 달라진다. 이것은 기존 임시 신호 주행이 잘못됐다는 뜻이 아니라 **새 배열 적합성이 없다는 뜻**이다.

합성 RGB에서 지름 5/8/12/20/28 px × 단일/쌍 광원, 중심 간격=지름×2인 10조건을 시험했다. 기존 검출기는 **출발 검출 0/10·오출발 0/10**이었다. 카메라 투영·광학·노출·실물 검증이 아니며 5 px 원은 기존 윤곽 면적 최소 조건에도 못 미친다. 실제 설치 거리에서 몇 px인지 아직 측정하지 않았다.

## 2. 시험 후보의 시각 판정

`OfficialStartSignal`은 기존 검출기를 바꾸지 않는 새 모듈이다.

1. 화면 상단에서 빨강 광원을 찾고 같은 x의 위아래 광원을 열로 묶는다. 네 열의 간격·크기·정렬이 확인된 **서로 다른 두 프레임**을 요구한다. 일부 빨강만 보이면 출발 준비로 확정하지 않는다.
2. 관측 열 간격으로 맨 오른쪽 다음 초록 위치를 계산한다. 특정 실물 mm 지름에만 의존하는 기존 비율 대신 실제 영상 배열을 쓴다. 예상 영역이 화면 밖이면 거절한다.
3. 빨강 후보가 사라진 뒤 그 영역에서 초록 광원이 **서로 다른 세 프레임** 확인될 때만 출발을 고정한다. 전체 소등·다른 위치 초록·바닥 잔디·빨강과 초록 동시 점등은 출발로 쓰지 않는다.
4. 시각 중복은 확인 횟수를 늘리지 않고, 되감기/무효 시각은 초기화한다. 확인 도중 0.35초 초과 프레임 공백·마지막 빨강에서 0.8초 초과 전환은 증거를 버린다. 두 값은 **후보의 임시 시간 계약**이며 공식 규정·실측값 또는 기존 보호 한도 변경이 아니다.
5. 출발 후 초록이 꺼져도 허가는 유지한다. 영상 유효성/입력 공백의 주행 정지는 별도 운영 보호가 계속 책임져야 한다. 이 모듈의 `started`는 센서 건강도나 현재 주행 허가가 아니다.

부분 가림, 너무 작은 광원, 배경의 유사 빨강 배열, 반사·노출·블러, 원근/회전, 실제 두 광원이 하나로 뭉치는 상황은 추가 검증 대상이다. 확인이 어려울 때 기다리는 정책은 오출발 위험을 줄이지만 그리드 가림으로 영원히 못 출발할 가능성도 있다. 이를 실차 안전 보증으로 부르지 않는다.

## 3. 경기 출발 허가와 일시 정지·명시 개입의 분리

`RacePermission`은 ROS 발행/MCU 서비스 호출이 없는 순수 계약 참조다. 실제 노드가 보고한 건강 상태·신선도·세대와 연결하기 전 기본 동작을 바꾸지 않는다.

| 사건 | 시험 후보 동작 | 운영 적용 전 조건 |
|---|---|---|
| 처음 부팅/새 경기 | 시각 출발 허가 없음. MCU ARM만으로 출발 불가 | 픽셀 검출과 race/vision 세대 연결 |
| 신선한 해당 경기의 시각 출발 확인 | 출발 사실 고정 | 타이머/UDP가 아닌 영상 판정의 실제 출처 감사 |
| 센서 일시 누락·G1 HOLD | 0 요청, 출발 사실은 유지. 입력/관측 정상화 뒤 다시 허용 | 기존 A4의 자동 복구 정책을 보존하되 MCU가 고정 고장 상태면 별도 해제 |
| 명시 STOP·영상 프로세스 고장 | 개입 번호 증가, 허가 차단 고정 | 하위 MCU 정지와 실제 정지는 별도 확인 |
| 위험 제거 + 사람의 명시 검토 | **현재 경기·개입 번호**가 맞는 해제만 수락 | 늦게 도착한 이전 해제가 새 STOP을 풀지 못해야 함 |
| 해제 완료 | MCU 미준비·센서 미준비면 계속 불허 | 이 계약의 해제가 CLEAR/ARM을 대신하지 않음 |
| 새 경기 / 시계 되감김 | 과거 시각 출발 허가 폐기. STOP을 자동 해제하지 않음 | 운영 reset과 명시 새 경기 명령의 관계 정리 |
| 프로세스 재시작 | 기억 복원 없이 최초 대기 상태 | 중도 복구를 위한 출발 사실 보존/운영 확인은 후속 설계 |

**미채택 정책 선택:** 같은 프로세스/같은 경기에서 이미 출발한 뒤 명시 STOP이 걸렸다면, 사람의 명시 해제와 MCU 재허가 후 최초 신호등을 다시 보지 않고 재개하는 후보를 시험한다. 이는 공식 심판의 재출발 허가를 대신하지 않는다. 현행 `CLEAR → DISARMED → 별도 ARM` 경계와 사람이 개입할 경기 운영 절차를 맞춘 뒤 연결해야 한다. 해제 확인에서 모터 평균 0을 차체 정지의 증명으로 쓰지 않는다.

## 4. 검증과 다음 연결 조건

운영 `StartSignal`, `/drive → 보호 → /drive/safe → MCU`, 트랙·임시 신호등은 그대로다. 후보 순수 함수/상태 시험과 기존 영상 회귀 **105개 통과**를 확인했다. 8/12/20/28 px 단일/쌍 배열은 출발하고 5 px 원은 면적 부족으로 거절했다. 중복·되감기·시간 공백, 녹색만/무관 녹색/부분 빨강/전체 소등, STOP·이전 경기/개입 해제 거절을 포함한다. 결과는 [산출물](../../artifacts/validation/2026-10-13/race_start_v1/README.md)에 정리한다.

후속으로 `VisionPipeline(signal_mode='official_4red_candidate')` 선택 인자와 모드 일치 검사를 추가했다. 기본은 `temporary_3light`이다. 실제 노드에는 명시적인 `start_signal_mode` 인자를 추가하되 새 모드는 `vision_execution=process`일 때만 허용한다. 기본 launch가 후보를 자동 선택하지 않는다. 자식 결과는 기존 세대·sequence·촬영/수신 시각·처리 watchdog을 통과한 뒤에만 부모 상태로 채택한다. 별도 [v2 회귀 124개](../../artifacts/validation/2026-10-13/race_start_v2/README.md)에서 실제 spawn/공유 버퍼 왕복·정상 종료, 초기화 중 이전 초록 결과 거절·모드 불일치 고정 고장·기본 동작 보존을 확인했다. `RacePermission`은 이 영상 선택 인자와도 아직 연결하지 않은 순수 정책 후보다.

### 4.1 픽셀 크기·열화 탐색

`validate_official_start.py`는 현재 B0183 설정의 1280×720·수평 75°에 **한 광원 15 mm·열 간격 30 mm·위아래 중심 간격 20 mm라는 시험 가정**을 투영했다. 실제 설치 거리/기구가 아니라 4배 해상도에서 축소한 합성 원이다. 광학 왜곡·센서 잡음·포화·실물 LED 밝기는 재현하지 않았다. 처리 간격 10 Hz는 이 검사 조건이며 카메라 최대 FPS를 뜻하지 않는다.

| 조건 | 결과 | 해석 |
|---|---|---|
| 가정 거리 0.5/1/1.5/2 m, 단일/쌍 광원 | 모두 출발 판정 | 검출 지연 약 0.2 s는 세 프레임 확인 규칙의 결과 |
| 가정 거리 2.5/3/4/6 m | 모두 미출발 | 픽셀 크기·윤곽 최소 조건 한계. 실제 인식 거리로 확정 불가 |
| 1 m, 가우시안 흐림 σ=1/2 px 또는 밝기 ×0.8 | 출발 판정 | 이 단순 열화 조건에서만 확인 |
| 1 m, 밝기 ×0.6 | 미출발 | 현행 절대 밝기 문턱의 한계. 자동 문턱 완화는 하지 않음 |
| 초록만/전체 소등/한 열 가림/빨강·초록 동시/엉뚱한 초록 위치 | 5개 모두 미출발 | 해당 합성 음성 사례이며 일반 오출발률 아님 |
| 1920×1080, 가정 3 m 진단 | 출발 판정 | 해상도 영향 탐색일 뿐 기본 해상도 변경 없음 |

26개 조건에서 조기 출발은 없었다. 필수 근거리 4개와 음성 5개만 사전에 합격 조건으로 두었으며 나머지 탐색 결과는 `passed=null`로 보존한다. 탐색 미검출을 합격으로 바꿔 표현하지 않는다. 관련 생성기 회귀는 3개다. [원시 요약](../../artifacts/validation/2026-10-13/race_start_v2/stress.json)에 처리 시간도 있으나 PC 합성 연산이며 Jetson 처리율 보장은 아니다.

### 4.2 선택형 실제 ROS 처리 경로

`validate_pipeline_faults_ros.py --scenario start_contract --signal-mode official_4red_candidate`로 픽셀→별도 영상 프로세스→제어기→독립 보호→가상 MCU→출력 보호를 연결했다. 신호 상태/타이머를 제어 입력으로 쓰지 않았다. 이 시험은 기존 신호 모드의 전체 A4 고장 행렬을 다시 수행한 것이 아니다.

첫 실행은 사전 회귀 161개와 12사례가 통과한 뒤, 주행 중에 ‘정지 상태의 무재개 검사’를 시작해 시험기 전제 오류로 중단됐다. 실패 당시 모델은 주행 중이었으며 최종 STOP 완료로 표시하지 않는다. 이후 소유 프로세스는 정상 정리됐다. [v1 실패](../../artifacts/validation/2026-10-13/race_start_ros_v1/README.md)를 보존하고 **제어기 종료→보호층 정지 확인→재시작**으로 시험 순서를 수정했다. 실패 경로에서도 정리 전에 별도 STOP을 시도하고, STOP 실패를 원래 오류와 함께 기록하도록 했다.

수정 후 회귀 **163개**, ROS **20/20사례** 통과다. 초록만/부분 빨강/초록 없는 소등에는 대기하고, 전환 출발·초록 소등 후 유지·영상 단절 정지/복구를 확인했다. 제어기 재시작 뒤에는 새 빨강→초록을 요구한다. 명시 STOP은 고정되고 CLEAR 후 DISARMED를 유지하며 별도 ARM 후 재개한다. 최종 STOP·신선한 출력 0·가상 모델 정지·단일 ROS 그래프·정상 종료·잔존 0·소스 해시 일치를 각각 확인했다. [v2 결과](../../artifacts/validation/2026-10-13/race_start_ros_v2/README.md).

상한 0.6 m/s·±2 m/s² 임시 종방향 모델의 직선 센서 시험이며 실제 제동/전체 코스/실물 신호 인식 결과가 아니다. MCU 마감 진단 목록은 비어 있으므로 ‘지연 없음’으로 해석하지 않는다. 순수 `RacePermission`은 미연결이며 새로운 운영 복구 정책 전체가 통과한 것도 아니다. 공식 모델의 그리드 시야·실물 노출 확인은 남는다. 기본 전환은 별도 검토하고 G1 실패도 유지한다.

## 5. 공식 SDF의 그리드 시야: 별도 기하 제약

동일한 공식 고정 커밋의 `scene.json`/`world.sdf`를 읽기 전용으로 받아 [기하 산출물](../../artifacts/validation/2026-10-13/race_start_geometry_v1/README.md)에 바이트·URL·해시를 보존했다. 기존 ZIP이나 운영 월드는 바꾸지 않았다. `audit_start_signal_geometry.py`는 공식 그리드 6개, 현행 B0183의 1280×720·수평 75°·장착 높이 0.145 m·수평 자세를 사용한다. base z=0 핀홀 가정이며 현가/차체 자세·광학 왜곡·다른 차량/벽/판의 가림은 제외한다.

- **공식 원위치에서는 6그리드 모두 광원 5개가 화면 위쪽 밖이다.** 중심 v 좌표는 약 −801~−31 px이며 화면 상단은 0이다. 명목 램프 높이 1.08 m와 가까운 그리드의 관계 때문이며 검출 문턱 문제가 아니다. 실물 설치 높이는 미확정이므로 실물에서도 실패한다는 결론은 아니다.
- 다섯 광원의 중심축은 이 구간 차량 진행 방향과 거의 평행하다. 따라서 ‘좌우로 4빨강+초록이 보인다’는 합성 배열과 다르다. 열 순서만 따졌을 때 좌우 그리드에 따라 방향도 바뀌며, 광원 간 투영 간격이 압축된다.
- 높이만 0.30 m로 낮춘 **진단 좌표**는 6그리드 모두 화면 안으로 들어오지만 배열 문제는 남는다. +90° 회전만 하면 높이 문제는 그대로이고, 높이까지 바꾸면 화면 안에는 들어와도 초록이 왼쪽이 된다. 회전 부호도 중요하므로 막연히 ‘90도 바꾸면 완료’라고 하지 않는다.

위 진단은 원인 분리를 위한 좌표 계산이지 실물 신호등/카메라 장착 변경의 채택이 아니다. 정확한 설치 높이·발광면 단위·진행 방향에서 본 빨강/초록 순서를 팀/공식 시공 자료와 대조해야 한다. 실제 그리드 시야가 확인될 때까지 공식 원위치와 조정한 시험용 배열의 결과를 분리하며, 시뮬레이터 신호 상태를 제어기에 전달해 이 문제를 우회하지 않는다.

후속 [회전 부호 대조](../../artifacts/validation/2026-10-13/race_start_geometry_v2/README.md)는 동일 원문을 재사용했다. 회귀 6개 통과, **−90°+z=0.30 m 진단 좌표**는 6그리드 모두 화면 내부·왼쪽 빨강/오른쪽 초록 조건을 만족했다. 여전히 가림/검출 성공은 아니며 운영 배치에 반영하지 않았다. 다음 제한 검사는 이 진단 배열에서 가까운/먼 두 그리드의 정적 off/빨강4/초록 영상을 Gazebo로 얻어 RGB 재질을 본다. 단계별 정적 영상을 재생하는 검사이며 실제 점등 전환 지연이나 전체 트랙/차량 가림의 재현이 아니다.

### 5.1 정적 재질 영상은 검출, Gazebo 종료는 실패

`validate_start_signal_render.py`는 위 진단 좌표의 공식 단일 구형 광원 위치/크기를 복사해 격리된 여섯 장면(가까운 grid 2·먼 grid 3 × 소등/빨강4/초록)을 생성했다. 현재 B0183 해상도/시야각을 사용하되 트랙·하우징·다른 차량은 없다. 소프트웨어 렌더링 설정은 해당 자식 프로세스에만 적용했다. **실제 점등을 녹화한 것이 아니라 각 정적 상태에서 얻은 RGB를 재배열하고 새 0.1초 간격 시각을 부여한 검사**다. 원래 촬영 시각도 따로 보존했다.

### 회귀 범위 정리

여기까지 전체 회귀는 1,566개 통과·1개 실패였다. 실패는 G1 평가기에 추가한 선택형 판단 기록 옵션의 해시 변경을 기존 후속 계약에 등록하지 않은 것이었다. 원래 `physics_step`/`scheduled_command_r0~r7` 계약을 수정하지 않고 `follow_trace_r0_sha256.json`을 새 연결로 추가했다. 기존/신규 해시·부모 계약 해시·변경 이유를 명시하고 관련 회귀 **64개 통과**를 확인했다. 전체 실패 로그는 `race_start_ros_v2/full_regression.log`, 후속은 `contract_regression.log`다. 검사 삭제나 현재 해시에 맞춘 기존 물리 시험 결과의 소급 변경은 하지 않았다. 이 정리는 물리 비교의 새 승인이나 G1 실패 해결이 아니다.

뒤이은 G1 후보/고정 관측 시험까지 포함한 [전체 회귀](../../artifacts/validation/2026-10-13/g1_candidate_regression_v1/README.md)는 **1,610개 통과**다. ROS 시험기의 소스 목록에 import되는 `local_follow`·`boundary_evidence`·`scene_motion`·`local_scene`·`follow_trace`도 추가하고 정적 import 포함 회귀를 뒀다. 앞선 B3 실행은 G1 비활성 조건의 결과이며, 당시 목록/스냅샷을 전체 의존성 보존으로 확대하거나 새 목록으로 덮어쓰지 않는다. 현재 목록은 후속 실행부터 적용하며 동적 문자열 import·외부 라이브러리 전체의 재현성 보증은 아니다.

## 7. 10/23 — 출발·대기·정지·재허가와 A1 수신기의 결합

부품/설계가 없는 동안 진행한 기록 도구 보충은 마감하고, 출발 정책과 구동 허가가 서로 어긋나지 않는지 격리 시험으로 확인했다. 사용자의 마감 요청에 따라 이 결합 검증까지만 수행한다. **운영 제어기의 연결 변경이나 자동 재출발 정책 채택은 아니다.**

### 7.1 방법과 범위

[`test_race_actuation_contract.py`](../../tests/test_race_actuation_contract.py)는 실제 `RacePermission`, 공식 배열의 합성 RGB를 처리하는 `VisionPipeline`/`recognize`, Python 참조 A1 `ActuationReceiver`를 함께 호출한다. 영상은 동기 시험 작업자로 처리하고, 엔코더는 신선한 고정 0카운트다. 단일 모터축 28카운트·15:1·65 mm와 기존 명령 만료/피드백/고장 조건은 그대로다. 카메라 촬영→수신 1 ms·영상 간격 100 ms·MCU tick 10 ms는 **시험 가정**이며 실측값이 아니다.

관련 **131개(새 결합 13개+기존 118개) 통과**, 실행 중 소스 불변을 확인했다. 당시 전체 회귀 4,656개와 범위가 겹치므로 합산하지 않는다. 초기 [v1 실패](../../artifacts/validation/2026-10-23/race_actuation_v1/README.md)는 촬영/수신을 같은 시각으로 구성한 시험의 부동소수점 차이 때문이었다. 운영 미래 시각 거절 조건을 유지하고 합성 촬영 시각만 명시적으로 1 ms 앞당겼다. [v2 결과·소스](../../artifacts/validation/2026-10-23/race_actuation_v2/README.md).

### 7.3 새 경기 초기화에서 확인한 결합 반례

`RacePermission.new_race()`만 초기화하고 영상 검출기를 그대로 두는 **잘못된 시험용 조합**에서는 이전 경기의 `VisionPipeline.signal.started=true`가 남는다. 이 상태에서 새 경기의 전체 소등 프레임을 처리해도 과거 출발 사실이 새 경기의 확인으로 전달될 수 있었다. 개별 모듈은 각자의 계약대로 동작하지만, 호출자가 경기/영상 초기화를 따로 수행하면 문제가 생기는 반례다. 현행 운영 경로에 이 조합을 연결하거나 실제 오출발을 재현한 것은 아니다.

별도 시험에서는 **STOP → 경기 허가와 영상 상태를 함께 초기화 → 이전 영상 작업 결과 거절 → 새 빨강/초록 시퀀스 요구**를 적용했다. 상위 명시 해제와 MCU CLEAR·ARM을 끝내도 초록만으로 새 경기 출발은 성립하지 않았고, 새 시퀀스 확인 후에만 양수 목표가 허용됐다. 이 순서는 시험용 연결 후보이며 기본 동작을 바꾸지 않는다.

### 7.4 다음 작업의 경계

다음 재개에서는 같은 단위 사례를 늘리기보다 **새 경기/명시 해제의 단일 호출 지점, 영상·경기 세대의 함께 갱신, 실제 MCU 상태 확인**을 운영 연결 후보로 설계한다. 신호를 다시 보지 않는 같은 경기의 명시 재개와, 새 시퀀스가 필요한 새 경기를 구별해야 한다. 독립 보호를 유지한 선택형 ROS 연결에서 출처·고정 상태·종료를 확인한 뒤 기본 채택 여부를 판단한다. 사람의 재개 승인 절차, 공식 설치 시야, 실물 입력/제동과 G1 실패는 별도로 남는다. 이번 작업에서는 이 후속 구현/ROS 시험을 시작하지 않았다.
