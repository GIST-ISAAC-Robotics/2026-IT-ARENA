# 경기 모니터·세이브포인트 재개·사건 기록 계획

**상태: 설계만 작성, 아직 구현하지 않음.** 11/1 최종 회의와 사용자 요청을 반영한다. [공식 확인 범위](../reports/OFFICIAL_UPDATE_2026_11_02.md), [전체 우선순위·기능 완성 기준](../DEVELOPMENT_PLAN.md), [현재 사용 가능한 B3 CLI](RACE_OPERATOR_RUNBOOK.md)를 함께 본다. 아래 버튼·화면을 기존 도구에서 이미 쓸 수 있다는 뜻이 아니다.

## 1. 필요한 만큼만 만든다

노트북 브라우저에서 Jetson의 작은 웹 화면을 열고, Jetson 안의 운영 어댑터가 기존 경기 상태/명령·MCU 정지 경로에 연결하는 방식이면 된다. Wi-Fi로 센서 연산이나 조향을 노트북에 옮기지 않는다. 새 관제 서버·클라우드·지도 화면·원격 운전은 필요하지 않다. 실제 공용 AP에서 두 기기의 직접 통신이 허용되는지는 현장에서 확인한다.

첫 구현의 화면은 아래로 제한한다.

| 화면/조작 | 필요한 정보·동작 |
|---|---|
| 상태 | 신호 대기 / 주행 / 일시 양보·정체 / 운영자 STOP / 복구 준비 / 재개 가능 / 입력·구동 고장. 경기 번호와 설정 이름 표시 |
| 속도 | 계획 속도·보호 후 속도·MCU 적용 목표·**모터축 환산 속도**. 실차 차체 속도로 오표기하지 않음 |
| 센서 | C1/RGB/IMU/엔코더 갱신 시각·입력 나이·오류, 앞차 거리/접근 추정, 현재 주행/감속 이유. RGB 작은 미리보기는 선택형 |
| 조작 | **STOP**, **복구 RESET**, **재개 START**. **새 경기**는 분리해 기본 조작 중 오누름 방지. 속도/조향 직접 입력 없음 |
| 기록 | 최근 감속·정지·우회/복귀·운영 명령 목록과 한 사건의 시간축/내보내기 |

상태 화면 갱신은 예를 들어 5 Hz부터 시작하고, 영상은 꺼 두거나 낮은 빈도로 제한한다(팀 초안값). 화면/로그 처리 때문에 제어 콜백을 기다리게 하지 않는다. 온보드 주행 주기와 화면 갱신률은 별개다. 이벤트 읽기와 상태 표시부터 작은 단위로 구현하고, 주행·통신 구조 전체를 새로 쓰지 않는다.

## 2. 기존 코드가 하는 것과 추가할 것

현재 `race_permission.py`·`race_session.py`는 **같은 경기의 STOP 해제와 새 경기 시작**을 구분한다. `acknowledge`는 기존 출발 사실을 유지하고, `new_race`는 출발 사실을 지운다. `legacy_reset`도 새 경기로 처리한다. [현재 CLI](../../scripts/race_operator.py)는 상태·STOP·새 경기·해제만 제공하며 `/race/command`에 보낸다. MCU STOP/ARM이나 실제 정지를 직접 보장하지 않는다.

따라서 세이브포인트에서 현재 reset을 그대로 누르면 다시 최초 신호를 기다릴 수 있다. **같은 경기의 복구 RESET**을 명시적으로 추가하는 것이 필요한 차이이다. 재부팅 기능을 만드는 것이 목적이 아니다.

| 조작 | 목표 의미 | 구현 시 보존할 조건 |
|---|---|---|
| STOP | 주행 허가를 잠그고 기존 MCU 정지 경로에도 전달. 언제든 다시 누를 수 있음 | UI에서 요청·서버 수락·MCU 확인·모터축 상태를 구분. 모터축 0만으로 차체가 멈췄다고 표시하지 않음. 기존 HW 정지는 별도로 유지 |
| 복구 RESET | 차를 옮겼거나 제어 이력이 꼬였을 때 현재 경기 안에서 경로·대상·운동 보정 이력을 초기화. **정지 상태 유지** | 경기/개입 번호와 최초 출발 사실을 보존하되, 옮기기 전 스캔·누적 이동·벽/경로 기억·우회 대상을 새 위치 근거로 재사용하지 않음 |
| 재개 START | 이미 출발한 같은 경기에서 운영자가 최종 배치를 확인하고 누른 뒤, 배치 이후 입력으로 다시 계산한 자율 명령을 허용 | 요청 수락과 주행 허가를 구분. 정지를 유지한 채 새 입력·기준 벽·경로·MCU 조건을 확인한 후 허가. 별도 10초·빨강 시퀀스 재대기 없음. 실제 앞길 점유는 경로 계획/독립 보호가 감속·정지 |
| 새 경기 | 경기 번호·최초 시각 신호 사실을 새로 시작 | 기존 출발 사실로 신호 전 움직이지 않음. 복구 RESET과 다른 메뉴·이름 사용 |

**STOP → 복구 RESET → 최종 배치 → START 한 번**을 대표 흐름으로 둔다. RESET은 이동 전이나 배치 후에 수행할 수 있고 정지 상태를 유지한다. 이동 전에 초기화를 끝냈더라도 이후 들고 이동하며 받은 스캔·운동·영상은 최종 위치의 준비 완료 근거로 쓰지 않는다. 운영자는 심판이 내려놓은 것을 확인한 뒤 START를 누른다. 별도 배치 확인 버튼이나 매번 session 숫자를 입력하는 조작은 추가하지 않는다. 화면은 현재 차량·경기·개입과 요청 결과를 구분해 보여 주며 서버의 오래된 번호 거절과 STOP 우선 처리를 재사용한다.

### 재배치 후 입력과 주행 허가

유효한 START 요청을 처리할 때 **최종 배치 확인 뒤의 입력 경계**를 만든다. 그 경계 이전 스캔·누적 이동·경로/벽 기하·우회 대상과 진행 중인 비동기 영상/계획 결과를 폐기하고, 경계 이후 취득한 센서 묶음으로 운동 보정과 경로를 다시 계산한다. 단순히 RESET 이후이거나 최근에 수신했다는 이유만으로 입력을 인정하지 않는다. 경계를 걸친 스캔이나 늦게 도착한 이전 프레임도 새 위치의 판단에 섞지 않는다.

요청 수락은 아직 주행 허가가 아니다. **같은 START 요청 안에서 정지를 유지하며 필요한 새 입력을 받고**, 유효한 기준 벽·경로와 기존 MCU 해제 조건이 갖춰지면 주행을 허용한다. 기존 입력 제한시간 안의 센서 갱신을 기다리는 절차이며 장시간 영점 보정·고정 안정 대기·추가 10초 대기를 도입하지 않는다. 미출발 경기, 경기/개입 불일치, 실제 HW 정지 입력이나 현재 고장 등 시작 자체가 불가능한 요청은 이유와 함께 거절한다. 준비 중 입력 제한시간 초과·새 STOP·경기/개입 변경·운영 연결 상실이 발생하면 그 요청을 취소하고 정지를 유지한다. 재연결 뒤 취소된 START를 실행하지 않으며, 다시 확인한 상태에 대한 명시 요청을 받는다.

### 기준 벽과 본선 방향 복구

출발 사실의 복원과 **현재 위치에서 본선을 이어 갈 기준 벽의 재수립**을 별도 완료 조건으로 둔다. 현재 [기본 reset](../../src/arena_autonomy/arena_autonomy/wall_follow.py)은 `side="left"`로 돌아가고, [마커 처리](../../src/arena_autonomy/arena_autonomy/local_pursuit.py)는 ID30에서 오른쪽, ID0/20/45에서 왼쪽을 선택한다. 이 동작을 새 복구에 그대로 사용해도 되는지는 아직 확인하지 않았다.

이동 전 벽/경로의 기하 기억은 버린다. 논리적 기준 벽·구간 상태는 무엇을 유지하고 무엇을 현재 관측으로 다시 판단할지 구현에서 명시하고 대표 주행으로 확인한다. `left` 기본값이나 이동 전 `side`를 그대로 유지했다는 사실만으로 복구 완료로 판정하지 않는다. **ID30이 보이지 않는 오른쪽 기준 구간에서 RESET 후 재개와 프로세스 재시작 후 복구**를 대표 사례로 포함한다. 평가자는 실제 본선 진행을 확인하되 제어기에 세이브포인트 좌표·번호·정답 위치를 넣거나 운영자가 좌우 진행 방향을 지정하지 않는다.

프로세스까지 재시작돼 최초 출발 사실이 사라진 경우는 별도다. 저장된 경기 기록과 운영자의 **같은 경기 복구** 확인을 통해 복원하는 작은 절차를 설계하되, 임의의 이전 경기 신호를 자동 재사용하지 않는다. 이 경우에도 새로 켜진 차량이 신호를 본 것으로 가장하지 않는다. 저장·복구 범위는 경기 번호/개입/출발 사실 정도이며 전체 경로 상태를 영속화하지 않는다. 이 최소 복원만으로 기준 벽까지 복구됐다고 간주하지 않고 위 대표 사례에서 본선 진행을 확인한다.

사람이 차량을 옮기는 동안 센서가 흔들려도 STOP은 유지한다. 실제 위치를 직접 넣거나 세이브포인트별 조향 명령을 준비하지 않는다. `/drive → 독립 보호층 → /drive/safe`를 유지하고 화면이 `/drive/safe`를 직접 발행하지 않는다. MCU 재ARM 등 별도 해제가 필요하면 기존 계약 안에서 위 단일 START 절차로 묶고, 준비 중·주행 허가·거절/취소의 결과를 구분해 보여 준다. 통신 복구 뒤 뒤늦게 실행될 START를 큐에 남기지 않는다.

## 3. 공용 Wi-Fi에서의 최소 운영

- 차량별 주소·식별 이름·접속 토큰으로 잘못된 차량 조작을 막고, ROS 전체 토픽/명령 포트를 공용망에 노출하는 대신 제한된 운영 API만 제공한다. 계정 시스템·클라우드는 만들지 않는다.
- UI 연결이 끊기면 **상태 오래됨/명령 결과 미확인**을 표시한다. 모니터 연결 단절만으로 정상 온보드 자율주행을 계속 급정지시키지 않는다. 센서·MCU 필수 입력 단절은 기존 차내 계약대로 처리한다.
- 요청 ID·현재 경기/개입 번호와 서버 ACK를 사용한다. 수신 확인이 없으면 성공/실패를 추측하지 않는다. START/RESET을 자동 재전송하지 않고 새 상태를 조회한다. STOP은 중복돼도 잠금을 유지하도록 한다.
- Wi-Fi STOP은 전파 혼잡/공유기 고장 때 전달되지 않을 수 있다. HW 정지와 검차 시연을 대체하지 않는다. 공유기 client isolation·IP 변경·재연결은 실제 네트워크에서 한 번 확인한다.

공식의 10초는 **사람이 개입할 수 있는 시점**이다. 화면에는 정지 경과를 참고로 보여 줄 수 있지만 그 값만으로 사람 개입을 자동 승인하거나 자동 출발하지 않는다. 심판의 이동/재개 절차를 따른다.

## 4. 급감속·우회·접촉 설명에 필요한 기록

목적은 그때 **무엇을 보고 어떤 명령을 냈는지** 짧은 시간축으로 설명하는 것이다. 의도나 면책을 판정하는 장치는 아니다. 기존 판단 기록·센서 기록기를 재사용하고 별도 거대한 저장 체계를 만들지 않는다.

| 기록 | 최소 내용 |
|---|---|
| 공통 식별 | 경기/개입/요청 ID, 소스 커밋·설정 해시, 센서 시각·수신 단조 시각·대응하는 실제 시각, 시뮬 여부 |
| 제어 변화 | 목표/보호 후/MCU 적용 속도·조향, 모터축 환산값, 급감속을 처음 요구한 계층과 이유, STOP/RESET/START 수락·거절 |
| 주변 근거 | 센서로 관측한 앞차 거리·접근 추정, 우회/본선 복귀/양보 상태, 점유·관측 부족 구분, 해당 판단의 입력 나이·누락·마커 ID |
| 사건 전후 | 급감속·정지·옆 이동/복귀 전환을 중심으로 짧은 센서/판단 버퍼. 예를 들어 전후 각 5초로 시작하되 저장 부담을 보고 조정 |
| 요약 | 한 사건의 속도·조향·이유·주요 프레임을 시간순 HTML/CSV로 내보냄. 원시 입력 누락과 시계 오차는 숨기지 않음 |

센서 로그에 정답 actor 상태나 Gazebo 자세가 있다면 평가용 파일로 분리한다. 실차 사고 설명 자료에 정답을 실제 관측처럼 섞지 않는다. 라이다/영상 전체를 항상 최대 속도로 디스크에 쓰거나 실시간 Wi-Fi 전송하는 것은 첫 구현의 필수 조건이 아니다. 파일 크기·보관 기간을 제한하고 기록 실패 자체가 조향 루프를 막지 않도록 한다. 큰 원시 bag·수신 로그의 기존 Git 제외 정책은 유지한다.

## 5. 최초 구현에서 갖출 운영 흐름

1. 기존 상태와 판단 로그로 읽기 화면·사건 요약을 먼저 연결한다. 표시한 속도/시각의 의미와 로그 누락을 확인한다.
2. 같은 경기에서 STOP → 복구 RESET → 최종 배치 → START 한 번 → 배치 이후 입력/경로 확인 → 주행 허가를 확인한다. RESET을 배치 후에 한 경우도 같은 입력 경계를 지킨다. 이동 중 스캔과 뒤늦은 이전 영상 결과를 준비 완료 근거로 쓰지 않고, RESET만으로는 움직이지 않아야 한다. 배치 뒤 추가 10초를 기다리지 않는다.
3. 새 경기에서 START만 눌러 최초 시각 신호를 우회하지 않는지, 출발한 경기의 개입 후에는 신호를 다시 요구하지 않는지 확인한다.
4. 왼쪽 기준 구간과 ID30이 보이지 않는 오른쪽 기준 구간에서 재개 후 본선 진행을 확인한다. 오른쪽 사례에는 프로세스 재시작 후 같은 경기 복구도 포함한다. 양수 속도 출력이나 출발 허가 복원만으로 통과시키지 않는다.
5. 끊긴 Wi-Fi·중복 STOP·응답 유실 START를 한 번씩 확인한다. START 준비 중 새 STOP이나 연결 상실로 취소된 요청이 뒤늦게 주행을 허용하지 않는지 함께 본다. 상위 상태 확인과 실제 MCU 정지 시험은 구분한다.
6. 위 운영 흐름과 대표 주행 사건의 내보내기가 실제로 연결돼 사용할 수 있는지 확인한다. 필수 조작이 동작하지 않으면 해결을 이어간다. **운영에 쓸 수준이 갖춰지면** 화면 미관·부가 기능보다 다른 미완성 필수 기능을 우선하고, 전체 기능이 갖춰진 뒤 보강한다. 실물 STOP/ARM·실제 재배치는 차량 가용 시 확인하며 그 전까지는 미검증으로 남긴다.
