# G1-b: Gazebo 앞차와 저속 추종·대기

작성: 2026-10-07(같은 날 중단 후 재개). 처음에는 정지 앞차 seed 0 통과·등속 seed 0 행동 실패 뒤 사용자 요청으로 잠시 중단했다. 재개에서 **등속 정체 원인을 보존 원시 자료로 규명하고 `local_follow.py`만 수정**했으며, 같은 최종 소스로 seed 0 등속·정지/재출발·정지 앞차를 모두 통과했다. 사전 등록 G1 3사례×3seed는 같은 제어기로 **모두 통과 실행이 있다.** seed 1 등속은 평가판 v2에서 STOP 직전 MCU 고정 1건(평가기 동시각 float 비교)으로 실패했고, 그 기록을 보존한 채 평가기만 고친 v4로 다시 실행해 통과했다. R0 비교 3개도 마쳤으며 R0는 정지 앞차에서 앞차에 닿았다. **G1-b 시작 직선 제한 행렬의 범위다.** 기본 G1 활성화·G1 전체 단계·곡선/옆차·전체 랩·실차 안전의 완료 보고서가 아니다. 중단 전 기록과 실패는 아래에 그대로 두고 [재개 절](#재개-등속-정체-원인과-수정)에 이어 적었다.

## 목표와 유지한 범위

[G1-a](LOCAL_FOLLOW_G1_2026_10_05.md)의 선택형 `g1_follow`를 실제 Gazebo 앞차·렌더링된 순차 C1·독립 LiDAR 보호층·가상 MCU와 연결한다. 공식 코스 출발 직선에서 정지 앞차 10초, 0.35 m/s 앞차 12초, 이동→정지→재출발 15초를 사전 등록한 [시험 설정](../../config/tests/g1_traffic_v1.json)으로 검사한다. G1 seed 0/1/2는 잡음 주입이 아닌 앞차 시작 위치 0/−0.10/+0.10 m의 결정론적 배치다. R0는 같은 명령 상한 1.0 m/s·seed 0의 비교이며 G1 행동 판정선 통과를 강제하지 않는다.

도로 폭 0.45 m, 차체 0.20×0.15 m, 모터축 28카운트·15:1·65 mm 바퀴·임시 축거 0.135 m, 센서 구성·높이·배치·독립 `/drive` → 보호층 → `/drive/safe`를 유지한다. 순차 10 Hz·both 운동 보정·제어 50 Hz와 기존 보호/MCU 마감도 유지한다. 우회·추월·코너/옆차 반례·전체 랩·Jetson·실차·센서 추가는 이번 범위 밖이다. 기본 단독 모드는 유지하며 G1은 선택형이다.

출발은 기존 임시 RGB 빨강→초록 시험 트리거다. [10/6 공식 소등 출발과의 불일치](../reports/OFFICIAL_UPDATE_2026_10_06.md)는 별도 미해결로 유지한다. 공식 원본 ZIP·`world.sdf`·`scene.json`을 바꾸지 않았고, 보수적 차체 노면 이탈 기준에 잔디 완화 메모를 적용하지 않았다.

초기 구현·두 파일럿은 Claude Opus 5.5와 Claude Sonnet 5.5가 맡았다. Claude 사용량 한도 도달 후 사용자의 명시 지시로 GPT 주 에이전트가 설계·검토, GPT-6.1 Sol이 수정·회귀·문서, GPT-6 Luna가 실행·대기·결과 회수를 맡았다. 한도 도달을 완료로 기록하지 않았다. 시작 HEAD `25dea6045098105a1289ac8ffdb9b2b366c16edb`와 기존 G1-a·10/6 미커밋 변경은 [최초 상태](../../artifacts/validation/2026-10-07/g1b_start_state/)에 보존했으며, GPT 수정 시작 소스는 [별도 보관](../../artifacts/validation/2026-10-07/g1b_sol_start_v1/)했다. 커밋·푸시·외부 게시·Jetson 실행은 하지 않았다.

## 시험기와 판정

`validate_g1_traffic.py`는 실행 사본에만 정적 상자 `eval_g1b_actor`(0.20×0.15×0.12 m, 바닥 0 m)를 넣고 평가 전용 `set_pose`로 옮긴다. C1의 0.095 m 측정면이 상자를 가로지른다. 모델 자세·중심선·일정·신호 상태·노면/벽/접촉 정답은 평가기만 사용한다. 제어기와 보호층, 가상 MCU의 구독·`/drive`/`/drive/safe` 발행자·actor 자세 구독자를 실행 그래프로 감사한다.

정적 모델은 무한 질량의 순간이동 장애물이며 저속 앞차의 차량 동역학이 아니다. [known-contact 확인](../../artifacts/validation/2026-10-07/g1b_contact_probe_v1/report.json)에서 새 위치의 접촉 메시지 33개와 옛 위치 잔상 없음은 확인했지만, 완전 중첩 순간이동으로 상대 상자를 밀어내지는 않았다. 접촉은 사건 기록이다. 이번 실행의 topic publisher/reader·파싱 오류 검사와 known-contact 소스 해시를 `contact_evidence`에 별도 기록하며, 수신 0개를 연속 무접촉 증명으로 해석하지 않는다.

기존 행동 판정선은 그대로다. 최소 차체 간격은 표본과 보수적 swept 하한 모두 0.15 m, 정지 앞차는 연속 HOLD 3초·끝 간격 0.70 m 이하, 등속 앞차는 진행 2.5 m 이상·연속 정체 2.5초 이하·끝 간격 1.2 m 이하, 재출발은 정지 구간 HOLD 1초·재출발 지연 2.5초 이하·재출발 뒤 진행 1 m 이상·끝 간격 1.2 m 이하다. 명시 STOP·출력 0·모델 안정 정지·MCU 고정 고장/마감·프로세스 정상 종료는 각각 검사한다. 정확한 수치·근거는 사전 설정이 기준이다.

평가판 `g1b_eval_v2_coverage`는 누락을 통과로 해석하던 경우를 거절한다. 비유한·시간 역전/중복 자세·빈 ego/actor/trace, 끝까지 도달하지 않은 창, 오래된 actor 자세의 재사용, 움직이는 actor의 빈 명령/오차 표본, 누락된 정지 요청, reader 파싱/handler 오류를 별도 검사한다. 기존 actor 수신 공백 0.05초를 ego/짝맞춤에도 적용하며, 10 Hz 상태 trace의 0.20초 넘는 공백은 연속 HOLD로 연결하지 않는다. 이는 새 계측 완전성 조건이고 기존 간격·대기·센서/MCU 한도의 완화가 아니다. 각 실행은 평가판과 소스 ZIP·SHA-256을 보존한다.

`harness_valid`는 actor 일정·관측·coverage, `integrity`는 소스·구독·계측, `stop_checks`는 모델/MCU 정지, `shutdown_clean`은 정상 종료/잔존, `behavior_gates_passed`는 행동 수치다. G1 최종 `passed`는 실행 유효성과 행동 판정을 모두 요구한다. R0 `passed`는 비교 실행의 유효성이며 `r0_meets_g1_gates`를 따로 기록한다.

고정 런타임 밖 [사후 상태/자세 감사](../../scripts/audit_g1_traffic_coverage.py)는 원시 autonomy 상태와 trace의 시각·내용, 경계 원천/참조 시각 진행·원천/경로 TTL, HOLD·STOP과 밀집 실제 자세 이동을 대조한다. 원시 autonomy는 정상 상태에서 0.2초마다 또는 상태 전환 때 발행하므로 trace보다 낮은 발행률 자체를 오류로 세지 않는다. 정지 앞차는 감사 v1을 통과했고, 이후 v2는 등속 사례에 HOLD가 없으면 그 교차 검사만 `not_applicable`로 명시한다(정지/재출발 사례는 HOLD 자료 필수). stale 관측을 거절하며 0명령을 내린 것은 진단으로, 오래된 근거를 사용한 양수 명령은 오류로 구분한다. v1 소스·결과는 보존하고 v2 반례 5개를 통과했다. 현재 기록에는 dynamics 진단·`/drive/safe`의 개별 원천 시각이 없어 **그 두 스트림의 신선성은 미확인**이다. 제어기/MCU 자체 입력 검사·평가기 graph/시각·밀집 자세 검사와 구분하며, 사후 감사가 원본 실행 판정이나 행동 수치를 바꾸지는 않는다.

v2의 환경 원인과 기계 판정을 구분한다. 기존 보고서의 `run_valid=true`를 바꾸지 않으며, 해당 실행은 실제 저속 추종의 행동 검증 근거로 채택하지 않는다. v1 저장 trace에서는 sim 7.171초에 `follow_release_wait`·원천 7.002초·참조 7.12초·경계 나이 0.118초·새 관측 수락을 기록했다. 7.273초 표본의 `follow_invalid_state`는 원천 7.102초·참조 7.260000000000001초다. 같은 MCU 시간 7.260초에는 유효 피드백 `mean_wheel_mps=-0.0486198863`, capture 7.253초·count 2170을 기록했고, 7.330초에는 count 2169·같은 signed 속도를 기록했다. 당시 모델의 종방향 속도도 7.273초에 −0.0083962 m/s였다. **한 카운트 잡음이라고 단정하지 않는다.**

기존 `LocalFollow.command`는 `speed < -0.02`를 invalid state로 취급해 `reset()`으로 경계 기억을 지웠다. 직전 확인 원천 7.002초는 7.26초 기준으로 0.258초여서 설정 TTL 0.30초 안에 있었지만, v1에는 원시 scan·연속 운동 이력을 남기지 않아 전체 이동 입력을 정확히 재생할 수 없다. 저장 trace/MCU와 이 코드 경로는 결합 실패의 근거이며, 이후 영구 정체의 유일 원인을 입증한 자료는 아니다. [정지 위치 합성 분석](../../artifacts/validation/2026-10-07/g1b_analysis_v1/v1_hold_pose_synthetic.json)은 양 경계가 앞차로 짧아진 상태에서 기억 없는 초기 재획득이 실패함을 보인다. 이상적 정지 기하 근사이며 actual moving replay가 아니다.

수정은 유효한 signed 역방향 측정과 비유한/시각·세대/센서 만료를 분리했다. 유한 음수는 실제 signed 운동 보정과 현재 관측·경계·점유 갱신을 수행한 뒤 `follow_reverse_motion` HOLD로 전진 명령을 금지한다. 음수를 0으로 치환하거나 역속도 무효 임계값을 올리지 않았다. 계속 역방향이면 매번 0명령·release 확인 0이며, 정상 측정 복귀 뒤에도 유효 경계/점유와 서로 다른 두 새 관측 확인 후만 재개한다. 원천 시각·TTL 0.30초·만료·미관측·NaN/inf·시간 역전/epoch reset은 유지한다. R0 shared math·LiDAR 보호·센서/물성은 수정하지 않았다.

### 수정

수정은 `local_follow.py`의 경계 후보 선택에만 있다. `local_path`·`lidar_safety`·`lidar_motion`·센서/차량 설정과 R0 공유 6파일은 그대로이며, [G1-b R0 source contract](../../config/tests/g1b_r0_sha256.json)도 바꾸지 않았다.

1. **지원점 2차 정제(`drop_protrusions`).** 기존 기억 지원 후보가 실패할 때만, 남은 지원점의 기대 벽 선분까지 부호 있는 수직 거리에서 중앙값(기준 경로의 일정한 치우침)을 빼고 `measurement_padding_m`(0.03 m)를 넘는 점을 경계 지원에서 뺀다. 점을 만들거나 옮기지 않고, 뺀 점도 점유·swept 검사에는 모두 남는다. 남은 실제 벽 반환이 기존 연결 한도 안에서 이어질 때만 후보가 길어지므로 긴 물체의 그림자는 잇지 않는다.
2. **같은 스캔의 긴 반대 벽을 기준으로 한 선호 벽 재선택(`bilateral_reference_support`).** 선호 벽 후보가 실패하면, 기존 긴 경계 조건을 만족하는 반대 벽 경로를 기준으로 선호 벽의 실제 반환을 다시 골라 그 후보 자체가 0.65 m·앵커 0.12 m·형상 일치 0.08 m를 모두 만족해야 채택한다. 기억이 없으면 기존처럼 서로 다른 두 fresh 확인을 거치고, 기억이 있으면 기억 경로와도 일치해야 한다. 무기억 초기 양측 확인에서 반대 벽만 얇은 물체로 끊긴 경우에도 같은 선택을 대칭으로 쓴다.

2번은 처음에는 무기억 재획득에만 적용했다. 그 1차 수정판(`local_follow` `48ba2f44…`)의 [등속 실행](../../artifacts/validation/2026-10-07/g1b_resume_v1_slow_s0/report.json)은 모든 판정을 통과했지만 sim 8.72초에 경계를 한 번 잃었다(최장 정체 0.404초). 재생 결과 직전 경로가 기둥 바로 앞에서 시작해 기둥 점이 **기억 경로 시작점 뒤 범위 밖 관측**으로 남아 `wall_shape_uncertain`이 난 것이었다. 그래서 2번을 기억이 있을 때도 쓰되 기억 일치를 추가로 요구하도록 넓혔다. 1차판 실행은 중간 결과로 보존하며 최종판 성공으로 합치지 않는다.

TTL 0.30초·이동 0.45 m·최소 전방 경계 0.65 m·앵커 오차 0.12 m·형상 일치 0.08 m·확인 2회·간격/재개 기준·보호층·MCU 마감은 그대로다. 최종 `local_follow.py` SHA-256은 `fddc808bae12f27b7f9ed674c71c52065c8330c3b0c4c882277c7b2adca96f29`이다.

### 평가판 v3: STOP 요청 시각의 정수 비교

평가기만 고쳤다(`g1b_eval_v3_stop_clock`). 제어기 `local_follow.py`(`fddc808b…`), 보호층·한도·행동 게이트·사전 등록 수치는 그대로다. 이전 평가판(v2)은 각 실행의 `source_snapshot.zip`과 [freeze v6](../../artifacts/validation/2026-10-07/g1b_unit_v6/source_freeze.json)에 보존했고, 그 판정들은 다시 계산하지 않는다.

- `validate_g1_traffic.py`는 평가기 노드에서 `/clock`을 정수 ns로 받아, MCU STOP 서비스를 호출하기 **직전** 값을 `stop_request_clock_ns`로 기록한다. 기존 `stop_request_sim_s`(요청 직후 수신 자세 시각)는 정지 대기 창에만 그대로 쓴다.
- `g1_traffic_eval.stop_latch_timing()`은 그 값을 µs로 내림해 MCU `now_us`(가상 MCU가 sim clock ns를 1000으로 내림한 정수)와 정수로 비교한다. 1 µs라도 이른 `FAULT_LATCHED`/`ESTOP_LATCHED`는 사유와 무관하게 STOP 전으로 센다. 같은 µs에서는 사전 등록 STOP 상태·사유(`ESTOP_LATCHED`/`software_stop`)만 요청 응답으로 보고, FAULT·다른 사유는 STOP 전으로 센다. 요청 시각 미기록, 정수가 아니거나 음수·NaN·누락인 MCU 시각은 판정 불가로 정지 검사를 실패시킨다. 주행 중 고정 상태를 받으면 즉시 중단하는 기존 abort와 STOP 서비스 성공·모델 안정·최종 MCU 상태 검사는 그대로다.
- 한계: 노드마다 `/clock`을 받는 순간이 달라, 요청 직전 평가기 시각과 MCU 처리 시각의 인과 순서를 증명하지는 않는다. 임의 epsilon이나 사유만으로 고장을 무시하지 않으며, 요청 전 수신된 고정 상태는 벽시계 순서의 기존 abort가 잡는다.
- 반례 회귀: float `15.719999999999999 < 15.72` 재현과 같은 µs 응답, 요청 ns가 같은 µs 안, ±1 µs, 같은 µs의 FAULT·다른 사유, 실제 조기 FAULT 뒤 명시 STOP, MCU 시각 누락/float/NaN/inf/bool/음수/문자열, 요청 시각 누락/비정수, STOP 서비스 실패·abort, 타이밍 기록 누락이 G1 `passed`와 R0 `r0_meets_g1_gates`에 같은 방향으로 반영되는지 확인했다. [회귀 v7](../../artifacts/validation/2026-10-07/g1b_unit_v7/pytest.log): **467 통과**(v6 443 + 평가기 반례 24). [freeze v7](../../artifacts/validation/2026-10-07/g1b_unit_v7/source_freeze.json)은 v6 대비 `scripts/g1_traffic_eval.py`·`scripts/validate_g1_traffic.py`·`tests/test_g1_traffic_eval.py`만 바뀌었음을 기록한다.

## 10/7 후속 — 단일 엔코더 재확인과 접촉 계측

### 엔코더는 과거의 좌우 두 개 설정이 아니다

사용자 질문에 따라 이전 `after_r0_stopped_s0_repeat` 실행의 보존 소스 ZIP·실제 모델·제어기 구독과 MCU 상태 3,483개를 대조했다. **PGE-213 모터축 단일 채널, 7 PPR × 4체배 = 28카운트/모터 회전, 기어비 15:1, 바퀴 지름 65 mm**가 모두 일치했다. 평균 바퀴 한 회전은 420카운트, 카운트당 이동 환산값은 약 0.486199 mm다. 기어비는 모터→차동 출력 회전비이고 바퀴 둘레는 그 후 이동거리 환산에 별도로 사용한다. [기계 감사](../../artifacts/validation/2026-10-07/braking_contact_v1/encoder_runtime_audit.json).

상위 주행 제어기와 보호층은 `/drive_motor/encoder`를 구독하고 `/wheel_states`는 구독하지 않았다. MCU도 `feedback_mode=drive_motor_shaft`, `motor_counts`를 사용하며 좌우 바퀴 값/틱은 null이었다. 앞서 언급한 좌우 속도는 **평가용 Gazebo 관절 정답**이다. 시뮬레이터는 실제 두 바퀴의 각을 기계식 차동 관계로 합성한 다음 모터축에서 양자화해야 하므로, 소스에 좌우 관절이 등장하는 것 자체는 센서 두 개를 뜻하지 않는다.

기초 양자화/모터축 계약 시험은 10/2에 이미 진행했고 이번에도 관련 검사를 다시 수행했다. 다만 [ADR 0026](../decisions/0026-motor-shaft-encoder-baseline.md)의 한계는 그대로다. **Gazebo 내부 모터 PI는 이상적인 좌우 관절 평균 속도를 사용**하고, 양자화된 모터축 센서는 상위 제어·운동 보정·가상 MCU 피드백 계약에 공급한다. MCU의 실제 카운트 기반 속도 제어까지 이 물리 폐루프가 완전히 재현한 것은 아니다. 별도 수치 PI 시험과도 구분한다.

### 바뀐 것은 평가 계측이며 차량 물성은 유지

`evaluation_wheel_contacts:=true`일 때만 실행 사본의 네 바퀴에 접촉 센서와 Contact 시스템을 추가한다. 기본값은 false이며 새로운 관측 토픽 `/eval/wheels/contact`는 제어 입력이 아니다. 네 센서를 제거한 실행 차량 XML은 직전 차량과 정규화 후 동일하다. 마찰·질량·모터 토크·PI·차동·엔코더·기어비·상위 제어기와 독립 보호층은 그대로다. 이전 해시 계약은 보존하고 계측 확장만 별도 `braking_contact_r0_sha256.json`으로 연결했다.

`probe_braking_contact.py`는 경로 판단 대신 시각으로 정한 `/drive` 요청만 발행한다. 1초 동안 0→1 m/s, 1초 유지, 0.5초 감속, 이후 0이다. 기존 LiDAR 보호층과 가상 MCU를 통과하며 `/drive/safe`에 직접 명령하지 않는다. 단일 평면 대조는 실행 사본의 노면 충돌체만 높이 3 mm 판으로 바꾼 **분리 시험**이고 공식/팀 기본 월드에는 적용하지 않았다.

첫 R0의 sim 5.352초에는 후륜 좌측의 **명시적으로 측정된 수직 접촉력 0 N**, 우측 약 9.297 N이 기록됐다. 근접한 전륜 접촉은 인접한 두 도로 조각에 걸쳐 있었다. 제동 구간에서 후륜 좌측 0.1 N 미만은 관측 표본의 약 1.21%, 우측은 0.60%였다. 이는 순간적인 하중 불균형의 근거이나, 미수신을 0으로 보간한 결과가 아니다. 이번 R0에서 이전 약 0.701 m/s의 큰 평균 휠–차체 차이는 재현되지 않았다. 고정 명령의 두 대조도 각 1회이며 제동 위치·조향 이력이 R0와 동일하지 않다. **분할 노면·무현가 강체·접촉 계산이 기여할 가능성은 남지만, 이전 접촉/역회전의 단일 원인은 아직 확정할 수 없다.**

종료 보완 v2에서는 더 작은 속도 불일치가 다시 나타났다. sim 5.290초 차체 약 1.040 m/s, 바퀴 평균 약 0.822 m/s, 좌우 타이어 표면 속도 약 1.050/0.593 m/s였다. 같은 시각 후륜 좌측 수직 접촉력은 약 9.195 N이며 우측은 ±6 ms 이내의 메시지가 없어 **하중 미확인(null)**으로 남긴다. 정지 초기의 네 바퀴 총 하중은 약 19.600 N으로 모델 중량과 근접했다. 접촉 계측이 가능하고 불균형/간헐적인 접촉 기록 공백과 휠 속도 분리가 동반됨은 확인했으나, 우측 메시지 부재 자체를 실제 바퀴 들림으로 단정하지 않는다. 별도 접촉 상태·연속 하중 계측 또는 동일 명령/위치 재현 없이 물성을 수정할 근거로 삼지 않는다.

### 시험기에서 확인한 실패도 보존

- 고정 명령 v1은 작성한 시험기의 명령 헤더 타임스탬프 누락으로 보호층이 `stale_input`을 적용했다. 차량이 움직이지 않았으므로 제동 결과로 쓰지 않고 중단·정상 종료했다. 시뮬레이션 시각을 넣은 v2 두 시험이 위 통과 결과다.
- 첫 접촉 R0는 직렬화/종료 중 Gazebo transport의 차체 위치가 sim 14.465초까지 계속 수집된 반면 ROS actor 위치는 14.210초까지여서 전체 coverage가 실패했다. 관측된 표본 중첩은 0이지만 누락 때문에 `no_sampled_overlap=false`이므로 무접촉 완주로 바꾸지 않는다. 평가기에서 STOP 확인 뒤 또는 실패 시점에 관측을 함께 닫도록 `EvaluationCaptureGate`를 추가했다. 이미 받은 행을 사후 삭제하거나 판정선을 완화하지 않는다.
- 초기 회귀의 해시 계약 실패는 평가용 launch 확장을 옛 고정 해시와 비교한 결과였다. 과거 manifest는 그대로 두고 새 계약을 연결했으며, 이전 실패 로그도 보존한다.

후속 R0는 `run_valid=true`, 원시 상대 위치 누락 0, 접촉/중첩 관측 0, 실제 STOP·정상 종료를 확인했다. 여전히 `r0_meets_g1_gates=false`다. 관련 최종 회귀는 **575 passed(57.76초)**이며 앞선 133개/517개와 합산하지 않는다. 다섯 실행의 원시 SHA/소스 ZIP과 평가 센서 외 차량 동일성을 [마감 감사](../../artifacts/validation/2026-10-07/braking_contact_v1/final_audit_v2.json)로 확인했다.

상세 입력/해시·원시 자료 제외 정책·접촉력 좌표계 근거·재현 명령은 [산출물 안내](../../artifacts/validation/2026-10-07/braking_contact_v1/README.md)에 있다. 전체 R0의 과거 접촉 실패, 큰 바퀴 속도 불일치, 단일 축의 슬립 비관측성 및 이상적 내부 PI 한계는 해결로 닫지 않는다. 저속 G1의 보수적인 추종/대기 결과와 별도이며, 실차 제동 성능이나 MCU 속도 제어 완성으로 확대하지 않는다.

## 10/7 후속 — 초기 부분 가림과 첫 U자 코너

기둥 없는 기본 코스에서 **기존 G1 제어기 그대로 두 제한 사례를 통과**했다. GPT 주 에이전트가 시험 설계·평가기 확장·최종 검토를 맡고 GPT-6 Luna가 실행·대기·마감 회귀를 맡았다. 제어기 `local_follow.py` SHA는 기존 `fddc808bae12f27b7f9ed674c71c52065c8330c3b0c4c882277c7b2adca96f29` 그대로다. 경로·속도 정책, 보호층, 센서, 차동/모터 물성, 코스는 수정하지 않았다.

### 사전 조건과 평가기 변경

별도 [설정](../../config/tests/g1_traffic_extensions_v1.json)에 seed 0 두 사례를 실행 전에 등록했다. 기존 직선 설정과 그 결과는 보존한다. 가까운 앞차 사례는 초기 중심 간격 0.55 m, 처음 3초 정지 후 0.35 m/s 이동이다. 첫 코너 사례는 초기 중심 간격 1.6 m, 0.35 m/s 앞차를 35초간 추종한다. 두 사례 모두 명령 상한 1 m/s이며 순차 C1 10 Hz·운동 보정·가상 MCU와 평가용 바퀴 접촉 계측을 유지한다.

## 10/7~8 후속 — 잔디 쪽 차량의 벽 가림과 제동 이상 재발

**왼쪽 가림 1회는 실행 자료·정지·종료가 유효하지만, 진행 조건 미달로 실패했다.** 큰 바퀴–차체 속도 불일치도 재발했으므로 오른쪽 사례를 자동 실행하지 않았다. G1 완료나 옆차 통과 성공으로 기록하지 않는다. GPT 주 에이전트가 시험기/평가기와 회귀를 확장하고 분석했으며, GPT-6 Luna가 Gazebo 실행·대기·마감 회귀를 수행했다. `local_follow.py`는 `fddc808b…` 그대로이고 제어기·보호층·센서·물성·기본 월드는 바꾸지 않았다.

### 감속·경계 상실·바퀴 불일치의 순서

[원시 시각 대조](../../artifacts/validation/2026-10-07/g1b_side_v1/failure_timeline.json)는 다음 순서를 보인다. 일반 상태는 약 0.2초마다 또는 상태 전이 때, 구동 진단은 약 0.02초마다 발행하므로 아래 시각은 **처음 기록된 표본**이다.

1. `t=5.48 s`: 확인된 전방 경로가 약 0.570 m로 짧아지면서 명령이 1.0에서 0.977 m/s로 감소한다. `5.68 s`에는 약 0.404 m·0.742 m/s다.
2. `5.769 s`: 목표 속도 약 0.589 m/s, 차체 약 1.018 m/s, 평균 바퀴 표면 속도 약 0.622 m/s로 조사 기준 0.35 m/s 차이를 넘는다. **최종 0명령 전에 불일치가 이미 발생했다.**
3. `5.82 s`: `follow_boundary_unconfirmed`로 HOLD·0명령에 들어간다. 뒤쪽 표본에서는 `offset_path_folded`도 보고된다. 독립 LiDAR 보호층은 이 구간에 `clear`였고 상위 경계 판단이 정지를 요청했다.

### 접촉 계측으로 좁힌 범위와 남은 원인

[제동 0.5초의 접촉 대조](../../artifacts/validation/2026-10-07/g1b_side_v1/left_braking_contacts.json)에서 최대 불일치 시각에 후륜 좌측은 서로 인접한 `surface_main_572/573`과 접촉하고 수직 하중 약 7.531 N이 있었다. 후륜 우측은 해당 시각 ±6 ms 이내의 접촉 기록이 없어 **null**이다. 분석 창 `5.8~6.3 s`의 우측 관측 공백 최대는 31 ms다. 이를 우측 하중 0이나 바퀴 들림의 확정 근거로 바꾸지 않는다. 초기 정지 구간 네 바퀴 총 수직 하중은 약 19.600 N으로 모델 중량과 근접한다.

현재 축약 모델은 이상적 차동 관계와 평균 관절 속도 PI, 40 ms 토크 응답을 사용하며 실제 MD20A 단락 제동 회로나 모터 반사 관성을 재현하지 않는다. 감속 중 하중/접촉 변화와 평균속도 PI가 결합했을 가능성은 있지만 **분할 노면, 접촉 계산, 단순 구동 모델 중 단일 원인은 아직 미확정**이다. 이 과정에서 모터축 속도를 쓰는 운동 보정도 영향을 받을 수 있으므로 경계 상실 전부를 순수 인지 오류 또는 순수 물리 오류로 단정하지 않는다. 앞선 완만한 고정 명령 대조는 위치·조향·감속 이력이 달라 이번 실패를 반박하는 시험이 아니다.

따라서 이번에는 기억 TTL·경계 허용치·최소 간격을 완화하거나 마찰·토크·질량을 조정하지 않았다. 다음은 **동일한 사전 고정 명령/조향 이력·초기 자세로 기존 분할 노면과 단일 평면을 대조**하고, 실제 적용 명령·바퀴별 접촉 관측·모터 토크·차체 운동을 같은 시각에 확인한다. 물리 원인과 독립적인 경계 판단은 보존 스캔 분석으로 분리하되, 평가 정답을 대회 제어기에 넣지 않는다. 차이가 남으면 접촉 계산/구동 모델의 단일 요인 대조로 좁힌 후 좌·우 가림 시험에 돌아온다. 이 문제를 둔 채 G2나 속도 증가로 넘어가지 않는다.

### 보존과 검증

관련 회귀 **590개 통과(67.28초)**, 실행 소스 44파일·실행 전 고정 8파일·원시 SHA·상태/자세 사후 감사·제어 구독 경계 검사를 통과했다. 이것은 `passed=false`인 주행을 성공으로 변경하지 않는다. 최초 사전 회귀의 새 시험 콜백 작성 오류 2건(146 통과/2 실패)은 로그로 보존했고, 콜백 래퍼를 바로잡은 뒤 148개가 통과했다. 오른쪽은 미실행이다. 상세 [실행·산출물 안내](../../artifacts/validation/2026-10-07/g1b_side_v1/README.md)에 소스·해시·명령·회귀 근거를 모았다. 원시 센서·접촉·MCU 기록은 로컬/Git 제외하며 커밋/푸시·외부 게시·Jetson·전원 설정 변경은 하지 않았다.

## 10/8 후속 — 동일 명령의 제동·노면 대조

**단일 평면에서도 큰 바퀴 평균–차체 속도 차이가 재현됐다. 분할 노면은 좌우 바퀴의 비대칭을 크게 만들었지만, 노면만 바꿔서는 현상이 없어지지 않았다.** 제어기·센서·차량 기본 물성·공식/팀 기본 월드는 유지했다. GPT 주 에이전트가 시험기와 분석을 작성하고 GPT-6 Luna가 실행·대기·회귀를 맡았다. 사전 등록한 A→B→B→A 네 번으로 이번 조사를 마쳤다.

### 입력과 비교 조건

- 지난 왼쪽 가림 trace의 속도와 마지막 조향 상태로 **32점·3.5초의 고정 요청**을 만들었다. 원래 50 Hz 명령 전체가 아니라 약 10 Hz 속도/약 5 Hz 상태 조향을 유지형으로 재구성한 입력이다. 따라서 **이전 실패 주행을 정확히 재생했다고 부르지 않는다**. 현재 센서나 정답 자세로 요청을 수정하지 않는다.
- 같은 슬롯 3 시작 자세·차량·물리 설정·센서를 사용하고 상대차/경로 제어기는 제외했다. A는 현행 분할 노면, B는 실행 사본에서 바닥/도로/잔디 충돌체만 **상단 z=3 mm·두께 100 mm**의 단일 판으로 교체했다. 표시 형상과 비노면 충돌체는 보존했다. 기존 도로와 마찬가지로 판에 마찰 계수를 별도로 지정하지 않았다. 이 대조를 공식 도로 수정으로 채택하지 않았다.
- `/drive` → 독립 LiDAR 보호층 → `/drive/safe` → 가상 MCU 경계를 유지했다. 두 쌍 모두 정규화한 **20 ms 간격 275표본**에서 요청/safe/MCU 목표의 속도·조향 차이가 0이었다. 기록된 활성 구간 보호 상태도 `clear`였다. 이는 해당 표본의 동일성이지 모든 콜백·물리 step 타이밍의 동일성을 보장하지 않는다.
- 프로필 상대 시각 **1.75~2.85초**를 제동 분석 창으로 사전 등록했다. 프로필 종료 후 1초간 0명령, 명시 STOP 후 1초 관측했다. 발행·구동 진단 공백/coverage·안정 정지·정상 종료·소스 불변을 별도로 검사했다.

첫 A의 최대 차이 표본에서 차체는 +0.692704 m/s, 평균 바퀴 표면 속도는 −0.082071 m/s였다. 좌/우 바퀴는 +21.070/−26.120 rad/s로 비대칭이었다. 같은 시각 후륜 수직 접촉력은 약 3.341/3.183 N이었다. 분석 창에서 접촉 기록 공백과 명시적인 0 N도 있었지만 공백을 0 N으로 보간하지 않았다.

첫 B의 최대 차이 표본에서는 차체 +0.500060 m/s에 바퀴 평균 −0.207459 m/s, 좌/우 −6.177/−6.590 rad/s였다. 두 후륜 수직 하중은 약 2.939/3.056 N이었다. 분석 창에서 양쪽 접촉 기록의 최대 간격은 1 ms, 최소 관측 수직력도 각각 약 2.764/2.890 N이었다. 따라서 **분할 도로의 접촉 공백이 없어도 평균 속도 불일치와 잠깐의 역회전이 나타날 수 있다**. 단일 평면에서 좌우 비대칭이 작아진 결과와 구분한다. 이로써 개별 도로 이음새·접촉 엔진·하중의 기여를 각각 확정한 것은 아니다.

### 구동 모델에서 확인한 별도 특성

현행 `SingleMotor::Step()`은 0속도 요청을 별도 수동 제동 상태로 바꾸지 않는다. 평균 관절 속도 PI와 적분항, **40 ms 토크 응답**을 계속 사용한다. 바퀴 회전 방향이 바뀌면 이전 부호의 토크가 잠시 남아 `motor_torque × motor_speed > 0`이 될 수 있다. 첫 A/B의 0목표 구간에서 이 양의 출력은 각각 최대 약 **0.830/1.515 W**였다. 이는 모터 축에서 구동 방향으로 동력이 전달됐다는 뜻이지, 차체가 가속했다는 뜻은 아니다. 단순 양수 표본 개수에는 정지 부근의 매우 작은 값도 포함되므로 연속 구동 시간으로 해석하지 않는다.

같은 헤더의 식과 현행 기본 매개변수를 사용하는 독립 C++ 특성 검사도 수행했다. 0목표·양의 바퀴 속도 +30 rad/s를 1초간 **강제 입력**해 제동 상태를 만든 뒤, 양쪽 관절 관측값을 −5 rad/s로 바꿨다. 이후 100개의 1 ms 표본 중 51개에서 양의 모터 기계 출력이 나왔다. 이것은 **속도 부호를 강제로 전환했을 때 현행 식이 갖는 특성**이며, 실제 차량이 51 ms 동안 역구동한다는 증명이나 Gazebo에서 강제로 속도를 바꾼 주행 시험이 아니다.

현재 모델에 회전자 반사 관성·전류/인덕턴스·MD20A 출력 회로가 없으므로 이 결과를 실제 드라이버 고장이나 실차 제동거리로 옮길 수 없다. 또한 최종 0명령 전 감속 중에도 속도 차이가 생겼으므로 **0목표의 토크만 수정하면 모든 문제가 해결된다고 단정하지 않는다**. 실제 제동에서도 바퀴 잠김/슬립은 가능하며, 정답 차체 속도를 엔코더에 덮어쓰는 방식으로 없애서는 안 된다.

### 검증·보존과 다음 작업

최종 관련 회귀는 **608개 통과(65.42초)**다. 두 쌍의 감사에서 동일 프로필·시작 설정·차량, 노면 충돌체 외 월드 동일성, 실행 소스 ZIP·현재 소스·원시 SHA·단일 모터축 피드백을 확인했다. 네 실행 모두 명시 STOP·안정 정지·정상 종료·잔존 시험 프로세스 없음이다. 모터축 단일 28카운트·15:1·65 mm, 기존 제어기 `fddc808b…`를 유지했다. 공개용 소스/요약과 로컬 전용 고빈도 원시 로그를 구분하고, 기존 실패 기록을 덮어쓰지 않았다.

다음은 **정상 감속·0속도 대기·명시 STOP의 출력 의미를 구분한 제동 모델 검토와 단일 요인 대조**다. 먼저 현행 능동 속도 PI와 선택형 수동 제동 근사를 같은 입력에서 비교하고, 적분/토크 응답의 영향과 0명령 전 잠김을 분리한다. 수동 제동 근사는 실물 회로 재현이 아니라 원인 분리 후보임을 명시하며 기본 모델로 자동 채택하지 않는다. 토크·마찰을 임의로 낮추거나 보호 한도를 완화하지 않는다. 구동 모델의 채택 근거가 확보되면 같은 좌측 가림을 재검증하고 오른쪽으로 돌아간다. 실제 카운트 기반 MCU 속도 루프·제동 출력 매핑은 별도 필수 통합 과제다. 오른쪽/G2/고속화는 이번 작업에서 진행하지 않았다.

## 10/8 새벽 후속 — 0속도 출력 의미와 구동 모델 대조

### 출력 의미와 구현 경계

정상 감속·0속도 대기·명시 STOP은 같은 개념이 아니다.

| 상황 | 상위/MCU 동작 | 현재 Gazebo 모터 입력 |
|---|---|---|
| 정상 감속 | 양의 목표 속도를 낮춤, DRIVE 계속 허용 | 기존 PI가 평균 관절 속도와 비교해 토크 결정 |
| 0속도 대기 | 신선한 0명령, `ARMED` 유지, 허용된 새 DRIVE로 진행 가능 | 목표 0 |
| 명시 STOP/고정 고장 | 상태·세대 고정, 후속 DRIVE 거절, 명시 CLEAR/ARM 필요 | 목표 0; 이유 자체는 플러그인에 전달되지 않음 |

이번 작업은 MCU 계약이나 독립 보호층을 바꾸지 않는다. 선택형 구동 실험은 하위 목표가 정확히 0일 때만 동작하고, 실제 드라이버의 PWM/방향/제동 매핑이나 물리 비상정지 회로를 구현한 것이 아니다. 현재 평균 관절 속도 PI가 양자화된 실물 카운트 PI로 바뀐 것도 아니다. 정상 감속의 음수 토크를 실물 후진 명령으로 바로 옮기면 안 된다는 기존 경계도 유지한다.

평가 옵션 `evaluation_zero_speed_mode`는 `legacy`가 기본이다. `reset_integral`은 영점에서 적분을 비우되 40 ms 응답을 유지하고, `no_lag`는 영점에서 응답 지연만 제거하되 기존 적분을 유지한다. `passive_damping`은 기존 Kp와 제동 상한으로 평균축의 회전을 거스르는 저항 토크를 즉시 적용하고 적분을 비운다. **수동적(passive) 제동 근사이지 사람의 수동 조작 모드가 아니다.** 새 저항 계수를 성공 결과에 맞춰 조정하지 않는다. 영점 밖에서는 세 모드 모두 기존 수식을 사용하되 이전 영점 동안 달라진 내부 상태는 이후에도 영향을 줄 수 있다.

이 구성에서 수동 근사는 0목표의 **적분 초기화 + 토크 지연 제거**를 함께 적용한 식과 같다. 따라서 원래 방식, 적분만 제거, 지연만 제거, 둘 다 제거의 효과를 비교할 수 있다. 정지 목표에서 계속 저항 토크를 걸 뿐 바퀴 속도를 강제로 0으로 지정하지 않으며, 기어비·효율·차동 토크 관계도 유지한다.

대안은 실행 사본에만 옵션을 추가하며 보존 경로가 없으면 거절한다. 기본 xacro/vehicle.yaml에는 옵션을 넣지 않는다. 수동 근사는 전기 회로·인덕턴스·회전자 관성·정지 유지·MD20A 실물 제동의 재현이 아니며 기본 모드로 채택하지 않는다.

### 계측 정정과 사전 조건

기존 `/sim/drivetrain`의 `motor_torque_nm`는 `PreUpdate`에서 구한 토크이고 `motor_speed_rad_s`는 물리 적분 뒤 `PostUpdate` 속도였다. 앞 절의 약 0.830/1.515 W는 **서로 한 물리 step 차이가 있는 값의 곱**으로, 정확히 같은 시점의 모터 동력으로 해석하지 않는다. 수식 특성 검사 결과는 유효하지만 과거 실행의 동시각 동력 증거와 구분해야 한다. 원시 자료와 기존 수치는 보존하고 여기서 계측 한계를 명시한다.

이번에는 계산 직전 속도 `pre_motor_speed_rad_s`·동시각 `pre_motor_power_w`·적분 전후·포화 전후 요구 토크를 추가했다. 0목표인 매 물리 step의 양의 일/표본 누적도 기록한다. 이 계측은 평가 전용이며 대회용 제어기는 사용하지 않는다. `τ×ω≤0`는 해당 계산 시점의 조건이지 이산 적분 뒤 전체 시스템 에너지 보존의 증명이 아니다.

같은 기존 입력/초기 자세로 단일 평면의 네 모드 각 1회, 수동 근사의 분할 노면 1회까지 사전 등록했다. 기존 제동 창·시각 coverage·정지·정상 종료 조건을 유지한다. 상세 정의는 [시험 등록](../../artifacts/validation/2026-10-08/zero_speed_v1/README.md)에 있다.

### 분할 노면과 남은 제한

수동 근사의 분할 노면 1회에서도 0목표 양의 축 일은 0이었지만, 제동 창 최대 평균 바퀴–차체 차이는 **0.612975 m/s**, 좌우 바퀴 표면 속도 차이는 **1.155665 m/s**였다. 특히 **최종 0목표 이전에 이미 0.592516 m/s** 차이(차체 +0.890855 / 바퀴 평균 +0.298339 m/s)가 있었다. 첫 0 진단→안정 정지 XY 이동은 0.105801 m다. 이때도 요청/safe/MCU 목표 275표본의 비교 차이는 0이고 실행 입력·STOP·정상 종료는 유효했다.

따라서 이번 범위의 결론은 다음과 같다.

1. 영점에서의 잔류 토크를 줄이면 단일 평면의 평균 역회전과 일부 속도 불일치가 줄어든다. 이 조건의 주된 기여는 적분보다 40 ms 토크 응답이었다.
2. 분할 노면에서의 감속 중 불일치는 영점 처리와 별개로 남는다. **0명령만 고쳐서 해결할 수 없으며**, 정답 차체 속도로 엔코더를 교체하거나 경계 기억을 늘려 가리는 작업은 하지 않는다.
3. 수동 근사도 평균축 관측/토크만 사용한다. 평균 역회전이 없다고 개별 바퀴 역회전·슬립까지 없어졌다는 뜻은 아니다. 타이어·접촉·무현가 강체·회전자 반사 관성 부재의 개별 기여는 아직 미확정이다.
4. `no_lag`가 이 실행에서 양의 축 일을 보이지 않았다고 일반적으로 수동성을 보장하는 것은 아니다. 적분을 유지하므로 다른 이력에서는 달라질 수 있다. 반대로 수동 근사는 계산 시점의 부호 조건을 보장하지만 실물 전기 응답/수치 적분의 정합성을 보장하지 않는다.

후륜 두 바퀴만 따로 보면 합산 회전 관성은 `4.225e-5 kg·m²`, 기존 Kp·반지름·기어비로부터 캐리어 저항 계수는 `0.04875 N·m/(rad/s)`다. 접촉·차체·모터 반사 관성을 제외한 비포화 스칼라 시정수는 약 **0.867 ms**로 현행 1 ms 물리 step과 비슷하다. 이 계산으로 현재 차량이 수치적으로 불안정하다고 단정할 수는 없지만, 같은 시점의 수동성만 확인하고 기본 모델에 채택해서는 안 된다.

다음은 **한정된 step 민감도 확인 후 동일 왼쪽 가림의 선택형 대조**를 권고한다. 먼저 같은 고정 입력에서 수동 근사의 step 의존성을 확인하고, 그 결과가 허용할 때만 기본식을 보존한 채 원래 실패 상황에 대한 영향까지 확인한다. 실제 MD20A 출력/카운트 PI 통합은 별도이며 이 근사를 실물값으로 굳히지 않는다. 오른쪽/G2/고속화는 이번에 진행하지 않았고, 기본 모드도 바꾸지 않았다.

## 10/8 후속 — 수동 제동 근사의 물리 step 민감도

**단일 평면은 1/0.5/0.25 ms 결과가 사전 허용치 안이었지만, 분할 노면은 수렴하지 않았다. 같은 1 ms 재실행에서도 앞선 0명령 전 불일치가 재현되지 않아 G1 선택형 대조는 실행하지 않았다.** GPT 주 에이전트가 범위와 최종 검토를, Claude Opus 5.5가 구현·분석·문서를, Claude Sonnet 5.5 서브에이전트가 Gazebo 실행·대기·회수를 맡았다. 기본 구동식(`legacy`)·차량 물성·토크·마찰·보호 판정선·센서 주기·기본 월드와 제어기 `fddc808b…`는 바꾸지 않았다.

### 구현과 사전 등록

평가 전용 launch 인자 `evaluation_physics_step`을 추가했다. 기본값은 빈 값이고, `0.0005`/`0.00025`만 허용한다. `runtime_artifacts` 증거 경로가 없거나, 실행 사본 월드에 값이 정확히 `0.001`인 `max_step_size`가 하나만 있는 경우가 아니면 거부한다. `real_time_factor`·센서/접촉 주기·물성은 그대로 둔다. 기본 경로의 실행 사본 월드는 직전 launch와 byte 단위로 같음을 회귀로 확인했다. 고정 명령 실행기에 `--physics-step`과 실제 시간/시뮬레이션 시간 기록을 넣었고, G1 실행기에도 선택형 `--zero-speed-mode`/`--physics-step`을 넣었다. 두 실행기 모두 기본 인자는 바뀌지 않는다. 소스 계약은 `config/tests/physics_step_r0_sha256.json`로 0속도 계약 뒤에 연결했다.

실행 전 [시험 등록](../../artifacts/validation/2026-10-08/step_sensitivity_v1/README.md)에 다음을 먼저 기록했다.
- 지표: 0명령 전/후 바퀴–차체 차, 좌우 차, 정지 이동·시간(마지막 0 요청 발행 시점과 첫 0 진단을 구분), 역회전, PreUpdate 동력/양의 일, 실측 step, 진단 간격, RTF, 명령 정렬.
- 허용치: 속도 `max(0.05 m/s, 10%)`, 거리 `max(0.01 m, 20%)`, 시간 `max(0.05 s, 20%)`.
- 분류와 G1 대조 관문.

step을 줄이면 Gazebo 접촉 적분뿐 아니라 플러그인의 PI·토크 응답·조향·오도메트리 이산화도 함께 바뀌므로, 결과를 물리엔진 단독 효과로 부르지 않는다. 입력 프로필 SHA-256 `a792af4a…a08`은 보존 파일에서 다시 계산해 실행 기록과 대조했다.

| 분할 노면 0.25 ms / 반복 | 0.008 / 0.016 | 0.399 / 0.401 | 0.658 / 0.660 | 0.048 / 0.048 m |

속도 단위는 m/s다. 등록 분류는 단일 평면 `consistent_including_1ms`, 분할 노면 `not_converged`이다. 분할 노면은 0.5/0.25 ms 사이에서도 좌우 차·정지 이동·시간이 허용치를 넘었다. 사후 진단에서는 각 실행의 요청값이 프로필과 같았지만 프로필 전환 뒤 첫 발행 지연이 실행마다 0~19 ms 범위에서 달랐다. 같은 1 ms 재실행에서는 기존의 **0명령 전 0.593 m/s 불일치가 0.019 m/s로 재현되지 않았다.** 0.25 ms 두 번은 서로 가까웠다. 사후 검토(v2)에서 20 ms 격자로 다시 비교한 결과, 모든 step 비교에서 요청/safe/MCU 목표의 속도·조향 불일치 표본이 나왔다(MCU 목표 속도는 274~275표본 중 3~11개, 최대 차는 최초 step 비교·기존식 보조 비교에서 요청 0.589 m/s·MCU 0.230 m/s, 1 ms 재실행을 기준으로 한 비교까지 포함한 전체 최대는 요청·MCU 모두 0.589 m/s). 프로필 전환 근처에서 발행·전달 위상이 달라 생긴 차이로 보인다. 마지막 속도 0 전환에서 MCU 0 목표까지의 지연도 8~38.75 ms로 실행마다 달랐다(기존 분할 노면 1 ms는 33 ms, 1 ms 재실행은 8 ms). 기존 `audit_passed`는 실행·보존 유효성 판정일 뿐 적용 입력의 동일성은 판정하지 않으므로, **step 단독 효과는 식별되지 않았다**(`step_only_effect_identifiable=false`).

기존식 단일 평면의 0명령 후 차이는 1 ms 0.708에서 0.25 ms 0.537(종료 실패 실행, 동역학 입력 유효)/0.423 m/s(재시도)로 달라졌다(`differs_at_1ms`). 0.25 ms에서도 0목표 양의 일(0.015~0.020 J)과 평균 역회전(최소 −0.044~−0.093 m/s)은 남았다.

### 해석과 한계

1. 같은 step(1 ms) 반복에서 출력과 발행/전달 위상이 함께 달랐다. 위상은 후보 원인이며 원인 분리는 아직 끝나지 않았다. 분류는 사전 허용치에 따라 여러 실행의 지표를 나눈 것이며 수학적 수렴의 증명이 아니다. [앞 절](#108-새벽-후속--0속도-출력-의미와-구동-모델-대조)의 분할 노면 0명령 전 불일치와 모드별 크기(0.708/0.660/0.443/0.415 m/s)는 **1 ms 한 위상의 단일 관측**으로 낮춰 해석한다. 40 ms 잔류 토크가 0목표 양의 일과 평균 역회전을 만든다는 정성 결론은 0.25 ms에서도 유지됐다.
2. 실행을 두 번씩만 비교했으므로 분포를 단정하지 않는다. 0.25 ms 반복은 2회뿐이고 기존식 0.25 ms 두 실행도 서로 달랐으므로, 0.25 ms가 안정적이라고 확정하지 않는다. step 효과와 위상의 기여도 분리하지 못했다. 진단은 약 20 ms 표본이라 매 step의 진동을 직접 보지 못한다. 수동 근사의 양의 일 0은 계산 시점 부호 조건에서 나온 구성상 성질이며 실물 수동성의 증명이 아니다.
3. 사전 관문에 따라 **왼쪽 가림 G1 선택형 대조는 실행하지 않았다.** G1 왼쪽 실패·오른쪽 미실행·기본 모델은 그대로다. 수동 근사는 실물 MD20A 회로·하드웨어 안전이 아니다.
4. 다음 최소 진단으로 권고하는 것은 다음과 같다. 고정 요청을 시뮬레이션 시계 격자에 맞춰 결정적으로 발행하되 `/drive`→보호층→MCU 경계는 유지한다. 소수의 등록 위상 오프셋에서 1 ms와 0.25 ms의 분포를 비교한다. 위상 민감도의 원인(분할 이음새 접촉/구동 이산화)을 좁힌 뒤 평가용 step을 정하고 G1 대조를 다시 검토한다.

## 10/8 저녁 후속 — 시뮬레이션 시계 격자 발행과 위상·step 변동

**같은 위상에서 관측한 요청·보호층·MCU의 속도/조향 전환 시각은 일치했지만, 1 ms 분할 노면은 같은 조건 반복에서 재현되지 않았다.** 전체 tick의 무지연이나 결정론성을 증명한 것은 아니다. 발행 위상 정렬만으로 반복 차이가 사라지지는 않았으며, 남은 출력 시점 차이와 물리 변동의 기여는 미분리다. GPT 주 에이전트가 설계·최종 검토를, Claude Opus 5.5가 구현·분석·문서를, Claude Sonnet 5.5 서브에이전트가 Gazebo 실행·회수를 맡았다(이번 작업에 한해 사용자가 Sonnet 5.5 유지를 지정). Claude 사용량 한도 도달 뒤에는 GPT-6 Astra가 검토·회귀 보완·기록 마감을 직접 수행했다. 기본 `legacy`·G1 꺼짐·기본 1 ms 월드·보호/MCU/플러그인 코드·차량 물성은 바꾸지 않았다.

### 구현과 등록

- 평가 전용 `--command-schedule sim_grid --schedule-phase-ms {0,10}`를 추가했다. 기본은 기존 폴링 발행이다.

### 해석과 한계

1 ms 반복에서 관측한 입력 전환의 차이는 7개 전환의 출력 시각 1 ms였고, 플러그인 중간 적용 시각은 관측하지 못했다. 이 미세 시각 차이가 원인인지, 관측하지 못한 적용 시점이나 물리 계산 변동이 원인인지는 **분리하지 못했다**. 0.25 ms 세 실행은 서로 가까웠다. 다만 그중 두 실행이 등록 스케줄 감사에 실패했고, 반복 2회는 분포가 아니므로 0.25 ms가 안정적이라고 확정하지 않는다.

이전 단계의 결론과 크기도 낮춰 해석한다. 직전 영점 대조·step 민감도에서 1 ms 분할 노면의 0명령 전 불일치와 모드별 크기는 반복성을 확보하지 못한 단일 실행 관측이다. 실행기 첫 판(r0)은 격자 모드에서 coverage·요청 감사·발행 그래프를 `input_valid`에 넣지 못했다. 이 때문에 R4에서 멈췄어야 할 배치가 R6까지 진행되었다. 6회 report는 보존하고 원시 기록을 재검증했다. **정지·종료/입력 무결성은 6회 통과, 스케줄까지 유효한 시험은 R1·R2·R3·R5 네 회**다. 실행 뒤 수정판을 r1 계약으로 등록했으며, 수정판으로는 Gazebo를 다시 실행하지 않았다.

## 10/9 후속 — 격자 실행기 실패 전파와 플러그인 명령 적용 시점

**수정 실행기의 실패 전파를 실제 실행 경로에서 확인했고(Gate A 통과), 플러그인의 명령 수신·적용 전환을 평가 전용 이벤트로 계측했다. 추적한 같은 스폰 반복 쌍에서 진단은 첫 적용 step 차이(656 ms) 직후 표본(658 ms)부터 갈라졌다.** 이는 1 ms 반복 차이가 물리 계산 자체보다 입력 적용 step과 차량 스폰 step의 변동에서 시작한다는 가설과 양립한다. 다만 추적 쌍은 하나뿐이고 선후 관계이지 인과 증명은 아니다. GPT 주 에이전트가 범위·최종 검토를, Claude Opus 5.5가 조사·구현·분석·문서를 맡았다. 시뮬레이션 실행·회수는 Claude Sonnet 5.5 서브에이전트가 맡았다(런타임에서 지정 모델 Haiku 5.5의 지원을 확인할 수 없어 사용자가 Sonnet 5.5를 승인). 기본 `legacy`·1 ms 월드·G1 꺼짐·차량 물성·보호/MCU 정책·센서는 바꾸지 않았다.

### 구현과 등록

### Gate A — 실패 전파와 자연 지연

- **배치 구성:** 정상 기준 `a1`, 지연주입 `a2`(프로필 2920 ms 0 유지 tick을 15 ms 지연), 실행되면 안 되는 `a3`의 순서였다.
- **결과:**
  - `a1`은 통과했다.
  - `a2`는 종료코드 1·`passed=false`로 기대 실패했다. 실패 검사는 `lateness_within_limit`·`all_ticks_lateness_within_limit` 둘뿐이었다(보류 poll 63회).
  - 명시 STOP·`software_stop`·안정 정지·정상 종료는 통과했다. 배치는 `a2`에서 멈췄고 `a3`는 시작하지 않았으며 잔존 프로세스는 0이었다.
  - 첫 시도는 실행 래퍼가 ROS 설정 전에 `set -u`를 켠 결함으로 사례 시작 전에 끝났다. 원본을 보존하고 고친 판으로 실행했다.
- **자연 지연(좁힘, 원인 미확정):** a1·a2·c1·c2에서 5 ms 이상 늦은 tick은 모두 평가기 Python 2세대 GC 정지 구간 안이었다.
  - 실행마다 2세대 GC는 8회였고, 20 ms 이상인 6회가 약 42→142 ms로 커졌다.
  - 각 정지 동안 노드 시계가 RTF(약 0.097)만큼, 약 4→14 ms 도약했다.
  - 이 때문에 C 반복 중 `c2`가 프로필 뒤 0 유지 tick 13 ms 지연으로 **무효**가 됐다. 등록 창 감사만 보면 통과였던 실행이며, 판정선은 완화하지 않았다.
  - OS·DDS·브리지 지연은 배제하지 않았다. 10/8 R4/R6에는 GC 계측이 없어 같은 원인이라고 단정하지 않는다.
  - 10/8 R2도 등록 창 밖 4.26 s 유지 tick이 11 ms 늦었다. 당시 등록 규칙의 유효 판정은 보존하고 사실로만 남긴다.

### Gate B — 플러그인 전환 계측

- **포착·대응:** 추적 실행 3회 모두 속도 16·조향 11 전환을 포착해 MCU/출력 단계와 대응시켰다. 이벤트 순번 결손과 수신기 오류는 없었다.
- **적용 시점:** 모든 전환은 수신 뒤 **첫 PreUpdate**에 적용됐고, 어떤 PreUpdate에도 보이기 전에 덮인 수신 전환은 0이었다. 적용−출력은 0~+1 step, 적용−MCU는 6~7 ms였다.
- **시각 의미:** PreUpdate의 `simTime`은 모든 이벤트에서 `iteration×dt`와 같았다. 진단 `sim_time_s`와 같은 축이다.
- **추적 끔 보존:**
  - 새 빌드(추적 끔) `a1`의 실행 사본 차량은 10/8 R1과 byte 동일했다. 월드는 launch 임시 메시 경로만 달랐고 메시 파일은 같았다.
  - 같은 스폰 부류에서 진단은 상대 557 ms까지 12자리 동일했다.
- **추적 켬 영향:** 추적 켬 `c1`의 실행 사본 차이는 추적 요소 하나뿐이었다. `a1`과 1081 ms까지 진단이 같았다.
- **비용:** 하네스 측정 장부 비용은 무변화 step당 약 13~15 ns다. 이벤트 전송(실행당 35개)·시계 호출 비용은 따로 재지 않았다.
- **출력 시각의 한계:** 10/8에 쓴 출력 단계 1 ms 차이는 적용 차이의 대용치로 충분하지 않았다. `a1`–`c1`은 975 ms 전환의 출력 시각이 1 ms 달랐지만 진단은 1081 ms까지 같았다. 추적한 `c1`은 그 전환을 출력과 같은 step에 적용했다. 출력 노드가 읽은 시계가 플러그인 step보다 늦을 수 있기 때문이다.

### Gate C — 같은 스폰 반복

c1·c2는 스폰 iteration이 2/3으로 달랐고 c2는 무효였다. 그래서 등록 규칙에 따라 같은 조건 1회(c3)만 추가했다(신규 Gazebo 총 5회, 상한 6회). c3는 유효했고 c1과 같은 스폰(iteration 2)이었다.

### 해석과 한계

1. **해석:** 10/8 1 ms 반복 비재현과 이전 단일 관측(분할 노면 0.593 m/s 등)은 큰 결과 차이로 나타났다. 이는 실행마다 달라지는 스폰 step과 ±1 step 적용 차이가 분할 노면·`passive_damping` 제동에서 크게 증폭된 것으로 해석된다. 두 변동은 모두 벽시계 의존 경로(`create` 서비스, 출력 노드의 벽시계 10 ms 타이머·전송)에서 생긴다고 보이지만, 그 경로를 바꾸거나 직접 검증하지는 않았다.

5. **다음 최소 작업:**

   - 평가기 GC 정지 완화(예: 실행 중 `gc.freeze`)를 평가기 한정 대조로 확인한다.
   - 그 뒤에야 수동 근사·step 비교를 다시 해석한다.

## 10/11 후속 — 평가기 GC 정지 완화와 시점 고정 범위 검토

사용자 요청에 따라 GPT 주 에이전트가 직접 수행했다(Claude/구현·실행 워커 미사용). 이번 변경은 평가 프로그램의 `--evaluation-gc native|defer`뿐이며 기본은 native다. defer는 짧은 `sim_grid` 실행 동안 순환 GC를 미루고 자식 프로세스 정리 후 원래 활성 상태를 복원한다. 참조 카운팅은 유지한다. 600초·평가기 최대 RSS 2 GiB 예산과 예외 복원 회귀를 넣었으며, 제어 노드의 GC·물리·센서·보호 계약을 바꾸지 않았다. freeze는 이후에 생기는 로그 객체까지 고정하지 못하므로 이번에는 제한된 disable/복원 대조를 선택했다.

신규 4회 모두 기존 입력·STOP·실제 정지·정상 종료를 통과했다. 첫 B1은 disable 전에 진단/RSS import를 수행하여 GC 0세대 1회가 계측에 포함됐고 사전 GC 조건에 실패했다. 원본 r3/실행을 보존하고 순서를 고친 r4를 등록했다. 남은 두 번은 A2/B2 한 쌍으로 수행했다. 원래 ABBA 반복 설계는 완수하지 못했다.

- 수정본 native/defer에서 최대 요청 지연 **6/0 ms**, p99 0/0 ms, 예정 326 tick씩·누락 0. native의 6 ms 지연은 87.5 ms 벽시계 GC 정지와 겹쳤다.
- 2세대 GC **8/0회**, 최대 GC 정지 **137.2/0 ms**, 최대 poll 공백 **139.4/5.91 ms**(벽시계).
- 평가기 최대 RSS **426.5/398.0 MiB**, 원래 GC 상태 복원. 이 차이는 메모리 절감 증거가 아니다.
- 이전 A1은 GC 최대 177.3 ms에도 요청 시각 감사상 0 ms 지연이었다. 따라서 GC와 지연의 관계는 실행 조건/처리 순서에 의존하며 항상 위반을 만든다고 단정하지 않는다.

최종 전체 회귀 **1,326개 통과**. 처음 전체 실행은 1,325개 통과/1개 실패였으며, 기존 계약 검사가 새 평가 스크립트를 여전히 r2 해시로 비교한 것이 원인이었다. r2 보존 검사를 유지하면서 r3/r4 후속 계약·현재 해시 연결을 검사하도록 갱신했다. [최초 실패 로그](../../artifacts/validation/2026-10-11/evaluator_gc_v1/pytest_final.log)와 [최종 로그](../../artifacts/validation/2026-10-11/evaluator_gc_v1/pytest_final_v2.log)를 모두 보존한다.

**결론:** 짧은 평가 프로세스의 GC 정지를 없애는 선택 옵션을 검증했다. 기본값 변경·장시간 GC 비활성화·Jetson 적용은 하지 않는다. 수정본 1쌍이므로 10/9 지연 위반을 일반적으로 해결했다거나 물리/주행 재현성을 확보했다고 볼 수 없다. [등록·실패·결과](../../artifacts/validation/2026-10-11/evaluator_gc_v1/README.md), [수정본 분석](../../artifacts/validation/2026-10-11/evaluator_gc_v1/analysis_ab2.json), [마감 검사](../../artifacts/validation/2026-10-11/evaluator_gc_v1/final_manifest.json).

**다음 최소 작업:** 스폰은 평가 실행 사본 월드의 초기 차량 포함 + paused 시작/구독 준비 확인으로 고정하는 방식을 우선 시험한다. 출력 노드의 sim 타이머 전환만으로 bridge/gz 비동기 전달까지 결정적으로 만들 수 없으므로 이번에는 바꾸지 않았다. 적용 deadline/ack의 평가 전용 설계를 별도로 만들고 벽시계 watchdog·같은 stamp 거부·STOP 우선 처리를 보존해야 한다. 명령을 소급 적용하거나 보호층을 우회하지 않는다. G1 좌우 가림·G2·고속·물성/기본 모델 채택은 계속 보류한다.

## 10/11 추가 — 초기 차량 포함·paused 준비 관문

사용자 후속 지정에 따라 GPT 주 에이전트가 설계·구현·분석을, GPT-6 Luna가 시뮬 실행·대기·결과 회수를 맡았다. 앞으로도 Clarisse 없이 GPT가 작업하면 이 실행 분담을 기본으로 사용한다.

`evaluation_startup:=embedded_paused`(평가기 `--evaluation-startup embedded_paused`)를 평가 전용으로 추가했다. 완성된 동일 차량을 실행 사본 월드에 슬롯 pose(z=0.01)로 포함하고 paused로 시작한다. 평가기는 sim 0/paused stats, ROS publisher·독립 보호 경로·ARM/STOP 서비스, gz 추적 및 접촉 reader 연결을 확인한 뒤 [Gazebo world control](https://gazebosim.org/api/sim/8/pause_run_simulation.html)로 시작한다. 첫 추적/센서 수신·정지는 실행 후 별도로 감사한다. 고정 시간 대기를 준비 완료로 취급하지 않는다. 기존 서비스 스폰이 기본이고, 보호 타이머·같은 stamp 거부·물리/센서/구동식은 그대로다.

신규 3회 중 기존 service 기준(S1)과 수정본(E2)은 입력·명시 STOP·실제 정지·정상 종료를 통과했다. S1의 첫 갱신은 **iteration 2, 2 ms**, E2는 **iteration 1, 1 ms**였다. 두 실행 요청 최대 지연은 0 ms, 명령 시작은 2.01 s였다. E2의 준비 해제까지 약 11.90초는 PC 벽시계 시작 비용이며 차량 명령 지연이 아니다.

첫 embedded 실행 E1은 준비 검사에서 **접촉 publisher=1**을 잘못 요구하여 90초 timeout으로 중단했다. 실제 네 바퀴 contact sensor는 같은 토픽에 각각 발행한다. 실행 SDF·생성기를 확인하고 r6에서 **정확히 4개**를 요구하도록 수정했다. 제어 publisher=1 조건이나 보호 한도를 완화하지 않았다. E1은 unpause·주행·명시 STOP가 없었으며 정상 종료·잔존 0·GC 복원만 확인했다. 원본 실패/r5를 보존했다.

사후 비교에서 삽입된 모델의 최상위 pose를 제외하면 차량 모델이 같고, 차량을 제외하면 월드/메시가 같았다. 원본 트랙·단일 모터축 28카운트·15:1·65 mm·플러그인 바이너리·센서·보호/MCU 소스 보존을 확인한다. 상세 해시는 [마감 감사](../../artifacts/validation/2026-10-11/initial_startup_v1/final_manifest.json)에 둔다.

**한계:** 신규 3회 상한 내에서 E1을 수정했으므로 수정본 유효 실행은 한 번이다. 단회 시작 기능만 확인했고 **두 반복 수용 조건은 미충족**이다. S1/E2는 초기 생성 시점이 다르므로 물리 결과 차이를 모델 개선으로 해석하지 않는다. 초기 배치 옵션은 명령 전달/적용 시점의 결정성을 보장하지 않는다. 출력/보호 계약·기본 실행 방식은 변경하지 않는다.

**다음 최소 작업:** r6 같은 조건 한 번으로 첫 물리 갱신 시점의 반복을 확인한 뒤, 기존 전환 추적으로 명령 적용 ±1 step 변동을 분리한다. 적용 deadline/ack를 검토하더라도 평가 경계에 한정하고 소급 적용·보호 우회는 금지한다. G1 좌우 가림·G2·고속·실차/Jetson 확장은 이번에 하지 않았다.

## 10/11 반복 마감 — 초기 배치 확인과 출력 이후 변동 분리

이전 E2와 같은 r6 소스·바이너리·프로필·차량/월드/메시·spawn pose로 **E3 한 번을 추가**했다. GPT 주 에이전트가 사후 분석기를 구현·검토하고 GPT-6 Luna가 실행·대기·회귀를 맡았다. ### 남은 차이는 어디서 시작되는가

같은 프로필 값의 전환을 순서대로 짝지어 비교했다. 아래 시각은 각 단계의 기록 기준이며, 다른 프로세스의 정확한 벽시계 전송 지연과 같지 않다.

| 단계 | 속도 16회 | 조향 11회 |
|---|---|---|
| 요청 예정/관측 시각 | 전부 같음 | 전부 같음 |
| 독립 보호층 출력 stamp | 전부 같음 | 전부 같음 |
| 가상 MCU 목표 변경 stamp | 전부 같음 | 전부 같음 |
| 출력 노드 진단 stamp | 7회에서 ±1 ms 차이 | 현행 출력 진단에 조향값 없음 |
| 플러그인 실제 적용 step | 8회에서 ±1 ms 차이 | 5회에서 ±1 ms 차이 |

속도에서 7개 적용 차이는 출력 시각 차이와 일치했다. 나머지 1개(0-based 전환 7, 약 0.69 m/s)는 출력 진단 stamp가 같아도 플러그인 수신/적용이 1 ms 달랐다. 모든 속도/조향 전환은 두 실행 모두 **수신 뒤 첫 물리 step에 적용**됐다. 플러그인이 수신한 값을 여러 step 쌓아 둔 현상은 관측하지 않았다.

첫 적용 차이는 프로필 시작 후 **0.656/0.657 s**의 약 0.24 m/s 전환이며, 첫 운동 진단 차이는 **0.658 s**, 바퀴/차체 속도 차이가 0.1 m/s를 넘는 최초 표본은 0.678 s였다. 367개 같은 시각 표본 중 첫 적용 차이 전까지는 기록 정밀도(12자리 유효숫자)에서 같았다. 이는 **동일 초기 배치·상위 명령 뒤 출력/수신 시점 차이가 먼저 관측되고 운동이 뒤이어 갈라졌다는 근거**다. 출력 타이머·DDS/bridge·Gazebo callback 중 하나만 유일 원인이라고 확정하거나 G1 왼쪽 실패의 직접 원인으로 확대하지 않는다.

코드상 `GuardedSimActuator.output()`은 벽시계 10 ms 타이머이고 속도/조향이 별도 메시지다. 플러그인은 `PreUpdate`에서 그때까지 받은 값을 읽는다. 같은 sim stamp로 표시된 출력이라도 물리 step 경계의 어느 쪽에 실제 수신됐는지는 달라질 수 있다. `AppliedGuard`의 같은 stamp 거부에 해당하는 기존 상태 순서는 두 실행의 속도 16/16 전환에서 같았으며, MCU→출력 진단 차이는 모두 5~6 ms였다. 이 보호 규칙을 바꾸어 반복 차이를 덮지 않았다.

### 다음 수정의 묶음과 수용 조건

다음은 평가 전용 **적용 예정 시각 + 수신/적용 확인** 경계의 구현·계약 회귀·동일 조건 반복을 한 작업으로 묶는다. 단순 출력 sim 타이머 전환만으로는 이번의 출력 이후 1 ms 차이를 없앤다고 보장할 수 없으므로 그것만 별도 개선으로 채택하지 않는다.

- 입력은 기존 `/drive` → 독립 보호층 → MCU → `AppliedGuard`를 통과한 출력만 사용한다. 예정 프로필/정답 운동을 플러그인 구동 입력으로 직접 넣지 않는다.
- 평가용 메시지는 속도·조향을 하나의 순번으로 묶고 원래 상태 stamp·epoch·유효 기한·명시 적용 예정 sim 시각을 보존해야 한다. 플러그인은 정상 입력을 예정 `PreUpdate`에서 적용하고 수신/적용 순번·실제 step을 확인할 수 있어야 한다.
- 지각·만료·역순/중복·epoch 변경·확인 누락은 해당 시험의 실패다. 과거 step 소급 적용, 순번 없는 “최신값이겠지” 처리, 오래된 양수 명령 유지로 통과시키지 않는다.
- **정상 0속도 대기와 명시 STOP/보호 정지는 분리한다.** STOP/보호 정지·watchdog는 정상 명령 큐보다 우선하여 양수 예약을 취소해야 하며, 원래 벽시계 감시·유효 기한·재ARM 경계를 유지한다. STOP 지연을 예정 시각에 맞추는 것은 금지한다.
- 예정 적용을 위해 추가하는 대기 시간은 명시된 **평가 조건**이다. 실차 지연 개선이나 실제 제동 성능으로 해석하지 않는다. 공통 제어/실물 인터페이스와 기본 실행 경로는 유지한다.
- 같은 입력 두 실행의 적용 순번/step이 같아진 뒤에도 물리 결과가 갈리면, 그것이 다음 물리/접촉 조사 조건이다. 예정 입력 자체가 다른 실행을 동일 입력으로 처리하지 않는다. 소스·설정·STOP/실제 정지·정상 종료·원시 증거 검사를 함께 통과해야 한다.

이 절은 후속 구현 조건이며 **예정 적용 기능은 아직 구현하지 않았다.** 이번에는 런타임을 바꾸지 않고 분석기와 관련 **80개 회귀**를 통과했다(이전 전체 1,367개와 합산하지 않음). 기본 service/native·물성/센서/단일 모터축/보호 한도·G1 보류는 유지한다. 커밋·푸시·외부 게시·Jetson·전원 변경 없음.

## 10/11 예약 적용 마감 — 같은 명령의 적용 시점과 제동 반복 확인

이전 절의 계획을 구현·보호 회귀·기본 경로 대조·동일 조건 두 실행까지 묶어 수행했다. GPT 주 에이전트가 설계/구현/분석/검토, GPT-6 Luna가 빌드·시뮬레이션·회귀 실행/대기를 맡았다. **이번 제한 조건에서 정상 명령 적용과 물리 진단의 반복 일치를 확인했다.** 실차 제동이나 일반적인 물리 결정성은 아직 확인하지 않았다.

### 변경한 것과 보존한 것

`evaluation_scheduled_apply:=true`로 명시한 평가 실행에서만 `ScheduledSimActuator`가 기존 `AppliedGuard`의 허가된 출력을 순번·epoch·원래 MCU stamp·원래 유효 기한과 함께 보낸다. 속도/조향은 한 메시지이며 **원래 stamp + 20 ms의 1 ms 물리 step**에 동시에 적용한다. 플러그인은 수신과 적용을 각각 ACK로 남긴다. 추가 대기는 비교를 위한 인위적인 조건이지 실차 통신/제동 개선이 아니다.

정상 감속·0목표 대기는 예약할 수 있지만, 명시 STOP/보호 개입/유효 기한/watchdog는 예약을 취소하고 출력 0을 우선한다. 지각·역순/중복·epoch 불일치·ACK 누락/잘못된 step은 실패로 고정하며 오래된 명령을 소급 적용하지 않는다. 보호가 개입한 시험도 실패로 분리한다. 단위 시험에서 양수 예약 전/후 STOP 취소, 만료/벽시계/시계 회귀, ACK 누락·중복·값/step 불일치, 보호 개입/관측 만료 및 자동 재개 금지를 확인했다.

기본 출력은 기존 `guarded_sim_actuator`를 유지한다. `actuation_ros.py`·`AppliedGuard`·공통 구동 계약·구동 식·차량/센서/물성·28카운트/15:1/65 mm·독립 보호 한도는 바꾸지 않았다. 새 바이너리의 N1 기본 경로 모델은 이전 E3 모델과 같고, 예약 경로와는 평가 태그 2개만 다르다. 월드/메시도 보존했다. r6/당시 실패를 수정하지 않고 [r7 계약](../../config/tests/scheduled_command_r7_sha256.json)에 변경 전후 해시를 연결했다.

| 실제 정상 적용 건수 | 별도 채널 기존 방식 | 1,098 | 1,098 |
| 최고 차체 속도 | 1.07247 m/s | 1.04528 m/s | 1.04528 m/s |

T1/T2의 프로필 시작~종료+0.2초 구간 **741개 정상 적용**은 순번·원래 stamp·속도·조향·예정/실제 step이 모두 같았다. 같은 소스/바이너리·형상·프로필·초기 자세·첫 step도 확인했다. 기존 비교 방식의 **367개 동시각 운동 진단이 기록 정밀도(12자리 유효숫자)에서 같고, 주 제동 지표 7개 차이는 모두 0**이었다. 따라서 이 쌍에서는 이전 E2/E3의 ±1 ms 적용 변동과 뒤이은 운동 분기가 재현되지 않았다. 이것이 모든 환경에서 해결됐다는 뜻은 아니다.

T1/T2 송신 개수 차이 1개는 STOP 직전의 마지막 **0속도 예약** 수신 여부이며, 실제 적용 건수는 같다. STOP은 두 실행 모두 sim 6.510 s에서 확인됐고 남은 예약을 각각 4개/3개 취소했다. STOP 뒤 새 ARM 없이 정상 적용된 명령은 없었다. 이번 Gazebo 프로필은 STOP 전에 이미 0목표로 감속한다. 따라서 **움직이는 중 양수 예약을 취소하는 우선순위는 C++/Python 회귀로 확인했으며, 해당 상황의 Gazebo/실차 제동 검증은 아니다.**

### 재현성은 좋아졌지만 남은 물리 현상

| 제동 지표 | T1과 T2 공통값 |
|---|---:|
| 0목표 전 평균 바퀴–차체 속도 차이 최대 | 0.00967 m/s |
| 0목표 후 평균 바퀴–차체 속도 차이 최대 | **0.40449 m/s** |
| 좌우 바퀴 표면 속도 차이 최대 | **0.74746 m/s** |
| 0요청부터 안정 정지까지 직선 변위 | 0.06178 m |
| 0요청부터 안정 정지까지 시간 | 0.228 s |

같은 결과를 얻었지 제동 모델 자체가 정확해진 것은 아니다. 수동 제동 근사는 계속 실험용이고 MD20A 회로/타이어/실차의 재현으로 부르지 않는다. N1과 T1은 의도적인 적용 대기가 다르므로 최고 속도나 정지거리 차이를 성능 개선으로 비교하지 않는다. 좌우 속도는 물리 진단이며 제어 입력 엔코더가 좌우 2개로 바뀐 것이 아니다.

초기 단위 시험 1건은 감사기의 9필드 메시지를 10필드로 센 구현 오류였으며 수정했다. 첫 빌드는 예전 `source_before`까지 colcon이 패키지로 검색해 실패했다. 보관본을 수정하지 않고 `--base-paths src`로 범위를 제한했다. 실패 로그와 변경 전/실행 전 소스를 보존했다. **최종 전체 회귀 1,410개 통과**이며 이전 1,367개/80개와 합산하지 않는다.

**다음:** 초기 배치/예약 적용 반복 확인은 여기서 마감한다. 같은 예약 출력·step을 사용해 분할 노면과 단일 평면의 0목표 이후 좌우 접촉/슬립을 대조한다. 명령 적용이 다르면 물성 효과로 해석하지 않는다. 반복 횟수부터 늘리거나 마찰·토크·보호선을 완화하지 않으며, 기본 제동 모델 채택·G1 왼쪽 재대조·오른쪽/G2·고속화는 아직 보류한다. 실제 카운트 기반 MCU PI와 MD20A 출력 매핑은 별도 필수 작업이다.

## 재현과 남은 범위

WSL Ubuntu 24.04에서 `/opt/ros/jazzy/setup.bash`·`install/local_setup.bash`를 불러오고, 기존 ROS `PYTHONPATH`를 보존하며 `src/arena_autonomy`와 `src/arena_vehicle_interface`를 앞에 둔다. 직선 행렬 당시 회귀는 [v8 run.sh](../../artifacts/validation/2026-10-07/g1b_unit_v8/run.sh), 초기 가림/코너 후속 마감 목록은 [run_final_checks.sh](../../artifacts/validation/2026-10-07/g1b_extensions_v1/run_final_checks.sh)에 남긴다. 실행 전 로그 출력 경로는 새 경로로 지정한다. 선택형 launch 설치가 필요하면 `colcon build --packages-select arena_autonomy arena_bringup --symlink-install`을 수행한다. 현재 설치본은 `build/arena_autonomy`가 소스 디렉터리를 가리키는 symlink 설치라 런타임 import가 작업 트리 `local_follow.py`로 연결됨을 확인했다.

Gazebo 실행은 [runner v3](../../artifacts/validation/2026-10-07/g1b_runner_v3/run_case.sh) 또는 순차 [batch](../../artifacts/validation/2026-10-07/g1b_runner_v3/run_batch.sh)(실행 전 시험 잔존 프로세스가 있으면 중단)를 쓴다. 사후 감사는 [`audit_runs.sh`](../../artifacts/validation/2026-10-07/g1b_runner_v3/audit_runs.sh), 보존 자료 재생은 [`run_replay_v1.sh`](../../artifacts/validation/2026-10-07/g1b_resume_analysis_v1/run_replay_v1.sh)·[`run_replay_v3.sh`](../../artifacts/validation/2026-10-07/g1b_resume_analysis_v1/run_replay_v3.sh)다.

```bash
/usr/bin/python3 -B scripts/validate_g1_traffic.py --case stopped_center --seed 0 --mode g1 --output artifacts/validation/<새 출력 경로>
```

다른 등록 사례는 `--case slow_lead`/`stop_restart`, 배치는 `--seed 1`/`2`, 비교는 `--mode r0`를 사용한다. 출력 디렉터리는 새로 만들며 각 실행의 `report.json`·`source_snapshot.zip`·자세/상태/명령/STOP/MCU 진단·원시 수신 해시를 보존한다. 큰 원시 수신 자료의 기존 Git 제외 정책을 유지한다.

원시 `scans_received`·autonomy 상태·ego/actor 자세·접촉·trace/trajectory·actuation trace·취득 상세는 로컬 보존/Git 제외이며 summary·SHA·snapshot·보고서는 추적 가능하다. 10/7 실제 산출물에 `git check-ignore`를 대조했고 원시 필수 파일의 tracked 상태는 0개였다. 파일을 삭제하지 않았으며 새 소스 감사에 상세 raw 9파일의 해시를 남긴다.

시작 직선 행렬에 더해 초기 부분 가림·첫 U자 코너를 각 1회 확인했다. 기둥에서 드러난 경계 처리 개선은 유지하지만, 다른 공식/임시 시설·곡선의 얇은 물체·벽 바로 앞 긴 물체에서의 진행성은 Gazebo로 확인하지 않았다. 측정 여유 0.03 m는 시뮬레이션 C1(잡음 0, 분해능 0.015 m) 기준이며 실물 C1 잡음에서의 2차 정제 거동은 미검증이다. 초기 양쪽 가림·낮은 차량/후방 사각·다른 코너/옆차/분기·전체 랩·Jetson 처리 마감·실물 센서·구동·제동·정지·공식 출발/재출발은 남는다. 가상 MCU와 임시 물리 모델의 정지 결과를 MD20A 실차 안전으로 확대하지 않는다.
