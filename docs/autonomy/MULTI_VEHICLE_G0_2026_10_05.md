# G0: 상대 표적 관측과 통과 기하 시험 기반

작성: 2026-10-05. **G0-a 관측 계약·단면 기하·고정 센서 시험 기반 검증 완료**. 이후 같은 날 코드 검토에서 판정 보완·비수평 입력 거절을 추가했다. 아래 최초 Gazebo 결과와 후속 회귀/보존 자료 재평가는 서로 다른 소스의 검증이며, G0 전체나 다중 차량 주행 제어 완료를 뜻하지 않는다.

## 목적과 범위

[다중 차량 설계](MULTI_VEHICLE_DESIGN_2026_10_04.md)와 [전체 계획](../reports/DEVELOPMENT_PLAN_2026_10_04.md)의 첫 묶음이다. 이번에는 **기존 제어기를 보존하고, 상대 표적을 볼 수 있는 조건과 도로에 통과 폭이 있는 조건을 분리해서 확인**한다. 추종·우회 제어의 구현이나 전체 코스 다중 차량 폐루프 성공을 뜻하지 않는다.

사용자는 센서와 배치를 기존 계획대로 유지하기로 했다. B0183 RGB + C1 + LSM6DSOX를 유지하며, C1의 임시 기준은 전방 6 cm·측정면 9.5 cm·후방 60° 마스크다. ToF·깊이 카메라 추가나 구매안 변경은 하지 않는다. 이 구성 유지 결정은 실차 장착과 관측성 검증을 대신하지 않는다.

## 기준선과 변경 경계

- 구현 전 작업 트리는 미커밋 변경을 포함한다. `main`의 커밋만으로 당시 실행 소스를 재현할 수 없어 [기준선 manifest](../../artifacts/validation/2026-10-05/g0_baseline/sha256_manifest.json)와 소스 ZIP, Git 상태를 따로 보존했다.
- 기준선 ZIP은 162개 파일이며 SHA-256은 `486c6c73d7ff89cea3dcf4d5848f1206494b321787e00ac909f0587ba20204fc`다. ZIP의 Git HEAD는 `bfa2049fa2515327217394f9c03bac638b05a19f`이나 **그 커밋에 작업 트리 변경이 추가된 상태**다.
- 실행 담당의 첫 명령은 ROS 모듈을 읽는 과정에서 실패했다. 환경 진단 후 ROS·저장소 overlay를 명시적으로 불러오는 스크립트로 재실행하여 기존 5개 파일의 **175개 시험 통과**를 확인했다. 패키지를 새로 설치하거나 소스를 바꿔 해결한 결과가 아니다. [최초 로그](../../artifacts/validation/2026-10-05/g0_baseline/baseline_pytest.log), [재시험](../../artifacts/validation/2026-10-05/g0_baseline/baseline_pytest_corrected.log), [재현 스크립트](../../artifacts/validation/2026-10-05/g0_baseline/baseline_pytest.sh).
- 새 관측 계약과 평가 도구는 기존 주행 경로에 연결하지 않는다. `/drive` → 독립 보호층 → `/drive/safe` 경계를 유지하며, 시험 표적의 정답 위치·차량 ID·도로 정답을 대회 제어 입력에 넣지 않는다.

## 새 계약의 역할

### 관측 자료

`LocalScene`은 계획 기준 시각의 `base_link`에서 광선 원점·방향·유효 반환 끝점과 개별 취득 시각·출처 프레임·세대를 보존하는 ROS 독립 자료다. 유효 반환, 미관측, 장착 마스크를 구분한다. 좌표를 현재 시각으로 옮겼다는 이유로 취득 시각을 갱신하지 않는다.

이 계약은 광선 사이 또는 물체 뒤를 자유 공간으로 채우지 않는다. 지도·상대차 정답·물체 분류를 담지 않으며, 상대차 자체의 운동 추정이나 도로 경계·경로 후보의 구현은 후속 작업이다.

### 통과 폭의 필요조건

평가용 도로 폭은 45 cm, 양 차량의 기본 외형은 20×15 cm다. 이번 단면 검토의 자차 여유는 양옆 각 2.5 cm이며 **기존 시험의 임시 여유이지 실측 오차가 아니다**.

- 중앙의 15 cm 폭 표적은 좌우에 각각 15 cm만 남긴다. 자차 폭 15 cm만 적용해도 여유가 없고, 양옆 여유까지 적용하면 필요한 20 cm보다 부족하다.
- 표적 중심을 옆으로 15 cm 옮긴 사례는 반대쪽에 30 cm가 남아 단면 필요조건을 만족한다.
- 차체가 회전하면 횡방향 외곽은 `|폭 × cos(yaw)| + |길이 × sin(yaw)|`로 커질 수 있다.

**단면의 폭이 남는다는 것은 진입·회전·복귀 경로가 있다는 뜻이 아니다.** 곡선 주행 외곽, 조향 응답, 시간에 따른 점유와 안전한 복귀는 아직 이 도구의 판정 범위가 아니다.

## 구현 검토와 첫 실패

1. 미관측 광선에도 기준 프레임의 방향을 남기도록 계약을 보완했다. 반환 끝점이 없다는 이유로 관측 방향까지 잃으면 후속 가림 검사에 사용할 수 없다.
2. 라이다 피치를 모든 방위에 같은 수직 성분을 넣는 원뿔이 아니라 **기울어진 측정 평면**으로 수정했다. 앞/뒤 광선의 높이 변화는 반대이며 좌우 광선은 피치만으로 높아지지 않는다.
3. 최소 측정거리 안의 물체도 뒤쪽 물체를 가리도록 수정했다. 앞 물체가 너무 가깝다고 삭제한 뒤 뒤벽을 반환으로 선택하지 않는다.
4. 첫 신규 단위 시험은 42개 통과·5개 실패했다. 다섯 실패는 도로/잔디/벽 간격의 `0.45 + 2 × 0.20 == 0.85` 비교가 부동소수점 표현 차이로 실패한 같은 원인이었다. 절대 오차 `1e-9`의 숫자 표현 허용으로 수정했다. 안전 여유나 센서 허용 오차를 완화한 것이 아니다. [첫 실패](../../artifacts/validation/2026-10-05/g0_unit_v1/pytest.log), [수정 후 47개 통과](../../artifacts/validation/2026-10-05/g0_unit_v2/pytest.log).
5. 빈 회랑에서도 정면 무반사 때문에 정지하는 입력과 상대차 영향을 혼동하지 않도록 시험 회랑 끝 `x=-2, 6 m`에 벽을 명시했다. 벽 높이는 공식 기준과 같은 40 cm로 맞췄다. 이 닫힌 직선 시험실은 **공식 코스 전체가 아니며**, 실제 트랙 형상을 수정하지 않는다.

이 항목들은 신규 시험기·계약의 구현 검토이며 기존 주행 결과의 실패를 소급해서 설명하는 것이 아니다.

## 실행 결과와 한계

신규 단위 시험, 합성 기하, Gazebo의 실제 광선 기반 관측은 각각 별도 판정으로 기록한다. Gazebo 시험은 고정 센서와 상대 표적을 사용하는 관측 시험이며, 자차의 실제 감속·정지·충돌 안전·추종 완료 판정은 `미시험`으로 남긴다. 원시 광선 취득 시각, 완성 스캔 취득 구간, 표적 이동의 명령/관측 오차, 정상 종료도 분리해서 확인한다.

### Gazebo 시험기의 실패와 수정

세 번의 중앙 정지차 실행이 실패했고, 모두 **시험기 결함**이었다. 센서 관측 실패나 실제 차량 문제로 해석하지 않는다. 각 실행의 소스 ZIP·보고서·로그는 덮어쓰지 않고 보존했다.

| 실행 | 첫 실패 | 원인과 수정 |
|---|---|---|
| [`central_v1`](../../artifacts/validation/2026-10-05/multi_vehicle_g0_gazebo_central_v1/report.json) | `NoneType` context manager 오류. 원시·순차 스캔 0개, 렌더러 증거 없음. 브리지에 강제 SIGTERM이 필요해 정상 종료도 실패 | 별도 ROS `Context`를 만든 뒤 기본 문맥의 전역 executor로 `spin_once`했다. 같은 `Context`의 `SingleThreadedExecutor`를 명시하고 브리지를 `ros2 run` 대신 설치 경로에서 직접 실행했다. 최소 `Context` 검사에서 타이머 3회를 확인했다 |

함께 보완한 점은 다음과 같다. 수치 한도·시험 시간·사례 정의는 바꾸지 않았다.

- 시작 대기에서 원시 광선, 표적 자세, 시작 이전 자세, `set_pose` 서비스 중 무엇이 빠졌는지 따로 기록한다. timeout이면 gz 측 실제 토픽 목록도 남긴다. `TimeoutError`는 원인 미확정(`timeout_cause_undetermined`)으로 분류한다.
- 표적 자세의 부모 프레임이 월드(`g0_lab`)가 아니면 그 자세로 평가 라벨을 만들지 않고 실패로 처리한다.
- 평가 라벨의 거리 일치 허용치 0.02 m를 설정 파일에 명시했다. 이 값은 정답 상자 라벨링을 위한 시험기 가정이며 센서 거리 정확도나 안전 여유가 아니다. 다른 실패 한도도 실측 사양이 아닌 시험기 가정임을 설정에 적었다.
- 결과 ZIP에 `Context` 검사 스크립트와 신규 시험 4개를 포함했다.

각 행은 14개 검사와 신규 렌더러 로그의 D3D12(RTX 5070 Laptop) 증거를 확인했다. 정적 사례에서 이동 단계 검사는 적용 대상이 아니며, `dynamic_phase_observation_verified=false`를 유지한다. 표적 반환 수의 합성/Gazebo 일치를 판정 조건으로 삼지는 않았으며, 가장자리 사례는 합성 15개·Gazebo 13개다. 사전 조건은 유효 반환 1개 이상이다.

- 시간은 **시뮬레이션 시각**이다. 원시 입력 약 500 Hz, 완성 순차 스캔 약 10 Hz, 출처 공백 때문에 폐기한 회전 0개를 확인했다. 실제 C1의 점별 물리 취득을 그대로 재현한 것은 아니다. 500 Hz의 Gazebo 광선 프레임에서 회전 순서대로 점을 추출하며, 명목 광선 시각과 실제 원시 프레임 시각의 차이는 최대 약 1.8 ms였다.
- 이동 표적은 물리 구동 차량이 아니라 `set_pose`로 옮기는 표적이다. 명령만 보지 않고 Gazebo에서 관측한 자세와 센서 반환을 함께 검사했다. 정지·재출발 사례의 각 단계 내부에서 측정한 거리 변화는 약 0.257 m / 0 m / 0.746 m였다. 단계 양끝 여유 구간을 제외한 값이며 전체 이동거리와 혼동하지 않는다.
- 자차는 고정되어 있으며 잡음 없는 시험 센서를 사용했다. 실제 센서 오차·자차 이동 보정·상대차 추적·충돌 물리·MCU·공식 코스 주행을 검증한 결과가 아니다. 기존 R0 출력은 순수 함수의 참고 계산뿐이고 구동 명령은 발행하지 않았다.
- 정상 종료는 서버 종료 요청 응답·실제 프로세스 종료·소유 프로세스 그룹 잔존 없음·브리지 종료를 따로 확인했다. 정상 종료가 차량 정지를 뜻하지 않는다.

## 사후 코드 검토와 제한 수정 — 2026-10-05

사용자가 초기 구현의 잔여 문제·최적화 여부를 확인하고 수정할 만한 부분은 바로 보완하도록 요청했다. 기존 검토에서 다룬 기하/시각 문제를 반복 실행하지 않고 관측 계약·평가 코드·회귀를 대조했다. 이번 수정은 시험기와 관련 시험에만 한정했으며 주행 코드·센서 설정·물성·보호 한도는 그대로다.

### 발견한 두 부분

1. **표적 미검출과 입력 전체 무효의 혼동:** 빈 회랑/낮은 표적의 기대값이 표적 반환 0개라서 모든 비마스크 광선이 무효여도 기존 `visibility_verdict`가 통과할 수 있었다. 이 무잡음·닫힌 회랑에서는 표적이 없어도 배경 벽 반환이 있어야 하므로, `unknown_rays == 0`과 `return_rays > 0`을 별도 관측 완전성 조건으로 추가했다. 장착 마스크는 미관측 수에 넣지 않으며 이 조건을 실차의 일반 센서 정책으로 확대하지 않는다.
2. **비수평 광선과 2D 관측 변환의 불일치:** `ray_direction`과 상자 교차는 피치를 지원하지만 `make_scene`은 경사 광선의 거리를 수평 거리처럼 사용했다. 현재 고정값 `pitch_rad=0`에는 영향이 없으나, 향후 설정만 바꾸면 XY 좌표·R0 참고 계산이 틀어질 수 있었다. 올바른 비수평 투영을 구현하기 전까지 시험 설정 읽기와 직접 장면 생성에서 유한한 숫자 0 이외의 피치를 거절한다. CLI는 출력 생성·Gazebo 기동 전에 거절하며, 순수 3D 광선 기하의 피치 검사는 유지한다. **피치 시험을 완성한 수정이 아니라 지원하지 않는 평가의 조용한 실행을 차단한 수정**이다.

두 함수는 Opus 인계 전 `central_v2` 소스에도 같은 형태로 존재했다. 특정 모델만의 품질 판정으로 일반화하지 않으며, 기존 검토가 이 두 조건까지 완전하게 다룬 것은 아니었다.
