# ESP32-S3·LSM6DSOX 실물 입력 점검 — 2026-11-11

상태: **식별·형식/단위·5분 재시험·리셋/재개방 점검 완료.** 첫 5분 수신 실패를 보존했고 GC를 중지한 수신기로 재시험한 1회에서 UART CRC/sequence 공백0을 확인했다. 보정·정확한 취득 시각·I1 배선 검증은 미완료다. GPT-6.1 Sol이 워커 없이 직접 수행했다. 사용자는 앞선 6.2 표기를 말실수로 정정하고 현재 모델에서 진행하도록 승인했다. ## 범위와 설치 조건

- 사용자 설명상 정품 Adafruit 4438이며 ESP32는 처음부터 호환 보드로 구입했다. 실제 개발보드 제조사·PCB 판본은 미확인이다. YD/VCC-GND 자료를 실물 회로도로 확정하지 않는다.
- 사용자가 ESP32–IMU 7선과 Jetson USB-A→ESP32 USB-C를 연결했다. 점퍼선 때문에 보드가 떠서 기울어져 있으며 장착/자세 고정은 하지 않았다. 절대 축 방향·회전 부호·정지 여부를 외부 기준으로 검증하지 않았다.
- 목적은 형식·단위·주기·시각·기본 수신 확인이다. 영점/가속도 값은 예비 관측으로만 남기며 보정 계수로 채택하거나 저장하지 않는다. 이번 항목도 최종 장착 후 재확인한다. 모터·서보·엔코더는 구동하지 않았다.

## 형식·설정·시각

1. 센서 원본은 FIFO tag와 뒤 6바이트다. gyro/accel 각각 signed int16 세 축이며 tag>>3은 gyro=1·accel=2·timestamp=4다. 진단 앱은 원래 tag/바이트/순서를 보존한다. 관측 배열에는 timestamp→gyro→accel 순서가 나타나지만 이것만으로 세 항목의 정확한 취득 동시성을 확정하지 않는다.
2. UART는 이번 진단 앱이 만든 별도 **68 B 고정 프레임**이다. 센서의 고유 USB 형식이나 기존 차량 명령 프로토콜이 아니다. version/boot ID/sequence·MCU 읽기 시작/끝·FIFO 상태·원본·CRC32를 포함한다. [전체 명세](../../src/arena_vehicle_interface/firmware_imu_probe/README.md#진단-프레임-v1).
3. readback은 `CTRL1_XL=0x5C`, `CTRL2_G=0x54`, `CTRL3_C=0x44`, `FIFO_CTRL3=0x55`, `FIFO_CTRL4=0x46`이다. accel/gyro 명목208 Hz·±8g/±500 °/s·BDU/자동 증가·압축 없는 FIFO·timestamp decimation1 설정이다. 필터는 별도 최적화하지 않았고 전체 관련 readback을 보존한다.
4. raw gyro는 `raw × 0.0175 × π/180 rad/s`, accel은 `raw × 0.000244 × 9.80665 m/s²`로 수신기에서 한 번 변환했다. 가속도는 중력을 포함하는 비력이며 raw 센서 축을 유지한다. 장착 transform·자세 quaternion·중력 제거를 적용하지 않았다.
5. 내부 timestamp는 uint32 raw 그대로 저장한다. 명목25 μs를 MCU/Jetson 시간과 동일시하지 않는다. `INTERNAL_FREQ_FINE(0x63)=0xE2`, signed−30이며 ST 명세의 0.15%/LSB로 **−4.5%**다. 이 판독으로 계산한 tick 후보는 `25/0.955 = 26.178010 μs`, 192tick 간격의 주파수 후보는198.958333 Hz다. 실제 약199 Hz와 부합하지만 운영 시계 변환은 채택하지 않았다.
6. MCU 읽기 시각, 센서 timestamp, Jetson monotonic/벽시계는 별도로 보존했다. `time_contract_verified=false`이며 ROS 취득 시각·LiDAR 운동 보정 입력에 연결하지 않았다. 센서 온도 원시값도 기록했다.

주파수 편차 설명은 [ST DS12814 Rev4 §9.65](https://www.st.com/resource/en/datasheet/lsm6dsox.pdf)의 판독과 실측 대조다. 보정값을 임의로 만들어 명목208 Hz로 재표본화한 것이 아니다.

`continuous_no_gc`, 동일 app v2/921600 baud + receiver v3, 10초 준비 뒤 **300.002246 s** 측정했다.

**판정은 이 재시험 1회의 UART 수신 검사 통과**다. sensor-side 고유 표본 sequence가 없으므로 모든 내부 취득이 무손실이었다는 주장으로 확대하지 않는다. 순환 GC 변경 뒤 호스트 정지/전송 공백이 줄어 원인 후보를 지지하지만 GC 원인을 독립 계측하거나 반복 검증한 것은 아니다. 초기 실패를 성공으로 소급하지 않는다. 시작 시 동기화 전 버린684바이트는 원문에 보존했고 측정 프레임 CRC 오류와 구분한다.

재시험 뒤 포트를 닫고 다시 열어10초 수신했다. 추가로 **같은 포트를 연 상태의 `R` 명령**에서 새 boot ID·software reset reason3을 확인했다. 이후 포트를 닫고 다시 열 때도 새 boot ID·reset reason1이 관측됐다. 포트 재개방을 연속 스트림 재사용으로 취급하지 않고 새 boot 세대로 처리해야 한다. USB 제어선/드라이버가 이 리셋을 일으키는 정확한 과정은 분리 검증하지 않았다. 실제 USB 케이블을 뺐다 꽂은 시험은 아니다.

각 수집 끝에는 `X` 뒤 비활성 응답을 확인했고 호스트 수신 프로세스는 모두 종료했다. 임시 `/dev/ttyACM0` ACL은 원래 값으로 복원·대조했다. **ESP32에는 진단 v2 펌웨어가 남으며 기본 대기/ODR OFF**다. 대기 상태의 상태 프레임 송신은 유지한다. 원래 Flash를 복구한 상태는 아니며 백업은 보존했다. Jetson은 켜 둔다.

원문 UART→JSONL→집계는 수신기 모듈을 쓰지 않는 [별도 감사](../../scripts/audit_imu_probe_recording.py)로 대조했고 Jetson/PC 결과가 같았다. 비공개 보존 묶음의 SHA-256은 `ba2258c20db1f5beb20919df5c18cdb5202dc4d86c43f291590c85aa7b4678cd`이며 전송 후 일치했다. Python compile·빌드 스크립트 syntax 및 부분 프레임/ROM 접두부/SI 변환/CRC 훼손/잘못된 길이 재동기화5검사도 통과했다.

## 예비 영점과 미확인 항목

- 첫 5분의 첫60초 gyro 평균 후보는 `[-0.0147371, +0.0003731, -0.0155825] rad/s`다. 정지 여부를 독립 검증하지 않았으며 최종 보정값이 아니다. 이후240초와의 잔차를 오프라인 참고로만 계산했고 센서/운영 코드에 적용·저장하지 않았다.
- 재시험 첫60초의 별도 후보는 `[-0.0149562, +0.0003616, -0.0156152] rad/s`다. 이후 구간에서 이 후보를 뺀 평균은 `[-0.0011364, -0.0003504, -0.0000037] rad/s`였다. 이 계산 역시 오프라인 참고만 수행했으며 실제 전송 값은 보정 없는 raw/SI다. 미세 움직임/온도/영점의 기여를 구분하지 않았으므로 운영 계수로 확정하지 않는다.
- ST 자체 시험, 여섯 방향 가속도 교정, 자이로 배율·축/부호, 장착 transform, 정밀 잡음/온도 곡선·ROS 운영 연결은 미실행이다. 이번에는 사용자 지정대로 형식/수신을 우선했고 장착 후 이번 형식/주기/영점도 재확인한다.
- **I1 배선 동작 미검증:** 현재 FIFO watermark8보다 폴링이 빨라 최대3항목에서 비워져 인터럽트 발생 조건이 충족되지 않았다. IRQ0을 배선 불량으로 판단하지 않는다. watermark1 후보 빌드는 성공했지만 이후 WSL 명령/파일 접근에 `Wsl/Service/E_UNEXPECTED`가 발생해 회수·업로드하지 못했다. 실제 보드에는 watermark8 v2가 유지되며 저장소 실행 소스도 이에 맞췄다. 빌드/전송 실패를 실물 적용으로 기록하지 않는다.
- 최초 CMake 빌드는 ST 경로 변수가 IDF의 의존성 검사 subprocess에 전달되지 않아 실패했고 환경 변수 전달로 수정한 v2 빌드가 성공했다. SDK의 기존 Kconfig 경고와 app 빌드 성공을 구분한다.
- 카메라/C1 동시 부하·차량 진동·실제 USB 케이블 재연결 시험은 별도다. 이번 장치 식별/원시 수신을 실차 주행 검증으로 확대하지 않는다.

## 기록과 시뮬 후속

원본은 PC `build/esp32_imu_hardware_2026_11_11/` 및 Jetson의 격리 진단 디렉터리에 둔다. 첫 Flash 백업·원문 UART·전체 프레임 JSONL·실패와 재시험·각 수신기 판본·바이너리/설정·SHA-256을 보존한다. 공개 산출물은 장치 고유 ID/원문이 없는 집계만 둔다.

실물 점검 당시 시뮬의 명목208 Hz·±500 °/s·±8g와 범위는 일치하지만 실제 시간축에는 공장 편차가 있다. 백색잡음·0영점·정확한 표본 시각 가정은 실측값으로 확정하지 않는다. 별도 원시 입력 어댑터에서 단위·독립 스트림·시간 계약·장착 frame을 검증한 뒤 운영에 연결한다. 위 실물 점검 단계에서는 시뮬/주행 정책을 수정하지 않았으며, 이후 사용자 요청으로 아래 작업을 수행했다.

적용 대상은 현재 [`b0390_c1_jr60p20_sim.yaml`](../../src/arena_description/config/b0390_c1_jr60p20_sim.yaml)이다. 명목 ODR은 `nominal_rate_hz: 208.0`으로 남겼다. 장착·범위·질량·카메라·LiDAR는 유지했고 이전 B0183 재현 프로필은 변경하지 않았다. 변경 전 B0390 프로필도 원문 해시가 같은 `baseline_sensor.before.yaml`로 보존했다.

기존 `MotionHistory`는 고정208분의1초가 아니라 입력 timestamp의 간격으로 적분한다. 따라서 실제199 Hz라는 이유만으로 회전량이 약4% 틀어지는 구조는 아니다. 반대로 센서 내부 tick을 명목25 μs로 단정하는 것은 별도 오차가 되므로 센서→MCU→ROS 시각 대응을 확인해야 한다. 영점 상수를 빼는 기능과 장착 roll/pitch 투영은 이미 있으나, 이번 예비 평균을 그 매개변수에 넣지 않았다.

[`prepare_imu_observation_trial.py`](../../scripts/prepare_imu_observation_trial.py)는 성공 기록의 원시 gyro를 SI로 재계산해 기록값과 대조하고, 현재 `MotionInput.on_imu`에 59,721개를 넣어 **수용59,721·거부0**을 확인했다. MCU 읽기 상대 시각을 쓴 오프라인 입력 검사이며 실제 취득 시각·ROS 통신 검증은 아니다. frame은 임시 `imu_probe`, raw z를 차체 yaw로 간주한 민감도 가정이다. 이 기록만으로 새 평활 필터나 보호 조건을 추가할 근거는 찾지 못했다.

### 단독 주행 두 조건

v2026.11.06 본선·기존 B0390/JR60P20·순차 C1 10 Hz/500점·운동 보정 both·virtual MCU·기존 속도와 보호/STOP 조건을 사용했다. 영상은 생성하지 않았다. 두 주행 사이에는 요청 주기/잡음·설정/소스를 유지하고 시험 relay의 gyro bias만0으로 변경했다. Gazebo 잡음 실현값과 스케줄링까지 같은 결정적 A/B는 아니다.

| 조건 | 진행 / 한 랩 판정 | 최고속도 | 접촉·노면 이탈 | 정지/종료 |
|---|---|---:|---|---|
| 관측 평균을 오차로 가정, bias 약−0.895 °/s | **35.05/46.64 m, 실패** | 2.861 m/s | 표본0 / 0 | 실패 회수 STOP·정상 종료 |
| 같은 주기·잡음, bias0 | **46.87/46.64 m, 통과** | 2.865 m/s(약10.31 km/h) | 표본0 / 0 | STOP 안정·정상 종료 |

첫 주행의 정지 원인은 `follow_boundary_unconfirmed`·`long_outer_reference_unavailable`이며 독립 보호층은 `clear`였다. 공개 motion 상태142개에서 운동 보정 거부0, gyro 거부 사유도 없었다. 원천 IMU7,768개의 bias·순서·지연0 주입과 현재 소스 불변을 확인했다. 저장 판단1,529개를 완전히 동일하게 재생했고, 마지막 연속0명령 시작에서 같은 상태를 복사해 bias만 제거한30판단도 양수 명령0이었다. 즉 **멈춘 시점의 영점 하나를 바꾸면 바로 재출발한다는 결과는 아니다.** 그 반사실은 궤적·속도·과거 조향이 고정된 판단 단계에 한정된다.

대조는 IMU7,990개·실제200 Hz·bias0을 확인했고 공개 motion 상태147개에서 보정 거부0이었다. 제어기의 `/imu/data` 구독과 IMU/모터축 공개 토픽의 relay 단독 발행은 보고서로 확인했다. 독립 보호층까지 각각 실시간 구독 수를 센 별도 감사는 하지 않았으며 공유 입력 연결은 launch 설정과 상태 기록 범위다. 노면 평가는 첫 주행19,416개·대조19,955개 자세 표본에서 차체/조향 외곽 이탈과 바퀴 벽 접촉0이었다. 두 주행 모두 잔류 시험 프로세스0·등록 실행 소스 불변이다.

**해석:** 관측 산포 수준·약200 Hz에서 완주한 대표는 확보했지만, 미보정 편향을 포함한 주행의 견고성은 확보하지 못했다. 주행 전부터 누적된 경로 차이와 잡음/스케줄링 차이가 있으므로 단발 비교로 실패를 bias 하나의 확정 원인이라 쓰지 않는다. 실제 차량 연결 전 고정 상태의 영점과 장착 축/부호 확인은 유지한다. 제어기나 보호 판정선을 완화해 이 실패를 없애지는 않았다.

대조의 명시 STOP은 안정까지1.502초·변위1.122 m였다. STOP/정상 종료 통과는 즉시 제동이나 실차 제동거리의 증명이 아니며 기존 고속 제동 한계는 별도다. 원 보고서는 [편향 주입](../../artifacts/validation/2026-11-11/imu_observed_sensitivity_v1/solo_run1/report.json), [영점0 대조](../../artifacts/validation/2026-11-11/imu_observed_sensitivity_v1/zero_bias_after_overlay/report.json), [저장 재생·부분 반사실](../../artifacts/validation/2026-11-11/imu_observed_sensitivity_v1/postrun_audit.json)에 있다.

### 변경 검사와 남은 작업

- 관련127개 검사가 통과했다. 현재 기본 프로필과 시험 프로필이 만드는 차량 XML의 동일성, 평균0 유지, 기존 B0183값 보존, 원시 단위·다중 boot 거절을 포함한다. 기본 프로필의 요청 주기/잡음은 대조에서 사용한 값과 같으며 관측 편향을 자동 보정한 설정은 아니다.

- 실물 후속은 **고정 상태 영점·장착 축/부호 → 센서 내부 시간/MCU/ROS 대응·새 boot 이력 분리 → 동시 센서/실차 입력 연결**이다. 이번에 새 펌웨어·운영 어댑터·필터를 추가하지 않았다.
- 편향 조건의 경로 정지는 다음 리뷰에서 저장 입력과 함께 검토한다. 시설+C1 오차 결합의 기존20.21 m 실패도 별도로 유지한다. 새 C1 비균일 입력의 운영 연결·시뮬 검증은 사용자 후속 지시에 따라 이번에 섞지 않았으며 기존204검사·저장344스캔 검증 범위 그대로다.
