# C1 제조사 ROS 드라이버와 점별 취득 시각의 차이

2026-10-23. **실물 연결 전 공개 소스 감사와 PC 합성 시험**이다. C1/Jetson/serial/ROS 드라이버를 실행하거나 설치하지 않았다. 기존 시뮬레이션·보정기·독립 보호층은 유지한다.

## 1. 결론

현재 확인한 제조사 `sllidar_ros2`의 기본 `/scan`을 그대로 받아 `motion_scan_timing_verified=true`로 켜면 안 된다. 우리 운동 보정은 `stamp + index × time_increment`가 해당 반환의 취득 시각이라는 전제인데, 드라이버의 **정렬·반전·각도 칸 복제·호스트 대기 시간**이 그 전제를 충족한다고 확인되지 않았다. `angle_compensate`는 운동 보정이 아니라 각도 칸 채우기다. 이를 끄는 것만으로 시간 출처가 복구되지는 않는다.

기존 시뮬레이션의 순차 취득 계약이 틀렸다는 결과는 아니다. **실제 드라이버 입력은 별도의 계약 검증이 필요하다**는, 원래 비활성 관문의 이유를 구체화한 것이다. 하드웨어에서 확인하지 않은 시간·회전 방향·전송 지연은 여전히 미확정이다.

## 2. 확인한 판본과 소스

10/23 조회한 [Slamtec/sllidar_ros2](https://github.com/Slamtec/sllidar_ros2)의 main은 `34300099fadfc772965962dec837bf436706188f`(2024-06-17 commit)다. 아래는 이 SHA로 고정했다. 별도 최신 SDK나 다른 fork의 동작을 이 결과로 대신하지 않는다.

- [C1 launch](https://github.com/Slamtec/sllidar_ros2/blob/34300099fadfc772965962dec837bf436706188f/launch/sllidar_c1_launch.py): serial 460800, `Standard`, `angle_compensate=true`, `inverted=false`, `frame_id=laser`. 현재 팀 보정 어댑터가 요구하는 `laser_frame`과도 다르므로 장착 좌표/부호를 확인한 명시 설정이 필요하다. 이름만 바꾼다고 장착 검증이 끝나지 않는다.
- [ROS 노드](https://github.com/Slamtec/sllidar_ros2/blob/34300099fadfc772965962dec837bf436706188f/src/sllidar_node.cpp): `grabScanDataHq` 직전/직후 `now()`의 차이를 `scan_duration`으로 사용한다. 정렬 후 각도 보완을 적용하고, 발행 함수에서 조건에 따라 배열을 반전한다. `time_increment`는 항상 `scan_duration/(N-1)`이다.
- [동봉 SDK 구현](https://github.com/Slamtec/sllidar_ros2/blob/34300099fadfc772965962dec837bf436706188f/sdk/src/sl_lidar_driver.cpp): `ascendScanData_`는 무효 거리의 각도를 보완한 뒤 각도순 정렬한다. 전체 scan holder에는 첫 표본 timestamp가 있으나 ROS 노드의 호출은 이를 버린다.
- [SDK 인터페이스](https://github.com/Slamtec/sllidar_ros2/blob/34300099fadfc772965962dec837bf436706188f/sdk/include/sl_lidar_driver.h): `grabScanDataHqWithTimeStamp`가 있으나 장치 지원에 따라 시각이 추정값일 수 있다고 설명한다. 이 동봉 구현의 `_updateTimingDesc`는 `native_timestamp_support=false`로 설정한다. API 이름만으로 하드웨어 timestamp라고 부르지 않는다.
- [Linux 시계](https://github.com/Slamtec/sllidar_ros2/blob/34300099fadfc772965962dec837bf436706188f/sdk/src/arch/linux/timer.cpp)는 `CLOCK_MONOTONIC`의 μs다. [normal node handler](https://github.com/Slamtec/sllidar_ros2/blob/34300099fadfc772965962dec837bf436706188f/sdk/src/dataunpacker/unpacker/handler_normalnode.cpp)는 디코딩 중 host `getus()`에서 표본/필터/명목 전송 지연을 빼는 추정식을 쓴다. USB/스케줄링 적체를 전부 측정한 식은 아니며 ROS 시각과의 연결도 별도다. 실제 C1이 사용하는 응답 형식/firmware와 이 경로의 일치부터 확인해야 한다.
- [ROS LaserScan 의미](https://github.com/ros2/common_interfaces/blob/jazzy/sensor_msgs/msg/LaserScan.msg): header는 첫 광선 취득 시각, 시간 간격은 광선 간격이다. 호스트 함수 대기 시간과 같은 개념이 아니다.

## 3. 원문 함수로 한 제한 재현

[증거 묶음](../../artifacts/validation/2026-10-23/sllidar_contract_v1/README.md)은 공개 원문에서 `ascendScanData_`, `publish_scan`, 각도 보완 분기를 추출해 타입 stub으로 C++17 컴파일·실행했다. 바깥 ROS 노드/SDK 통신은 실행하지 않았다. 선택 함수의 로직을 Python으로 다시 써서 원문인 것처럼 비교한 시험이 아니다. 타입 stub·합성 입력이라는 한계는 남는다.

| 합성 조건 | 실제 원문 함수의 출력 | 의미 |
|---|---|---|
| 취득 순서 ID `[1,2,3,4]`, 각도 `[270,0,90,180]°` | 정렬 뒤 `[2,3,4,1]`, 기본 반전 발행 뒤 `[1,4,3,2]` | 발행 인덱스를 원래 취득 순서로 간주할 수 없음 |
| 같은 4점, 대기 인수 100/1/0 ms | `time_increment` 약 33.333/0.333/0 ms | 같은 데이터도 대기 인수로 시간 간격이 달라짐. 실제 대기 시간 측정이 아님 |
| 원래 서로 다른 500점, 보완 배수 2 | 720개 칸, 원본 500개·추가 중복 220개 | 동일 반환을 복제한 칸에도 서로 다른 시간 인덱스가 붙음 |
| 위 복제의 한 예 | 인덱스 716/717, 표시 시간 차 약 0.139 ms | 실제 두 번 측정한 증거가 아님 |
| 희소 유효 입력 | 717개 `+Inf` | 무효 거리/비어 있는 보완 칸의 원인을 발행 메시지만으로 구별하지 못함 |

500점·배수 2는 합성 사례다. 실제 수신 개수는 선택 scan mode·SDK 응답·회전 속도를 기록해 확인해야 하며 무조건 720점이 나온다고 확정하지 않는다. `+Inf`를 자유 공간으로 간주하지 않는 기존 정책은 유지한다.

## 4. 권장 이관 순서와 하지 않을 일

1. 사용할 드라이버/동봉 SDK SHA·C1 firmware·scan mode·실제 표본 주기를 먼저 보존한다.
2. 각도 정렬/복제 **전** 원래 각도·거리·quality·sync flag·원본 순번과 SDK 시각/호스트 수신 구간을 기록한다. SDK 시각도 추정인지, 어떤 host clock인지 검증한다. SDK 내부 callback에는 점별 시각이 있지만 공개 interval API는 그 시각을 보존하지 않으므로 호출 이름만 보고 선택하지 않는다.
3. 원본 순서와 시각을 유지하는 점별 표현을 보정기에 연결할 준비를 한다. `/scan`은 표시·기존 소비자용으로 별도 생성할 수 있지만, 복제된 칸을 새 관측으로 세지 않는다. 기존 균일 스캔 경로는 그대로 보존한다.
4. 장착 방향/회전 방향·시계 연계·이동 중 정적 벽/외부 기준으로 검증한 뒤 시간 관문을 승인한다. 실제 데이터를 얻기 전에는 합성 수학 검사까지만 한다.

**보류:** 기본 드라이버 설치/패치·장치 접근·시각 보정 상수 채택·운영 관문 true 전환. `inverted=true`, `angle_compensate=false`, `time_increment` 부호만 변경하는 식의 일괄 처방도 채택하지 않는다. 취득 순서와 각도 정렬은 별개이며 SDK의 추정 시각도 자동 정답이 아니다. 원본 `/scan`만으로 사라진 원천 시각을 정확히 복원한다고 약속하지 않는다.

## 5. 점별 입력 투영의 오프라인 후보

[`lidar_point_review.project_acquisition_points`](../../src/arena_autonomy/arena_autonomy/lidar_point_review.py)는 비균일 각도·점별 시각을 원래 취득 순서대로 받아 기존 `MotionHistory`의 평면 운동 이력을 적용한다. 기존 균일 `LaserScan` 투영 함수를 바꾸지 않았으며 **ROS 노드/launch/보호층에는 연결하지 않았다**. SDK 드라이버도 아니다.

- 입력: 동일 길이의 거리·센서 기준 각도·같은 시간 영역의 명시 시각 배열(2~8,192점), 현재 시각·거리 유효 범위. 8,192는 이 후보의 유한 처리 상한이며 C1 수신 개수 확정값이 아니다.
- 시각은 음수/비유한/역전/중복·미래·오래됨을 거절한다. 점이 무응답이더라도 해당 시각 검사를 생략하지 않는다. 이 후보는 엄격한 증가를 요구하므로 실제 clock 해상도 때문에 같은 시각인 표본에 임의 시간을 덧붙여 맞추지 않는다.
- `timing_verified`의 기본값은 false이며 명시한 Python `True`만 허용한다. 이는 호출자가 검증을 완료했다는 승인 조건이지 함수가 하드웨어 시각 정확도를 증명하는 기능이 아니다. 현재 합성 검사에서만 True를 사용했다.
- `deskew`는 마지막 원본 점 시각, `both`는 현재 시각으로 옮긴다. 기존 이력 공백/외삽 제한을 그대로 사용하고 누락을 0으로 채우거나 자동 무보정 전환하지 않는다.
- 반환은 원본 인덱스와 XY·원래 관측 나이다. `+Inf`/NaN/범위 밖 거리는 점으로 만들지 않으며 자유 공간을 생성하지 않는다. 각도 정렬·칸 복제·새 `LaserScan` 생성도 하지 않는다.

[v1](../../artifacts/validation/2026-10-23/lidar_point_review_v1/README.md)은 기존 보정과 합쳐 **55회귀 통과·소스 불변**이다. 균일 입력/양·음 각도 간격에서 기존 출력과 배열 단위로 같았고, 비균일 입력은 독립 직선 벽·정속 회전 기하와 대조했다. 입력 순서/시각/자료형·미래·무응답·이력 부족 거절도 확인했다. 실물 오차·timestamp 출처·지연·전체 제어기 처리량·새 폐루프 주행의 검증은 아니다. 실제 점별 시각 계약이 확보되기 전까지 운영 미연결로 둔다.

## 6. 움직이는 장면에서 제조사 발행과 보정을 연결한 대조

10/23 사용자 전달: 새 설계 자료와 도착한 부품은 없으며, 연결 가능한 시점과 차량 설계 수령은 다음 주 주말쯤으로 예상한다. 확정 납기나 실제 연결 승인은 아니다. 그동안 동일한 A1/G1 실패를 반복하는 대신, 앞 절에서 각각 확인했던 **제조사 배열 변환 → 현재 운동 보정 → 독립 기하 정답**을 한 시험으로 연결했다. 이번 묶음은 GPT가 워커 없이 구현·실행·검토했다.

### 6.1 방법과 판정 범위

[`audit_c1_motion_pipeline.py`](../../scripts/audit_c1_motion_pipeline.py)는 로컬의 고정 원문 SHA를 검사하고 `ascendScanData_`·각도 보완 분기·`publish_scan` 본문을 변경 없이 추출한다. ROS 자료형/발행은 시험 stub이며 **전체 SDK·실제 드라이버의 통신/스레드 실행은 아니다**. C++17+UBSan 검사, 원본과 시험 소스 snapshot·입출력·해시를 [v1 증거 묶음](../../artifacts/validation/2026-10-23/c1_motion_pipeline_v1/README.md)에 보존했다. 기존 저장소 상태와 운영 설정은 변경하지 않았다.

- **장면:** 공식 코스가 아닌 6×3 m 직사각형 방. 독립 폐형식으로 광선과 네 벽의 최초 교차점을 계산한다. 시작 시각 1.0 s, 500점/10 Hz, 마지막 점 1.0998 s, 평가 시각 1.15 s. 각도는 원문 Q14 표현, 거리는 0.25 mm 단위 반올림을 적용한다. 따라서 거리 양자화의 이론상 최대 오차는 0.125 mm다. 실제 C1의 정확도나 오차 분포를 뜻하지 않는다.
- **운동:** 정지, 직진 1 m/s, 좌/우 회전 1 m/s·±1 rad/s. `MotionHistory`에는 이상적인 200 Hz 평균 바퀴 속도 한 채널과 자이로만 전달한다. 축거 135 mm/바퀴 반지름 32.5 mm/센서 전방 60 mm를 사용한다. 모터축 28카운트의 양자화·IMU 잡음·슬립은 이번 시험에서 추가하지 않는다. 정답 pose는 광선 생성/평가에만 쓰며 제어기 입력이 아니다.
- **취득/호스트 조건:** 시작 위상 0°/93°, 함수 대기 100 ms/1 ms를 조합한 16조건과 무응답 1조건이다. 100 ms 사례는 함수 시작과 첫 취득이 우연히 일치하는 유리한 조건이고, 1 ms 사례는 이미 취득한 자료를 1.119~1.120 s에 가져온 경우다. 실제 C1 동기 경계·회전 방향·시계 동작의 실측이 아니라 명시한 가설이다.
- **오차 지표:** 같은 원본 반환의 현재 좌표에 대한 점 끝점 오차와, 벽 법선 방향 오차를 따로 계산한다. 무보정 열은 과거 점을 그대로 현재 좌표처럼 사용했을 때의 차이이므로 스캔 내부 운동과 평가 시각까지의 이동이 함께 들어 있다. 어느 값도 곧바로 조향 오차/차체 충돌 거리로 해석하지 않는다.
- **평가용 원본 ID:** 같은 원문 함수를 원본 ID를 거리로 표시한 별도 입력으로 한 번 더 실행하여 정렬/복제의 출처를 추적한다. 이는 시험의 정답 정보이며 `/scan`에서 실제로 제공되거나 복원 가능한 정보가 아니다. 원문에서 거리 크기는 정렬/칸 선택에 관여하지 않고 0/비0 여부만 관여하는 것을 확인했다.

아래 `원래 시각만 복원` 열은 **각도 칸은 그대로 둔 채 평가용 ID로 참 취득 시각을 주었을 때**의 잔차다. 이를 실제 복구 기능으로 구현한 것은 아니다. `원본 점별` 열은 칸 복제 없이 원래 각도/시간을 보존한 오프라인 후보의 결과다.

전체 17조건의 원시 수치·RMS·벽 법선 오차는 [report.json](../../artifacts/validation/2026-10-23/c1_motion_pipeline_v1/report.json)에 있다. 주요 해석은 다음과 같다.

1. **잘못된 시간으로도 겉보기 개선은 가능하다.** 위 사례는 무보정보다 오차가 작아졌지만 원래 형상을 복원하지 못했다. 두 위상 전체의 회전 조건에서 잘못된 시각 보정 잔차는 약 233~443 mm였다. 따라서 단순히 보정 전후 화면이 좋아졌다는 이유만으로 시간 계약을 승인할 수 없다.
2. **시간과 각도 칸 오차는 별개다.** 정지에서도 약 40 mm의 최대 끝점 차이가 있고, 원래 시각만 되찾아도 같은 수준이 남는다. 제조사 배열의 각도 칸과 해당 칸에 복사된 원본 광선의 각도가 다르기 때문이다. 이는 수 m 떨어진 점의 끝점 오차이며 실제 거리계 오차가 4 cm라는 뜻이 아니다. 위상 0° 정지의 최대 벽 법선 오차는 31.64 mm다.
3. **원본 시각 보존에는 의미가 있다.** 원래 점별 각도·시각 후보는 17조건 모두 양자화 상한 0.125 mm 이내였다. 이는 이상적인 동일 시계·정속 운동 이력 조건의 수학적 연결 확인이다. 실제 C1에서 이 정밀도를 달성했다거나, 실물 드라이버를 완성했다는 뜻이 아니다.
4. **시계 오차를 따로 남겨야 한다.** 동일 원본 점 시각에 ±10 ms를 더한 민감도 대조에서는 직진 최대 약 10.12 mm, 회전 최대 약 39.07 mm가 남았다. 이 값은 장면/거리/회전에 따라 변하며 허용 시계 오차를 10 ms로 정한 것이 아니다. SDK 추정 timestamp를 곧바로 정답으로 승인하지 않는 이유다.
5. **빈 반환을 복제된 새 측정으로 세면 안 된다.** 전부 유효한 입력은 500개 원본→720칸/추가 220회였고, 13점마다 하나를 뺀 사례는 유효 원본 461개→유효 685칸/추가 224회였다. 살아 있는 원본은 461개 그대로다. 제거한 원본이 새 유효 측정으로 복구된 것은 아니며, 빈 칸/실제 무응답/복제의 의미를 구별해야 한다.

17조건의 기하·출처·정지 불변·양자화 상한 검사는 모두 통과했고 소스/제조사 해시는 불변이다. 방위축/첫 교차점/좌우 반전·원본 투영·시각 오프셋/무응답·잘못된 원문 SHA/기존 증거 덮어쓰기 거절을 포함한 관련 회귀는 **72통과·exit 0·소스 불변**이다. 이전 전체 4,301회귀와 합산하지 않는다. 운영 코드를 수정하지 않아 전체 회귀와 Gazebo를 다시 실행하지 않았다.

### 6.3 다음 이관의 수용 조건

이번 결과로 운영 경로를 바꾸지는 않는다. 실물 연결 시 다음 항목을 **원본 기록 → 오프라인 대조 → 운영 연결** 순으로 확인한다.

1. 원본 점의 순번·각도·거리·quality·sync와 취득 시각의 출처/clock을 함께 보존한다. 정렬/복제된 `/scan`만 기록해 놓고 나중에 정확한 시각을 복원하려 하지 않는다.
2. 실제 packet/scan mode의 순서·시계 주기·SDK 추정 지연을 확인하고 C2의 host/ROS 시각과 연계한다. 제조사 timestamp라는 명칭만으로 `timing_verified`를 켜지 않는다.
3. 정지 벽에서 장착 축/각도 칸의 차이를 확인하고, 출력 비활성 수동 이동의 짧은 기록에서 무보정/원본 점별 보정을 같은 시각과 같은 원본으로 비교한다. 회전에서 남는 오차를 시간/자이로/장착/슬립으로 구별한다.
4. 실제 준비가 되기 전에는 점별 표현을 대회 제어기에 연결하지 않는다. 별도 `/scan` 표시가 필요하더라도 표시용 복제 칸의 수를 새 측정 개수로 쓰지 않는다.

G1의 43.093540 m·완주 0회, 후방 관측 문제, 독립 보호 경계와 기본 미활성 후보는 그대로다. 이 시험은 그 실패의 원인을 실물 C1 드라이버 탓으로 바꾼 것이 아니다.

### 6.4 벽이 반듯하다는 것만으로 시각을 교정할 수 없는 경우

[추가 진단](../../artifacts/validation/2026-10-23/c1_time_identifiability_v1/README.md)은 위에서 저장한 입력만 읽고 정속 직진/좌우 회전에 시각 오프셋 0/±10 ms를 적용했다. 새 제조사 코드/장치/주행은 실행하지 않았다. 서로 다른 원본 점을 오연관하지 않도록 **평가용 원본 ID와 벽 ID**를 사용했다. 이 연관 정보는 실물 제어기에 있다고 가정하지 않는다.

| 동일 시간 오프셋 +10 ms | 올바른 현재 좌표와 최대 차이 | 벽의 직선 맞춤 RMS 변화 | 0오프셋 결과와 최적 강체 정렬 뒤 최대 차이 |
|---|---:|---:|---:|
| 직진 1 m/s | 10.12 mm | <1e−11 m | <1e−11 m |
| 좌회전 1 m/s·1 rad/s | 38.98 mm | <1e−11 m | <1e−11 m |
| 우회전 1 m/s·−1 rad/s | 39.01 mm | <1e−11 m | <1e−11 m |

즉, **틀린 위치에 놓인 반듯한 벽**이 가능하다. 일정한 전진 속도/회전율에서는 모든 취득 시각에 같은 오프셋을 더한 결과가 점군 전체의 동일한 평행이동·회전으로 나타난다. 점군을 벽에 다시 맞추거나 매번 자유롭게 위치를 보정하면 시각 오차까지 숨길 수 있다. 위 회전 조건의 강체 회전 차이는 약 0.573°다. 이 수학적 조건에서 아홉 대조와 양·음성 대조가 통과했으며 소스/저장 입력은 불변이다.

따라서 첫 실물 시험에서 정지 벽과 일정한 수동 이동은 축/형상 확인용으로 사용하되, **그 결과만으로 clock offset을 추정·승인하지 않는다.** 시간 연계 자체의 측정 근거를 확보하고, 필요하면 출력 비활성 상태의 속도/회전율이 달라지는 수동 이동과 독립 시간/운동 기준을 별도로 기록한다. 가변 운동이 있다고 모든 지연/IMU 바이어스/장착 오차가 유일하게 분리되는 것도 아니다. 실제 기록의 관측 가능성을 먼저 점검하고, 독립 근거 없이 잔차가 가장 작아지는 계수를 자동 채택하지 않는다.

## 7. 정렬 전 normal 응답 decoder의 바이트·시각 대조

앞 절의 시작점은 이미 해석된 HQ 점이었다. 그 앞단도 확인하기 위해 [`audit_c1_normal_decoder.py`](../../scripts/audit_c1_normal_decoder.py)는 고정 SDK의 **normal 응답 `0x81` handler 전체와 실제 wire 자료형**을 C++17+UBSan으로 컴파일했다. [원문 보관본](../../artifacts/validation/2026-10-23/c1_normal_decoder_sources_v1/README.md)의 13개 입력 파일은 해시로 고정한다. 통신/스레드 의존성은 shim, host 시계·callback 수신기는 시험 대역이다. handler 본문·자료형·타이밍 구조체는 수정하지 않았다. 응답 descriptor와 scan mode 선택, 전체 SDK 수신기는 실행하지 않았다.

**실제 C1의 `ans_type`·firmware·표본 주기는 아직 미확정**이다. 기본 launch의 `Standard` 문자열만으로 모든 장치가 반드시 이 handler를 사용한다고 단정하지 않는다. 다른 capsule/HQ 응답은 별도 checksum·시간 계산 경로를 사용하므로 아래 결과를 그대로 적용하지 않는다.

### 7.1 같은 바이트도 host 처리 시각에 따라 timestamp가 달라진다

합성 입력은 50개 normal node(250 B), `sample_duration_uS=200`, baud 460800, UART, linkage delay 0이다. 200 μs/baud는 이 시험의 명시 입력이며 실측값이 아니다. 원문 추정 지연은 `200 + 100 + floor(50,000,000/460800) = 408 μs`다.

| 동일한 50점의 입력/가짜 host 시계 | 출력 점의 시각 범위 | 인접 timestamp 중복 | 각도·거리·quality·원본 순서 |
|---|---:|---:|---|
| 점마다 200 μs 뒤에 해석 | 9,800 μs | 0 | 동일 |
| 전부 한 청크, 시계가 같은 μs | 0 μs | 49 | 동일 |
| 전부 한 청크, decode마다 시계 +1 μs | 49 μs | 0 | 동일 |
| 25점씩 두 청크, 사이 20 ms | 20,000 μs | 48 | 동일 |

이는 실제 컴퓨터에서 이 지연이 발생했다고 측정한 표가 아니라, **동일 원문에 명시한 시계를 주었을 때의 동작 대조**다. 이 handler는 각 점의 해석 순간에서 408 μs를 뺄 뿐, 청크 안의 원래 취득 간격을 복구하지 않는다. 추정 timestamp가 단조 증가하더라도 취득 간격이 맞는다는 보장은 없다. callback 값의 존재만으로 `timing_verified`를 켤 수 없는 이유다.

### 7.2 바이트 무결성과 값 유효성도 별도다

- 원문 handler는 합성 분할 입력에서 순서를 유지한다. 4점의 모든 두 청크 경계 19가지와 고정 seed의 200점 임의 분할을 대조했다. 각도순 정렬·복제는 이 경로에 없다.
- 마지막 점이 잘리면 남은 1~4 B는 대기하며, 명시 `reset()`은 이를 버린다. 긴 시간 간격만으로 자동 reset되지는 않는다. 재연결 여부는 상류가 식별해야 한다.
- 잘못된 sync/check bit를 가진 지정 반례는 건너뛰고 회복했지만, 이것은 임의 바이트 손상의 완전 복구 보장이 아니다. normal 본문의 거리에는 CRC 검증이 없으므로 **유효 헤더 뒤 거리 bit flip은 다른 거리값으로 반환**됐다.
- 0거리·quality 0을 그대로 내보낸다. 유효 점 또는 자유 공간으로 자동 승격하지 않는다. 360°를 넘는 합성 wire 각도도 handler에서 명시적으로 거절하지 않고 Q14 정수로 축약된다. 실제 센서가 그런 값을 만든다는 주장은 아니다.
- 추정 지연보다 작은 합성 host 시각은 unsigned 차감으로 매우 큰 timestamp가 됐다. 이는 실제 Linux uptime에서 발생했다고 관측한 문제가 아니라 wrap/잘못된 시계 입력 반례다. 나중 수신기에서도 미래/역전/세대/범위를 검사해야 한다.

[v1](../../artifacts/validation/2026-10-23/c1_normal_decoder_v1/README.md)의 13조건·12판정과 [관련 회귀](../../artifacts/validation/2026-10-23/c1_normal_decoder_checks_v1/README.md) **126개가 통과**했다. timestamp 중복에 대해 점별 보정의 기존 기본 거절과, 실수로 승인해도 취득 순서 검사에서 거절하는 것을 확인했다. 시간 간격이 틀려도 단조 증가하는 경우는 자동 판별하지 못하므로 출처 검증은 여전히 필요하다. 운영 소스/ROS/주행·물성·기존 실패 결과는 변경하지 않았다.

**이 단계는 제한 마감한다.** 실제 response 정보를 얻기 전 모든 SDK 응답을 추측으로 구현하거나 시각을 일정 간격으로 강제 덮어쓰지 않는다. 실물 기록에는 SDK/firmware/응답 형식·원시 수신 청크와 host 구간·callback 원본 순번/값·SDK 추정 시각을 함께 남기고, 파일 무결성·디코더 통과·관측 유효성·시간 승인·운영 허가를 서로 구분한다.
