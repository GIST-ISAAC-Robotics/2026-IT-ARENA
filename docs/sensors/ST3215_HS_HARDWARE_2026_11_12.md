# ST3215-HS · Adapter A 최초 실물 시험

기준일: 2026-11-12. GPT가 워커 없이 준비·실행했다. **기본 통신·작은 각도 무부하 왕복·호스트 명령 공백 후 토크 해제를 확인했다.** 사용자도50초5회 왕복과 복귀를 육안 확인했다. 기존 IMU 앱은 실제 app partition 전체 바이트를 복구했으며 IMU는 사용자가 현재 분리했다고 확인했다.

## 조건과 범위

- 사용자 확인: 구동 모터 전원은 분리했으며 서보는 서보혼·조향 링크가 없는 상태다. 엔코더 시험은 CF 전원 배선을 확인하기 위해 중단했고 아직 펌웨어 변경/계수 시험을 하지 않았다.
- [통합 배선](../hardware/ESP32_GPIO_WIRING_2026_11_11.md)의 GPIO17 TX→Adapter A TX, GPIO18 RX←Adapter A RX, 공통 GND를 시험한다. 설계상 서보 전원은 M01 CH5 또는 CH6의12 V/2 A 단일 출력이다. 실제 채널 선택·극성·단자 전압은 이번 원격 작업에서 실측하지 않았다.
- 어댑터 전원 LED가 켜져 있다는 사용자 답변을 받았다. 최초 조회 시 A/B 점퍼 위치는 미확인이었다. 이후 전원을 분리하고 점퍼캡 두 개를 모두 A로 맞춘 뒤 재연결했다는 사용자 응답 후 통신이 성립했다. 초기 무응답을 삭제하거나 성공으로 소급하지 않는다.
- 읽기 성공·위치 모드/전압/상태 확인 후에만 현재 위치 기준 최대±114 counts(약±10.02°) 저속 왕복을 계획했다. 물리 조향 중립·한계, 외부 각도 정확도·실제 링크 부하는 별도다.

## 준비와 처음 조회

기존 IMU 앱과 일치하는 실제 Flash 앞쪽 `0x110000`바이트를 업로드 전에 읽어 PC/Jetson에 보존했다(SHA-256 `a91fd7217055977843888a9cb4d5156b181d61ad3f4b0d8a4d754f963eb7ef59`). 기존 app의 바이트 일치도 확인했다. 원래 전체16 MB 백업은 [IMU 실측](ESP32_LSM6DSOX_HARDWARE_2026_11_11.md)의 보존본을 유지한다.

[`firmware_servo_probe`](../../src/arena_vehicle_interface/firmware_servo_probe/README.md)를 ESP-IDF v6.1 캐시 환경에서 빌드하고 app만 `0x10000`에 올렸다. bootloader·partition/NVS는 변경하지 않았다. app SHA-256은 `64647128b46fe6a9f145b1c951a4c91f9dc2b798beeb6b4beb4ece8c33aeb645`다. 일반 WSL 진입 오류는 살아 있는 Ubuntu namespace에서 기존 사용자로 빌드해 우회했다. 시스템 재시작은 하지 않았다.

| 조회 | 실제 결과 |
|---|---|
| ESP32 `INFO` | `servo_probe_v1`, TX17/RX18, motor PWM/DIR readback0, armed=false |
| 기본 ID1, 지원8 baud | PING8회 모두 응답 없음. 서보 상태/위치 표본0 |
| ID0–253, 지원8 baud 전수 | PING2,032회 모두 응답 없음. 유효 응답/상태 표본0 |
| 쓰기·이동 | ARM/WRITE/EEPROM 변경/위치 명령 없음 |
| 최초 조회 뒤 | 호스트 조회 프로세스 종료·포트 소유자 없음. 진단 앱은 읽기 전용 대기 |

지원 속도는1,000,000 /500,000 /250,000 /128,000 /115,200 /76,800 /57,600 /38,400 baud다. 변경한 것은 ESP32 UART1의 전송 속도이며 서보 저장 baud가 아니다. 무응답을 서보 고장이나 모델/ID/속도 식별 성공으로 해석하지 않는다. USB 호스트 통신과 실제 외부 UART·어댑터·서보 통신을 구분한다.

## 점퍼 A 확인 후 실제 수신·움직임

공식 사진을 기준으로 **점퍼캡 두 개 모두 A 위치**를 안내했다. A는 UART→SERVO, B는 USB→SERVO다. 사용자가 A로 맞추고 재연결한 뒤 아래 결과를 얻었다. 이전 점퍼의 실제 배치는 사진/도통으로 독립 확인하지 않았다.

| 항목 | 실제 결과 |
|---|---|
| ID / baud | **1 / 1,000,000**, 8N1. 반환 상태0 |
| 모델/버전 필드 | model raw little endian **777 =0x0309**, firmware major/minor3/9, endian0. 이것만으로 HS 판본을 독립 식별하지 않음 |
| 구성 | mode0(position), resolution1, min0/max4095, offset0, phase12, 응답 레벨1 |
| 명목 형식 | ST 12-bit 단일 회전 위치0–4095, little endian. 부호 있는 위치/속도는 bit15, load는 bit10 부호-크기 형식으로 해석 |
| 읽기10초 | 피드백200개·요청204개, 위치3879 counts, 전압12.1 V, 온도28–29°C |
| 첫 제한 왕복 | 현재3879→3993→3879→3765→3879, 각 목표2.5초. 피드백264개, 정착 목표 오차 최대4 counts |
| 사용자 관찰용 반복 | 현재3877 기준±114 counts·**5회/20목표·이동 구간50초**. 피드백1,064개, 목표별 끝 오차 최대**5 counts(약0.439°)**. 사용자가 정상 움직임·복귀 육안 확인 |
| 반복 중 상태 | 전압12.1–12.2 V, 온도30–33°C, status0, 체크섬/순번 공백/응답 시간 초과0 |

| 설정 보존 | 매 실행 EEPROM0–39의 전후 원시 바이트가 같음. EEPROM/ID/baud/offset/모드 쓰기0. SRAM40(torque)·41–47(acc/goal/speed)만 호스트가 기록 |

목표 각도는 **서보축 약±10.02°**이며 조향 휠 각도가 아니다. 목표 정착 오차는 서보 자신의 자기식 위치 피드백과 명령 사이의 차이다. 외부 각도 기준에 대한 절대 정확도·부하 중 추종·링크의 중립/끝단/유격 교정을 뜻하지 않는다. 각 목표의 끝 표본이 운영 deadband 안이라는 식으로 허용 기준을 소급 변경하지 않았으며, 시험 전 설정한8 counts 이내 도달을 사용했다.

### 피드백 단위와 시각의 한계

상태는50 ms 요청 간격(20 Hz)으로 주소56–70의15바이트를 읽었다. 실제 레지스터 원문·MCU 요청 시작/종료 us·호스트 monotonic 수신 시각을 보존했다. **진단 UART 함수가 수신 창30 ms를 기다리므로, 호스트에서 관측한약35–37 ms를 서보 자체 응답 지연이라고 부르지 않는다.** 최대 제어율·순수 버스 지연·운영 시계 계약은 미검증이다.

전압은0.1 V, 온도는1°C 단위의 서보 내부 보고값이다. 전원단 멀티미터/오실로스코프로 전원 과도를 측정하지 않았다. current raw는 이번 작은 이동에서0–2였다. ST 표의6.5 mA/LSB를 적용한 환산은 후보이며, HS 센서 교정·정확성이나 **M01 입력/서보 전원선 전류**를 독립 측정한 값으로 취급하지 않는다. load는 모터 구동 PWM 비율 보고이며 토크 센서 값이 아니다. 이 결과로 M01의2 A 한도가 실제 조향·구속 전류까지 충분하다고 결론내리지 않는다.

## 종료·복구와 남은 작업

명시 종료와 명령 공백 후에 torque register40=0을 읽었다. 통신 단선/MCU 정지/전원 이상에서도 실제 토크 해제를 보장하는 독립 보호 시험은 아니다. MCU가 재부팅되면 진단 앱의 허가 상태는 사라지지만 외부 서보의 기존 토크 상태를 항상 해제한다고 보장하지 않는다.

서보 시험 후 기존 IMU 앱을 다시 올리고 **app partition1,048,576바이트를 실제 readback하여 시험 직전 이미지와 전부 일치**함을 확인했다(SHA-256 `a493bcf3af32abafc0240605fa0003b1cfa1407aeff14c2a337d9a82e5f216ca`). bootloader/partition/NVS는 이번 쓰기 대상이 아니었다.

복구 뒤 IMU 형식 상태4개는 비활성/ODR OFF였으나 WHO_AM_I가0이라 최초 복구 점검의 `restoration_verified=false`가 남았다. 이어 사용자가 **IMU는 현재 분리해 두었다**고 확인했다. 따라서 물리 IMU 재시험 통과라고 바꾸지 않고, 별도 Flash 전체 app partition 일치로 **앱 복구 완료**, 센서 응답은 **분리 상태**로 구분한다. 그 뒤 readback은 MCU를 다시 부팅하며 기존 앱은 기본 비활성 상태다.

최종 서보 토크는0, 호스트 수신/제어 프로세스와 포트 소유자는 없고 serial ACL은 원래 `root:dialout 0660` 그대로다. 새 진단 앱을 운영 구동 앱으로 채택하지 않았다. 다음은 IMU 재연결/CF 전원·파형/엔코더 손회전, 서보 장착 후 조향 중립·끝단·전류와 동시 UART/IMU/PCNT 시험이다. 모터는 구동하지 않았다.

원문/로그·Flash·빌드/해시 manifest는 비공개 `build/servo_hardware_20261112/`와 Jetson의 격리 시험 폴더에 보존한다. [공개 집계·재현](../../artifacts/validation/2026-11-12/st3215_servo_bench_v1/README.md)에 고유 장치 ID/원문 없는 요약과 감사 결과를 둔다. 수신 도구는 [`probe_bus_servo.py`](../../scripts/probe_bus_servo.py), 공식 프레임/체크섬·에코/깨진 응답·부호/단위 파서4검사는 [`test_bus_servo_probe.py`](../../tests/test_bus_servo_probe.py)다. 별도 [`audit_bus_servo_probe.py`](../../scripts/audit_bus_servo_probe.py)가 수신기 모듈을 사용하지 않고 전체 저장 요청/응답의 체크섬·순번·raw/JSON 일치·EEPROM 쓰기0·목표 범위·전후 설정을 대조했다.
