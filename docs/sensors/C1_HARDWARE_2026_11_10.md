## 결론과 시험 조건

**USB 통신·기본 ROS 수신은 통과했으나 시뮬레이션의 점별 취득 계약과 같지는 않다.** Standard 기본 출력에서 워밍업 5초를 제외한 **300.028998초·3,003스캔·10.005700 Hz**를 확인했다. 정상 종료했고 드라이버 오류/경고·USB 재연결은 관측하지 않았다. **201.027581 ms의 수신 공백 1회**는 보존한다. 센서 순번이 없어 원천 회전 누락인지 SDK/호스트 지연인지 확정할 수 없으며 무손실 판정을 하지 않는다.

사용자 요청에 따라 GPT가 워커 없이 직접 수행했다. 차량 모터·서보·자율주행·`/drive`는 실행하지 않았고 LiDAR 내부 회전 모터만 제조사 SDK로 시작/정지했다. 제어기·보호층·시뮬 프로필과 `motion_scan_timing_verified`는 변경하지 않았다.

**환경:** Jetson의 USB-A에 지급 어댑터로 연결했다. 사용자는 회전부가 위를 향하지만 의자 위여서 수평이 정확하지 않고, 약 5 cm 거리의 검은 가방 등으로 주변 대부분이 가려졌다고 설명했다. 이동하려면 Jetson을 꺼야 한다는 후속 설명에 따라 배치를 유지했다. 따라서 기울기·스캔면·기준 거리·거리 정확도·반사율·실차 장착 방향은 검증하지 않았다. 이 환경의 무응답 비율을 일반적인 C1 고장률/잡음 분포로 쓰면 안 된다.

## 원시 취득과 ROS의 실측

### 정렬 전 Standard SDK 반환

[`probe_c1_sdk.cpp`](../../scripts/probe_c1_sdk.cpp)는 `grabScanDataHqWithTimeStamp`의 **SDK 디코딩 후, 정렬·각도 보완 전** HQ node를 기록한다. UART 바이트 자체를 덤프한 것은 아니다. 원래 점 순서·`angle_z_q14`, `dist_mm_q2`, quality, sync flag, 함수 시작/종료 단조 시각, SDK 추정 첫 점 시각을 보존했다. SDK timestamp는 센서 하드웨어 시각으로 검증되지 않았다.

| Standard 원시 측정 10.080766초·102스캔 | 결과 |
|---|---:|
| 회전 수신률 | 10.019080 Hz |
| 회전당 점 수 최소 / 중앙 / 최대 | **500 / 508 / 524** |
| 측정창 총점 / 계산한 초당 점 수 | 51,924 / 약 5,100.01점/s |
| 인접 각도 차이(360° wrap 해제) 최소 / 중앙 / p99 / 최대 | **0.472412 / 0.703125 / 0.845947 / 0.983276°** |
| 첫 점 native 각도 최소~최대 | 356.385498~359.187012° |
| 0° wrap의 원본 인덱스 | 2~6 |
| sync flag | 102회 모두 첫 인덱스에 정확히 1개 |
| 거리 0 반환 비율 | 약 22.45%, 이번 배치에 한정 |

각도는 `angle_z_q14 × 90 / 16384` 도, 거리는 `dist_mm_q2 / 4000` m로 변환한다. 각 회전 배열 내부에는 359°→0° wrap가 1회 있었고 wrap를 풀면 취득 순서의 각도는 모두 증가했다. **고정된 -π부터 같은 간격으로 500점을 읽는 시뮬 배열과 다르다.** wrap 해제한 한 묶음의 각도 합은 356.984~361.890°로 변했다. 이것을 매번 정확히 360°인 균일 격자로 간주하지 않는다.

SDK 보고값은 Standard `us_per_sample=200`, answer type `0x81`이다. 실제 수신 count·주기에서 계산한 약 5.1 kpoint/s와 명목 5 kHz를 구분한다. 이 값으로 점별 실제 취득 시각을 강제로 196 μs 등으로 다시 만들어 검증됐다고 할 수 없다. 거리 표현의 0.25 mm 단위도 제조사의 **거리 분해능 15 mm/정확도 ±30 mm**와 다른 개념이다.

### 제조사 ROS 출력

[`probe_c1_ros.py`](../../scripts/probe_c1_ros.py)가 제조사 노드를 그대로 실행하고 LaserScan metadata·ranges·intensities·호스트 수신 시각을 기록했다. 5분은 기본 `angle_compensate=true`, 추가 20초는 false로 비교했다.

| 항목 | true: 5분·3,003스캔 | false: 20.002954초·201스캔 |
|---|---|---|
| 수신률 | 10.005700 Hz | 9.998523 Hz |
| 배열 길이 | **720 고정** | **485~535 가변** |
| 각도 | -π~+π, 약 **0.500695°/칸** | 양끝과 균일 표시 간격 모두 가변 |
| `time_increment` 중앙값 | **0.138896 ms** | **0.196674 ms** |
| `range_min` / `range_max` | 0.05 / **16 m** | 0.05 / **16 m** |
| frame / intensities | `laser` / ranges와 같은 길이 | 동일 |
| 종료 | 코드0·Stop motor·강제 kill 없음 | 동일 |

5분 수신 간격 중앙 100.294991 ms, p95 102.904322 ms, p99 105.087462 ms, 최대 **201.027581 ms**다. 150/200 ms 초과는 각각 1회다. 측정창의 NaN·-Inf·유한 범위 밖 값·header 역전·연속 동일 본문은 0이었다. `+Inf`는 회전당 **63~158개**였고 자유 공간으로 해석하지 않는다. 유한 반환의 관측 범위는 약 **0.0615~3.6105 m**이며 기준자로 검증한 거리가 아니다.

제조사 원문은 0 거리를 +Inf로 바꾸고 quality를 우측 2 bit 이동해 intensities로 전달한다. intensities를 교정된 반사율로 해석하지 않는다. 원시 native 각도는 `π - angle`의 ROS 각도로 변환하며 기본 배열을 반전해 각도 증가 순서로 만든다. 원래 취득 순서와 ROS 배열 순서를 같다고 볼 수 없다. `frame_id=laser`를 `laser_frame`으로 바꾸는 것만으로 실제 장착 축이 검증되지는 않는다.

**실제 원시 입력의 원문 함수 재생:** 앞의 102스캔을 고정 SHA의 `ascendScanData_`·각도 보완·`publish_scan` 함수에 변경 없이 넣었다. C++ 타입/전송은 기존 시험 stub이고 원본 인덱스 추적용 별도 label pass는 분석용이다. 회전당 **189~209칸(중앙198)**이 이미 사용한 같은 원본 반환을 재사용했다. 0~2개의 유효 원본 반환은 칸 충돌 등으로 표시되지 않았다. 따라서 720칸은 720번의 독립 측정이 아니다. 실제 ROS 메시지와 동시 취득한 쌍을 직접 일치시킨 결과도 아니다.

**시각 계약:** 원문 `scan_time`은 `grabScanDataHq` 함수의 호스트 대기 시간, `time_increment`는 그 값을 `(N-1)`로 나눈 값이다. 이번 true 출력에서 중앙 약 0.138896 ms였고 201 ms 공백 뒤에는 약 0.278747 ms까지 늘었다. 원시 명목 0.2 ms나 점별 노출 시각과 같지 않다. false도 정렬·반전과 가상의 균일 각도/시각 간격을 유지하므로 보정기 시간 관문을 승인할 근거가 되지 않는다. 기존 [시각 감사](C1_DRIVER_TIME_CONTRACT_2026_10_23.md)의 경고가 실물 이관에서도 유효하다.

## 옵션·회전수·정확도

장치가 보고한 모드는 **Standard(id0, 0x81)**와 **DenseBoost(id1, 0x85)**이며 둘 다 명목 200 μs/점이다. DenseBoost도 기본 회전에서 20.070470초·202스캔·10.014713 Hz, 회전당 **487~534점(중앙508)**으로 수신됐다. Standard와 다른 디코더/전송 형태를 쓰며 이번 결과만으로 더 높은 거리 정확도를 의미하지 않는다. 선택 기본값은 Standard를 유지한다.

장치/SDK는 모드별 최대 거리를 **Standard16 m·DenseBoost40 m**로 보고했지만, [C1 공식 사양](https://www.slamtec.com/en/c1/spec)은 흰색70% 반사율 **12 m**, 검은색10% **6 m**, 명목 분해능15 mm·정확도±30 mm다. 능력 조회 metadata를 실물 유효 거리나 시뮬 range 상향 근거로 사용하지 않는다.

공식 사양의 운용 범위는 **8~12 Hz, typical10 Hz**다. 명목 5 kpoint/s로 계산하면 8/10/12 Hz에서 약625/500/417점, 각도 간격0.576/0.720/0.864°다. 빠른 회전은 갱신과 한 회전 안의 운동 왜곡에 유리하지만 공간 점 밀도가 줄어든다. 거리 오차가 회전수에 따라 얼마나 달라지는지는 이번 환경에서 측정하지 않았다. 제조사가 typical10 Hz를 선택한 세부 이유는 공개 자료에서 확인하지 못했으며, 균형점이라는 설명은 설계적 해석이다.

**최초 속도 조회 실패:** C1 [사용자 설명서](https://wiki.slamtec.com/download/attachments/83066883/SLAMTEC_rplidarkit_usermanual_C1_v1.0_en.pdf?api=v2&modificationDate=1700531526658&version=1)에는 회전 속도 조절 기능이 있다. 그러나 동봉 SDK의 `checkMotorCtrlSupport`는 model major4인 C1을 내장 RPM 제어(major≥6) 분기로 보내지 않고 accessory-board 질의를 수행하며 실제 **0x80008002 timeout**을 반환했다. 최초 probe는 지원 확인에 실패해 **480/720 RPM 설정 명령 전에 중단**했다. 이때의 `support=0`은 하드웨어 기능 부재를 증명하지 않으며 실패 기록을 보존했다.

2026-11-10 조회한 공식 `rplidar_sdk` master SHA `99478e5fb90de3b4a6db0080acacd373f8b36869`에도 같은 판정 분기가 있었다. 소스만 보존했고 그 SDK로 운영 드라이버를 교체하지 않았다. 기존 ROS의 `scan_frequency`는 각도 보완 칸 계산용이며 실제 수치로 motor speed를 설정하지 않는다. 따라서 launch 값을8/12로 바꿨다는 로그만으로 회전수 변경을 주장하지 않는다.

### 사용자 재시도 요청 뒤 실제 RPM 제어 성공

공식 [MOTOR_SPEED_CTRL 프로토콜](https://wiki.slamtec.com/download/attachments/83066883/LR001_SLAMTEC_lidar_protocol_v1.0_en.pdf?api=v2&modificationDate=1677801912000&version=2)의 `0xA8`·16-bit RPM payload와 기존 SDK의 해당 송신 분기를 대조했다. **공식 원본을 유지한 별도 SDK 사본**에서 C1 major4도 기존 RPM 분기로 들어가도록 조건 한 줄만 바꾸어 진단용으로 링크했다. [patch·원본/변경 해시](../../artifacts/validation/2026-11-10/c1_hardware_input_v1/c1_rpm_classification.patch)를 보존했다. 분기 변경 뒤의 `support=2`만을 독립 하드웨어 증거로 삼지 않고 실제 도착 주기와 점 수를 판정했다.

| 요청 | 실제 수신 회전률 | 회전당 점 수 중앙 | 유효 측정창 | 판정 |
|---|---:|---:|---:|---|
| 480 RPM / 8 Hz | **8.012739 Hz** | **640점** | 20.093006초·162스캔 | 적용 |
| 720 RPM / 12 Hz, 시작 직후 요청 | **9.961163 Hz** | **508점** | 20.077977초·201스캔 | **미적용**. 1032점 묶음1개도 보존 |

12 Hz 성공 절차는 기본 스트림의 첫 반환 후5초 대기 → `setMotorSpeed(720)` → 추가5초 안정화 제외 →20초 측정이다. `--rpm-after-warmup`으로 이를 재현한다. 처음 명령이 초기화 과정에서 영향을 받았을 가능성은 있으나 **미적용의 정확한 내부 원인은 미확정**이다. API 성공 반환을 속도 적용으로 간주하지 않고 최초 실패와 후속 성공을 별도로 유지한다. 8 Hz 점 수612~660, 지연12 Hz 점 수412~440으로 실제 밀도 차이를 확인했다. 각도 간격은 여전히 불균일하며 거리 정확도 차이를 측정한 것은 아니다.

분기 수정 뒤 장치 설정 조회도 성공해 최소480·기본600·최대1200 RPM을 반환했다. 최대1200 RPM이라는 capability 값은 20 Hz의 안정성/정확도를 시험한 결과가 아니다. 이번에는 공개 nominal 범위8~12 Hz에서만 시험했다. 원래 ROS 드라이버는 변경하지 않았고 속도 제어는 이 firmware1.02/장치에서 별도 진단 실행만 확인했다. **최종 기본10 Hz 수신을 실측한 뒤 stop/속도0 성공과 잔여 프로세스0·권한 복원**을 확인했다.

| 가변 점 수·불균일 각도·시작 위상 | 원시 count/각도 배열·sync를 재현 입력으로 사용. 500점 고정·시작 -π 가정과 별도 프로필로 비교 |
| 회전 방향과 배열 순서 | native 순서·`π-angle`·정렬/반전·0° wrap를 분리. 실제 차체 x축/yaw는 실장 후 교정 |
| 드라이버 표현과 원천 취득 | 720 표시 칸/칸 재사용을 별도 변환층으로 재현. 복제 칸을 새 관측·새 취득 시각으로 만들지 않음 |
| 시간·지연·회전 누락 | SDK 추정 시각·호스트 batch·ROS header/간격을 분리. 이번201 ms 공백을 1회 관측한 값으로 보존하되 고정 손실률로 일반화하지 않음 |
| 거리와 무응답 | 12/6 m 사양과16/40 m metadata 구분. +Inf/거리0은 미관측 유지. 이번 기울어진 가림 환경으로 오차 분포/정확도 상수를 맞추지 않음 |
| 속도·스캔 모드 | Standard/DenseBoost를 구분. 위 8/10/12 Hz 실측과 불균일 점 배열을 속도별 후보로 사용하되 짧은8/12 Hz 시험을5분 안정성/정확도 검증으로 확대하지 않음 |

**현재 시뮬 설정은 수정하지 않았다.** 후속에서는 이 기록을 입력 경계 재현에 사용하고, 평탄·기준거리·장착 방향·이동 중 정적 벽/외부 시간 기준을 확보한 뒤 실제 운동 보정 계약을 검증한다. 물성·차체 크기·보호층을 이 기록에 맞춰 임의로 바꾸지 않는다.

## 11/11 선행 수정: 비균일 원천 각도 입력

사용자의 즉시 수정 요청에 따라 GPT가 [`local_scene.py`](../../src/arena_autonomy/arena_autonomy/local_scene.py)에 `scene_from_measurements`를 추가했다. 이전 `scene_from_scan`은 `angle_min+i*angle_increment`인 균일·양수 간격 입력만 표현했다. 새 함수는 **각 측정의 각도·거리·취득 시각·SE(2)를 같은 순서로 받아** 가변 개수·비균일 각도·시계 방향·각도 wrap를 표현한다. 배열을 정렬·패딩·보간하거나 같은 각도의 측정을 삭제하지 않는다. 기존 함수와 변환·장착 마스크·거리 유효성·출처 검사를 공유하며, 기존 함수의 출력·오류 계약은 비교 검사로 유지했다.

[`audit_c1_measurement_scene.py`](../../scripts/audit_c1_measurement_scene.py)로 11/10 저장 SDK CSV를 검사했다. 원시 값의 `π-angle` 좌표 대응은 vendor 표시 기준이며 실제 차체 yaw 교정은 아니다. 품질0/거리0/범위 밖 값은 유효 반환으로 만들지 않는다.

| 입력 기록 | 스캔 | 원천 측정점 | 회전당 최소/중앙/최대 | 각도·순서·개수·유효 거리 |
|---|---:|---:|---|---|
| Standard 10 Hz | 102 | 51,924 | 500/508/524 | 보존 |
| 안정화 후 12 Hz | 242 | 102,716 | 412/424/440 | 보존 |

**검증 범위:** 새 입력·기존 생성부·격자 원본 대조·장착·순환 인접성 관련 204개 검사 통과(새 검사31개 포함). 최초201통과/3실패는 테스트 실행 환경의 ROS Python 경로 누락이었다. ROS setup만 재적용하거나 환경변수를 덧붙인 실행에서도 해결되지 않아, 설치된 `xacro` 위치를 확인하고 명시 경로를 사용한 뒤 해당3개가 통과했다. 소스 오류로 우회하거나 실패를 숨기지 않았다. [집계와 재현](../../artifacts/validation/2026-11-11/c1_measurement_scene_v1/README.md).

**미완료 경계:** 저장 CSV 검사의 시각은 **투영 확인용 합성 상대 시각(점당200 μs)**이며 실제 SDK 시각을 검증한 결과가 아니다. `motion_scan_timing_verified`는 바꾸지 않았다. 새 함수는 ROS/SDK 운영 어댑터에 아직 연결하지 않았고, 기존 `source_valid`의500점·방향 조건, 고정 각도 셀 폭, 순환 인접성, 점별 운동 보정 입력까지 해결한 것은 아니다. 이 조건들을 숫자만 바꿔 우회하면 복제된 ROS720칸을 독립 측정으로 잘못 받아들일 수 있으므로 명시적 원천 입력 계약과 함께 검토한다. 기존 시뮬 설정10 Hz·주행 정책·독립 보호층은 불변이다. 새 시뮬/하드웨어 구동은 하지 않았다.

**11/11 후속 연결(위 선행 단계 이후):** native 원천 배열·점별 보정·가변 관측 셀·ROS 제어/독립 보호·기록/재생과 선택형 시뮬까지 연결했다. 실제 입력의 각도 템플릿을 쓰되 시간은 시뮬 근사이며 실물 취득 시간 승인은 아니다. 두 초기 실행 실패(overlay metadata·header 반올림 비교)와 수정/후속 주행은 [native 검증 기준 기록](../../artifacts/validation/2026-11-11/c1_native_sampling_v1/README.md)에 관리한다. 위204검사/미연결 문구는 당시 선행 단계의 범위다.

**자문 예약 변경:** 11/11 오전5시 Fable 5.2·effort medium 예약은 사용자 후속 지시로 삭제했다. 자문은 별도 요청 때만 진행한다. 이전 xhigh 자문은 조사 중5시간 한도로 최종 의견 없이 종료했으며, 이번 수정은 GPT의 독립 선행 작업이다. 12 Hz 채택·주행 상태 전이·경기 프로필 정리는 리뷰 후 판단한다.


**11/11 native 전송 후속:** [r81](../../artifacts/validation/2026-11-11/native_nonreturn_r81_v1/PLAN.md)에서 시뮬 원천 +Inf와 NaN을 모두 JSON null로 합친 전송 문제를 분리했다. +Inf는 `"+inf"`, -Inf는 `"-inf"`, NaN은 null로 보존하며 모두 관측 공간을 자동으로 만들지는 않는다. 기존 저장 null은 출처를 알 수 없어 NaN으로 유지한다. 이는 실물 SDK의 거리0/품질0을 일괄 +Inf로 바꾸거나 실제 취득 시각을 승인한 작업이 아니며, 제조사 ROS 변환과 원시 native 어댑터의 판정은 각각 확인해야 한다.

**11/11 반복성 진단:** 원시 Standard10Hz 두 기록의102스캔씩을 [각도 조건을 둔 반복성 비교](../../artifacts/validation/2026-11-11/c1_repeatability_v1/README.md)로 재분석했다. 실제 방위 차이0.08° 이하인 연속 쌍의 거리 차이95백분위는 관측률만 선별한 집합에서4.75/3.00mm였다. 이 짧고 기울어진 가림 환경은 절대 정확도·전체 표면·주행 진동의 검증이 아니다. 제조사±30mm **정확도**를 매 측정 독립±30mm **균등 잡음**으로 동일시하지 않으며, 기존 균등 잡음/추가 지연 프로필은 그대로 스트레스 시험으로 남긴다. 이번 결과로 잡음 상수·재관측 거리·보호 조건을 교정하지 않았다.

**11/11 SDK 시각 일관성 진단:** [r111 저장 배치 비교](../../artifacts/validation/2026-11-11/c1_time_consistency_r111_v1/README.md)에서 SDK 추정 첫 시각에 명목200 μs를 붙이면 초기10 Hz 기록의101개 연속 쌍 모두 명목 마지막 점이 다음 배치 첫 시각과 겹쳤다(중앙1.791 ms). 8/12 Hz·최종10 Hz에서도 같은 종류의 불일치를 확인했다. 약196 μs의 배치 평균을 실제 취득 주기로 교정하거나 운영에 적용하지 않았으며, 기존 시뮬 시간·실물 시간 승인도 바꾸지 않았다. 실물 운동 보정 전 점별 시간 계약을 별도로 검증해야 한다.

**같은 SDK 소스의 시각 출처 확인:** [r127](../../artifacts/validation/2026-11-11/c1_timestamp_source_r127_v1/README.md)은 Standard 점에 하드웨어 timestamp가 없고, SDK가 호스트 해석 시각에서 C1 명목 조건의408μs 지연 추정치를 뺀다는 것을 확인했다. 회전 시작 sync 점의 이 값을 배치 첫 시각으로 반환한다. 따라서 SDK 첫 시각과 명목200μs를 조합한 값은 실제 점별 취득시각으로 검증되지 않았다. 실제 주기 편차와 USB/호스트 지연의 기여는 미분리이며, 장치 재구동·교정값 채택·운영 연결은 하지 않았다.
