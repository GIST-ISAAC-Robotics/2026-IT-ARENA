# ESP32 통신 단절·발열 사건 증거 정리

대상은 2026-11-14 조립 후 DC 시험 중 MCU 응답이 끊긴 사건이다. 2026-11-15 첫 정리에서는 노트북 파일을 모았고, 후속 회수에서 **Jetson의 시험 원본 83개와 사건 시간대 커널 로그**를 읽기 전용으로 복사했다. ESP32 조회·리셋·출력·재현 시험은 하지 않았다. [경기 무주행 결과](../reports/COMPETITION_RESULT_2026_11_14.md)와 고장 원인 분석을 구분한다.

## 현재 확인할 수 있는 결론

마지막 정상 MCU 수신 뒤 **27.314343111초**에 15% 시험을 위한 상태 조회가 기록됐다. 원 명령에서 이 단계는 `?`와 약 2.008초 뒤 `X`뿐이며 **재연결 뒤 구동용 ARM/PULSE가 없다.** UART 원시 바이트를 CRC 검사해 해석 프레임 14,145개와 모두 대조했다. 조회 이후 새 프레임은 0개, 이후 재접속 UART도 0바이트였다. [회수 증거](../../artifacts/validation/2026-11-15/esp32_jetson_recovery_v1/README.md)

앞서 **모터 전원을 분리한 15% 논리 출력 검사**는 1회 존재한다. 따라서 ‘15% 명령이 한 번도 없었다’고 전체 기록을 요약하면 틀린다. 전원 없는 보호 검사와 전원을 다시 연결한 뒤 시작하지 못한 구동 시험을 구분해야 한다.

LED 소등·발열·보드 단독 단락 의심은 사용자의 현장 전달이다. 전압·전류·온도 파형과 안정된 저항 실측값이 없으므로 **전기적 고장 순간과 원인은 확정할 수 없다.** 역기전력, 전원·배선 문제 또는 MCU 보드 손상 중 하나로 단정하지 않는다.

## 사건 시각

아래 밀리초 단위 절대 시각은 [당시 DC 보고서](MOUNTED_DC_TEST_2026_11_14.md#통신-중단-시각-대조--한국시간)의 monotonic↔realtime 대응 기록을 보존한 값이다. [기존 시각표](../../artifacts/validation/2026-11-15/esp32_incident_v1/timeline.json)의 원문은 커밋 `0af38406664de39ba7152bb5922397b2f48f6bbe`에 고정했다. 후속 회수는 UART·명령의 단조 시각 차이와 커널 로그의 초 단위 벽시계를 직접 확인했다. 남은 journal에 해당 시간대 기록은 없었다.

| 한국시간 11/14 | 기록된 사건 | 이번 로컬 증거 |
|---|---|---|
| 13:35:48.387 | 엔코더 손 회전 결과 표본 | 결과 JSON과 방향 정정 있음 |
| 13:36:26.551 | 마지막 유효 MCU 프레임. PWM 0·미무장·비활성 | seq 14144를 UART 원본과 대조. 파일 최종 수정 13:36:26.549953205 |
| 13:36:53.865 | 15% 구동 전 상태 조회, 새 응답 없음 | 명령 로그에 `?`·`X`와 오류. 새 프레임 0 |

USB 분리는 마지막 수신보다 약 3분 52초 뒤였다. 회수된 `kern.log`에서 포트 1-1의 분리 4회, 재등록 4회, ACM 등록 4회를 확인했다. 포트 이벤트만으로 변환칩·본체·전원 중 어느 부분에서 이상이 시작됐는지는 알 수 없다.

## 출력·엔코더 증거

아래 시간은 MCU의 `ended_us - started_us`다. PWM 파형이나 모터 단자 전압을 외부 계측한 값이 아니다. 전원 연결 상태는 당시 사용자 확인/시험 단계의 기록이다. [원본 JSON 사본·계산값](../../artifacts/validation/2026-11-15/esp32_incident_v1/observations.json).

| 시험 | 모터 전원 | 요청 | 논리 출력 지속 | 종료 사유 | 종료 상태 |
|---|---|---|---|---|---|
| 5% | 연결 보고 | 5초 | 360.041ms | `no_encoder_start` | duty0·PWM pin0·미무장 |
| 7.5% | 연결 보고 | 0.5초 | 500.052ms | `deadline` | duty0·PWM pin0·미무장 |
| 15% 보호 검사 | 분리 확인 | 5초 | 360.029ms | `no_encoder_start` | duty0·PWM pin0·미무장 |
| 15% 실제 구동 준비 | 재연결 보고 | 구동 전 조회 | 시작하지 못함 | response timeout | 새 상태 확인 불가 |

세 출력 검사 모두 엔코더 증가가 0이다. 5% 시험 뒤 사용자는 무회전을 보고했고 7.5% 육안 회전은 확인되지 않았다. 그 후 손 회전에서는 PCNT/software 모두 **+690**, invalid/drop 증가 0을 확인했다. 원 JSON의 ‘전진’ 보고는 후속 사용자 정정으로 **후진**이다. 원본을 덮어쓰지 않고 [원 결과](../../artifacts/validation/2026-11-15/esp32_incident_v1/evidence/manual-encoder-result.json)와 [방향 정정](../../artifacts/validation/2026-11-15/esp32_incident_v1/evidence/operator-direction-correction.json)을 함께 보존했다.

## 재접속과 상태 판정

- [구동 전 오류](../../artifacts/validation/2026-11-15/esp32_incident_v1/evidence/start15-precommand-error.json): `waiting_for_ready`, `response timeout; no automatic retry`.
- [재접속 오류](../../artifacts/validation/2026-11-15/esp32_incident_v1/evidence/start15-reconnect-error.json): `startup`에서 같은 timeout.
- [회수된 명령2건](../../artifacts/validation/2026-11-15/esp32_incident_v1/reconnect_command_excerpt.json): `?`→5.010867012초 뒤 `X`. 이 파일 범위에 ARM/PULSE 없음. 원 JSONL은 로컬 보존한다.
- [종료 기록](../../artifacts/validation/2026-11-15/esp32_incident_v1/evidence/start15-reconnect-closed.json): `port_closed=true`, **`stop_confirmed=false`**, `last_motor=null`. 포트 닫힘은 MCU의 새 정지 응답이 아니다.
- [부트로더 조회 발췌](../../artifacts/validation/2026-11-15/esp32_incident_v1/rom_query_excerpt.txt): `No serial data received`. 장치 식별 경로만 가렸고, 원본 SHA256은 manifest에 남겼다. 당시 reset을 사용했으나 flash 쓰기는 없었다는 범위는 원 보고서를 따른다.

당시 호스트의 `state.json`은 새 MCU 수신 없이도 갱신될 수 있었으므로 파일 수정 시각만으로 통신이 살아 있다고 판단할 수 없었다. 구동기 내부의 새 info 응답 요구가 실제 출력을 막았으며, 후속에 MCU 수신 시각 기반 신선도 검사와 포트 종료/정지 확인 구분을 보완했다. 이 수정은 고장 원인 규명이 아니다.

## 후속 원본 회수에 따른 상세 원인 검토 (2026-11-15 추가)

### 1. Jetson 원본의 무결성과 범위

Jetson의 `mounted-dc-test.5qyIBL` 시험 폴더를 읽기 전용으로 회수했다. 원격 SHA-256과 대조한 파일은 **83개 전부 일치**한다. UART 원시 바이트는 **3,948,430 bytes**이며 CRC를 포함해 해석한 프레임 **14,145개**가 `frames.jsonl`과 모두 일치한다. 완전한 줄 중 파싱 실패 0, 불완전한 마지막 바이트 0이다. 이로써 회수된 UART 자료의 무결성과 해석 파일의 대응은 확인했지만, 센서 전압·전류나 보드 내부 상태를 측정한 것은 아니다.

프레임 구성은 info 3, status 6,685, motor 6,687, reply 2, edge 768이다. 프레임 수신이 이어지던 동안 시퀀스/CRC 검증을 통과했으며, 마지막 motor 프레임은 seq 14144다. 이 프레임의 값은 `active=false`, `armed=false`, `duty_permille=0`, `pwm_pin=0`, `pulses=1`, `reason=no_encoder_start`다. 즉, 이 세션에서 마지막으로 관측된 출력은 정지 상태이며, 해당 세션의 펌웨어가 기록한 유효 펄스는 1회다.

### 2. 명령 이력을 다시 대조한 결과

9개 `commands.jsonl` 스트림에서 총 61개 명령 레코드를 정규화해 대조했다. 주요 시험 흐름은 다음과 같다.

- 최초 진단 세션은 `?` 상태 조회, `X` 정지, `S` 스트리밍 시작 후 모터 전원을 분리한 보호 검사로 진행됐다.
- 별도 5% 시험은 5초 요청이었지만 MCU가 약 **360.041 ms** 후 `no_encoder_start`로 출력을 종료했다. 이는 5초 동안 모터가 구동됐다는 뜻이 아니다.
- 7.5% 시험은 **500.052 ms** 동안 논리 출력이 유지됐으나 엔코더 변화는 0이었다. 사용자는 육안 회전을 확인하지 못했다.
- 15% 앱의 `no_power_guard_check`에서는 모터 전원을 분리한 상태에서 ARM/PULSE 150‰·5,000 ms 요청이 실제로 한 번 기록됐다. 엔코더 시작이 없어 약 **360.029 ms** 후 차단됐다. 이 기록은 15% 논리 출력 검사이며, 모터 전원이 연결된 구동 시험이 아니다.
- 이후 `waiting_for_ready` 구간의 명령은 `?`와 약 **2.007685초** 뒤 `X`뿐이다. 이 구간에는 ARM/PULSE가 없다. 따라서 실부하 15% 구동은 시작되지 않았다.
- 별도 `powered-start15-reconnect-v1` 재접속에서도 명령은 `?`와 `X`뿐이며 UART 수신은 **0 bytes**다. 종료 파일은 `stop_confirmed=false`, `last_motor=null`을 기록한다. 포트 닫힘을 MCU의 정지 확인으로 해석하지 않는다.

마지막 유효 MCU 프레임의 호스트 수신 시각과 15% 구동 전 조회 사이의 실제 차이는 **27.314343111초**다. 조회 뒤에는 새 MCU 프레임이 0개다. 앞선 요약에서 사용한 27.314초와 일치하며, 이제 원시 UART와 명령 로그에서 직접 재대조한 값이다.

### 3. USB 커널 기록과 사용자의 수동 재연결 조치 구분

사건 시간대의 `/var/log/kern.log`에서 USB 포트 1-1 이벤트를 추렸다. 13:40:18 첫 분리 이후 **분리 4회, USB 재등록 4회, `ttyACM0` 등록 4회**가 관측됐다. 첫 분리의 커널 단조 시각은 3381.416278초다. 커널 로그의 벽시계는 초 단위이므로 UART의 나노초 단조 시각과 같은 정밀도로 비교하지 않는다.

**사용자의 후속 설명:** MCU 통신 이상을 인지한 뒤 USB 케이블을 직접 뺐다 다시 연결하고, Jetson의 USB 포트를 바꿔 보고, 케이블도 교체하는 등 연결 경로를 차례로 점검했다. 따라서 13:40:18 이후의 반복적인 USB 분리·재등록은 장치가 스스로 반복 재부팅하거나 USB 연결이 자발적으로 불안정해진 증거라기보다, **사용자가 수행한 케이블·포트 점검 과정이 커널에 기록된 것일 가능성이 높다.**

시간상 첫 MCU 응답 실패는 13:36:53.865의 상태 조회에서 이미 확인됐고, 첫 커널 USB 분리는 그보다 약 3분 24초 뒤인 13:40:18이다. 그러므로 커널에 기록된 반복 분리·재등록을 최초 통신 단절의 원인으로 해석하면 안 된다. 이는 통신 단절을 확인한 뒤 수행한 문제 해결 시도와 시간상 부합한다.

다만 현재 공개된 커널 발췌는 동일한 논리 경로 `1-1`의 이벤트만 추렸고, 각 분리·재등록이 사용자의 어느 케이블 교체 또는 물리 포트 변경에 대응하는지는 기록되어 있지 않다. 사용자가 실제로 USB를 뺐다 꽂았다는 설명과 시간대는 일치하지만, **각 이벤트의 개별 대응 관계까지 확정한 것은 아니다.** 포트를 바꾸어도 동일한 논리 경로로 표시될 수 있는지 여부 역시 이 발췌만으로 판단하지 않는다.

재등록은 USB 브리지/장치가 호스트 USB 계층에 다시 나타났다는 뜻이지, ESP32 애플리케이션이 정상 부팅했다는 뜻은 아니다. 실제로 재접속 세션의 UART 수신은 0 bytes였고, 별도 ROM 식별 시도도 `No serial data received`였다. 반대로 USB 분리만으로 ESP32 칩 손상을 입증할 수도 없다. USB 브리지, 케이블·커넥터, 보드 전원, MCU 중 어느 부분이 최초 원인인지는 로그만으로 구분되지 않는다.

해당 시간대 시스템 journal 조회는 항목을 반환하지 않았다. 이번에 확인 가능한 USB 이벤트는 `kern.log` 발췌에 한정된다. 따라서 journal에 오류가 없었다고 결론 내리지 않는다.

### 4. 인접한 서보·Jetson 자료가 말해 주는 것과 말해 주지 않는 것

사건 폴더 바깥의 직전 서보 캡처 및 관련 호스트 소스 등 **57개 파일**도 별도 SHA-256 대조를 거쳐 보존했다. 조립 상태에서 수행한 서보 왕복 시험은 23/23 요청 방향 이동, 실제 위치 2606–2976 counts, 서보 보고 전압 12.0–12.1 V, 상태 오류 0, 온도 30–31°C를 기록했다. 이 자료는 해당 서보 시험 시점의 서보 전원·서보 동작에 관한 근거다. ESP32 보드의 5V/3.3V 전원 레일을 측정한 자료가 아니며, 이후 DC 모터 시험 당시 전원 상태를 보증하지 않는다.

별도 Jetson 관측의 모듈 입력 소비전력 약 4.8–5.1 W, 접합 온도 약 38°C, OC 카운터 0도 짧은 Jetson 자체 관측이다. 이는 J01 출력이나 ESP32 USB 5V 레일의 전압·전류를 측정한 값이 아니다. 따라서 ESP32 전원 정상의 증거로 사용하지 않는다.

### 5. 원인 후보의 재평가

이번 회수와 사용자의 USB 점검 경위 보충으로 확실해진 것은 **통신 단절이 실부하 15% 구동 명령의 결과가 아니라는 점**이며, 이후 USB 분리·재등록 반복은 수동 케이블/포트 점검으로 설명될 가능성이 높다는 점이다. 마지막 MCU 상태가 PWM 0·미무장이었고, 이후 구동 전 조회가 실패했으며, 재접속 세션에도 ARM/PULSE가 없었다. 그러므로 실부하 15% 출력에 의한 역기전력이나 과전류를 이번 고장의 직접 원인으로 지목하는 가설은 현재 명령 이력과 맞지 않는다. 다만 앞선 5% 실부하 시험은 별도로 존재하므로, 그 시험 또는 차량 전원·배선 상태 변화가 관련됐는지까지 배제하는 것은 아니다.

현재 증거에 따른 조사 우선순위는 다음과 같다.

1. **전원·접지·커넥터·하네스의 과도 상태 또는 오결선:** 모터 전원 재연결 보고 뒤 MCU 응답이 없고, 이후 LED 소등·발열이 보고됐다. 시간상 우선 조사할 경로다. 다만 실제 투입 순서, 접점 상태, 전압 강하/상승, 전류 경로가 기록되지 않아 직접 증거는 없다.
2. **ESP32 보드의 3.3V 전원부 또는 외부 신호 핀 손상:** 보드 단독 상태에서 기술자가 3V3–GND 단락을 의심했고, 발열·전원 LED 소등·ROM 무응답 보고와 양립한다. 하지만 저항의 단위·안정값과 레일 측정이 없으므로 단락 자체도 확정 사실이 아니다. 전원 레귤레이터가 원인인지 피해자인지도 알 수 없다.
3. **TXS0108E/엔코더 인터페이스 또는 공통 GND 경로:** 5V/3.3V 경계와 다수 공통 접지 연결이 있으므로 점검 대상이다. 하지만 이번 회수 로그에는 해당 핀의 전압·전류 파형이나 보드 간 전위차가 없다. 정상 손 회전 +690 counts는 그 시점의 입력 경로가 동작했음을 보여줄 뿐, 이후 고장이나 과전압을 입증하지 않는다.
4. **USB 브리지·케이블·포트 또는 MCU 펌웨어 단독 문제:** 최초 통신 실패 시점에는 이 경로도 후보였지만, 이후 USB 분리·재등록은 사용자의 수동 점검 조치였을 가능성이 높다. 따라서 반복 USB 이벤트 자체를 보드의 반복적인 자발 고장 증거로 사용하지 않는다. 발열과 보드 단독 단락 의심을 함께 설명하지 못하므로, 전기적 손상 후보와 분리해 판단해야 한다.

따라서 현 단계의 가장 타당한 표현은 **“전원/접지/외부 인터페이스를 포함한 전기적 이상으로 ESP32 보드 또는 통신 경로가 응답 불능 상태가 되었을 가능성을 우선 조사하되, 고장 부위와 최초 원인은 미확정”**이다. “15% 모터 구동 중 ESP32 소손”, “역기전력으로 확정”, “TXS0108E가 5V를 역류시켜 파손” 등은 증거가 지지하지 않는다.

### 6. 남은 한계와 증거 보존 위치

- 5V·3.3V·모터 전원 레일의 사건 순간 전압/전류 파형이 없다.
- 발열 위치·온도·발생 시작 시각이 계측되지 않았다.
- USB 및 외부선을 모두 분리한 보드의 안정된 저항값·다이오드 측정값이 없다.
- 실제 전원·GND·신호 커넥터 상태와 전원 투입 순서를 보여주는 사건 직전 사진이 없다.
- 회수한 `kern.log`는 USB 이벤트 발췌이며, 해당 시간대 system journal은 비어 있다.

Jetson 사건 폴더 원본 83개는 `incident-originals.zip`, 인접 서보·호스트 자료 57개는 `jetson-incident-supplement.tar.gz`로 저장소 밖 백업에 보존했다. 원시 UART, 장치 식별자, 펌웨어 백업은 공개 Git에 직접 넣지 않는다. 공개 요약·해시는 [Jetson 회수 README](../../artifacts/validation/2026-11-15/esp32_jetson_recovery_v1/README.md), [회수 manifest](../../artifacts/validation/2026-11-15/esp32_jetson_recovery_v1/recovery_manifest.json), [추가 manifest](../../artifacts/validation/2026-11-15/esp32_jetson_recovery_v1/supplement_manifest.json)에 둔다.
