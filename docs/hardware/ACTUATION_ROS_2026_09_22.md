# A1-2: ROS 구동 경로와 가상 MCU 연결

날짜: 2026-09-22. 상태: **선택형 ROS/가상 MCU 연결·고장 14조건·Gazebo 부분 주행 2회 검증 완료**. [A1-1 PC 계약](ACTUATION_CONTRACT_2026_09_22.md)의 후속이며 실물 구동/안전 검증이 아니다.

## 이번 범위

선택형 `actuation_mode:=virtual_mcu`를 추가한다. 기본 `legacy`와 이전 시험은 보존하며, 주행 알고리즘·속도·차량 형상·공식 트랙·구동 물성은 바꾸지 않는다.

```text
지역 Pure Pursuit → /drive → 독립 LiDAR 보호층 → /drive/safe
  → 호스트 어댑터 → CRC 프레임 → 별도 가상 MCU → 최종 출력 감시 → Gazebo 모터
                                   ↑
                          시각 있는 좌우 누적 엔코더
```

- 가상 MCU는 부팅 시 구동 금지다. 사용자가 `ARM`을 요청해야 출력이 허가된다. 신호등 판단은 기존 자율주행 노드에 남으며 ARM 자체가 출발 명령은 아니다.
- 명령/엔코더 누락, 제어 갱신 실패는 정지 상태를 고정한다. 명령/노드가 돌아온 것만으로 재주행하지 않는다. 신선한 좌우 저속 관측 후 `CLEAR`로 정지만 해제하고, 별도 `ARM`을 요청한다.
- 호스트/MCU 재시작 시 각각 새로운 세션 ID를 사용한다. 이전 명령·순번·부팅 세대를 새 출력 허가에 재사용하지 않는다.
- ROS 서비스는 **수신기의 승인/거절 응답**을 기다린다. 응답 시간 초과는 ‘실패가 확정’이 아니라 ‘결과 미확인’이며 상태를 확인해야 한다. STOP은 소유 호스트와 무관하게 요청할 수 있다.
- 최종 Gazebo 출력 감시는 MCU 프로세스가 사라져도 독립적으로 목표 속도를 0으로 만든다. 스트림 복구만으로 풀리지 않으며 새로운 ARM 세대의 0속도 허가를 먼저 관측해야 한다. 조향은 마지막 유효 각도를 유지한다.
- 출력부가 현재 MCU의 부팅/세대를 실제로 받았다는 확인을 되돌린다. 그 확인 전에는 ARM을 거절하고, 새 ARM을 출력부가 확인하기 전에는 호스트가 DRIVE를 보내지 않는다. 재시작 직후의 토픽 연결 지연을 정상적인 구동 허가로 오해하지 않기 위한 왕복 확인이다.

여기서 고정 정지는 **구동 계약의 STOP·명령/피드백/시계 고장**이다. 보호층이 센서 일시 누락 때문에 신선한 0속도 명령을 계속 보내는 경우는 정상 0명령으로 처리한다. 따라서 모든 센서 복구·자율주행 노드 재시작에 대한 재출발 정책까지 통일한 것은 아니다. 그 상위 정책과 공식 경기 상태/신호는 별도 후속 작업이다.

## 시간과 전송 경계

가상 MCU의 운동 시간은 `/clock`이다. 명령 유효기간 100 ms, 엔코더 신선도/제어 공백 50 ms 등은 A1-1의 임시 시험값을 그대로 쓴다. 호스트는 `/drive/safe`의 생성 시각을 보존하며 같은 명령을 계속 새 시각으로 포장하지 않는다. 원래 토큰/명령의 만료보다 최종 수신 감시가 출력 수명을 늘리지 않는다.

가상 센서 `/wheel_states`의 양자화된 누적 위치와 **원래 취득 시각**을 사용한다. header 없는 틱 토픽에 임의 도착 시각을 붙이지 않는다. `/clock`와 센서·상태가 별도 토픽으로 도착하는 순서 차이는 작은 대기열로 흡수하며, 신선도 한도는 늘리지 않는다.

별도 단조 벽시계 감시를 두어 `/clock`가 멎어도 0 출력을 보낸다. 처음 `/clock`를 받기 전의 부팅 대기는 구동 금지 상태로 기다리고, 이미 진행하던 시계의 멎음/역전은 고정 정지 후 가상 MCU 재시작을 요구한다. 다시 시작해도 ARM은 별도다. 기본 벽시계 한도 3초, 느린 오프라인 실행에서 늘리는 값은 **시뮬레이션 운용 한도**이며 실차 허용 지연이 아니다.

CRC 프레임은 시험용 ROS byte array로 전달한다. UART/CAN/USB 드라이버, baud, 실물 MCU 시계 동기화와 전기적 차단을 구현한 것이 아니다. DDS 토픽·서비스는 여기서 인증되지 않으므로 신뢰하는 격리된 로컬 시험 환경에서만 사용한다.

## 모터 제어에 관한 중요한 한계

이번 가상 MCU가 확인하는 것은 **명령 유효성·정지/재허가·엔코더 신선도**다. Gazebo의 기존 단일 모터 토크/속도 PI는 그대로이며 그 내부 피드백은 여전히 실제 시뮬레이션 관절 속도다. A1-1의 `SpeedPI`를 여기에 이중으로 덧붙이지 않았다.

따라서 MCU 내부 속도 루프가 잡음 있는 실제 엔코더만으로 제어되는 상황, 실물 ESC의 정지/제동/역회전, 실제 ESP32의 실행 지터는 아직 검증하지 않았다. ESC 모델/명령 방식과 엔코더 분해능·통신 주기는 여전히 미정이다. 최종 출력 감시·ROS 브리지까지 함께 죽는 경우의 기존 Gazebo 0.5초 fallback도 실제 독립 차단 회로의 대체물이 아니다.

## 실행

ROS 환경과 작업 공간을 로드한 후:

```bash
ros2 launch arena_bringup local_pursuit.launch.py actuation_mode:=virtual_mcu
ros2 service call /actuation/arm std_srvs/srv/Trigger '{}'
ros2 service call /actuation/stop std_srvs/srv/Trigger '{}'
# 양쪽 바퀴의 저속 지속 관측 이후에만:
ros2 service call /actuation/clear_stop std_srvs/srv/Trigger '{}'
ros2 service call /actuation/arm std_srvs/srv/Trigger '{}'
```

시험 도구에서 하는 1회 ARM은 평가자가 명시적으로 요청하는 시험 동작이다. 운영 노드에는 자동 ARM/자동 재허가가 없다. `/drive/safe` 직접 발행으로 보호층을 우회하지 않는다. ROS 합성 시험만 격리된 `/test/safe_command` 입력으로 통신 상태를 검사하며 코스 주행 결과와 구분한다.

호스트 종료 시험의 정지 요청→검사 종료는 1.448초, 위치 변위는 0.965680 m였다. STOP 시험보다 약 0.19 m 크지만 출발 표본·속도/구간·실행이 다르므로 차이를 통신 지연만의 효과로 확정하지 않는다. 시간에는 0.5초 안정 정지 확인이 포함된다. **약 8 km/h의 가상 구동계에서도 정지까지 여유 거리가 필요하다. 이 수치를 실제 ESC/노면 제동값으로 쓰지 않는다.**

아래는 실패와 보완 이력이다.

- `build_v1`: 2패키지 빌드·회귀 350개 통과. 이후 최종 출력 감시의 옛 세대/부팅 재생 회귀 2개를 추가했다.
- `ros_v1`: 부팅 중 `/clock=0` 상태를 이미 작동하던 시계의 멎음으로 오인해 시작하지 못했다. 첫 이벤트·오류·빈 노드 로그·정상 종료 3개를 보존한다. 최초 양의 시계를 받기 전에는 구동 금지 대기로 구분하도록 수정했다. 실제 작동 후 시계 감시는 유지한다.
- `ros_v2`: 앞선 12조건은 통과했지만 시계 고장 후 재시작/허가 단계에서 MCU는 ACTIVE, 출력부는 정지 고정 상태여서 전체 실패였다. 출력부의 실제 수신 준비를 확인하지 않던 경계를 보완하고 epoch/수신 시각 진단을 추가했다. 정확한 DDS 내부 지연 원인은 계측하지 않았으므로 특정 미들웨어 결함으로 단정하지 않는다. 여섯 프로세스는 정상 종료·잔존 없음이다.
- `ros_v3`: 아래 14조건과 프로세스 종료를 통과했다. 이후 호스트 시계 역전 시 소유 ID 초기화·잘못된 ACK 타입 거절·출력 감시 비정상 시각 거절·명시적인 저속 준비 상태 표시를 보완했으며, 최종 코드 재검증과 구분한다.
- `gazebo_stop_v1`: **12.21847 m**, 최고 **2.26440649 m/s(8.15186 km/h)**, MCU STOP 고정/실제 모형 정지·주행/정지 벽 겹침 표본 0·자식 14/14 정상 종료·잔존 없음으로 전체 통과했다. 정지 요청부터 검사 종료까지 1.348초, 변위 0.773847 m다. 검사 시간에는 0.5초 안정 정지 확인이 포함되며 변위는 표본 시작/끝 위치 간 거리다. 실차 제동거리나 전체 코스 완주가 아니다.
- 위 첫 코스 실행 후 `actuation_ros.py`, `applied_guard.py`, 코스 검사기에 후속 경계 보완이 있었다. 실행 당시 소스 스냅샷/해시는 보존하고 최종판 주행 근거와 구분한다. 보완은 시계/ACK/준비 판정이며 속도·조향/제동 한도를 높이거나 늦춘 것이 아니다.

ROS 합성 14조건: 부팅 구동 금지, 명시 ARM 후 주행, 명령 누락 정지, 명령 복구만으로 재출발 안 함, CLEAR만으로 재출발 안 함, STOP 고정, 호스트 재시작, MCU 프로세스 손실 때 출력 정지, MCU 재시작, 엔코더 누락, 시계 정지 때 0출력, 시계 고장 후 CLEAR 거절, 명시 재시작/허가 복구, 시계 역전 후 정지 유지다. 양쪽 바퀴를 합성하는 모형의 정지와 Gazebo 정지는 구분한다.

최종판 `ros_final`에서 이 14조건을 다시 통과했다. 코스 두 번은 약 12 m 부분 주행으로, 전체 코스/다중 차량·고속 완주 근거가 아니다. 별도 노면 다각형 전수 감사는 이번에 하지 않았으며 벽 겹침 0을 노면 이탈 0이나 연속 충돌 없음의 증명으로 바꾸지 않는다.

## 다음 경계
