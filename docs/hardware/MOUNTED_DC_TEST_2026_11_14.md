## 준비와 시험 앱

사용자는 차량 고정·구동 바퀴 띄움·모터와 서보 전원 분리를 확인했다. 서보 앱 파티션1 MiB를 보존한 뒤 모터 진단 앱을 설치했고, 모터 전원만 연결해 시험했다. 이후 서보 전원을 다시 연결했다는 보고는 없다. [이전 단독 모터 시험](../sensors/MD20A_MOTOR_HARDWARE_2026_11_12.md)과 조립 후 결과를 구분한다.

기존 `motor_probe_v1`의 무전원 종료 검사 뒤 약5% 단발을 실행했다. 사용자의 5초 요청에 따라 별도 `ARENA_MOTOR_GUARDED_5S` 빌드인 `motor_probe_guarded_5s_v1`을 모터·서보 무전원 확인 후 app 영역에 기록했다. 설치 이미지 SHA-256은 `ebbf8e0aa18c478bfa5a41d69a140b2a3253f4dc0441387f553577115d4e0e92`다. 기존 서보 파티션 백업 SHA-256은 `a92d8736f7b798472ef5c69b65dfec26321f0056e7bce8be1699e777a8bd5496`다.

이 앱의 500 ms 이하 단발 상한은100‰이며, 그보다 긴 명령은 최대5000 ms·50‰다. 긴 명령에서 약350 ms 내4카운트의 움직임이 없거나, 이후 진행이 끊기면 조기 종료한다. MCU 타이머 마감·GPIO8 STOP·표본 엔코더 속도 검사를 유지한다. 실제 STOP 스위치의 O 전환 시험은 사용자의 DC 우선 지시로 미실행이며, I/LOW 읽기만 확인했다. 공칭 환산·표본 속도 검사를 실제 최고 속도13 km/h 보증으로 취급하지 않는다.

## 현재 상태와 재개점

7.5% 시험 종료 뒤 PWM0·미무장을 확인했고, 이후 사용자 모터·서보 전원 분리 응답을 받은 뒤 기존 세션의 `X`·포트 종료를 확인했다. 설치된 앱은 아래15% 상한 임시 모터 진단 앱이며 서보/운영 앱을 복구하지 않았다.

사용자는 5초씩 관찰하며 보이지 않을 때마다 출력을 두 배로 올리기를 요청했다. **2배 자동 상승은 실행하지 않았다.** 후속 사용자는 MD20A 전원 LED 점등을 확인했다. 이는 입력 전압의 실제 크기나 모터 출력·배선 도통 확인과 다르다.5초 명령의 조기 차단을 숨기거나 제거해 성공으로 기록하지 않는다.

다음 단발용 `ARENA_MOTOR_START15_5S=ON` / `motor_probe_start15_5s_v1`은 긴 구동의 상한을150‰로 두되 무회전 시작 차단·회전 후 진행 소실·표본 속도/간격·GPIO8 STOP·5초 타이머를 유지한다.500 ms 이하의100‰ 제한과 기본 빌드의 동작도 유지한다. 호스트는 다른 앱에150‰를 보내지 않으며 상승 반복을 수행하지 않는다. 관련 호스트5검사를 통과했다. **설치·무전원 검증까지 완료했고15% 실제 모터 구동은 아직 하지 않았다.**

ESP-IDF 빌드 이미지 SHA-256은 `6688957992ac2730c641a912bd9a36ed8effacc7ce1dec47cf69c32cf2abc3ab`이며 Jetson 전송본과 일치한다. 사용자 두 전원 분리 확인 뒤 파티션 표를 대조하고 직전 앱1 MiB를 별도 보존했다(SHA-256 `7ed2ab003798f5e44f23b0296cb3f9a1152daa0655a918684fc91690827aae95`). app 주소 `0x10000`만 교체했고196800바이트 readback digest가 일치했다. 새 앱은 무전원150‰·5000 ms 요청을360.029 ms에 `no_encoder_start`로 종료했다. PWM0·미무장을 확인하고 사용자 요청의 엔코더 손 회전 관찰을 시작했다. 실제 모터 구동 전에는 모터 재연결·구동부 비움 확인이 필요하다. 앞선5%·7.5% 결과 JSON도 노트북으로 회수해 원격과 해시 일치를 확인했다.

`start15-run` 세션은 같은 UART 연결에서 엔코더 손 회전 관찰을 수행했다. 기준 저장 전 A 하강1에지·순계수+1이 있었으며 이를 수동 회전 확인으로 판정하지 않았다. 기준 `manual-before.json` 대비 사용자 손 회전 완료 후 **PCNT/software 모두+690**, 에지690개, A 상승/하강173/172·B 상승/하강172/173, invalid/drop 증가0을 확인했다.3,931상태 표본의 계수 범위는1~691로 일치했다. 사용자가 최초 전진 보고를 **후진이었다고 정정**했으므로 +690은 후진으로 기록한다. 원 결과의 최초 보고는 삭제하지 않고 `operator-direction-correction.json`을 별도로 보존했다. 반대 방향 실측·회전당 계수·속도 정확도는 아직 검증하지 않았다.

### 전원 재연결 뒤 조회 무응답과 재접속 실패

사용자가 모터 전원 연결·구동부 비움과15% 시험 준비를 확인했으나, 실제 실행 전 `?` 조회의 새 응답을 받지 못했다. 이 구간에는 새 ARM/PULSE가 송신되지 않았다. 마지막 유효 motor 표본은 PWM0·미무장이었지만 조회 시점보다 약27.3초 오래됐다. 기존 호스트는 새 MCU 프레임이 없어도 `state.json`을 갱신하므로 파일 수정 시각만으로 신선함을 판단할 수 없었다. 실행기 내부의 새 info 응답 요구가 실제 ARM을 막았다.

호스트에 MCU 수신 `host_ns` 기반 신선도 검사와 `telemetry_fresh` 상태를 추가하고, 오래된 motor/encoder에서는 ARM/PULSE를 전송하지 않도록 했다. 포트 종료와 정지 응답 확인도 분리해 `stop_confirmed`로 기록한다. 기존3검사·출력 범위2검사·신선도/종료 회귀3검사로 총8검사를 통과했다.

사용자는 모터 전원을 유지한 재접속을 명시적으로 지시했다. 새 호스트로 한 번 재접속했으나 **UART 수신0바이트**, identity 조회와 종료 `X` 모두 응답 없음이었다. 이 재접속에서도 ARM/PULSE는 송신하지 않았고 자동 재시도하지 않았다. `powered-start15-reconnect-v1/closed.json`은 포트 종료와 `stop_confirmed=false`·`last_motor=null`을 기록하며 포트 소유자0을 확인했다. 새 정지 상태를 확인했다고 주장하지 않는다. 설치 앱은15% 상한 진단 앱이며 추가 플래시는 없었다.

발열 보고 직전 사용자 확인상 모터 전원은 연결돼 있고 서보는 분리 상태였다. 발열 보고 뒤에는 USB·차량 전원 전체 분리를 요청했으며 실제 분리 완료는 미확인이다. **식힌 뒤에도 외부 배선·전원부 점검 전에는 재인가하지 않는다.** USB 장치 경로가 보이는 것만으로 MCU 정상 동작을 판정하지 않는다. 발열 위치·온도·보드 전원 전압은 미측정이며, 외부 단락·전원부 이상·영구 손상 여부와 원인은 아직 확정하지 않았다.

사용자 후속 재확인 요청에서는 ESP32의 USB 장치 경로가 사라져 포트를 열 수 없었다. 커널에 분리→재연결→다시 분리 기록이 있었다. 이어 같은 USB 장치가 다시 등록됐지만 앱 조회는 다시 무응답이었다(`esp32-recheck-v2`). 구동 명령 없이 수행한 부트로더 식별 검사도 `Failed to connect to ESP32-S3: No serial data received`로 실패했다(`esp32-rom-recheck-v1`). 이 검사에는 리셋을 사용했고 플래시 쓰기는 하지 않았다. USB 변환칩 등록과 MCU 응답을 구분하며, 현재 ESP32 자체 전원 LED 확인을 요청한 상태다. 모터15% 구동은 여전히0회다.

사용자는 모든 LED가 꺼졌고 USB 케이블을 바꿔도 같다고 보고했다. 케이블 교체 뒤 USB 변환칩은 다시 등록됐지만 앱 재조회는 수신0바이트였다(`esp32-cable-recheck-v1`, ARM/PULSE0). 고장 원인은 확정하지 않았으며, 외부 연결을 분리한 보드 단독 시험과5 V/3.3 V 실측은 아직 없다. 실제 보드 판본은 [기존 확인 범위](ESP32_IMU_BRINGUP_PLAN_2026_11_11.md#2-부품-확인과-조립)대로 미확정이며, RGB 소등을 곧바로 전원 표시등 소등과 동일하게 해석하지 않는다.

## ESP32 없이 제어하는 대안 조사

**후속 도면화:** 사용자 요청으로 기존 도면 형식의 [Jetson 직접 제어 전체도](schematics/jetson_direct_wiring_v1.html)와 [J12 연결표](schematics/jetson_direct_pin_table_v1.md)를 작성했다. ### 현장 조건과 확인 범위

11/14 사용자는 예비 MCU가 없고 실제 서보 어댑터에 USB 단자가 없다고 확인했다. 멀티미터가 있으며 ESP32를 분해하는 동안 대체 경로 조사를 요청했다. 보드 분리 완료·5V–GND/3V3–GND 저항값은 아직 받지 않았다. 따라서 ESP32 영구 손상이나 외부 배선 정상 여부를 확정하지 않는다. 기존 어댑터를 Waveshare USB 탑재 제품과 동일시한 가정은 [배선 문서](ESP32_GPIO_WIRING_2026_11_11.md)에서도 정정했다.

앞선 읽기 전용 조회에서 Jetson은 Orin Nano Developer Kit Super·L4T R36.4.4였고 `/dev/ttyTHS1`, `/dev/ttyTHS2`와 PWM 컨트롤러가 등록돼 있었다. 이는 헤더의 전기적 출력 검증이 아니다. 이번 추가 핀 설정 조회는 SSH 연결 시간 초과로 명령 실행 전에 끝났다. 분해 중 장비의 전원 상태나 네트워크 단절 원인을 추정하지 않으며 재접속을 반복하지 않았다. GPIO 요청·PWM export/enable·UART 열기·핀 설정 변경·재부팅·배선 이동·구동은 수행하지 않았다.

| 조향 | Jetson 헤더 UART → 기존 UART/서보 버스 어댑터 → ST3215-HS | 실제 어댑터의 입력/출력 기능·논리 전압 확인, 헤더 UART와 Linux 장치 대응 확인, 직접 직렬 통신 구현. 서보 12 V 전원은 기존 별도 전원 경로 유지 |
| DC 모터 | Jetson 하드웨어 PWM + DIR GPIO → MD20A → 모터 | PWM 핀 mux·부팅 기본 상태·LOW 정지 확인, 유한 시간 출력과 정지 처리 이관. MD20A는 3.3 V 논리와 최대20 kHz PWM 지원 [1] |
| 엔코더 | PGE-213 → 기존 CF의 3.3 V 측 A1/A2 → Jetson GPIO 입력 | CF VA/OE 전원을 ESP32와 분리해 공급하는 방식 확인, GPIO 에지 계수 구현, 누락·방향·표본 지연·속도 환산 검증. HA/HB의 5 V 측을 Jetson에 직접 연결하지 않음 |
| IMU | LSM6DSOX SPI → Jetson SPI | pinmux·전원·CS·SPI 드라이버와 시간/축 계약 이관. 기존 MCU용 앱을 그대로 실행할 수 없음 |
| 물리 STOP | 스위치 상태를 Jetson 입력으로 읽는 경로 | 현재 GPIO8 판독은 ESP32에 의존한다. Jetson 입력만으로 바꾸면 Jetson 정지와 독립적인 차단 경로가 생기지 않음 |
| C1·B0390 | 기존 Jetson USB·CSI 경로 유지 | ESP32를 통과하지 않는 구성이다. 이번 조사에서 센서 수신을 새로 검증하지 않음 |

추가 부품이 없는 후보는 **조향 UART 직접 연결을 먼저 준비하고 DC PWM·엔코더·정지를 묶어서 이관하는 순서**다. 이는 구현·검증 순서 제안이며 실물 배선 변경이나 대체 제어기 채택 완료가 아니다. 나중에 3.3 V USB–UART 변환기를 확보하면 조향의 헤더 UART 설정 부담을 줄일 수 있지만, 서보 버스 변환 어댑터와 DC PWM/엔코더/정지 구현은 여전히 필요하다. 예비 MCU 없는 현재 즉시 사용 가능한 부품으로 가정하지 않는다.

### 재사용 가능한 코드와 필요한 변경

`scripts/probe_bus_servo.py`의 `packet`·`responses`·`feedback`은 서보 명령 프레임·체크섬·위치 해석에 재사용할 수 있다. 그러나 `Probe`는921600 baud의 ESP32 JSON 중계에 `INFO`, `B`, `Q`, `ARM`, `X`를 보내는 구조다. `/dev/ttyTHS1`로 경로만 바꾸어도 작동하는 프로그램이 아니다. 직접 통신에서는 서보의 기존 ID1·1,000,000 baud·8N1을 대상으로 바이트 전송/응답 시간 제한을 구현해야 한다. 장치 경로는 현재 헤더 대응 확인 뒤 선택한다.

중앙2811·왼쪽3031·오른쪽2550 counts와 전동 시험 내부 목표2600–2980은 기존 [조향 기록](MOUNTED_SERVO_SETUP_2026_11_14.md)의 실측 범위로 재사용한다. 초기 동작은 위치/전압/상태 조회와 토크 OFF 확인부터 하며, 전원을 넣거나 연결했다는 이유로 중앙으로 이동시키지 않는다. 기존 MCU의1초 lease와 토크 해제 처리는 Jetson 직결 시 자동으로 따라오지 않는다. 서보 자체 통신 두절 보호의 동등성도 미확인이다.

NVIDIA `jetson-gpio`의 Orin Nano는 NX와 같은 핀 정의를 사용한다. 공식 소스에서 BOARD15→`3280000.pwm`, BOARD32→`32e0000.pwm`, BOARD33→`32c0000.pwm`를 확인했다 [2]. **부품별 후보 표이며 현재 연결할 핀 지시가 아니다.** `pwmchipN` 번호를 고정하지 않고 실제 장치 경로와 핀 mux를 대조해야 한다. Jetson.GPIO는 하드웨어 PWM만 지원하며 라이브러리가 pinmux를 자동 설정하지 않는다 [3]. 이후 읽기 전용 확인에는 Jetson-IO의 `config-by-pin.py` 및 `config-by-function.py -l enabled`를 사용한다. 실제 변경은 기존 CSI 카메라 설정 보존과 재부팅 영향을 검토해야 한다 [4].

엔코더는 Python 반복 읽기 대신 GPIO character-device의 에지 이벤트를 수집하는 경로를 우선 검토한다. 커널 타임스탬프·동일 요청 내 순서·순번 누락 검사가 가능하지만 버퍼 오버플로와 검출 누락 가능성이 있어 ESP32 PCNT와 동등하다고 주장하지 않는다 [5]. 최종 속도 환산은 기존 회전당 계수 미확정 문제와 별도로 해결해야 한다.

### 정지 처리와 시험 범위

하드웨어 PWM의 존재는 프로그램 종료·OS 정지 시 자동 차단을 의미하지 않는다. 일반적인 Linux PWM 설정에는 모터 명령의 유효시간 계약이 없으며, disable 상태의 실제 출력 LOW조차 일반 API에서 보장하지 않는다 [6]. 따라서 `finally`나 UI의 정지 버튼만으로 기존 MCU의 시간 제한·STOP 검증을 대체했다고 하지 않는다. 설계 시 duty0·정지 readback/물리 관측·명령 만료를 분리하고, 실제 독립 차단 경로가 마련되지 않은 상태를 명시한다. 기존 `/drive` → 독립 보호층 → `/drive/safe` 경계는 유지한다.

MD20A 자체 MA/MB 시험 버튼은 제조사 데이터시트상 **최대 출력 회전**이다 [1]. ESP32 없이 반응을 볼 수는 있지만 요청한 저속·유한 시간 시험의 대안으로 채택하지 않는다. 이 버튼을 누르거나 모터에 배터리를 직접 연결하는 시험은 수행하지 않았다.

다음 실물 단계는 분리 보드의 저항 측정 결과를 받고 외부 전원·배선 이상과 구분하는 것이다. 이후 실제 어댑터 핀/전압 확인 → UART 조회 → 조향 제한 이동, 별도로 PWM0/부팅·종료/STOP 확인 → 엔코더 손 회전 → 유한 시간 저출력 DC 시험 순서로 준비한다. 조향과 DC 모두 이관 가능성은 있지만 현재 대체 제어 코드 구현·실물 성공·경기 운용 준비 완료를 뜻하지 않는다.
