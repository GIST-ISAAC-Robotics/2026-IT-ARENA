# 공식 트랙 전환 중 프로젝트 내부에서 확인한 문제

기록일: 2026-08-31. 이 문서는 우리 생성기·검사기·WSL GUI의 문제를 다룹니다. [주최 측 이슈 초안](OFFICIAL_UPSTREAM_ISSUE_DRAFTS.md)의 공식 원본 오류와 섞지 않습니다.

| 문제 | 관찰·원인 범위 | 처리·상태 |
|---|---|---|
| 실행 신호등과 장면 높이가 다름 | 공식 scene을 복사한 뒤 기존 시설 함수가 `gantry_height_m`를 갱신하지 않아, SDF는 0.42 m인데 scene은 원본 1.2 m를 유지 | 장면 값을 설정에서 갱신하고 SDF/scene 일치 회귀 검사를 추가. 해결 |
| 피니시 설정 주석이 실제 위치와 다름 | 실제 생성기는 설계의 `start_line.s≈46.2461`을 사용하지만 새 프로필 주석이 ID 0의 `s=0`이라고 잘못 설명 | 기하는 유지하고 주석·출처 기록 수정. 공식 start line/ID0 불일치는 별도 이슈로 유지 |
| 새 기본 지도와 완주 평가 월드 불일치 | 데모를 official로 바꾼 직후 검사기의 경로/충돌 판정 입력이 experimental로 하드코딩되어 있었음 | 같은 official 월드를 사용하도록 수정. 새 출력 폴더와 보고서 track 필드도 분리. 수정 뒤 한 바퀴 실증 통과 |
| 과거 실험 방지턱 마찰이 바뀔 위험 | 공식 턱에 임의 0.8을 넣지 않도록 공통 생성기를 바꾸자 기존 experimental의 계수도 빠짐 | experimental 프로필에 과거 팀 가정 0.8을 명시하고 회귀 검사 추가. official은 계수 미지정. 과거 비교 조건 보존 |
| 정적 통과 보고서가 오래된 차량/검사기를 인증할 위험 | official 출처 기록의 입력 해시에 차량 설정과 `inspect_geometry` 구현 파일이 없었음 | 두 입력 해시 추가. 차량 설정 변경 때 `--check`가 재생성을 요구하는 회귀 검사 추가 |
| 사용자 지정 프로필의 `--check` | 생성은 `--profile`을 사용하지만 검사 경로는 기본 프로필만 해시 | `check(destination, profile_path)`로 CLI 연결 수정 |
| WSLg 창 캡처 | Windows 창 캡처에서 대상 Gazebo 대신 다른 앱 내용이 반환됐고 XWD의 픽셀 포장도 일반적인 32-bit 가정과 다름 | 해당 잘못된 이미지는 공개하지 않음. Gazebo 카메라 서비스·X11 캡처 후 실제 화면 육안 확인. 원시 캡처는 build 아래 보존 |
| 첫 GUI에서 동적 차량이 보이지 않음 | 서버의 `gz model`에는 정상 pose/질량의 `arena_car`가 있었으나 GUI 장면에 표시되지 않음. GUI만 재연결하자 표시됨 | 서버·차량을 재생성하지 않고 GUI만 재시작하여 회복. 초기 장면 동기화 문제로 의심되지만 내부 원인은 확정하지 않음. 사진은 회복 후 촬영 |
| ID 30 보고 시점 사진의 비동기성 | 자율주행 상태에서 ID 30을 확인했을 때 저장한 최신 RGB에는 이미 마커가 없었음. PNG 재검사에서 0/20/45는 검출, 30은 미검출 | 원시 실행 자료를 유지하고 고정 사본을 `marker_30_status_snapshot_not_detection.png`로 명확히 구분. 이 사진을 인식 성공 증거로 사용하지 않음. 후속 검사기는 실제 검출 프레임과 상태의 타임스탬프 대응을 보강할 필요가 있음 |

마지막 두 항목은 주최 측 트랙 파일의 오류라고 단정할 수 없어 보고 대상에서 제외했습니다. GUI 재연결·참고 사진의 한계와 본선 실주행 보고서의 통과 여부는 각각 별개입니다.

## 원본 로드 재감사에서 분리한 진단 도구·환경 문제

- Gazebo Python transport 바인딩의 직접 import가 `ModuleNotFoundError: gz`로 실패했습니다. 설치를 추가하거나 원본 탓으로 돌리지 않고, 이미 설치된 ROS–Gazebo bridge로 실제 RGB를 수신했습니다. 영상 시험의 서버·bridge는 종료 코드 0/0으로 정리됐습니다.
- 초기 실행 수집기의 물리 로드 메시지 검색 문자열이 실제 로그와 달라 요약 flag가 false로 기록됐습니다. 원시 로그는 그대로 보존하고 수집기를 수정했으며, 최종 공개용 요약은 로그의 실제 `Loaded system [gz::sim::systems::Physics]` 및 `World ... initialized` 문구를 다시 판독했습니다. 첫 갱신의 완료 여부는 메시지 flag와 별도로 명령 완료·시간 상한으로 판정했습니다.
- `pkg-config`에서 vendor 라이브러리가 조회되지 않아 Gazebo 버전 명령·Debian 패키지 정보로 환경을 확인했습니다. 선택 환경 변수가 없을 때 `printenv`가 비정상 종료하는 현상도 원본 트랙 결함에서 제외했습니다.
- GUI의 QML/FSAA 경고와 진단 카메라의 visibility mask 경고는 정상 대조군에서도 나타났습니다. 이것만으로 추가 이슈를 만들지 않았습니다. 1,113링크 첫 갱신 지연, 필수 script/name 누락, 실제 이미지 경로·검은 재질 문제는 [원본 감사 근거](../../artifacts/validation/2026-08-31/official_raw_load/README.md)의 재현 증거로 구분했습니다.
- 최종 근거 검사에서 45초 강제 종료 로그 두 개에 끝이 잘린 ANSI 색 코드가 남아 실패했습니다. 완전한 색 코드만 지우던 수집기 정제를 보완하여 남은 ESC를 `<ESC>`로 표시하고, 회귀 검사를 추가했습니다. 검토용 로그 두 개에서만 제어 문자를 가시화했으며 원시 로그·SHA-256·시간 관측은 변경하지 않았습니다.
- 단일 이슈용 Physics+RGB 재검증 중 `03_black_material`은 각 3프레임을 수신한 뒤 서버가 SIGINT·SIGTERM에 종료되지 않아 SIGKILL로 정리됐습니다(bridge 0·서버 -9, 잔류 PID 없음). 재질과 종료 실패의 인과관계는 확인하지 않았습니다. 다른 조건과 같은 visibility mask 경고 외에 추가 오류는 관찰하지 못했으므로 원본 결함으로 단정하지 않습니다. [해당 결과](../../artifacts/validation/2026-08-31/issue_consolidation/retest/render/03_black_material/result.json)와 로그를 그대로 보존했으며, 최종 `04_ready`는 10프레임/4.5 sim s·네 ID 검출 후 0/0으로 정상 종료했습니다.
- 기록 파일까지 stage한 뒤 Git 공백 검사에서 재현용 `.diff` 세 개의 빈 줄 12개를 지적했습니다. 이는 원본 SDF에서 script 태그만 제거하여 남은 들여쓰기 자체를 기록한 것으로, 실행 소스에 새 문장을 잘못 쓴 문제가 아닙니다. 원본/사본과 대응하는 수정 근거를 바꾸지 않고 보존했으며, 해당 기록용 patch를 제외한 소스·문서·로그의 공백 검사는 통과했습니다. 일반 파일의 검사 규칙을 완화하거나 Git 설정을 변경하지 않았습니다.
