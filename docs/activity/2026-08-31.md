# 활동 기록: 2026-08-31

## D435i 명목 사양과 고속 프로필 적용

- 사용자 승인에 따라 초기 통합 RGB-D 모델을 독립 RGB·깊이 센서로 교체했습니다. 기본값은 각각 848×480의 60/90 FPS이며, 같은 주기 60/60과 저부하 30/30도 실행 시 선택할 수 있습니다.
- 공식 RealSense D400 데이터시트의 해상도별 스트림·Min-Z·품질 조건과 D435i 제품 사양을 확인했습니다. RGB 69.4°×42.5°, 깊이 87°×58°를 명목값으로 적용하고 실제 장치 보정과 구분했습니다.
- 두 카메라의 수평·수직 내부 파라미터를 각각 계산하고, 별도의 `CameraInfo`와 광학 좌표계를 연결했습니다. RGB 최대 렌더링 거리는 20 m, 깊이는 0.195~3 m로 분리했습니다. 4 m는 비활성 확장 실험 후보이며 정확도 보장 거리로 취급하지 않습니다.
- 기존 RGB·깊이·IMU·점군 토픽 이름은 유지했습니다. 점군은 별도 브리지에서 구독자가 있을 때만 전송하도록 구성했습니다.
- 실제 장치와 다른 `32FC1` 깊이 표현, 미정렬 RGB·깊이, 실제 컬러가 아닌 점군의 회색조 `rgb` 필드, 임시 결합 IMU와 이상적 자세 출력을 문서화했습니다. 노출·롤링 셔터·스테레오 오차와 실제 보유 카메라의 보정값은 아직 반영하지 않았습니다.
- 대용량 영상용 Fast DDS 전송 선택을 해당 프로젝트 실행과 검사 프로세스에만 적용했습니다. Windows/WSL 재설치, Jetson 변경, 시스템 네트워크 설정 변경은 하지 않았습니다.

## 실행 검사와 발견한 한계

- 영상 검사에서 해상도·인코딩·좌표계·내부 파라미터·유효 깊이 범위뿐 아니라 실제 수신 프레임률, 시뮬레이션 시간 대비 실제 시간과 동일 시각 쌍의 비율을 기록하도록 보완했습니다.
- 초기 best-effort 영상 수신 진단에서는 깊이 수신률이 약 81.8 Hz로 낮아진 실행이 있었고, reliable 영상 수신으로 바꾼 직후에는 주행 도중 검사 도구의 수신 처리량과 종료 순서 문제도 발견했습니다. 영상 큐를 계속 처리하면서 명령 발행만 제한하고, 종료 시 수신자를 먼저 해제하도록 보완했습니다. 송수신을 바꿨다는 이유만으로 모든 누락 원인이 해결됐다고 단정하지 않습니다.
- 최종 세 프로필 검사에서 해상도 848×480, RGB `rgb8`, 깊이 `32FC1`, 각 `CameraInfo`와 광학 좌표계, 점군·IMU·서로 다른 좌우 엔코더 증가량을 확인했습니다. 약 22 cm 전진·약 0.07 rad 방향 변화·명령 중단 후 0.01 m/s 미만 정지와 오류 없는 종료를 통과했습니다.

| 지도·프로필 | RGB / 깊이 수신률, 시뮬레이션 시간 기준 | RGB / 깊이 수신률, 실제 시간 기준 | 시뮬레이션 진행 배율 |
|---|---|---|---|
| 원본 `synchronized_60` | 62.5 / 62.5 Hz | 약 18.68 / 18.69 Hz | 약 0.30배 |
| 실험 `low_load_30` | 약 30.30 / 30.30 Hz | 약 17.48 / 17.49 Hz | 약 0.58배 |
| 실험 `high_speed_async` | 62.5 / 약 90.91 Hz | 약 14.60 / 21.22 Hz | 약 0.23배 |

- 위 값은 각각 약 1.4~1.5초의 시뮬레이션 구간을 관측한 짧은 검사 결과이며 평균 성능 보장이 아닙니다. 점군 수신을 확인한 뒤 해당 구독은 중단한 조건입니다. 동일 주기 프로필의 RGB·깊이 시각 쌍 비율은 각각 100%, 약 97.8%였으며, 실물의 하드웨어 동기화 시험은 아닙니다.
- Gazebo Sensors 8의 정수 ms 주기 처리로 명목 60/90/30 Hz가 약 62.5/90.91/30.30 Hz가 되는 것을 소스와 실행 결과로 확인했습니다. 실제 D435i가 이런 주기로 동작한다고 해석하지 않습니다.
- 마지막 세 프로필의 상세 결과는 `artifacts/tests/original_synchronized_60_smoke.json`, `experimental_low_load_30_smoke.json`, `experimental_high_speed_async_smoke.json`에 있습니다. 반복 실행 산출물은 기존 원칙대로 Git에서 제외하고 요약을 이 문서에 보존합니다.
- 이후 기본 인수를 사용한 실험 지도 고속 재검사도 통과했습니다. 시뮬레이션 시간 기준 RGB 62.5·깊이 약 90.91 Hz, 실제 시간 기준 약 15.04·21.83 Hz와 약 0.24배 진행 속도를 확인했고, 주행·정지와 정상 종료까지 통과했습니다. 이 재검사 결과는 `artifacts/tests/experimental_smoke.json`입니다.
- ROS 패키지 4개 빌드, 자동 회귀 검사 29개, 차량·원본·실험 월드의 엄격한 SDF 검증을 통과했습니다. 트랙 원본 ZIP의 SHA-256은 `DE448BA10C614E0F635D44B2F36BAB29EBF455C323DE442562DD01A8296758E4`로 같고 압축 해제 파일 23개도 바이트 단위로 일치합니다.
- 단독 완주·경쟁 차량·지속 점군 처리량·Jetson 실시간 성능·실물 D435i 연결은 검사하지 않았습니다.

## 시설 검사 결과와 별도 정지 문제

- `validate_facility_visibility.py`가 실제 차량 RGB를 수신하고, 배치 서비스 응답뿐 아니라 별도의 세계 위치·방향 관측과 영상 시각을 확인하도록 구성했습니다. 정답 정보는 시험 배치·판정에만 사용하며 대회용 인지 입력과 분리합니다.
- 최종 실행에서 출발 위치 6곳의 빨간 렌즈, 마커 4개의 각 1.5·1.0·0.75 m 상류 접근을 모두 확인했습니다. **18/18 가시성 조건 통과**이며 OpenCV 4.6.0 기본 ArUco 검출 설정입니다.
- 0.16 m/s 방지턱 통과에서 1.11496 m 이동했습니다. 차체 기준점은 초기 z=0.002998 m, 최대 z=0.008059 m, 최종 z=0.003000 m였습니다. 약 5.06 mm 상승 후 평지 높이로 복귀했으며 노란 색 띠도 실제 RGB에서 확인했습니다.
- 별도 정지 판정인 ‘6초 이내에 속도 절댓값 0.01 m/s 미만을 0.5초 연속 유지’는 실패했습니다. 마지막 2초의 피드백 범위는 방지턱 시험에서 약 -0.0591~+0.0559 m/s, 평지 대조에서 약 -0.0550~+0.0533 m/s였습니다. 마지막 0.5초 양 끝 차체 위치 차이는 각각 약 0.94 mm·1.35 mm였습니다. 작은 위치 차이를 근거로 완전 정지로 처리하지 않습니다.
- 평지에서도 나타나므로 새 방지턱 통과 결과와 구분하고, 차량 제어의 원인 진단을 다음 작업에 추가했습니다. 종합 보고서는 `facility_checks_passed: true`, `stop_check.passed: false`, `passed: false`와 종료 코드 1을 유지합니다. 두 검사 프로세스의 종료 자체는 정상이고 오류 로그는 없습니다.
- 자동 회귀 검사 40개, 원본·실험 월드의 엄격한 SDF 검증, ZIP 및 압축 해제 파일 23개 보존 검사가 통과했습니다. 최종 실험 월드는 링크 13개·충돌체 1,116개·시각 형상 1,295개입니다. 본선 2,332개·분기 155개/141개 표본과 저층 장애물 661개의 정적 외형 검사도 통과했습니다.
- 변경 후 `low_load_30`의 기존 기본 동작 검사도 통과했습니다. RGB·깊이 각각 약 30.30 Hz(시뮬레이션 시간), 약 16.11·16.12 Hz(실제 시간), 약 0.532배 진행, 0.22066 m 전진·0.07208 rad 조향 변화·엔코더·점군·IMU 수신 및 정상 종료를 확인했습니다. 이 도구의 순간 정지 통과는 위 지속 안정성 실패를 해소한 결과가 아닙니다.
- 시설 안내·결정 0005를 추가하고 프로젝트 현황·실험 트랙 안내·결정 0003·트랙 감사·센서 문서·README를 갱신했습니다. 대표 RGB 4장과 두 원본 보고서를 `artifacts/screenshots/2026-08-31/facilities/`에 보존했습니다. 전체 실행 로그·18조건 영상·위치 기록은 Git에서 제외한 `artifacts/tests/`에 있습니다.

- WSL 전체 종료·재설치·그래픽 드라이버 변경은 수행하지 않았습니다. 서버를 유지한 상태에서 WSLg 화면 합성기를 다시 연결한 뒤 `use_gfxredir = 1`, `COPY MODE` 제목 경고가 사라진 Gazebo 창과 실제 트랙 화면을 확인했습니다. 관련 원리 설명은 [WSLg 유지관리자 답변](https://github.com/microsoft/wslg/discussions/312)을 참고하되, 재연결이 모든 환경에서 통한다는 보장은 아닙니다.
- 사용자가 직접 촬영·탐색할 수 있도록 시뮬레이션을 일시정지하고, 관찰 카메라를 높은 사선 항공뷰로 조절했습니다. 실제 D435i 센서의 위치·시야각이나 물리 모델은 변경하지 않았습니다.
- 수정 후 전체 사선 항공뷰와 출발 그리드·차량·피니시 근접 화면을 각각 `artifacts/screenshots/2026-08-31/facilities/track_oblique.jpg`, `start_grid.jpg`로 촬영했습니다. 두 사진 모두 실제 GUI의 1707×1019 px 원본 캡처입니다. 최종 관찰 카메라는 XYZ=(15, 2, 14) m, RPY=(0, 1.02, 2.625) rad, 수평 시야각 1.1 rad입니다.
- 마지막 실행은 `low_load_30`과 별도 통신 영역 `ROS_DOMAIN_ID=164`, `GZ_PARTITION=it_arena_facilities_view_20260831`을 사용했습니다. 앞선 검사 실행들은 종료했지만, 이 탐색용 서버·GUI는 사용자의 요청대로 종료하지 않고 열어 두었습니다. README의 대표 사진을 수정 후 화면으로 교체하고 이전 사진은 링크로 보존했습니다.
- 마지막 파일 검사에서도 자동 회귀 검사 40개·원본 보존·실험 트랙 재생성 검사가 통과했습니다. 문서의 로컬 링크 49개와 공백 검사를 확인했고, 실제 영상 보고서의 입력 파일 SHA-256 4개가 최종 파일과 일치함을 확인했습니다.

## 후속 요청: 동적 신호등·임시 C1 라이다·기초 반복 주행

- 사용자는 RPLIDAR C1 기준의 임시 2D 라이다와 신호등 전환, 지름길을 타지 않고 계속 도는 가장 간단한 자율주행을 요청했습니다. 기존 정답 위치 기반 중심선 추종 계획과 별개로 RGB 출발 신호·ArUco 벽 선택·라이다 벽 추종으로 설명 가능한 데모를 구현했습니다.
- SLAMTEC 공식 C1 웹 사양표에서 360°·8~12 Hz(대표 10 Hz)·5,000표본/초·대표 각도 간격 0.72°, 70% 반사율의 0.05~12 m와 10% 반사율의 0.05~6 m, 거리 분해능 15 mm·정확도 ±30 mm를 확인했습니다. 공식 데이터시트 v1.2 링크는 확인했으나 다운로드가 거부되어 PDF 세부 주석을 읽은 것으로 기록하지 않습니다.
- 모델에는 360°·10 Hz·500점·0.05~12 m를 적용했습니다. 스캔 평면은 지면 기준 약 12.5 cm, 차량 중심보다 3 cm 뒤입니다. 110 g 질량과 단순 원통 표시 형상을 추가했습니다. 실제 구매·기계 도면·브래킷·감지 높이의 확정값은 아닙니다.
- 스캔은 실제 ROS `/scan`, `laser_frame`으로 발행되며 고정 좌표 변환을 추가했습니다. 첫 주행에서 약 10.0002 Hz를 관측했습니다. GPU 광선 거리는 15 mm로 양자화되지 않으며, `scan_time`·`time_increment`는 0입니다. 반사율·실물 오차·순차 스캔 왜곡은 미반영이라고 명시했습니다.
- 별도 신호등 제어기가 렌즈의 실제 재질·발광색을 빨강 8초→노랑 2초→초록 유지로 바꿉니다. 첫 RGB가 준비된 뒤 시뮬레이션 시간으로 진행하며 수동 색 변경·순서 재시작 서비스도 제공합니다. 원본 월드나 시설 형상은 변경하지 않습니다.
- `arena_autonomy` 패키지의 입력은 RGB와 라이다뿐입니다. 빨강을 먼저 보고 같은 신호등의 초록을 연속 세 번 확인하면 출발 허가를 유지합니다. ID 20에서 왼쪽 벽, ID 30에서 오른쪽 벽을 선택해 두 지름길 반대편을 따라갑니다. ID 0·45에서 왼쪽 기본값으로 복귀합니다. 랩 수로 멈추는 조건은 없습니다.
- 최고 속도 명령은 0.35 m/s이며 커브에서는 감속합니다. 사용자 정지·센서 데이터 지연/누락·벽 추정 실패·가까운 장애물에는 정지를 명령합니다. 다중 차량 회피나 누락된 마커에 대한 복구는 이번 구현의 보장 범위가 아닙니다.
- `demo.launch.py`만 RGB 30 Hz·깊이 꺼짐을 기본으로 하여 사용하지 않는 센서의 부하를 줄였습니다. `depth_camera:=true`로 복원할 수 있으며 일반 실행의 RGB 60·깊이 90 기본값과 카메라 명목 사양은 유지합니다.

## 정지 진동 원인 분리와 수정

- 설치된 Gazebo Math 7.6.0의 속도 제한기만 호출하여 물리 접촉·방지턱·ROS 없이 정지 진동을 재현했습니다. 1 ms 주기에서 0.16 m/s 명령 7초 후 0 명령 6초를 유지할 때 jerk ±20 제한을 켜면 마지막 2초 출력이 약 -0.0631~+0.0676 m/s였고, jerk 제한만 끄면 정확히 0이었습니다.
- 따라서 jerk 제한만 제외하고 속도 ±2 m/s·가속도 ±4 m/s² 제한은 유지했습니다. 조향 비례 이득 12도 현재 시뮬레이터 관절 응답을 위한 임시 설정으로 명시했습니다. 실물 ESC·서보·제동 성능의 검증 결과는 아닙니다.
- 수정 후 시설 재검사: RGB 가시성 18/18, 0.16 m/s 방지턱 통과, 지속 정지, 정상 종료가 모두 통과했습니다. 이동량 1.11597 m, 최대 차체 기준점 z=0.008057 m·복귀 z=0.003000 m였습니다.
- 수정 후 평지 대조 시험도 통과했습니다. 평지와 방지턱 시험 모두 약 0.54초 안에 `abs(odom_speed)<0.01 m/s`를 0.5초 연속 유지했고 최종 속도는 0이었습니다. 마지막 0.5초 양 끝 위치 차이는 약 0.004 mm였습니다.
- 새 보고서는 `artifacts/tests/facilities_after_limiter_fix/`와 `artifacts/tests/flat_stop_after_limiter_fix/`에 있습니다. 이전 `facilities/visibility_report.json`·`flat_control_report.json`의 실패 기록은 덮어쓰지 않았습니다.

## 두 바퀴 주행 결과와 종료 검사 분리
