## GPU 사용 여부 확인

- 조회 전 Ubuntu-24.04 WSL2는 정지 상태였다. 조회를 위해 시작했으며 `/dev/dxg`와 WSLg DISPLAY/Wayland 환경이 존재한다. NVIDIA 사용률 0%는 시뮬레이션 미실행 상태의 값이므로 과거 GPU 미사용의 근거로 쓰지 않는다.
- `/home/jinhyeong/.gz/rendering/ogre2.log`의 수정 시각은 2026-09-06 00:55:47 KST다. 00:53:01 초기화에서 `EGL_MESA_device_software`, `GL_RENDERER = llvmpipe (LLVM 20.1.2, 256 bits)`, `Device Name: llvmpipe`를 확인했다. 해당 실행의 렌더링은 CPU 소프트웨어 경로였다. 모든 과거 실행의 렌더러를 확인한 것은 아니다.
- [기존 로그 보존 사본](../../artifacts/validation/2026-09-07/gpu_audit/ogre2_previous_run.log)을 남겼다. 텍스트 사본이며 바이트 동일 보존은 아니다. llvmpipe 해석은 [Mesa 공식 문서](https://docs.mesa3d.org/drivers/llvmpipe.html)에 근거한다.
- 실행 소스는 Gazebo 서버를 `gz sim -r -s`로 시작하고 `headless`는 GUI 실행을 분리한다. 읽은 셸 설정에서 강제 소프트웨어 렌더링 환경변수는 발견하지 못했다. `glxinfo`는 설치되지 않아 현재 GLX 렌더러는 미확인이다.
- CPU 렌더링은 지연의 유력한 기여 요인이지만 전체 지연 중 비율은 미계측이다. 다음은 WSLg/렌더러의 하드웨어 선택 경로 확인과 동일 조건의 짧은 실행 비교다. 이번에는 드라이버·실행 설정·센서·물리 모델을 변경하거나 주행을 다시 실행하지 않았다.

## 후속 승인: GPU 실행 경로 복구와 같은 조건 비교

- 사용자의 후속 요청에 따라 실행 설정 수정과 짧은 비교 시험을 진행했다. 위 미수정 기록은 최초 조회 단계다. Ubuntu 공식 `mesa-utils`와 `gdb` 진단 도구를 설치했으며 GPU 드라이버·WSL 업데이트나 전역 셸 설정 수정은 하지 않았다.
- `glxinfo` 기본/어댑터명 단독 지정은 llvmpipe였다. `GALLIUM_DRIVER=d3d12`와 NVIDIA 이름을 함께 주면 RTX 5070 Laptop GPU·Accelerated yes로 바뀌었고 Gazebo 실제 GL_RENDERER에서도 확인했다. 기존 EGL software 표시는 장치 탐색이며 실제 당시 렌더링은 GLX였다.
- 실행 파일에 렌더링 선택을 추가하고 CPU·기존 환경 복귀를 지원한다. 환경 진단의 NVIDIA 장치 존재 표시를 실제 렌더러 검증과 구분했다. 센서 구성·물리 시간 간격·차량·코스는 변경하지 않았다.
- CPU/GPU 각각 공식 코스·RGB/깊이 848×480@30·ToF6·GUI/녹화 없음·영상 150개 계측과 직진/조향/정지를 수행했다. CPU 0.11843 RTF·111.36초, 최초 GPU 0.11743 RTF·115.76초였다. 총시간에는 준비·제동·종료가 포함된다. RGB/깊이 시뮬레이션 수신은 양쪽 약 30.297 Hz였다. GPU 사용만으로 속도 개선은 없었다.
- CPU 22개 자식 모두 정상 종료. 첫 GPU는 센서·주행·실제 정지 후 Gazebo SIGKILL로 종합 실패였다. 짧은 진단은 종료 SIGSEGV였고 GDB 부착 전에 충돌하여 그 시도에서는 스택을 얻지 못했다.
- Gazebo 제공 sensors_demo.sdf 100회 갱신을 GDB 아래 실행하여 프로젝트와 무관한 렌더 스레드 종료 충돌을 재현했다. [스택](../../artifacts/validation/2026-09-07/gpu_audit/minimal_debug.txt)을 보존했다. [WSLg #1497](https://github.com/microsoft/wslg/issues/1497)의 같은 Mesa 버전 core 해제/TLS 문제와 일치하는 강한 추론이며 모든 주소의 라이브러리 귀속을 확인한 것은 아니다.
- D3D12 라이브러리 직접 preload는 초기화 충돌로 폐기했다. 뒤의 dlopen 보조 첫 시도는 LD_PRELOAD의 공백 경로 해석 문제였으며 검색 경로와 파일명을 분리한 재시험에서 최소 예제가 정상 종료했다. 실패 로그는 모두 보존한다.
- 최종 보조 기능은 정확히 libd3d12core.so의 로드에 RTLD_NODELETE만 더한다. Gazebo에만 적용하며 미리 드라이버를 초기화하거나 다른 라이브러리 해제를 막지 않는다. 최종 첫 프로젝트 실행은 0.11231 RTF·112.13초이며 센서/주행/실제 정지/정상 종료를 통과했다. 성능 개선으로 표현하지 않는다.
- [설정과 제한](../simulation/GPU_RENDERING.md), [전체 검증 산출물](../../artifacts/validation/2026-09-07/gpu_audit/)을 추가했다. 첫 비교의 실행 소스는 initial_source에 보존한다. GPU 미사용 문제와 실행 속도 병목을 분리하며 순차 LiDAR·고속·장시간 녹화·마커 검출을 이번에 재검증했다고 하지 않는다.
- 최종 반복 2회차는 0.10980 RTF였고 센서·주행·실제 정지 후 Gazebo 종료 대기로 실패했다. 보조 적용 결과는 1회 정상 종료·1회 실패이며 해결 완료가 아니다. GPU 기본 적용을 철회하고 simulation/demo/smoke의 기본을 `system`으로 정리했다. GPU 선택과 실험적 수명 보조는 명시적 진단용으로 보존한다.
- 마지막 검사: Python 56개·C++ 1개 통과, arena_gazebo 빌드 성공. 첫 최종 GPU는 22/22 자식 정상 종료, 두 번째는 21/22 정상·Gazebo SIGKILL이다. 검사 종료 후 gz sim·parameter_bridge·smoke 프로세스 잔존 없음. 기본값 복구 후 Python 56개를 다시 통과했다. 성능 계측이 끝난 두 번째 실행의 주행/정지 단계에서 자동 검사를 병행했으므로 그 실행의 전체 벽시계 시간은 엄밀한 속도 비교에 쓰지 않는다.
- 미해결: GPU 종료 안정성, 전체 약 0.11배 실행의 지배적 병목. 물리·ROS 전송/스케줄링 등이 후보이나 이번에는 원인을 확정하지 않았다. GPU 사용률 단일 표본은 다른 Windows 작업도 포함하여 병목의 증거로 쓰지 않는다. GitHub 게시·팀 센서 결정·기존 실패 판정 변경은 하지 않았다.
