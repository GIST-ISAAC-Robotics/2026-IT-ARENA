## 팀 실행 월드 갱신

- `track:=official` 입력을 `official_v2026.09.01.yaml`로 교체했다. 새 공식 마커 pose·PNG/PBR 표현을 보존하고, 구버전에 필요했던 벽 스냅·비텍스처 코드 셀 대체는 제거했다.

- 파생 월드의 20×15 cm 본선/지름길 정적 통과 검사, 입력·출력 해시 검사와 엄격한 SDF 검사가 통과했다.

## 새 관찰과 보류

- 공식 벽 부착 마커는 정면 진단 카메라에서는 모두 검출됐지만 차량 전방 카메라의 정지 표본에서는 접근각에 따라 검출 구간이 짧았다. 기본 표본은 12개 중 6개, 촘촘한 표본은 37개 중 9개가 해당 ID를 검출했다. 저속 한 바퀴에서는 네 ID 모두 검출됐으므로 “사용 불가”가 아니라 고속·가림·실물에서 확인할 위험으로 기록했다.
- 위 관찰은 게시하지 않았다. 운영진 확인 요청 형식의 초안만 갱신했으며, 실제 D435i·인쇄 마커·속도/각도 시험 후 사용자의 별도 승인을 받아야 게시할 수 있다.
- ROS OpenCV 4.6의 ArUco API 차이, ZIP에 포함된 `.pyc`, 장시간 검사 중 발생한 bridge 종료 오류와 Gazebo 종료 지연은 내부 환경·포장 관찰로 남겼다. 독립 실행이 정상 종료했으므로 공식 트랙 오류로 단정하지 않았다.

상세 근거는 [`artifacts/validation/2026-09-01/official_update/`](../../artifacts/validation/2026-09-01/official_update/README.md)와 [공식 재감사](../track/OFFICIAL_V2026_09_01_REAUDIT.md)에 정리했다.

## 공식 출발 그리드 visual 복구

- 사용자 검토에서 `v2026.09.01` 원본에 매몰 문제가 해결된 25×17 cm 흰색 채움 슬롯 6개가 있는데도, 팀 공통 시설 생성기가 이를 제거하고 기존 U자/번호 표시로 다시 그린 사실을 확인했다. 공식 pose만 보존하고 공식 visual을 버린 상태였으므로 정정했다.
- 보존 ZIP은 수정하지 않았다. `official_filled_slots` 표현에서는 원본 `grid_slot_0`~`grid_slot_5`의 pose·0.25×0.17×0.001 m 상자·흰 재질·비충돌 속성을 런타임 병합까지 유지한다. U자/번호는 `experimental` 전용으로 명시했고, 공식 원본에 없는 피니시 체크무늬는 계속 임시 표시로 분류했다.
- 공식·실험 생성본의 해시 검사를 통과했고, 원본과 파생 슬롯 visual을 직접 대조하는 회귀 검사를 추가했다. 전체 Python 검사 115개, `arena_gazebo` C++ 단일 모터·차동 검사 1개, ROS 패키지 5개 빌드와 공식 월드 엄격한 SDF 검사를 통과했다. 처음 `build/arena_vehicle_interface`에 CTest를 잘못 조회해 검사 0개로 나온 것은 코드 실패가 아니며, 실제 C++ 검사가 있는 `build/arena_gazebo`에서 다시 확인했다.
- 새 공식 월드를 Gazebo GUI에 실제 로드하고 차량 생성을 확인한 뒤 [출발 구역 근접 사진](../../artifacts/screenshots/2026-09-01/official_grid_restore/start_grid_with_vehicle.png)과 [전체 사선 조감도](../../artifacts/screenshots/2026-09-01/official_grid_restore/track_overview_oblique.png)를 2129×1447 PNG로 저장했다. Computer Use로 실제 화면과 저장 결과를 다시 확인했다.
- 이번 변경은 collision이 없는 시각 형상 복구이므로 기존 본선 한 바퀴를 다시 수행하지 않았다. 주행·인지 성능은 앞 절의 기존 검증 경계를 그대로 유지한다.

## 미게시 upstream 이슈 초안 두 건 재정비

- 주최 측 저장소 `main`이 계속 커밋 `921f3f9a044f1a38ff849cb8e19d00182dd5533b`임을 확인하고, 현재 `.github/ISSUE_TEMPLATE/question.md`와 `bug.md`를 다시 읽었다. ArUco 설치 방향은 질문 양식의 `질문`·`해본 것 / 참고한 문서`, 트랙 형상은 문제 양식의 `어떤 파일에서`·`무엇이 이상한가요`·`환경` 항목만 사용하도록 초안을 고쳤다.
- ArUco 초안에서 이전 이슈 해결 감사 문단과 실제 D435i 추가 시험을 약속하는 문장을 제거했다. ID 30이 0.9 m보다 가까워졌을 때의 미검출은 커브와 시야각으로 화면 밖에 나간 결과이므로 “비연속적인 검출”로 표현하지 않았다. 초안은 공개 SDF의 벽 평행 pose가 실제 시공 방향인지 묻는 `[질문]`으로 분류했다.
- 공식 ZIP의 설계 통로와 실제 노면 visual/collision 상자 합집합을 다시 비교했다. 설계상 21.793955 m² 중 0.324238 m²(1.4877%)가 노면 상자에서 빠졌고, 오른쪽 아래 급커브의 한 단면에서 명목 가장자리부터 최대 0.149 m가 비었다. 공식 원본과 현재 실행본의 노면 collision 148개·잔디 collision 254개 pose/크기는 같아 #7의 링크 병합 결과가 아니라 공식 생성 형상 자체임을 확인했다.
- 갈림길 전용 잔디 상자가 생성되지 않고 본선 잔디도 분기 입구에서 잘리는 정책을 별도 관찰로 정리했다. `MANUAL.md` §6의 잔디 진입 패널티는 여전히 미정이므로, 확정 규칙으로 단정하지 않고 후속 확정 시 시뮬레이션 판정이 모호해질 수 있다는 조건부 영향만 문제 초안에 적었다.
- 두 본문에 공식 `preview.png`·`map_with_grass.png`와 기존 ID 30 차량 시점 사진 링크를 사용했다. 공식 ZIP의 두 지도도 직접 열어 노면의 삼각형 공백과 갈림길 주변 잔디 띠 단절이 실제 이미지에서 드러나는지 확인했고, 네 raw URL이 로그인 없는 요청에서 모두 HTTP 200임을 확인했다. 이 시점에는 주최 측 이슈·댓글을 만들거나 수정하지 않았다.

## upstream 이슈 #12·#13 등록

- 사용자의 최종 지시에 따라 ArUco 질문의 설명 문단에서 가까워진 뒤 화면 밖으로 나가는 서술을 제거했다. 대신 1.50 m 정지 표본에서 네 ID가 모두 미검출이고, 확인된 가장 먼 검출 거리가 ID별 0.75~1.20 m여서 고속 주행·다른 차량 가림 시 인식 기회가 부족할 수 있다는 관찰을 중심으로 고쳤다. 거리별 원자료 표의 `ID 30 / 0.75 m / 화면 밖`은 짧은 검출 구간을 보여주는 관측값이므로 사용자 확인에 따라 유지했다.
- 공식 저장소 `main`이 계속 `921f3f9a044f1a38ff849cb8e19d00182dd5533b`임과 기존 이슈 중 새 두 건과 중복되는 열린 항목이 없음을 확인했다. 증거 이미지 네 장도 게시 직전 로그인 없는 요청에서 모두 HTTP 200이었다.
- 명시적 게시 승인에 따라 `[질문] 벽 부착 코스 ArUco의 실제 설치 방향`을 [#12](https://github.com/MOSW626/istech-it-arena/issues/12), `[문제] 급커브 노면과 갈림길 주변 잔디에 공백이 생깁니다`를 [#13](https://github.com/MOSW626/istech-it-arena/issues/13)으로 `leejinh0225` 계정에서 등록했다.
- 게시 직후 두 이슈가 `OPEN`이고 GitHub의 제목·본문이 로컬 최종본과 정확히 일치함을 다시 조회했다. 공식 템플릿의 `question`·`bug` 라벨은 저장소 권한 부족으로 추가가 거부돼 비어 있으며, 제목과 본문 양식은 그대로 유지된다.
- 등록 후 현재 공식 월드의 보존 ZIP·입력·출력 해시와 29개 출력 형상을 `scripts/build_official_track.py --check`로 다시 대조해 `status=ok`를 확인했다. 처음에는 일반 WSL 셸에서 바로 전체 검사를 실행해 `xacro`·ROS 메시지·작업공간 모듈을 찾지 못하며 수집 단계에서 중단됐고, 이는 코드 실패가 아니라 ROS 환경 미적용이었다. `/opt/ros/jazzy/setup.bash`와 현재 `install/setup.bash`를 불러온 뒤 같은 범위의 Python 검사 115개가 모두 통과했다.
