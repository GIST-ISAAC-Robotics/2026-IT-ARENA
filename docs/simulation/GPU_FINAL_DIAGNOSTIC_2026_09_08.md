# 시뮬레이터 GPU 최종 추가 진단

작성: 2026-09-08. 사용자 요청에 따라 로봇의 영상 인식·제어 코드는 제외하고 시뮬레이터 계산만 확인했습니다.

## GPU가 맡는 범위

- 가상 RGB 영상 생성은 `camera`, 깊이 영상 생성은 `depth_camera`입니다.
- C1급 LiDAR와 여섯 ToF는 이미 `gpu_lidar`입니다. 순차 취득의 500 Hz 원시 광선도 같은 렌더러에서 계산합니다.
- 따라서 `render_backend:=wsl_nvidia`로 확인한 GPU 렌더러는 RGB만 가속하는 설정이 아닙니다. 이 센서들의 그래픽 기반 계산에 함께 적용됩니다. `gpu_lidar`라는 형식 이름만으로 하드웨어 GPU 사용을 보장하지 않으며 실제 `GL_RENDERER`를 확인해야 합니다.
- 센서 결과를 ROS 메시지로 변환·전달하는 부분, 회전 스캔의 시각별 표본 선택, DART 물리 계산은 GPU 렌더러 전환으로 옮겨지지 않습니다.
- 현재 설치된 DART 물리 경로에는 이번 렌더러처럼 선택할 수 있는 GPU 가속 인수가 없습니다. [Gazebo의 지원 엔진과 설정](https://gazebosim.org/api/sim/8/physics.html)을 확인했습니다. 다른 GPU 물리 엔진의 플러그인 통합·차량 모델 및 접촉 검증은 별도 개발 범위이며, 현재 GPU 설정에서 빠뜨린 스위치로 취급하지 않습니다.

## 센서 생성만 분리한 비교

동일한 단순 상자 네 면을 보고, Gazebo Rendering 8.2.3의 Ogre2 센서를 직접 실행했습니다. 물리·ROS·공식 코스·실시간 제한은 없습니다. 준비 3회 후 정해진 수의 결과를 실제 CPU 메모리로 회수합니다. RGB 중앙 색상, 깊이/광선 중앙 거리 약 2.5 m, 프레임 크기·콜백 수와 정상 종료를 검사했습니다. 픽셀 전체 일치나 ArUco 검출 검사는 아닙니다.

CPU/GPU를 첫 반복에는 CPU→GPU, 둘째에는 GPU→CPU 순서로 실행했습니다. 서로 다른 계측은 병행하지 않았습니다. 아래는 두 번의 평균이며 시작·장면 로드·종료를 제외한 계산 시간입니다.

| 동일 작업량 | CPU 시간 | GPU 시간 | 시간 감소 |
|---|---:|---:|---:|
| 848×480 RGB+깊이 30쌍 | 1.06139초 | 0.80768초 | 23.9% |
| 500점 LiDAR 광선 500프레임 | 12.37875초 | 7.56550초 | 38.9% |
| 8×8 ToF 여섯 개, 각 15프레임 | 1.06194초 | 0.80201초 | 24.5% |

12회 모두 출력 검사·정상 종료를 통과했고, CPU는 llvmpipe, GPU는 D3D12 RTX 5070 Laptop을 매번 로그로 확인했습니다. 센서 처리에 GPU 이득이 존재합니다. 다만 이 표는 단순 장면에서 각 센서를 따로 갱신한 소규모 계측이며 전체 시뮬레이터 RTF나 센서 동시 처리량으로 합산하지 않습니다. 순차 LiDAR의 광선 계산과 Python 취득 조립 역시 구분합니다.

## 화면 연결을 생략하는 EGL 시도

[Gazebo EGL 방식](https://gazebosim.org/api/sim/8/headless_rendering.html)은 GUI 창만 생략하는 기존 `headless:=true`와 다릅니다. 센서 계측기에 `headless=1`을 적용했고 로그의 EGL 시작과 실제 D3D12/NVIDIA 렌더러를 함께 확인했습니다. RGB/깊이 30쌍 0.80517초, 출력 검사와 정상 종료를 통과했습니다.

기존 GPU GLX 평균 0.80768초와 거의 같으므로 속도 개선으로 채택할 근거는 없습니다. 1회 센서 단독 정상 종료를 실제 Gazebo 렌더 스레드 종료 문제 해결로 확대하지 않으며 운영 실행 옵션은 늘리지 않았습니다. EGL 장치 열거의 `software` 문자열만으로 최종 렌더러를 CPU라고 오판하지 않습니다.

## 500 Hz 순차 취득의 실제 주행 적용

기존 독립 LiDAR 시험기에 `--render-backend` 선택을 추가했습니다. 기본 `system`은 유지합니다. 기존 5 km/h 직선·10 Hz 순차 취득·500 Hz 원시 광선·8초 주행/정지 조건에서 CPU와 GPU를 비교했습니다. 이 시험장은 공식 코스가 아니며 기본 DART 충돌 검출·차량·센서/제어 조건을 동일하게 유지했습니다.

| 조건 | 준비·주행·정지·종료 포함 시간 | 순차 취득 | 주행/정지 | 정상 종료 |
|---|---:|---|---|---|
| CPU llvmpipe | 161.701초 | 통과 | 통과 | 21/21 자식 |
| GPU D3D12 RTX 5070 Laptop | 108.582초 | 통과 | 통과 | 21/21 자식 |

전체 시험 시간은 **32.9% 감소, 약 1.49배 처리 속도**였습니다. 각 1회 비교이며 준비·종료를 포함한 실행 시간입니다. 주행 구간은 7.992/7.989 sim초로 같은 8초 명령을 완료했고, 양쪽 10 Hz 스캔·100 Hz 제어·주행 중 80개의 서로 다른 스캔을 확인했습니다. 순차 광선의 최대 시간 근사 오차는 양쪽 약 1.8 ms, 원시 프레임 공백 폐기는 0회입니다. 제어 입력은 `/scan`·`/clock`뿐이며 GPU 적용을 위해 정답 위치를 추가하지 않았습니다.

3초 이후 중심선 RMSE는 CPU/GPU 약 3.735/3.733 mm, 도로 이탈·벽 겹침 표본 0개, 정지 확인 모두 통과했습니다. 스캔 나이 평균은 153/157 ms로 완전히 같지는 않습니다. 같은 실제 시간에 더 빨리 실험을 완료한 것이지 실제 LiDAR의 10 Hz 관측 공백이나 순차 왜곡이 해결된 것은 아닙니다.

사용 예: 기존 시험 명령에 `--render-backend wsl_nvidia`를 추가합니다. 일반 launch에서는 기존 `render_backend:=wsl_nvidia`를 사용할 수 있습니다. GPU 렌더링 선택은 시뮬레이터에만 적용하며 로봇 인식 코드의 CUDA 이식을 요구하지 않습니다.

## 최종 적용 판단

- **500 Hz 순차 LiDAR 실험에는 GPU 선택을 사용할 근거를 확보했습니다.** 기존 시험기에 선택 인수를 연결하고 실제 적용·통과까지 확인했습니다.
- 앞선 공식 코스의 순간 스캔 RGB-D 시험에서는 추가 이득이 없었습니다. 이번 결과로 그 측정을 뒤집거나 모든 실행에서 33% 빨라진다고 하지 않습니다.
- 이번 GPU 주행의 정상 종료 1회를 과거 간헐적 종료 문제 해결로 취급하지 않습니다. 전역 기본은 `system`으로 유지하고 GPU 실행은 자식 종료까지 검사합니다. 장시간 반복 안정성은 미확정입니다.
- 앞으로는 필요한 고부하 센서 시험에 확보한 선택형 GPU 경로를 활용하고, 추가 GPU 엔진 이식보다 자율주행 알고리즘·운동 보상·실험 품질에 우선 투자합니다. 새 장시간 진단·GPU 물리 엔진 이식은 이번 범위에서 시작하지 않습니다.
- 관련 Python 검사 19개를 통과했습니다. 센서 단독 13회와 실제 주행 2회 원문을 보존합니다. 운영 코스·센서 사양·물리·자율주행 로직은 이번 작업에서 변경하지 않았습니다.
