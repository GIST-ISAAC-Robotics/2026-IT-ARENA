# A3 Jetson 센서 기록 재생 시험

처음 작업을 인계받는 경우 [기록·재생/Jetson 통합 인수인계](../reports/RECORD_REPLAY_JETSON_HANDOFF_2026_09_29.md)를 먼저 읽는다. 이 문서는 단계별 원자료·조건·실패를 보존하며, 각 절의 과거 후속 계획을 현재 할 일로 누적하지 않는다.

**최신 결론, 9/29 계측 비용 비교:** ABBA 네 회에서 기존 `topic` 계측은 두 회 모두 운영 통과했다. 새 `buffered` 계측은 IMU 누락·CPU를 줄였지만 보호 0명령 2/4개와 순간 지연을 만들어 **개선안으로 채택하지 않는다**. [결과와 전환 판단](#상세-진단-발행-비용-비교--929) 기준으로 기존 방식의 입력·소스·결과를 개발 기준선으로 보존하고 A4 제한된 이상치/고착 대응으로 넘어갈 것을 권고한다. 현재 속도/입력에서의 연산·정지 경로 확인이지 실차 준비 완료나 모든 지연 해소가 아니다. **기본 system/legacy·센서율·QoS·MCU 수신 한도·보호 시간은 유지**한다. 아래 이전 실패와 당시 결론은 보존한다.

## 목적과 범위

PC의 [A2 처리 개선](RECORD_REPLAY_2026_09_24.md#2026-09-27-제어기-내부-계측과-1배속-적체-개선)에 사용한 원시 입력을 Jetson에서 재생해 ARM64/Humble 호환성과 처리량·지연을 확인한다. Gazebo·MCU·모터는 실행하지 않는다. 저장 명령은 비교 자료일 뿐 입력으로 발행하지 않으며 `/replay`와 별도 ROS 도메인·localhost를 사용한다. 보호 한도·센서율·경로/속도 정책을 낮춰 통과시키지 않는다.

## 실기 환경과 준비

- Ubuntu 22.04.5, aarch64, Jetson Linux 36.4.4, 커널 5.15.148-tegra. 초기 RAM 총 7.4 GiB·가용 약 5.4 GiB, 루트 파일시스템 여유 약 34 GiB.
- 기존 전력 모드는 `MAXN_SUPER`(ID 2). 시험을 위해 전력 모드·클록을 변경하지 않았다.
- 시작 시 `/opt/ros`가 없었다. 사용자가 공식 ROS 저장소 추가와 ROS 2 Humble/Python 시험 의존성의 관리자 설치를 명시적으로 승인했다. ROS 저장소 설정 패키지와 Humble 설치를 마쳤으며, apt 계획/실행은 **304개 신규·10개 의존 패키지 갱신·제거 0개**, 추가 디스크 약 200 MB였다. 갱신은 Python 3.10 계열·SQLite·OpenSSL 등이며 전체 OS 업그레이드는 하지 않았다. JetPack 재설치·재부팅·전원 종료는 하지 않았다.
- Python 3.10.12·NumPy 1.21.5·기존 시스템 OpenCV 4.8.0(기본 스레드 6개). ArUco와 `ArucoDetector`를 확인했다. PC 기준은 Python 3.12.3·NumPy 1.26.4·OpenCV 4.6.0(기본 스레드 32개)이므로 CPU 종류만의 엄밀한 대조는 아니다. 기존 OpenCV를 pip로 덮어쓰지 않았다.
- 이전 자동 승인 502 장애 이후 SSH 접속과 [접속 정보 비공개 저장](../hardware/JETSON_ACCESS.md)을 확인했다. 이후 패키지 설치 실행은 별도 승인을 받아 진행한다.

## 입력과 재현 단위

`capture_v2/sensor_recording`의 20.968초 입력을 그대로 사용한다. 소스 두 패키지·재생/감사 도구·선택 회귀·원시 기록을 명시적인 파일 목록으로 묶고 해시를 남겼다. 원시 묶음은 PC의 Git 제외 `build/jetson_a3_20260928.tar.gz`와 사용자 Jetson의 비공개 `/home/q/it_arena_a3_20260928`에만 보관한다. 전송 목록과 해시는 [산출물](../../artifacts/validation/2026-09-28/jetson_a3/)에서 확인한다.

0.5배속 기능 확인 후 1배속 반복 시험을 수행하고, 입력 무결성·콜백 전달·발행 스케줄·명령 유지·EOF 0명령·정상 종료를 각각 판정한다. `tegrastats`와 프로세스 CPU/RSS 기록을 함께 남긴다. 짧은 개방루프 기록의 통과를 실제 차량 주행·USB/CSI 센서 경로·모터 지연·장시간 발열 검증으로 해석하지 않는다.

## 호환성 문제와 수정

초기 묶음 62개 파일의 SHA-256·크기 확인, Humble에서 두 패키지 빌드, 선택 회귀 88개를 통과했다. 과거 코너 표본 파일을 포함하지 않은 소형 묶음이라 해당 자료를 읽는 2개 시험만 제외했으며 실행 실패를 제외한 것은 아니다.

그 뒤 초기 감사는 `metadata.yaml` 15행의 `yaml-cpp: bad conversion`으로 중단됐다. Jazzy의 v9 메타데이터에서 QoS 항목은 YAML 목록인데, Humble의 [공식 자료형](https://github.com/ros2/rosbag2/blob/humble/rosbag2_storage/include/rosbag2_storage/topic_metadata.hpp)은 문자열이다. **이 단계에서는 ROS 센서를 발행하거나 재생하지 않았다.** MCAP 자체를 직접 열자 86,306개 메시지를 모두 읽을 수 있었다.

`audit_sensor_bag.reader_for`에 제한적인 호환 경로를 추가했다. 기존 디렉터리 읽기가 위 변환 오류로 실패하고, metadata v9·MCAP 1개·`relative_file_paths` 일치 조건일 때만 그 MCAP를 직접 연다. 여러 파일 중 하나만 읽거나 다른 I/O 실패를 숨기지 않는다. 원본 metadata·MCAP·manifest는 그대로 두고, 이후 **파일 해시·전체 토픽/형식·CDR 해시/개수·시각 순서·수신 로그**를 계속 감사한다. 결과에 실제 읽기 경로도 남긴다.

호환 처리와 기록 계약 검사 41개를 Jetson/Humble 및 PC/Jazzy 양쪽에서 통과했다. 젯슨에서 전체 기록 감사도 통과했다. 최초 실패 로그·초기 소스 묶음·수정 후 소스 스냅샷을 별도로 보존한다. 이 변경은 기록 도구의 이식이며 주행 제어·안전 한도 변경이 아니다.

## 재생 결과

입력 평균은 RGB **61.927 Hz**·LiDAR **10 Hz**·IMU **250 Hz**·후륜 **100 Hz**다. 원시 RGB를 낮은 프레임률이나 압축 영상으로 바꾸지 않았다. 단, 기존 제어기는 영상 콜백 안에서 약 0.095초 간격으로 신호/마커 인식을 수행하므로 **62 fps 수신 부하와 62 fps 전체 인식 부하는 다르다**. 이번에 인식률을 올리거나 줄이지 않았다.

### 실제 입력 누락과 진단 누락의 구분

- 위 입력 처리 개수는 `/timing_snapshot`으로 **제어기 내부 누적 카운터**를 읽은 값이다. 1배속의 IMU 누락 202개(3.85%)·230개(4.39%), RGB 각 3개는 진단 로그 누락을 잘못 센 것이 아니다.
- 반대로 보호층 IMU는 내부에서 5,242개를 모두 처리했지만, 수집된 진단 행은 A 4,547개·B 4,792개였다. 관측 도구 쪽에도 별도의 누락이 있다. 따라서 1배속 `delivery_audit.json`은 누락 위치를 **미확인**으로 표시한다. IMU 누락이 모두 출발 전이라는 결론은 내릴 수 없다.
- 0.5배속에서는 진단 행과 완료 수가 일치했고 누락 IMU 2개는 원본 시각 0.032·0.036초였다.
- 현재 재생기는 한 executor에서 진단 수집과 발행 스케줄 대기를 함께 처리한다. 별도 읽기 전용 수집 executor로 분리하는 방안을 검토했지만, 전송 전 자동 승인 서비스의 502 오류가 재발했다. **개선안은 실행·검증하지 않았고 기본 코드에도 남기지 않았다.** 이미 완료한 세 시험과 결과 회수는 이 오류 이전에 끝났다. 이것은 재생 자체의 실패나 젯슨 장애가 아니다.

### 처리 시간: 수집된 표본에 한정

| 지표, 실제 시간 ms | 0.5배속 | 1배속 A | 1배속 B |
|---|---:|---:|---:|
| 지역 제어 콜백 p99 / 최대 | 8.47 / 10.96 | 6.73 / 8.05 | 6.43 / 8.05 |
| 지역 영상 콜백 p99 / 최대 | 28.34 / 44.14 | 18.64 / 31.36 | 18.53 / 35.55 |
| 제어 콜백 시작 간격 p99 / 최대 | 66.00 / 77.53 | 39.58 / 48.29 | 41.98 / 60.39 |

**1배속 시간표는 진단 행이 누락된 표본의 분포이며 전체 실행의 상한이 아니다.** A의 제어 진단 행은 932개인데 스냅샷 완료 수는 1,115개, B는 1,020개 대 1,115개다. 스냅샷 뒤 종료까지 콜백이 더 실행될 수도 있어 두 수의 차이를 그대로 최종 유실 개수로 단정하지도 않는다. 수집 표본에서 20 ms 초과 제어 콜백이 없었다고 전체 콜백이 모두 20 ms 미만이었다고 주장하지 않는다.

0.5배속에서는 시뮬레이션 20 ms가 실제 40 ms에 해당하므로 시작 간격을 1배속과 그대로 비교하면 안 된다. 또한 함수 실행 시간이 짧아도 executor 대기·영상 처리 때문에 실제 시작 간격은 길어질 수 있다. **50 Hz 실시간 마감 보장은 확인하지 못했다.**

PC 1배속의 제어 p99 4.64–4.78 ms에 비해 이번 수집 표본은 6.43–6.73 ms였지만, CPU·ROS·OpenCV·NumPy 버전과 수집 완전성이 다르므로 단순한 하드웨어 배수 비교로 쓰지 않는다.

### 자원 사용

1배속 A/B에서 원래 주행 구간의 **재생기+두 제어기** CPU 합계 중앙값은 약 275%/282%였다(코어 하나를 100%로 계산). 이는 약 2.75–2.82코어 분량이며 6코어 CPU가 275% 과부하라는 뜻이 아니다. 시험용 재생기와 계측도 포함하므로 실제 차량의 제어기 단독 사용량으로 쓰지 않는다.

전체 시험의 세 프로세스 RSS 합계 최대는 약 316/307 MiB, 시스템 RAM 최대 약 2.21/2.19 GB, 보고된 센서 온도 최대 약 50.4/51.7°C였다. RSS 합계는 공유 메모리 페이지를 중복 포함한다. GPU 사용량 중앙값은 0%, 최고 표본은 0%/4%였으며, 제어 코드는 CPU 경로다. GPU가 자동으로 NumPy/일반 OpenCV를 가속했다고 해석하지 않는다. 짧은 시험이므로 열 포화·장시간 안정성이나 앞으로 추가할 알고리즘의 여유를 보장하지 않는다.

## 기준 시험 종료 시점의 상태와 후속 과제

- 마지막 Jetson 선택 회귀는 **94개 통과·과거 코너 자료 의존 2개 제외**다. 앞선 88개/41개와 합산하지 않는다. PC/Jazzy 호환 검사 41개도 통과했다.
- 결과 아카이브를 로컬로 회수하고 원격 SHA-256과 일치함을 확인했다. 원시 sensor recording은 결과 아카이브에 넣지 않았으며 기존 로컬/Git 제외 정책을 유지한다. 제어기·재생기·측정 프로세스 잔존이 없음을 확인했다. 젯슨 전원은 켜 두었다.
- 첫 후속은 **진단 수집의 완전성 확보**다. 이후 영상 처리와 IMU 수신의 executor/큐 간섭을 분리해 실제 누락과 시작 간격 변동을 줄인다. 보호 기준 완화나 IMU 주기 하향으로 숨기지 않는다. 20 ms 이상 영상 콜백과 짧은 센서 QoS 큐가 원인 후보지만 아직 기여도를 분리하지 않았다.
- 그 다음 충분히 긴 입력·반복/열 시험과 계측 비활성 비교를 수행한다. 지금은 20.968초 기록의 주행 부분이 약 10초인 기준 시험이다.
- A4 제한된 이상치/고착, 실물 센서 시간 계약·MCU/ESC, 정지 차량/앞차 대응은 계속 남아 있다. 새 하드웨어가 오기 전에도 앞의 수집·처리 개선을 먼저 할 수 있다.

## 재현

접속은 [Jetson 접속 안내](../hardware/JETSON_ACCESS.md)를 따른다. 현재 시험 폴더에서 서로 겹치지 않는 새 출력 이름을 사용한다.

```bash
cd /home/q/it_arena_a3_20260928
source /opt/ros/humble/setup.bash
source install/setup.bash
python3 scripts/run_jetson_replay_trial.py \
  artifacts/validation/2026-09-24/record_replay/capture_v2/sensor_recording \
  --output artifacts/jetson_a3/full_next --rate 1
```

전체 결과·최초 실패·소스 보존·해시 경로는 [산출물 안내](../../artifacts/validation/2026-09-28/jetson_a3/README.md)에 있다. GitHub 게시·주최 측 댓글·컴퓨터 종료는 이번 작업에서 하지 않았다.

## 후속 개선 시험

사용자의 개선 요청 뒤 SSH 연결이 다시 가능해져 아래 작업을 재개했다. 앞의 기준 시험 결과와 소스는 그대로 보존한다.

### 채택하지 않은 시도와 시험 도구 수정

- **동일 프로세스의 별도 수집 스레드(`observer_v1`)**: Jazzy/Humble 선택 회귀는 각각 49개 통과했지만, 실제 1배속 두 실행은 기능·스케줄 실패였다. 스케줄 p99 지연이 약 12.60/12.22초로 늘었고 진단 누락도 남았다. 보호층은 오래된 입력에 정지를 유지했으며 EOF 0명령·정상 종료는 통과했다. 이를 제어기 개선 성공으로 보지 않고 이 수집 구조를 폐기했다. Python 실행 간섭과 executor 운용 비용의 기여도는 개별 분리하지 않았다.
- **프로세스 분리 초기 검사**: PC 선택 회귀 87개 통과·1개 실패. 별도 재현에서 500개 중 처음 60개만 빠지고 61~500은 연속 수신됐다. 종료 뒤 마지막 기록이 잘린 형태가 아니었다. 발행자 쪽 구독 발견뿐 아니라 수집기 쪽 발행자 발견·서비스 응답까지 확인하는 시작 절차를 추가했다. 고빈도 수집에서는 executor에 노드를 한 번 등록해 유지하고, 센서 발행 구간에서는 매 메시지의 불필요한 `spin_once`를 제거했다.
- **OpenCV 작업 스레드 축소**: 원본에서 뽑은 1280×720 영상 218장을 6→1→1→6 스레드 순서로 처리했다. ID·출발 상태·ROI·연속 판정 횟수는 모두 같았지만, 영상 연산 p99는 6개에서 약 20.9~21.8 ms, 1개에서 약 26.2 ms였다. 스레드 수를 줄이지 않는다. 연속 실행 중 DVFS/캐시 상태가 다를 수 있어 정밀 배수 비교로 쓰지 않는다.

## 영상 인식 프로세스 분리 — 9/29 후속

### 구현과 시험 경계

지역 제어기의 RGB 수신 콜백은 최신 영상 보관만 하고, 공유 버퍼를 통해 별도 작업 프로세스에서 신호/마커를 인식한다. 한 번에 한 장만 처리하고 대기는 최신 한 장으로 제한한다. 인식 결과 후보의 촬영 시각·단조 수신 시각·요청 번호·reset 세대를 부모가 확인한 뒤 출발 상태와 벽 추종 방향에 반영한다. 오래된 결과는 연속 신호 판정에도 누적하지 않는다. 프로세스 사망·1초 처리 watchdog·형식/식별 오류는 고장으로 고정하고 기존 `SENSOR_STOP`으로 0명령을 발행한다. 설계와 대안은 [ADR 0025](../decisions/0025-isolated-vision-processing.md)에 정리했다.

`vision_execution=process`가 지역 Pure Pursuit 기본값이고 `inline`은 기존 동기 경로 비교용이다. RGB 원시 수신률·해상도, 기존 0.095초 인식 간격 제한, 검출 임계값, LiDAR/IMU/엔코더 입력, 경로·속도·독립 보호 조건은 바꾸지 않았다. 다만 타이머가 작업을 제출하고 최신 프레임을 고르므로 **인식 대상과 결과 반영 시점은 기존 동기 경로와 달라질 수 있다**. 이번 20.968초 재생에서는 각 209~210장을 처리했으며, 모든 RGB 프레임을 인식한 것이 아니다.

초기에는 호스트명과 이전 IP가 모두 응답하지 않아 원격 시험을 시작하지 못했다. 사용자 전원 재연결 뒤 기존 SSH 호스트 키로 접속이 복구됐다. 전원 재연결이 필요했던 근본 원인은 확인하지 못했으며 Wi-Fi·OS·전력 설정은 변경하지 않았다. 원격 기존 파일은 별도 묶음에 보존하고, 새 소스 64개 파일 해시 확인 후 Humble 두 패키지를 다시 빌드했다. 원본 bag은 그대로 유지했다.

### 정확성·고장 경계와 PC 폐루프

- PC/Jazzy 선택 회귀 **62개**, Jetson/Humble 선택 회귀 **113개·과거 자료 의존 2개 제외**를 통과했다. 공유 버퍼/최신 대기 한 장, 과거·미래 결과 거부, reset 이전 초록 신호 거부, 프로세스 사망·처리 timeout·식별 불일치·잘못된 영상 형식, 고장 고정 및 종료를 검사했다. PC에서는 실제 제어 함수가 오래된 결과·고장에 0명령을 발행하고 원래 촬영 시각을 유지하는지도 확인했다.
- 원본 기록의 동일 영상 **218장**을 같은 순서로 처리했을 때 양 환경 각각 출발 상태·연속 판정·ROI·마커 ID가 기존 동기 경로와 모두 일치했다. 이는 동일 입력 순서의 판정 일치이며 실제 병렬 재생의 조향 명령 비트 동일성을 뜻하지 않는다.
- PC 계측 비활성 폐루프는 `local_fast`·순차 C1 10 Hz·양쪽 운동 보정·50 Hz 제어·가상 MCU·방지턱 임시 해제로 **12.01849 m** 진행 후 정지·정상 종료를 통과했다. 최고 정답 속도는 2.267 m/s(약 8.16 km/h), 주행/정지 중 정적 벽 충돌 표본은 0개였다. 정지 요청 후 이동은 0.815 m, 최종 정답 속도는 약 1.29×10⁻⁶ m/s다. 즉시 물리 정지·전체 코스·실차 주행을 검증한 것은 아니다. 느린 WSL 시험의 기존 수신 벽시계 한도 30초와 원래 센서 관측 나이 제한을 구분하며, 영상 작업 watchdog은 1초다.
- PC 1배속 재생은 기능·스케줄·진단 완전성·EOF 0명령·제어기 정상 종료가 통과했지만 IMU 22개·RGB 2개가 누락됐다. 당시 WSL 실행 wrapper는 종료 코드 1을 보고했고 보존된 Python 출력에는 `passed=true`, `error=[]`만 있다. 현 소스는 `passed`에 따라 종료 코드를 정하므로 이를 입력 누락 때문이라고 설명할 수 없다. 원인은 미확인으로 남기며 보고서 판정과 셸 종료를 구분한다.

이전 동기 경로 두 회의 제어 시작 간격 최대 약 53 ms에 비해 이번에는 약 28~36 ms로 줄었다. 반면 제어 함수 자체의 p99는 약 6.5~6.7 ms에서 약 7.6~8.2 ms로 늘었고, 영상 계산은 여전히 별도 프로세스에서 수십 ms 걸린다. **콜백 분리 효과는 확인했으나 입력 무손실·안정적인 연속 주행·50 Hz 마감은 미달**이다. 재부팅/실행 순서와 스케줄 변동까지 통제한 엄밀한 단일 변수 성능 배수로 쓰지 않는다.

주행 구간의 재생기·수집기·제어기·영상 작업 프로세스 CPU 합계 중앙값은 약 301~320%(3.0~3.2코어), RSS 합계 최대 약 442~447 MiB, 센서 최고 온도는 약 52°C였다. 시스템 GPU 표본은 대부분 0%이고 B에서 최대 55%가 한 차례 관측됐지만 이 코드에 GPU 인식 경로를 넣은 것은 아니다. RSS 공유 페이지 중복·시험 도구 포함과 짧은 시험이라는 한계는 그대로다.

추가 시험 전에는 Python 도구의 이름 조회가 다시 실패했다. Windows 기본 SSH가 IPv6로 연결하고 **기존 호스트 키가 일치함**을 확인한 뒤, `-ConnectAddress`로 TCP 주소만 지정해 복구했다. 키 검증 이름/거부 정책은 유지했으며 별도 단위 검사 4개를 통과했다. [접속 안내](../hardware/JETSON_ACCESS.md#이름-조회만-실패할-때)에 절차를 남겼다.

**다음 작업:** 엔코더 수신의 간헐적 적체를 우선 분리 계측한다. publisher→DDS→콜백 진입과 공통 executor 반복 등록 비용을 나눠 확인하고, 입력 개수뿐 아니라 신선도와 주행 중 보호 정지를 통과 조건으로 사용한다. 검증 없이 QoS 큐를 늘리거나 운동 정보 유효 시간/보호 기준을 풀지 않는다. 이후 더 긴 기록·열 시험으로 반복성을 확인하고 A4 이상치/고착·다중 차량 작업으로 넘어간다.

### 준비한 비교 옵션 — 기본 실행은 유지

1. 재생기에 `--trace-wheels-publication`을 추가했다. 원본 CDR를 바꾸지 않고 엔코더의 원래 취득/기록 시각, 재생 ROS 시각, 같은 호스트 단조 시계의 발행 시작/끝, 발행 스케줄 지연을 별도 `wheel_publication.jsonl`에 남긴다. 선택 계측이므로 기본 비활성이다. 엔코더 헤더를 읽는 추가 역직렬화 비용이 있어 비교 양쪽에서 동일하게 활성화하고 채택 전 비활성 대조도 필요하다.
2. `analyze_wheel_delivery.py`는 원시 콜백 나이/처리 시간/시각 역전, 선택 발행 추적과 콜백의 간격을 대조한다. 발행 종료 전에 수신 콜백이 시작될 수 있으므로 음수 간격을 0으로 숨기지 않는다. 취득 시각 중복은 임의로 짝짓지 않으며 미계측 값은 `null`이다. DDS 내부 수신과 executor 대기까지 각각 측정한 도구는 아니다.
3. 공통 실행기에 `executor_mode=retained` 비교 옵션을 준비했다. 선택하면 단일 executor에 노드를 한 번 등록해 유지한다. **기본은 기존 `legacy`**이며, 재생의 `--executor-mode`로만 명시 비교한다. 콜백 완료 뒤 정지 출력을 내고 executor/context를 정리하며 예외를 숨기지 않는다. 아직 ROS/Jazzy·Humble에서 새 옵션을 실행하지 않았다.
4. 기본 `passed`와 별도로 `active_window_continuity`, `operational_passed`를 추가했다. 기본 기능·스케줄·진단 완전성 외에 기준 이동 구간의 0명령/역행/비유한 명령이 없어야 운영 비교 판정을 통과한다. 명령 발행 사이의 모든 순간이나 실차 이동을 보장하는 지표는 아니다. 기존 A~D 원자료에 새 함수를 적용하면 A/B는 연속 명령, C/D는 중단으로 구분된다. 과거 결과 파일은 수정하지 않았다.

ROS 없는 Windows 모의 단위 검사는 수명/종료 경계 6개·지연 집계 5개·연속성 3개, **14개 통과**했다. Python 구문 검사와 diff 검사도 통과했다. 분석 단위 검사의 초기 임시 파일 fixture는 Windows Temp 권한 때문에 4개 오류가 났으며, 파일 쓰기가 필요 없는 메모리 fixture로 바꾼 뒤 5개 통과했다. 이는 ROS 실행 검증을 대신하지 않는다. Jetson에 올라간 소스는 앞선 영상 분리 버전이며 이번 로컬 시험 옵션은 아직 전송하지 않았다.

## 엔코더 발행 추적과 executor 교차 비교 — 9/29 재개 결과

### 시험 범위와 회귀

원격 기존 소스를 보존한 뒤 센서 bag 없는 69개 파일 묶음의 해시를 대조하고 Humble 두 패키지를 재빌드했다. 원본 기록·센서율·QoS·보호 한도·전력 모드를 유지했다. 새 소스에서 `legacy A → retained A → retained B → legacy B` 순으로 같은 20.968초 기록을 1배속 재생했다. 네 회 모두 엔코더 발행 추적을 켰다. 계측 비용이 포함된 결과이며 비계측 성능 시험은 아니다.

- Jetson/Humble 회귀 **129개 통과·기존 자료 의존 2개 제외**, PC/Jazzy 회귀 **113개 통과**. 이전 실행 당시 회귀 개수와 합산하지 않는다.
- Jetson 네 회는 기본 기능·스케줄·진단 완전성·EOF 0명령·제어기 종료 코드 0/0·재생 CLI 코드 0을 확인했다. 남은 시험 프로세스는 없었다. 자원 기록기 종료 코드 -15는 실행기가 정상적으로 `terminate()`한 결과이며 제어기 비정상 종료가 아니다.
- 두 방식 모두 주행 비교 구간에서 보호 정지가 발생한 실행이 있다. `operational_passed`는 false/true/false/true이며 기본 `passed=true`와 구분한다.
- PC retained 1회도 재생/운영/스케줄/계측/EOF 정지/종료는 통과했다. 그러나 출발 전 지역 엔코더 최대 나이는 **698.91 ms**, 발행 종료→콜백 최대는 **696.89 ms**였고 지역 IMU 279개·RGB 2개가 누락됐다. 운영 판정은 원본 이동 구간 10.96~20.96초에서 관측된 명령만 검사하므로 출발 전 지연까지 없다는 의미가 아니다. PC 재생 전달 감사 첫 호출의 잘못된 `--output` 인자는 사용법 오류로 끝났고 positional 인자로 수정해 완료했다.
- 이번에는 새 Gazebo 폐루프 시험을 하지 않았다. 앞선 12 m 결과를 retained 모드 주행 검증으로 사용하지 않는다.

### 지연 구간에서 실제로 일어난 일

1. **legacy A, 엔코더 시각 17.183초:** 발행 호출은 약 **0.049 ms**, 발행 스케줄 지연은 **0.210 ms**였으나 지역 콜백은 발행 종료 뒤 **766.08 ms**에 진입했다. 같은 표본을 보호층은 취득 시각 기준 약 **3.08 ms**에 처리했다. 지역 제어기는 이 대기 동안 IMU **192회**, 영상 **47회**, 스캔 **8회**, 제어 **38회**를 실행했다. 제어 시작 간격 최대는 해당 구간에서 29.84 ms였다.
2. **retained B, 엔코더 시각 14.263초:** 발행 호출은 약 **0.105 ms**, 스케줄 지연은 **4.075 ms**였으나 두 수신자는 발행 종료 뒤 **688.57/688.94 ms**에 해당 엔코더를 처리했다. 두 콜백 진입 차이는 약 0.365 ms였다. 대기 중 지역/보호층 IMU는 **171/175회**, 제어는 **34/34회** 계속 실행됐고 그 제어 함수 최대 계산 시간은 **3.75/4.87 ms**였다.

따라서 이 표본들의 수백 ms 지연을 원본 bag 시각, 발행 스케줄, 엔코더 계산 시간 또는 노드 전체의 긴 정지로 설명할 수 없다. **특정 엔코더 전달·수신 준비 경로에서 지연됐다는 근거**이며, DDS 신뢰성 복구·수신 큐·토픽별 준비 알림/선택 중 어느 단계가 원인인지는 아직 구분하지 못했다. 다른 콜백이 실행됐다는 사실만으로 executor의 토픽별 문제까지 배제하지 않는다. 보호층 한쪽만 제때 받은 사례와 양쪽이 같은 표본을 함께 늦게 받은 사례를 모두 보존했다.

### 다음 비교에 필요한 조건

읽기 전용 확인 결과 Jetson은 `rmw_fastrtps_cpp` **6.2.10**, Fast DDS **2.6.12**를 사용하며 Cyclone DDS는 설치되어 있지 않았다. 시험 종료 뒤 `/dev/shm`에 Fast DDS 파일이 없었다는 관측은 **시험 중 SHM을 사용하지 않았다는 증거가 아니다**. 재생기는 새 도메인·`/replay`·localhost 격리를 적용한다.

설치 버전에 대응하는 [ROS 공식 participant 소스](https://github.com/ros2/rmw_fastrtps/blob/6.2.10/rmw_fastrtps_shared_cpp/src/participant.cpp#L145-L161)는 `ROS_LOCALHOST_ONLY=1`일 때 builtin transport를 끄고 loopback UDP와 SHM을 직접 추가한다. [Fast DDS 환경변수 문서](https://fast-dds.docs.eprosima.com/en/2.6.x/fastdds/env_vars/env_vars.html#fastdds-builtin-transports)는 `FASTDDS_BUILTIN_TRANSPORTS`가 builtin transport 활성화 시에만 작동한다고 명시한다. 그러므로 **해당 변수만 UDPv4로 바꿔 놓고 UDP 단독 비교라고 부르면 안 된다.**

후속은 localhost 격리를 유지하고 실제 적용 transport를 검증할 수 있는 설정/계측을 먼저 준비한 뒤 SHM·UDP 경로를 대조하는 것이다. [SHM 문서](https://fast-dds.docs.eprosima.com/en/2.6.x/fastdds/transport/shared_memory/shared_memory.html)는 세그먼트 용량과 메시지 크기의 관계를 경고하지만 이번에는 실행 중 세그먼트 사용량·전송 손실·ACK/NACK를 측정하지 않았으므로 이를 확정 원인으로 쓰지 않는다. OS 네트워크/전력·ROS/DDS 설치·영구 환경변수·QoS·보호 한도를 변경하지 않았다. 무작정 수신 큐를 키우거나 보호 시간을 늘리는 조치는 보류한다.

## DDS 전달 방식 대조 — 9/29 후속

### 비교 방법과 변경 경계

제어기·원시 기록·센서율·QoS·보호 기준·전력 모드는 그대로 두고 **재생 도구의 통신 설정만** 선택형으로 추가했다. `--dds-transport`를 지정하지 않는 일반 재생은 기존 실행을 유지한다. 이번 Jetson 시험에서는 `legacy` executor와 엔코더 발행 추적을 양쪽 모두 사용한다.

- `system`: Humble의 `ROS_LOCALHOST_ONLY=1`이 구성하는 UDP 루프백 + SHM.
- `udp_loopback`: builtin transport를 끄고 주소 허용 목록이 `127.0.0.1` 하나인 UDP만 명시한다. 다른 컴퓨터와 통신하도록 OS 네트워크 설정을 바꾸지 않는다.
- 재생기·수집기·지역 제어·보호층의 **실제 생성된 Fast DDS participant 설정을 각각 조회**한다. 예상과 다른 방식, 제한 없는 builtin 또는 외부 UDP 주소가 있으면 센서 입력을 시작하지 않는다. 환경변수 이름만 보고 적용됐다고 간주하지 않는다.
- 조회 모듈은 기존 participant의 설정을 읽기만 한다. 이는 구성 확인이며 패킷 흐름·ACK/NACK·SHM 실제 점유량 계측은 아니다. SHM descriptor의 `segment_size=0`은 기본 크기 선택을 뜻한다. 대응하는 [Fast DDS 2.6.12 초기화 소스](https://github.com/eProsima/Fast-DDS/blob/v2.6.12/src/cpp/rtps/transport/shared_mem/SharedMemTransport.cpp#L222-L245)는 이를 512 KiB로 치환한다. 실제 할당·사용량을 직접 측정한 값과 구분한다.
- 비교용 `shm_default`·`shm_16m` 프로필도 준비했다. 준비·단위 검사와 실제 재생 검증을 구분한다. 세그먼트 용량이 지연 원인이라는 가정은 아직 입증되지 않았다.

처음 probe 컴파일은 C++ `dds` namespace의 모호성으로 실패했고 완전한 namespace를 지정해 수정했다. 전체 소스 묶음 적용은 자동 승인 검토에서 범위가 넓다는 사유로 거절됐다. 사용자가 좁은 적용을 승인한 뒤 **재생·검사 파일 6개만 적용**, 기존 4개는 개별 백업·해시 검증했다. 제어기 패키지를 다시 빌드하거나 원시 bag을 전송하지 않았다. 이 거절은 이전의 승인 서비스 사용량/502 장애나 SSH 오류와 다르다.

Jetson probe 컴파일과 신규 단위 검사 **7개**, PC 관련 회귀 **79개**를 통과했다. PC의 기본 옵션 1배속 재생도 기능·스케줄·진단·운영·EOF 정지·정상 종료를 통과했다. 이 PC 실행은 Humble용 transport 감사/UDP 단독 시험이 아니다.

**UDP 단독은 두 회 모두 악화되어 해결책으로 채택하지 않는다.** 모든 회의 엔코더 발행 호출 최대는 1.03~2.88 ms였다. UDP B의 최장 지연 표본을 기다리는 동안 지역 제어 50회·IMU 242회·영상 62회·스캔 10회가 실행됐다. SHM을 사용하지 않는 구성에서도 긴 지연이 나타났으므로 SHM만의 문제로 단정할 수 없다. 그렇다고 이 결과만으로 DDS 신뢰성 복구와 executor의 토픽 선택/수신 큐를 구분할 수 있는 것은 아니다.

`system B`는 이동 구간 보호 0명령이 없지만 출발 전 엔코더 지연이 존재했다. 운영 판정의 검사 구간은 **10.96~20.96초**이며 전체 입력의 지연 상한을 뜻하지 않는다. `system A`의 19.8615초 `MOTION_STOP` 직전 최신 엔코더는 19.813초였고 IMU는 19.856초였다. 노드 전체 계산 정지가 아니라 운동 입력의 신선도 저하와 정지 판단이 일치한다. 장시간의 엔코더 최대 지연과 주행 중 짧은 정지 사례를 같은 사건으로 혼동하지 않는다.

이 4회의 제어 시작 간격 최대는 약 32.92~40.69 ms, 주행 구간 CPU 합계 중앙값은 약 3.12~3.26코어, RSS 합계 최대는 약 438~444 MiB, 최고 온도는 약 50.4~51.6°C였다. 재생·수집기 부하가 포함되며 짧은 시험의 값이다. CPU 총량 여유만으로 토픽 지연이 해결됐다고 판단하지 않는다.

새 6회 지역 제어의 최대 취득 시각 간격은 16~28 ms였다. 원래 IMU 250 Hz의 4 ms 간격과 비교해 작은 공백이 여러 번 생기는 양상이며, 엔코더의 약 1초 적체와 같은 현상이라고 묶지 않는다. 기존 운동 이력은 취득 시각을 사용하고 입력 공백/신선도 한도를 검사한다. 허용 구간의 마지막 값을 사용한 적분이 계속된다는 사실이 **빠진 IMU 회전량을 정확히 복원했다는 의미는 아니다**. 실차 자세 추정 오차나 새로운 필터 검증으로 확대하지 않는다.

- 실제 IMU 잡음·편향 교정/필터, 센서 드라이버, MCU/ESC·실차 제동과 다중 차량은 이번 작업 범위가 아니다. IMU 누락이 작은 공백으로 나타난다는 사실만으로 빠진 회전량의 오차가 작다고 보장하지 않는다.

### 목적·변경 범위

사용자가 반복 최적화의 목적과 종료 시점을 요청했다. 이번 목표는 누락 0개나 하드 실시간을 끝까지 추구하는 것이 아니라 **정상 입력에서 누적 적체/반복 정지 없이 개발할 연산 기반, 낡은 입력의 정지, 구조 변경 전후 비교 절차**를 확보하는 것이다. 10월부터 Claude와 이상치·다중 차량 작업도 병행할 계획을 반영하되 일정 때문에 실패를 통과로 바꾸지는 않는다.

기존 59.53초 입력을 재전송·새 주행 없이 사용했다. 같은 소스·매개변수에서 **topic A → buffered A → buffered B → topic B**로 실행했다. 네 회 모두 1배속·legacy·SHM 16 MiB·IMU/엔코더 발행 추적 ON·최소 수신자 OFF다. 차량/경로/속도/센서율/QoS/보호 시간/전력 모드를 변경하지 않았다.

- `topic`: 기존 콜백별 JSON 작성·진단 토픽 발행·독립 관측기 저장.
- `buffered`: 동일 단계·취득/진입/종료 시각·순번을 노드별 최대 100,000행 메모리에 보존하고, 센서 공급과 EOF 검사가 끝난 뒤 서비스 체크포인트에서 파일로 저장. 완료 횟수·SHA-256·행 수·순번·overflow를 확인하며 기존 파일을 덮어쓰지 않는다. 저장 뒤 콜백은 체크포인트 범위 밖이다.
- 기본 계측은 여전히 비활성, 기본 재생 계측은 topic이다. buffered도 메모리 할당/단계 계측 비용이 있어 무계측 실운용을 그대로 재현한 것은 아니다. 관측기 부하까지 함께 달라지므로 순수 JSON 함수나 DDS 발행 한 요소의 인과 효과로 분해하지 않는다.

### buffered에서 발생한 정지

저장된 완료 콜백을 제어 호출 직전까지 대조했다. **데이터 전량 수신과 제때 수신은 다르다.** 엔코더는 전부 도착했어도 해당 제어 호출 시점에는 최신 값이 아직 반영되지 않아 정지가 발생했다.

- 약 15초: 지역 제어기의 최신 엔코더 나이는 A **37.09 ms**, B **55.06/57.08/51.38 ms**였다. 기존 외삽 한도 **30 ms**를 넘어 `MOTION_STOP / motion_stale`로 0명령을 만들었고 보호층이 전달했다. IMU 나이는 해당 호출에서 약 16~20 ms였다.
- 약 24.067초: 지역 제어기는 양수 명령을 냈지만 보호층의 엔코더 나이가 A/B **53.07/53.70 ms**여서 독립 보호층이 0으로 제한했다.
- 다음 관측 양수 명령까지 최대 간격은 A **21.67 ms**, B **60.48 ms**였다. 명령 로그상의 간격이지 실제 차가 그 시간 동안 멈췄다는 뜻은 아니다. 최종 EOF의 정지는 별도로 모두 통과했다.

두 buffered 시험에서 비슷한 시점에 나타났지만, 메모리 할당·GC·스케줄링·수신 큐 중 무엇이 순간 지연의 근본 원인인지는 이번 계측으로 확정하지 않는다. 이번 대안은 CPU/IMU 누락을 줄이는 대신 최악 지연과 운영 판정을 악화시켰으므로 개선안으로 채택하지 않는다. 숫자 한 가지가 좋아졌다는 이유로 성공으로 바꾸지 않는다.

### 판단·다음 단계와 기준선

1. **기존 topic 재생 방식을 유지한다.** buffered는 명시적으로 선택하는 실패 재현/진단 옵션으로 남기며 기본값·실차 운용으로 승격하지 않는다. SHM 16 MiB도 명시된 Jetson 시험용 후보이며 일반 DDS 기본값을 바꾸지 않는다.
2. **A3의 현 단계 집중 최적화는 여기서 보류하고 A4 제한된 이상치·고착 시험으로 진행할 기반은 확보했다고 판단한다.** 현재 코드의 기존 방식 두 회에서 반복 보호 정지와 지속 적체가 없었고 EOF 정지·계측·종료가 확인됐다. 이전 D 실패와 이번 buffered 실패는 그대로 남긴다. “무정지 보장”, “모든 IMU 전달”, “매 20 ms 실행”, “실차 준비 완료”는 주장하지 않는다.
3. 다음은 IMU/엔코더의 순간 튐·NaN/Inf·고착/일시 단절에 대한 기존 거절/정지/복구 경계를 우선 확인하고, 위험한 변화가 확인된 경우만 필터나 고착 검출을 보완한다. 이어 정지 차량·앞차 추종/정지·저속 우회로 확장하며 이동 차량 추월/고속화는 후순위다. 이번에 A4/다중 차량을 구현하지는 않았다.
4. 10월 공동 작업에서 제어기/필터/영상/로그 구조를 바꾸면 같은 원시 입력으로 **동일 조건의 변경 전후 비교**를 수행한다. 새 반복 보호 정지·증가하는 적체·정지 실패가 나오면 A3를 다시 다루고, 작은 누락의 내부 원인만으로 다른 개발을 무기한 막지 않는다. 실제 드라이버/MCU 통합·실차 저속·5랩 연속/열 포화는 별도 필수 검증이다.
