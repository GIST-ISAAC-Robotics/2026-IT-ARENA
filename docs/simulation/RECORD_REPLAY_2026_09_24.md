# A2 원시 센서 기록·격리 재생·처리 시간 계측

전체 경위와 현재 재개 조건은 [기록·재생/Jetson 통합 인수인계](../reports/RECORD_REPLAY_JETSON_HANDOFF_2026_09_29.md)에서 확인한다. 이 문서는 A2 단계의 상세 결과와 당시 실패를 보존한다.

작성일: 2026-09-24. 후속 갱신: 2026-09-27~28. **1배속 적체의 주원인인 동기 상태 로그를 제어 콜백에서 분리한 뒤, 같은 입력의 1배속 2회와 0.5배속 1회가 기능·스케줄·EOF 정지·정상 종료를 통과했다. 일부 입력 누락은 남아 있다.** 9/24의 실패와 중간 실험은 당시 결과 그대로 보존한다.

요약: 12 m 주행 입력을 원시 데이터로 기록하고 다시 시험할 수 있다. 9/27 후속 작업에서는 내부 단계 계측으로 원인을 좁혀 로그 처리와 출발 후 불필요한 신호 영상 연산을 개선했다. 센서율·경로/속도 정책·보호 한도는 유지했다. 아래의 9/24 결과와 [9/27 처리 개선 결과](#2026-09-27-제어기-내부-계측과-1배속-적체-개선)를 구분하며, Jetson/실차 실시간 대응 완료로 확대하지 않는다.

## 이번 작업의 범위

같은 센서 입력을 다시 흘려 제어기를 시험하는 기반이다. B0183 RGB+C1+IMU+후륜 엔코더·지역 Pure Pursuit·독립 LiDAR 보호층을 그대로 사용한다. 새로운 필터, 상대 차량 추종/우회, 속도 상향, 차량/코스 변경은 하지 않는다.

기록은 Gazebo가 움직이는 폐루프 시험에서 얻지만 **재생은 구동부 없는 입력 재생**이다. 새 명령에 맞춰 다음 센서 장면이 바뀌지 않으므로 재생 통과를 새 주행 완주로 해석하면 안 된다. Jetson 접속·실행도 별도다.

설계 근거: [ADR 0024](../decisions/0024-isolated-sensor-record-replay.md).

정답 자세·코스 중심선·평가용 차량 동역학은 기록 허용 목록에 없다. 기존 주행 검사기의 정답 자료는 별도 판정용으로 남으며 재생 제어기에 들어가지 않는다.

### 시간 지표 해석

- **원래 취득 시각**은 `header.stamp`를 그대로 유지한다. 순차 LiDAR는 스캔 시작 시각이므로 입력 나이에 한 회전 취득 시간이 포함된다.
- **기록기 수신 시각**은 기록기에서 해당 메시지를 받은 ROS 시각이다. 제어기 수신 시각과 동일하다고 가정하지 않는다. 파일의 재생 순서/간격 기준이다.
- **콜백 소요시간**은 Python 콜백 진입부터 반환까지 실제 경과 시간이다. CPU 점유율, 순수 CPU 실행시간, GPU 커널 시간 또는 센서에서 모터까지 전체 지연이 아니다. 메시지 역직렬화 전의 큐 대기는 제외된다.
- **콜백 입력 나이**는 해당 제어기의 ROS 시각−원래 헤더 시각이다. PC 시뮬레이션이 느릴 때의 실제 대기 초와 구분한다.
- **재생 스케줄 지연**은 파일에서 요구한 발행 시점보다 실제 발행이 얼마나 늦었는지다. 이것이 크면 제어기 성능뿐 아니라 재생기/압축 해제/전송 부하도 확인해야 한다.
- **명령 차이**는 해당 시각 직전의 기록 명령과 재생 명령의 절대 차이다. 원래 ROS 수신 시각과 비동기 타이머의 차이도 포함하며 경로 오차나 완주 판정으로 사용하지 않는다. EOF 이후 명령은 이 비교에서 제외한다.
- RGB 콜백 수는 내부 ArUco/신호 인식 횟수가 아니다. 기존 노드는 약 0.095초 간격으로 인식을 실행하며 그 사이 프레임은 콜백에서 건너뛴다.
- 최종 재생기의 `completed_callback_counts`는 제어기 내부 완료 횟수이고 `callback_counts`는 수집한 진단 로그 수다. 이전 `replay_half_v2/v3`, `replay_1x_v2`는 후자만 기록했으므로 부족한 개수를 전부 센서 콜백 누락으로 확정하지 않는다.

## 실행 방법 — 현재 PC의 Jazzy 기준

WSL 저장소에서 `source install/setup.bash` 후 실행한다. 출력 폴더가 이미 있으면 덮어쓰지 않으며 새 이름을 사용한다.

```bash
python3 scripts/validate_basic_autonomy.py \
  --autonomy-mode local_pursuit --speed-profile local_fast \
  --lidar-acquisition sequential --lidar-compensation both --control-rate-hz 50 \
  --disable-speed-bump --grid-slot 3 --target-progress-m 12 \
  --actuation-mode virtual_mcu --record-inputs --shutdown-mode service --render-backend wsl_nvidia \
  --sensor-wall-timeout-s 30 --max-sim-seconds 90 \
  --wall-timeout-s 900 --stop-wall-timeout-s 120 \
  --output artifacts/validation/2026-09-24/record_replay/capture_new

python3 scripts/replay_sensor_bag.py \
  artifacts/validation/2026-09-24/record_replay/capture_v2/sensor_recording \
  --rate 1.0 --output artifacts/validation/2026-09-24/record_replay/replay_new
```

`--record-inputs`가 없으면 새 기록기/계측은 켜지지 않는다. 개별 노드 계측만 필요하면 `timing_probe:=true`를 사용한다. 기록 전용 도구는 기존 시뮬레이터의 같은 도메인에서 `record_sensor_bag.py --output ...`로 실행하고 SIGINT로 종료할 수 있다. 원시 6 GiB·실제 1,200초 한도, 시작 전 디스크 여유 10 GiB, 실행 중 여유 2 GiB 제한을 둔다. 제한에 걸린 자료는 부분 기록으로 보존하고 정상 재생용으로 받지 않는다.

재생은 원래 도메인을 상속하지 않고 임의의 별도 도메인을 고른다. 점유된 도메인은 사용하지 않는다. 모든 센서/제어 명령/시계/자율주행 서비스는 `/replay` 아래에 두고 실제 구독/발행 경로를 검사한다. 모터·가상 MCU·Gazebo를 시작하지 않으며 저장된 과거 명령을 발행하지 않는다. EOF 뒤 1.5초의 재생 시각을 더 진행해 오래된 입력에 대한 0명령을 확인한다.

최종 재생기는 검증한 CDR 바이트를 그대로 `rclpy`에 전달한다. 큰 RGB 메시지를 Python 객체로 역직렬화했다가 다시 직렬화하는 복사를 피하되, 해상도·픽셀·헤더·프레임 수를 줄이지 않는다. 기록된 출력/상태는 사전 감사에서만 비교 자료로 읽고 재생 시계나 발행 주기를 만들지 않는다. 발행이 밀려도 재생 시계를 늦은 메시지 시각으로 되감지 않는다.

재생 성능을 측정할 때는 시뮬레이션·pytest 등 큰 부하를 동시에 실행하지 않는다. 재생기 발행 지연은 시뮬 시각 기준 p99 ≤20 ms·최대 ≤100 ms를 별도 기준으로 사용한다. 이는 시험 전달기의 기준이지 실물 안전 한도 인증이 아니다. 기본 `passed`는 기능·발행 지연 통과이고, 모든 입력의 전달 여부는 `input_callback_delivery_complete`를 함께 확인한다.

## 초기 검증·중단 이력

- `artifacts/validation/2026-09-24/record_replay/build.log`: 3패키지 빌드 통과.
- 같은 폴더 `regression_initial.log`: 당시 회귀 **391개 통과, 41.02초**. 이후 추가한 최종 소스까지 모두 재검증한 결과는 아니다.
- `capture_v1`: 12 m 기록 주행을 시작했으나 시뮬레이션 약 6초·빨간 신호 대기·진행 0 m에서 사용자 중단을 요청했다. 느린 실행의 원인은 이번에 분석하지 않았다. 주행/재생 통과가 아니다.
- 재생·기록 사후 감사·부분 기록 거절 시나리오·Jetson 시험은 미완료다.
- **중단 정리 완료:** 검사 결과 `passed=false`, 사유 `검사 중단 요청`, 진행 0 m. 자식 14/14 정상 종료·잔존/강제 종료 없음이다. 기록기는 내부 `complete=true`·반환 코드 0으로 닫았으며 원시 1,785,405,572바이트가 MCAP 32,991,832바이트로 저장됐다. 입력/매개변수 기록 완료 조건만 만족한 것으로, 주행/재생 검증 통과가 아니다. 사후 무결성 감사는 남아 있다.

### 중단 당시의 재개 순서

1. `capture_v1/report.json`, `sensor_recording/manifest.json`, 종료 로그와 프로세스 잔존을 확인한다. 중단 기록을 주행 성공으로 사용하지 않는다.
2. `python3 scripts/validate_recording_failure.py --output artifacts/validation/2026-09-24/record_replay/failure_v1`로 입력 없는 부분 기록/재생 거절을 검사한다.
3. 최종 소스 회귀를 재실행하고 위 기록 명령의 출력만 `capture_v2` 등 새 이름으로 바꿔 짧은 주행을 진행한다. 이전 자료는 덮어쓰지 않는다.
4. `audit_sensor_bag.py` 무결성 감사 뒤 `replay_sensor_bag.py --rate 0.5`와 `--rate 1.0`을 각각 새 출력 폴더에서 실행한다.
5. 기능 통과·입력 콜백 전달량·실행 속도·EOF 0명령·정상 종료를 구분해 검토하고 결과/현황/활동을 갱신한다. 재생을 폐루프 완주/Jetson 성능으로 확대하지 않는다.

## 재개 후 기록 검증

- `capture_v1` 사후 파일·CDR 감사와 입력 없는 미완료 기록 거절(`failure_v1/v2`, 각각 7조건)을 통과했다. 최초 중단 자료는 계속 보존한다.
- `capture_v2`는 **12.11848 m·최고 8.16 km/h·코너 중앙값 4.74 km/h**, 실제 모형 정지·주행/정지 벽 겹침 표본 각 0·자식 14/14 정상 종료로 통과했다. 잔존/강제 종료는 없다. 전체 코스 완주나 별도 노면 전수 감사는 아니다.
- 기록 길이 **20.968초**, 원시 합계 **3,608,286,772바이트**, 압축 MCAP **59,526,815바이트**다. 실제 렌더러는 `D3D12 (NVIDIA GeForce RTX 5070 Laptop GPU)`였으며 이전 중단 실행의 llvmpipe와 구분한다.
- RGB **1,298**, CameraInfo **1,311**, LiDAR **209**, IMU **5,242**, 후륜 **2,097**개다. RGB 기록 수신률은 약 **61.93 Hz**, LiDAR **10 Hz**, IMU **250 Hz**, 후륜 **100 Hz**다. 카메라 설정의 명목 주기와 시뮬 출력/기록 실측률을 구분한다.
- `capture_v2_audit.json`의 파일 해시·토픽별 CDR 해시·개수·수신 로그 대조를 통과했다. 다만 같은 실행의 평가기 RGB는 **1,310개**로 기록기보다 12개 많았다. 시작/종료 경계와 DDS 전송 차이 등을 분리하지 않았으므로 센서 발생부터의 완전 무손실은 미확인이다. DDS 시각/순번은 읽히지만 송신자 GID가 없어 송신자별 누락 인증도 하지 않는다.

### 보존한 재생 실패와 보완

1. `replay_half_v1`: 노드별 DDS 그래프 조회 준비 전 접근으로 발행 전에 실패했다. 실제 구독/발행 경로가 조회될 때까지 제한 시간 안에서 기다리도록 수정했다.
2. `replay_half_v2`: 기능은 통과했지만 발행 최대 지연이 약 19.97초였다. 비교용 상태 메시지마다 시계/스핀을 실행하던 비용을 제거했다. 당시 `passed=true`를 실시간 재생 성공으로 사용하지 않는다.
3. `replay_half_v3`: 기능/스케줄 기준을 통과했다. 실제 시간 최대 지연 약 28.98 ms(0.5배속 시뮬 시각 14.49 ms)다. 진단 로그에서 IMU 15개·RGB 1개 부족이 관측됐으며 당시에는 실제 콜백 완료 횟수를 따로 수집하지 않았다.
4. `replay_1x_v2`: 기능·스케줄 기준 실패, 발행 최대 약 8.33초 지연. 이 실행은 회귀 시험과 부하가 겹쳤으므로 단독 성능 결과로 쓰지 않는다. EOF 0명령과 두 제어기 정상 종료는 확인했다.
5. 위 결과를 바탕으로 RGB 중복 직렬화를 제거하고, 노드 내부 콜백 완료 횟수의 직접 조회를 추가했다. 원시 센서/제어 정책·속도/보호 한도는 바꾸지 않았다. 최종 재생 결과는 별도로 기재한다.

### 확인한 원인

`TimingProbe`에 영상 변환·신호/마커 인식·운동 보정·경로 명령·발행·상태 직렬화·텍스트 로그 단계 시간을 추가했다. 기본 비활성 상태에서는 단계 계측을 하지 않으며, 활성 상태에서도 기존 진단 메시지 안에 결과를 넣고 별도 고빈도 토픽을 추가하지 않는다.

수정 전 `baseline_io_stages`의 p99는 운동 보정 **1.16 ms**, 경로 명령 **3.85 ms**, 명령 발행 **0.34 ms**, 상태 JSON/발행 각각 **0.20/0.29 ms**였다. 반면 **상태 변경 때의 동기 `logger.info`는 중앙값 37.51 ms·p99 42.69 ms·최대 63.59 ms**였다. 제어 콜백 전체의 20 ms 초과가 157/955회였다. 상태 로그가 제어 스레드를 막고, 운동 입력이 늦어져 보호 정지로 상태가 바뀌면 다시 로그 비용을 지불하는 구조였다. 운동 보정이나 Pure Pursuit가 40 ms를 소비한 것이 아니다.

폐루프 산출물의 소스 목록 점검에서 새 로그 모듈과 비활성 계측 모듈이 빠진 것을 확인했다. 당시 원본 보고서/ZIP은 그대로 보존하고 동일 소스의 최종 재생 ZIP을 [보충 근거](../../artifacts/validation/2026-09-27/controller_performance/README.md#폐루프-소스-보존-보충)로 연결했다. 이후 검사기의 보존 목록에는 두 파일을 항상 포함하도록 수정하고 관련 회귀 **45개, 4.89초**를 재확인했다. 이는 시험 메타데이터만의 변경이며 주행 로직은 최종 재생·폐루프와 동일하다. 400개 전체 회귀는 목록 보완 전, 45개 관련 회귀는 보완 후 결과다.

다음 우선순위는 A3 Jetson의 같은 입력 1배속 처리량/지연 확인과 초기 영상 처리·잔여 누락 진단이다. 이후 A4 제한된 이상치/고착 시험으로 이어간다. 로그 문제를 해결했다는 이유로 필터·실물 시간 계약·MCU/ESC 검증을 생략하지 않는다. 이번에는 속도 상향·상대 차량 기능·하드웨어 변경을 하지 않았다.

## 저장과 실패 판정

- 파일 SHA-256뿐 아니라 실제 MCAP를 다시 읽어 토픽/형식·시간 순서·CDR 해시/개수와 수신 로그를 대조한다.
- DDS 순번은 송신자 GID별로 비교한다. 부가정보가 제공되지 않은 이전 파일은 미확인으로 남기고 0누락으로 해석하지 않는다. 운영체제 시각 기반 DDS 시각을 시뮬레이션 헤더 시각에서 직접 빼지 않는다.
- `complete=true`는 기록기 내부 큐 유실 없이 필요한 토픽·매개변수·파일 저장을 마쳤다는 뜻이다. 센서 송신부터 DDS까지의 완전 무손실 증명은 아니다. 가능한 송신 순번 누락 관측도 별도로 남긴다.
- 재생 기능 판정과 입력 콜백 완전 전달 판정을 분리한다. 명령이 한 번 나왔다는 사실만으로 모든 프레임을 처리했다고 하지 않는다.
- 원시 MCAP·수신 JSONL은 `.gitignore`로 로컬에만 남긴다. 해시·매개변수·요약은 보존한다. 나중에 다른 PC로 옮길 때는 `sensor_recording` 폴더 전체를 별도 복사한 후 무결성을 검사한다. 원시 파일을 지우면 요약만으로는 재생할 수 없다.

## Jetson 후속 작업에 넘길 것

1. 현재 JetPack/Ubuntu/ROS·OpenCV·ARM64 의존성부터 확인한다. [ADR 0001](../decisions/0001-simulation-platform.md)의 JetPack 유지/Humble 이식 방향을 보존하며 OS부터 재설치하지 않는다. 이번 rosbag2 Python API 검증은 Jazzy에서만 했으므로 Humble 차이를 먼저 점검한다.
2. 원시 기록과 소스/매개변수 스냅샷을 옮겨 같은 검사기를 실행한다. 먼저 느린 재생으로 기능을 확인한 다음 실제 시간 1배속에서 메시지 누락/콜백 시간/적체를 본다.
3. 기록의 실제 RGB·LiDAR·IMU·엔코더 수신률이 목표 부하에 맞는지 확인한다. 특히 낮은 수신률의 녹화를 단순 1배속으로 틀었다고 실제 RGB 60 Hz를 시험한 것은 아니다. 부족하면 목표 주기의 가상 송신을 별도로 준비한다.
4. 제어 50 Hz의 20 ms 주기와 계측한 p95/p99/최대, 입력 만료 한도를 함께 본다. `tegrastats` 등의 자원/클록/열 기록도 동시 수집한다. 필요할 때 큐·복사·영상 처리부터 최적화한다.
5. 이는 연산과 입력 재생 시험이다. 실제 카메라/USB/CSI·C1 점별 시각·IMU/MCU 시계·모터/ESC·무선 STOP·실차 제동은 별도로 남는다. A4의 제한된 이상치/고착 검증을 다음 로컬 과제로 권고하며, 이동 차량 추월/고속화는 보류한다.

### 2026-09-28 Jetson 접속 준비와 실행 차단

아래는 **당일 최초 시도**의 기록이다. 이후 승인 서비스 복구·사용자 설치 승인으로 SSH/비공개 저장과 Jetson 기준 재생을 수행했다. 진행 결과와 남은 문제는 [A3 보고서](JETSON_REPLAY_2026_09_28.md)를 따른다.

사용자가 제공한 바탕화면의 `jetson_orin_nano_jp621_headless_runbook.md`에서 접속 정보를 확인했다. 런북은 데이터로만 읽었으며 비밀번호와 전체 원문을 저장소·로그·응답에 복사하지 않았다. 접속 대상은 `q@jetson-orin.local`이고, 이번 DNS 조회의 IPv4는 사설 주소 `192.168.0.134`였다. 기존 `known_hosts`에 해당 이름의 호스트 키가 있으나 **SSH 연결·호스트 키 일치·현재 OS/ROS 상태는 아직 확인하지 못했다.**

[접속 정보 저장 스크립트](../../scripts/save_jetson_access.ps1)는 원문에서 계정/비밀번호/호스트를 읽어 저장소 밖 `%LOCALAPPDATA%\IT-Arena\private\jetson-access.clixml`에 Windows DPAPI와 디렉터리 접근 권한을 적용해 저장하도록 준비했다. 원본은 보존하고 기존 저장 파일은 덮어쓰지 않는다. PowerShell 구문 검사만 통과했으며, **스크립트 실행·암호화 저장·재읽기 검증은 미실시이고 목적지 파일도 없다.**

정식 실행 승인 경로를 두 번 요청했으나 승인 서비스가 `502 Bad Gateway / Previous response owner account is unavailable`을 반환했다. 도구는 명령이 실행되지 않았음을 명시했다. 저장 스크립트 및 후속 SSH 라이브러리 설치는 모두 실행되지 않았고, Jetson으로 자료를 전송하거나 설치·설정·시험을 수행하지 않았다. GPT-6 Luna 실행 담당은 로컬 패키지 의존성 확인까지만 진행하고 대기 작업을 종료했다. 이는 Jetson 자체나 재생 시험의 실패 판정이 아니라 실행 전 승인 서비스 장애다.

재개 순서는 승인 경로 복구 → 접속 정보 비공개 저장 → 기존 호스트 키를 사용한 SSH 및 OS/JetPack/ROS·자원 상태 조회 → ARM64/Humble 호환성 확인 → 원시 기록 무결성 검사와 0.5배속/1배속 격리 재생이다. 원시 기록의 Git 제외 정책과 `/drive` → 보호층 → `/drive/safe` 경계를 유지한다. JetPack 재설치·재부팅·전원 종료는 이번 준비에서 수행하지 않았다.
