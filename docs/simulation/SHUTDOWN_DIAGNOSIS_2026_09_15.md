# Gazebo 종료 지연의 원인과 해결 후보

진단일: 2026-09-15. 설치 라이브러리: Gazebo Sim 8.11.0, Common 5.8.0, ROS Jazzy·WSL Ubuntu 24.04.

## 결론과 확실성

**과거 스택에서 확인된 가장 유력한 설명은, 종료 신호가 메모리 할당 작업을 중단시킨 상태에서 센서 스레드 종료를 기다리며 생긴 교착입니다.** GPU 계산이 느리다는 설명만으로는 부족합니다.

다만 대기 중인 메모리 잠금의 소유자까지 추적한 것은 아닙니다. 또한 9월 15일 실패 실행의 중단 당시 스택은 없고 이번 재시험에서는 지연을 재현하지 못했습니다. 따라서 **기존의 모든 -9 종료를 동일한 교착으로 확정하지 않습니다.**

운영체제 종료 신호 대신 Gazebo의 공식 `/server_control` 종료 요청을 사용하는 해결 후보를 진단 서버에서 시험해 정상 종료를 확인했습니다. 기존 방식도 이번에는 정상 종료했으므로, 해결률 개선이나 완전 해결은 아직 증명되지 않았습니다.

## 무엇이 실패했는가

이전 원본 거리 촬영·전체 코스 촬영 등은 이미지 수신을 마친 뒤 서버가 정상 종료되지 않아 검사기가 SIGKILL로 정리했고 반환값이 -9였습니다. -9 자체는 GPU 오류의 종류가 아니라 **검사기가 강제로 끝냈다는 결과**입니다.

기존 촬영 검사기의 유예는 SIGINT 8초, SIGTERM 4초입니다. 9월 8일 별도 시험은 SIGINT 유예를 60초로 늘려도 한 번은 약 65.28초 후 강제 종료했습니다. 그러므로 단순 유예 연장을 보장된 해결법으로 보지 않습니다. 사진 확보, 주행 중 센서 수신, 실제 정지, 정상 종료는 각각 별도 판정으로 유지합니다.

## 저장된 스택에서 확인한 사실

[2026-09-08 원본 GDB 기록](../../artifacts/validation/2026-09-08/performance/gpu_shutdown_stack.txt)을 다시 분석했습니다.

- **주 스레드(Thread 1):** DART 접촉 계산의 메모리 할당 `malloc` 도중 신호 처리 함수가 끼어들었습니다. 그 신호 처리 안에서 `SensorsPrivate::Stop()` → `std::thread::join()`을 호출해 센서 스레드가 끝나기를 기다리고 있었습니다.
- **렌더링 스레드(Thread 47):** `RenderUtil::Destroy()` → Ogre 장면 노드 제거 → `free()`에서 내부 잠금 대기 `__lll_lock_wait_private`에 머물렀습니다.
- 당시 D3D12 core 라이브러리는 여전히 메모리에 로드되어 있었습니다. 이 기록을 라이브러리 조기 해제만으로 설명할 수 없습니다.

여기서 가장 유력한 대기 고리는 다음과 같습니다. **메모리 작업 중 신호로 중단된 주 스레드가 센서 종료를 기다림 → 센서는 메모리 해제를 위해 잠금을 기다림 → 주 스레드는 원래 메모리 작업으로 복귀하지 못함.** 잠금 소유자 주소는 기록하지 않아 이 마지막 연결은 강한 추론입니다.

## 설치 버전 소스와의 대조

버전이 맞는 공개 소스 세 개와 설치 파일 해시를 [근거 폴더](../../artifacts/validation/2026-09-15/official_update/shutdown_sources/manifest.json)에 보존했습니다.

- [Common 5.8.0 SignalHandler](https://github.com/gazebosim/gz-common/blob/gz-common5_5.8.0/src/SignalHandler.cc)는 OS 신호 처리 안에서 mutex를 잡고 콜백을 직접 호출합니다. SIGINT와 SIGTERM 모두 같은 처리 경로입니다.
- [Sim 8.11.0 ServerPrivate](https://github.com/gazebosim/gz-sim/blob/gz-sim8_8.11.0/src/ServerPrivate.cc)는 신호 콜백에서 `Stop()`을 호출합니다.
- [Sim 8.11.0 Sensors](https://github.com/gazebosim/gz-sim/blob/gz-sim8_8.11.0/src/systems/sensors/Sensors.cc)의 Stop은 센서 렌더 스레드를 깨우고 join으로 종료를 기다립니다. 센서 스레드는 종료 전에 장면·센서를 해제합니다.
- Gazebo 공식 [Common #530](https://github.com/gazebosim/gz-common/issues/530)도 비동기 신호 처리 안의 잠금·출력 때문에 중단될 수 있음을 지적합니다. 이슈가 Closed라는 사실만으로 현재 설치 버전에 수정이 적용됐다고 판단하지 않습니다. 닫힌 경위를 추가 조회하려던 API는 rate limit 403으로 실패했고, 수정 PR·안전한 교체 버전은 이번에 확정하지 않았습니다.

## 이전 GPU 문제와 같은가

구분해야 합니다.

1. 과거 WSLg GPU 기본 센서 예제에서의 **SIGSEGV/렌더러 수명 문제**는 [기존 GPU 기록](GPU_RENDERING.md)으로 보존합니다. 관련 [WSLg #1497](https://github.com/microsoft/wslg/issues/1497)은 EGL 종료와 D3D12 core 수명 문제입니다.
2. 이번에 재분석한 기록은 **신호 처리 안의 센서 종료 대기·메모리 잠금**입니다. CPU/GPU 속도의 문제가 아니라 종료 타이밍과 스레드 관계가 핵심인 후보입니다.
3. 9월 15일 사진 검사기는 `LIBGL_ALWAYS_SOFTWARE=true`를 명시한 실행에서도 -9를 기록했습니다. 따라서 NVIDIA GPU 사용 여부 하나로 모든 종료 실패를 설명하지 않습니다. 해당 실패 당시 스택이 없으므로 위 두 원인 중 하나로 확정하지도 않습니다.

## 이번 재시험 결과

현재 실행본을 복제한 진단 월드에 도형 앞면을 추가하고 기존 촬영 절차를 유지했습니다. 운영 월드·검출기·시스템 라이브러리는 변경하지 않았습니다. 각 실행의 통신 영역을 분리하고 해당 프로세스 그룹만 정리했습니다.

| 진단 실행 | Gazebo 종료 요청 | 종료 관측 시간 | 결과 |
|---|---|---:|---|
| `shutdown_group_01` | SIGINT | 2.024초 | 0·잔존 없음 |
| `shutdown_group_02` | SIGINT | 4.029초 | 0·잔존 없음 |
| `shutdown_group_03` | SIGINT | 4.030초 | 0·잔존 없음 |
| `shutdown_overview_04` | SIGINT, 전체 코스 촬영 | 2.021초 | 0·잔존 없음 |
| `shutdown_warm_` | SIGINT | 2.086초 | 0·잔존 없음 |
| `shutdown_service_01` | `/server_control`, `stop: true` | 2.388초 | 응답 true·0·잔존 없음 |

시간은 요청부터 종료 관측까지이고 기본 관측 간격이 2초입니다. 정밀한 종료 시간이나 방식별 속도 순위가 아닙니다. SIGINT 5회와 서비스 1회 모두 촬영을 완료했습니다. 10초 이상 지연 시 GDB를 붙이도록 준비했으나 이번에는 해당 분기에 들어가지 않아 **새 정체 스택은 없습니다.**

반복 실행 명령의 변수 전달 오류로 최초 시도는 실행 전에 인자 오류가 났고, 이후 `shutdown_warm_` 한 번 뒤 같은 이름의 두 요청이 기존 폴더 보호로 거부됐습니다. 이를 Gazebo 실패나 추가 유효 시험으로 세지 않습니다. 원래 이름과 산출물을 그대로 보존했습니다.

## 해결 방법의 우선순위

1. **우선 검토:** 차량 정지 확인·필요한 로그 저장 후, 실행별로 격리된 Gazebo 서버에 `/server_control`의 `gz.msgs.ServerControl {stop: true}`를 요청합니다. 공식 소스에서는 별도의 일반 스레드가 Stop을 처리하므로 메모리 할당 도중 신호 콜백이 끼어드는 위 경로를 피할 수 있습니다. 이번 진단에서는 한 번 작동했습니다.
2. 요청 응답만 보고 성공 처리하지 말고 실제 서버/하위 프로세스 종료와 반환값을 확인합니다. 일정 시간 후 SIGINT/최종 강제 정리는 실패 회수 수단으로 남겨야 합니다. 전역 `/server_control`에 무차별 발행하면 다른 서버까지 영향을 줄 수 있어 실행별 통신 영역 격리가 전제입니다.
3. 신호 처리의 안전한 콜백 위임을 포함한 라이브러리 업데이트/백포트를 별도 환경에서 검토합니다. 이번에는 교체·패치를 수행하지 않았고, 특정 버전 업그레이드만으로 해결된다고 권하지 않습니다.
4. 다음 장시간 차량 실행에서 다시 지연되면 강제 종료 전 스택을 확보해 9월 8일 잠금 대기와 같은지 비교합니다. 유예 연장만 반복하거나 GPU를 무조건 끄는 것은 원인 해결 검증이 아닙니다.

이 작업은 원인 분석입니다. 운영 종료 함수, ROS launch, 주행 제어, 공식 트랙은 이번 진단에서 바꾸지 않았습니다. 주최 측 트랙 오류로 제보할 근거도 아닙니다. **테스트 주행은 진행하되, 정상 종료 실패를 기록하고 시험 프로세스가 남지 않게 관리할 과제**입니다.

진단 재현은 `scripts/diagnose_gazebo_shutdown.py --name 새이름 --stacks`이며 종료 서비스 후보는 `--signal-mode service`를 추가합니다. 설치 소스 근거 수집은 `scripts/collect_shutdown_sources.py`입니다. 모두 기존 기록을 덮어쓰지 않도록 구성했습니다.
