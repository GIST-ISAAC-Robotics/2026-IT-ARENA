# 센서 기록·재생 및 Jetson 연산 검증 인수인계

정리 기준: **2026-09-29**, A2 기록·재생 구축부터 A3 계측 비용 ABBA 비교까지. 이 문서는 후속 개발자가 작업의 목적, 실패와 수정의 연결, 현재 기준선, 재현 방법을 한 번에 파악하기 위한 **통합 진입점**이다. 단계별 상세 원자료는 [A2 보고서](../simulation/RECORD_REPLAY_2026_09_24.md), [A3 보고서](../simulation/JETSON_REPLAY_2026_09_28.md)와 아래 산출물에 보존한다. 과거 보고서의 “다음 작업”은 당시 계획이며, 현재 우선순위는 이 문서와 [현재 현황](../PROJECT_CONTEXT.md)을 따른다.

## 1. 현재 결론부터

**같은 센서 입력을 보존·감사·격리 재생하고 Jetson에서 변경 전후를 비교할 기반은 확보했다. 초기 PC의 반복적인 제어 적체는 개선했고, 최근 Jetson 기준 조건에서는 정상 입력에 대한 명령 유지·입력 종료 후 0명령·정상 종료를 확인했다. 다만 IMU 누락과 간헐적 입력 지연은 해결 완료가 아니다.**

- 유지하는 구현: 제한 큐 기반 텍스트 로그, 독립 진단 수집기, 판정 동등성을 확인한 신호 영상 연산, 지역 제어기의 영상 작업 프로세스 분리, 원본 보존형 Humble 읽기 호환, 기록기 조기 종료 감시, 조향 송신값의 float32 경계 보완.
- 다음 비교의 기준: 정상 `capture_v3`의 **59.53초** 입력, 1배속, `legacy`, **명시적 `shm_16m`**, `topic` 계측, IMU/엔코더 발행 추적 ON, 최소 IMU 수신자 OFF. 이는 검증에 사용한 **재생 조건**이지 일반 실행 기본값 변경이 아니다.
- 가장 최근 같은 소스의 ABBA 네 회에서 `topic` 두 회는 운영 통과, `buffered` 두 회는 안전 0명령 **2/4개**로 운영 실패했다. CPU와 IMU 누락만 줄어든 `buffered`를 개선안으로 채택하지 않는다.
- 현재 단계의 A3 집중 최적화는 보류하고 **A4 제한된 IMU/엔코더 이상치·고착 대응**으로 넘어갈 기반은 확보했다고 판단한다. 새 지연·반복 정지 또는 구조 변경이 있으면 이 기준선으로 돌아온다. A4와 다중 차량 기능은 아직 구현하지 않았다.
- **실차 준비 완료, 센서 무손실, 매 20 ms 실행, 20 km/h 주행, 경기 5랩/열 안정성 검증이 아니다.** 현재 긴 기록의 실제 시뮬레이션 최고 속도는 약 8.21 km/h다.

이번 문서 정리에는 회수된 로컬 결과만 사용했다. Jetson은 사용자가 꺼 둔 상태이며 추가 접속·재시험 없이 정리했다. 과거 “잔존 프로세스 없음”은 각 시험 종료 당시의 확인이다.

## 2. 처음 하려던 일과 검증 경계

실물 센서·모터·차량을 사용할 기간이 짧고, 당시 가용 실기는 Jetson뿐이었다. 따라서 차량 제작 전에 다음을 준비하려 했다.

1. 시뮬레이션에서 얻은 원시 센서 입력과 실제 실행 설정을 저장한다.
2. 제어기 변경 전후에 **같은 입력**을 공급해 기능 차이·지연·누락을 비교한다.
3. PC와 다른 Ubuntu/ROS 환경인 Jetson에서 이식 가능성과 기본 연산량을 확인한다.
4. 입력이 오래되거나 끝났을 때 보호 0명령이 나오고 프로세스가 정상 정리되는지 확인한다.
5. 뒤에 필터·다중 차량 기능을 추가해도 성능 퇴행을 찾을 재현 가능한 기준을 남긴다.

설계 근거는 [ADR 0024](../decisions/0024-isolated-sensor-record-replay.md), 전체 작업 순서는 [개발 계획](DEVELOPMENT_PLAN_2026_09_22.md)이다. 이번 계열 작업은 조향 알고리즘 교체, 센서 주기 하향, 보호 시간 완화, 속도 상향을 통한 통과가 목적이 아니었다.

### 2.1 기록과 재생은 다른 시험이다

```text
PC 폐루프 기록
Gazebo 센서 → 지역 제어 / 독립 보호층 → 가상 MCU → Gazebo 차량
       └→ 원시 CDR + 수신 시각 + 설정 + 무결성 manifest

PC 또는 Jetson 격리 재생
검증한 센서 CDR → /replay 센서 → 지역 제어 → /replay/drive
                                             ↓ 독립 보호층
                                      /replay/drive/safe → 비교·관측만
```

재생에는 Gazebo·MCU·모터가 없다. 새 명령을 내도 다음 센서 장면은 원래 기록대로 들어온다. 따라서 **재생 통과는 새 폐루프 주행 완주가 아니다.** 기록된 과거 명령은 비교 자료로만 읽으며 재발행하지 않는다. 지도·Gazebo 정답 위치·심판 신호 상태도 제어기에 공급하지 않는다. 평가용 정답은 별도 주행 검사에만 사용한다.

재생은 새 ROS 도메인, `/replay` 네임스페이스, localhost 격리를 사용하고 실제 토픽·서비스 경로를 검사한다. `/drive` → 독립 보호층 → `/drive/safe`에 대응하는 경계를 그대로 유지하며 보호층을 우회하지 않는다.

### 2.2 반드시 나눠 볼 판정과 시간

| 항목 | 실제 의미 | 이것만으로 알 수 없는 것 |
|---|---|---|
| 기록 `complete` + 사후 `audit` | 기록기 내부 저장·필수 입력/설정 조건, 파일·CDR 해시·개수·순서·receipt 대조 | 센서가 생성한 모든 표본이 기록기에 도착했는지 |
| `functional_passed` | 오류 없이 예정 센서 발행, 유효 비영 속도 명령, EOF 0명령, 제어기 정상 종료 등의 조건 | 주행 구간 내내 명령이 유지됐는지 |
| `schedule_passed` | 재생 발행 지연 p99 ≤20 ms, 최대 ≤100 ms | 제어기 매 20 ms 마감 또는 실물 전달 지연 |
| `measurement_passed` | 내부 완료 카운터 체크포인트까지 진단 순번 완전성 | 입력 무손실, 체크포인트 이후 전체 종료 구간의 계측 |
| `input_callback_delivery_complete` | 기록된 입력 수와 제어기 내부 완료 수 일치 | 모든 입력이 제어 전에 제때 처리됐는지 |
| `operational_passed` | 기능·스케줄·계측 통과 + 원래 이동 명령 구간에서 관측 명령의 중단 없음 | 실제 주행/충돌 안전, 모든 명령 주기의 상한 |
| `passed` / CLI 종료 코드 0 | 기본 기능·스케줄 조건의 통과 | 운영 통과까지 포함한 종합 합격 |
| EOF 0명령 / 정상 종료 | 입력 종료 후 오래된 입력을 정지 명령으로 처리 / 프로세스 정리 | 실제 모터 제동거리 |

현재 `active_window_continuity`는 기준 이동 구간의 **관측된** 명령에서 0·역방향·비정상 값을 확인한다. 비어 있는 표본 구간의 모든 명령을 증명하는 검사나 엄격한 최대 발행 간격 게이트는 아니므로 시작 간격·명령 간격 통계도 별도로 읽어야 한다. 특히 `buffered` 실패도 CLI 코드 0이므로 자동화가 코드 0만 읽으면 실패를 놓친다.

- 원본 `header.stamp`: 센서 취득 시각. 순차 LiDAR는 한 회전의 시작 시각이므로 입력 나이에 회전 취득 시간이 포함된다.
- 기록기 수신 ROS 시각: 재생 순서/간격 기준. 원본 제어기가 받은 시각과 같다고 가정하지 않는다.
- 콜백 입력 나이: 해당 노드 ROS 시각 − 원본 헤더 시각. 시뮬레이션이 느릴 때의 실제 벽시계 대기와 다르다.
- 콜백 본문 소요시간: 진입→본문 종료의 실제 경과 시간. 역직렬화 전 큐 대기·콜백 사이 대기, `TimingProbe`의 후속 진단 JSON 작성/발행 비용은 포함하지 않는다.
- 발행 완료→콜백 진입: 같은 호스트 단조 시각의 차이. DDS 내부 도착·큐 점유·ACK/NACK를 직접 측정한 것은 아니다.
- RGB 수신 약 62 fps와 신호/마커 인식 약 10 Hz는 다르다. 기존 0.095초 인식 간격을 유지했다.
- CPU 100%는 한 코어 분량이다. 제시한 합계에는 재생기·관측기·영상 작업자도 포함되며 RSS는 공유 페이지가 중복 집계된다.

## 3. 문제와 수정의 진행 이력

아래 순서가 조사 흐름이다. 나중의 성공으로 앞선 실패를 지우지 않았으며, 서로 다른 소스·짧은 독립 실행을 하나의 장시간 시험으로 합치지 않는다.

### 3.1 A2 최초 기록·재생: 공급 도구와 제어기 문제를 분리

9/24 최초 `capture_v1`은 사용자 중단으로 진행 0 m에서 끝났다. 저장/종료가 완료됐어도 주행 성공은 아니다. 이후 `capture_v2`는 **12.11848 m** 주행·모형 정지·자식 14개 정상 종료를 통과했고 **20.968초** 기록을 확보했다.

초기 재생에서는 서로 다른 문제가 있었다.

1. DDS 그래프 준비 전 조회로 발행 전 실패 → 실제 구독/발행 경로가 준비될 때까지 제한 시간 안에서 기다리도록 수정.
2. 비교용 상태 메시지마다 시계 발행/스핀 → 0.5배속에서도 최대 약 19.97초 발행 지연. 비교 자료를 공급 스케줄에서 제외.
3. 큰 RGB의 Python 역직렬화·재직렬화 중복 → 검증된 CDR 바이트를 그대로 발행. 픽셀·해상도·헤더·센서율은 유지.
4. 진단 행 부족이 센서 누락인지 구별 불가 → 노드 내부 `timing_snapshot` 완료 카운터 추가.
5. 회귀 시험과 동시에 돌린 1배속 실패는 경쟁 부하가 섞여 있어 단독 성능 근거에서 구분.

최종 9/24 단독 실행의 0.5배속은 기능/스케줄 통과, 1배속은 발행 스케줄만 통과하고 기능 실패였다. 1배속 지역 IMU는 **3,679/5,242**, RGB는 **1,053/1,298**개만 처리했고, 안전 명령 최고값도 **0.03 m/s**로 유효 명령 기준 0.1 m/s에 못 미쳤다. `RUNNING`과 `MOTION_STOP`이 반복됐다. 제어 콜백 p99 **43.97 ms**는 목표 주기 20 ms보다 길었다. Gazebo를 켜지 않은 재생이므로 그래픽 FPS 문제로 설명할 수 없었다.

당시 전체 회귀 395개·미완료 기록 거절 7조건 통과와 1배속 기능 실패를 함께 보존했다. 또 같은 기록 주행의 평가기 RGB 1,310개와 기록기 1,298개의 차이는 이후 재생 손실과 별개의 미확인 지점이다. [A2 초기·최종 결과](../simulation/RECORD_REPLAY_2026_09_24.md)

### 3.2 PC 내부 계측: 핵심 병목은 상태 텍스트 로그

9/27 단계별 계측에서 운동 보정 p99 **1.16 ms**, 경로 명령 **3.85 ms**, 명령 발행 **0.34 ms**였지만 상태 변경 시 동기 `logger.info`는 중앙값 **37.51 ms**, p99 **42.69 ms**, 최대 **63.59 ms**였다. 보호 상태가 바뀔 때 로그가 막히고 그동안 운동 입력이 늦어 다시 보호 상태가 바뀌는 구조였다.

표준출력 저장 위치만 네이티브 임시 경로로 옮겨도 제어 p99 44.38 ms로 개선되지 않았다. 로거 단독 계측에서는 25회 `info`의 0.341초 중 호출자/소스 경로 조회가 0.337초였다. 이 PC의 `/mnt/c` 소스에 대한 `stat/lstat` 비용이 지배적이었다. Jetson도 같은 원인이라고 일반화하지 않았다.

적용한 변경은 다음과 같다.

- 완성된 텍스트만 **256개 제한 큐 + 별도 로그 스레드**로 전달. 제어 상태 계산·명령 발행 권한은 옮기지 않음. 구조화 상태 토픽은 유지.
- 접수/출력/유실/실패/잔량 카운터와 최대 2초 종료 배출. 출력이 영구 정체돼도 제어·종료를 무한 대기시키지 않음.
- 출발 확정 뒤 결과에 영향을 주지 않던 신호등 전체 영상 처리를 생략. 출발 전 검출·ArUco는 유지.
- 재생 준비에 `timing_snapshot` 응답 추가. 소스 스냅샷과 실행 중 변경 검사 보강.

로그 분리만으로 제어 p99는 **4.45 ms**까지 줄었지만 안전 0명령 27/500개가 남았다. 후속 신호 처리 생략·준비 응답을 합친 최종 1배속 A/B는 제어 p99 **4.78/4.64 ms**, 이동 비교 구간 0명령 **0/500개**였다. 두 후속 변경의 기여를 각각 분리한 시험은 아니다.

1배속 2회·0.5배속 1회, 전체 회귀 400개·미완료 기록 거절 7조건, 계측 비활성 PC **12.17847 m** 폐루프·정지·종료를 통과했다. 그러나 1배속 A/B에 IMU **36/131개**, RGB **5/6개** 누락과 제어 시작 간격 최대 **72.26/95.42 ms**가 남았다. 함수가 빨라진 것과 매 주기 실행 보장은 다르다. 폐루프 소스 목록 누락은 당시 ZIP을 바꾸지 않고 보충 근거를 연결한 뒤 후속 보존 목록만 수정했다. [PC 분석·소스·재현 자료](../../artifacts/validation/2026-09-27/controller_performance/README.md)

### 3.3 Jetson 이식: 기록 형식 호환과 최초 기준 시험

기존 JetPack 6.2.1 계열 환경을 유지했다. 확인 환경은 Ubuntu **22.04.5**, L4T **36.4.4**, ARM64, 기존 `MAXN_SUPER`다. 사용자 승인으로 ROS 2 Humble과 의존성을 설치하고 두 제어 패키지를 빌드했다. JetPack/OS 재설치·전력/클록 변경은 하지 않았으며 기존 OpenCV 4.8.0을 유지했다. PC는 Ubuntu 24.04/Jazzy/OpenCV 4.6.0이므로 단순 CPU 배수 비교는 아니다.

첫 기록 감사는 Jazzy metadata v9의 QoS 목록을 Humble이 문자열로 읽으면서 `yaml-cpp: bad conversion`으로 중단됐다. 이때는 센서 발행 전이었다. MCAP 본문은 직접 읽을 수 있었다.

`audit_sensor_bag.reader_for`에 **특정 오류 + metadata v9 + MCAP 한 개 + 명시 경로 일치**에서만 직접 MCAP 읽기를 허용했다. 원본 YAML/CDR/manifest를 수정하지 않았고, 전체 해시·형식·개수·순서·receipt 감사는 유지했다. 여러 MCAP 중 하나만 읽거나 다른 파일 오류를 숨기는 일반 fallback이 아니다. PC/Jetson 호환 검사 41개가 통과했다.

첫 Jetson 0.5배속 1회·1배속 2회는 기능/스케줄/EOF/종료와 이동 구간 0명령 0/500개를 확인했다. **처음부터 Jetson에서 아예 실행 불가였던 것은 아니다.** 다만 1배속 지역 IMU **202/230개**, RGB 각 **3개**가 누락됐고, 보호층은 IMU를 모두 처리했는데 관측된 진단 행은 4,547/4,792개뿐이었다. 센서 입력 누락과 별도로 측정 도구 자체도 빠뜨리고 있었다. 초기 처리시간 표는 이 불완전 표본의 통계다. [설치·초기 결과](../simulation/JETSON_REPLAY_2026_09_28.md), [초기 산출물](../../artifacts/validation/2026-09-28/jetson_a3/README.md)

### 3.4 먼저 관측 도구를 바로잡고 영상 연산을 최적화

같은 프로세스에 수집 스레드만 추가한 `observer_v1`은 단위 검사는 통과했지만 실제 1배속 두 회에서 발행 지연 p99가 약 **12초**로 악화돼 폐기했다. 제어기 성능과 수집기의 부하를 섞은 실패였다.

`replay_observer.py`로 수집을 **별도 프로세스**로 분리했다. 시작 초기에 첫 60/500개만 빠진 별도 시험을 바탕으로, 발행자와 구독자 양쪽 발견·서비스 응답을 확인하도록 했다. 수집기는 executor 등록을 유지하고 재생 발행 루프의 불필요한 `spin_once`도 제거했다. 이후 1배속 A/B에서 스냅샷까지 진단 순번 완전성을 확보했다. 이제 누락 위치를 분석할 수 있게 됐다.

지역 IMU 누락 249/229개 중 185/189개는 보호층 수신 시각 기준으로 지역 영상 콜백 실행과 겹쳤다. 이는 영상 처리 간섭의 **상관 근거**이지 보호층 콜백이 실제 DDS 도착 시각이라는 뜻은 아니다.

- OpenCV 6→1 스레드는 같은 218장 판정은 같았지만 p99 약 21→26 ms로 느려 채택하지 않았다.
- 신호 색상 마스크의 NumPy 중간 배열을 `cv2.inRange`/`bitwise_or`로 바꾸되 엄격 부등식·임계값을 보존했다. 임의/경계 픽셀과 실제 218장 결과 일치를 확인했다.
- 개선 A/B의 영상 콜백 p99는 약 **15.8/16.0 ms**, IMU 누락은 **77/84개**로 줄었다. 두 실행 누락 합계 478→161개는 해당 비교의 관측치이며 장기 손실률 보장이 아니다.
- 제어 시작 간격 최대는 여전히 약 **53 ms**였다. 영상 함수를 빠르게 만드는 것만으로 실행 경합이 사라지지 않았다.

첫 영상 동등성 비교는 ROI의 튜플/JSON 리스트를 직접 비교해 실패했다. 좌표 자료형을 맞춰 통과한 **비교 도구 오류**이며 검출 결과를 바꿔 통과시킨 것은 아니다. [후속 수집·영상 최적화 이력](../simulation/JETSON_REPLAY_2026_09_28.md#후속-개선-시험)

### 3.5 영상 계산 프로세스 분리: 적용한 구조와 남은 엔코더 지연

`local_pursuit`의 `vision_execution=process`를 기본으로 채택했다. ROS 상태를 `fork`하지 않고 `spawn`한 자식이 같은 신호/ArUco 판정을 계산한다. **처리 한 장 + 최신 대기 한 장**, RGB 공유 버퍼, 작은 메타데이터 파이프를 사용한다. 부모만 출발 상태·방향을 채택하고 명령을 발행한다.

요청 번호·촬영 시각·단조 수신 시각·reset 세대를 검사한다. 오래된 결과를 신호 연속 판정에 누적하지 않으며 작업자 사망·1초 watchdog·형식/식별 오류는 고장 고정 후 `SENSOR_STOP`으로 처리한다. 결과 도착 시각으로 취득 시각을 새로 붙이지 않는다. 설계와 오류 경계는 [ADR 0025](../decisions/0025-isolated-vision-processing.md)가 기준이다.

PC/Jetson 동일 영상 218장 판정 일치, PC 선택 회귀 62개·Jetson 113개(자료 의존 2개 제외), 계측 비활성 PC **12.01849 m** 주행·정지·종료를 통과했다. 실제 비동기 재생은 선택 프레임·반영 시점이 달라질 수 있으므로 조향 명령 비트 동일성까지 주장하지 않는다.

Jetson 1배속 네 회에서 영상 수신 콜백 p99는 **0.13~0.21 ms**, 제어 시작 간격 최대는 **약 28~36 ms**로 개선됐다. 그러나 IMU는 154/3/10/10개 누락했고, C/D의 이동 구간 안전 0명령은 **3/46개**였다. C는 지역 엔코더 나이 약 68 ms, D는 보호층 엔코더가 약 **1.005초** 늦게 처리된 사례다. 개수는 최종적으로 맞아도 해당 순간의 제어에는 늦었다. 이 때문에 기본 재생 통과 외에 이동 구간 운영 판정을 명시했다. [영상 분리 결과·정지 근거](../../artifacts/validation/2026-09-29/vision_process/README.md)

별도 PC 재생의 Python 보고서는 통과지만 WSL wrapper가 코드 1을 낸 사례는 원인 미확인으로 보존했다. 입력 누락 때문이라고 설명하지 않았으며 이후 정상 종료 결과로 소급 삭제하지 않았다.

### 3.6 executor와 DDS 비교: 일부 개선은 확인, 단일 원인은 미확정

엔코더 발행 시작/종료와 각 수신자 콜백 진입을 추가 기록했다. `legacy → retained → retained → legacy` 네 회 중 각 방식 한 번씩 운영 실패, 안전 0명령 **70/42개**가 발생했다. 최대 약 **766/689 ms** 대기 중 다른 IMU·영상·제어 콜백은 계속 실행됐다. 원본 시각·발행 지연이나 노드 전체가 멈춘 현상만으로 설명할 수 없었다. `retained` 기본 전환은 보류했다. [발행·executor 비교](../../artifacts/validation/2026-09-29/wheel_dispatch/README.md)

이후 Fast DDS participant의 **실제 transport 설정**을 읽는 probe를 추가했다. 환경변수만 지정하고 적용됐다고 가정하지 않았다. Humble localhost 구성에서는 builtin 설정이 덮어써질 수 있어 UDP/SHM 허용 목록을 명시하고 실제 네 participant를 확인했다. 기존 환경·센서 QoS는 유지했다.

| 대조 | 결과 | 결론 |
|---|---|---|
| `system` ↔ UDP loopback 단독, 4회 | UDP 두 회 0명령 165/292개, LiDAR 누락도 발생 | UDP 단독 미채택. 모든 문제를 SHM만의 결함으로 설명 불가 |
| SHM 기본 용량 ↔ 16 MiB, 4회 | 기본 용량 B에서 약 985 ms 엔코더 나이·0명령 74개. 16 MiB 두 회 운영 통과·RGB 전량 | `shm_16m`을 **명시적 재생 후보**로 유지. 근본 원인 확정/일반 기본값 변경 아님 |
| SHM 16 MiB 추가 6회 + IMU 발행 추적 2회 | 모두 운영 통과. IMU 누락은 추가 6회 67~120개, 추적 2회 18/91개 | 약 1초 적체의 반복성은 개선됐으나 무손실 아님 |

SHM 크기 비교는 설정 descriptor를 확인한 것이지 실행 중 실제 점유량·ACK/NACK를 계측한 것이 아니다. UDP에서도 지연이 났으므로 작은 SHM 하나로 모든 실패를 설명하지 않는다. `shm_16m`은 같은 호스트 전용이며 원격 ROS 운용으로 그대로 확대할 수 없다. [DDS 비교](../../artifacts/validation/2026-09-29/dds_transport/README.md), [반복 6회](../../artifacts/validation/2026-09-29/shm_repeat/README.md), [IMU 발행 추적](../../artifacts/validation/2026-09-29/shm_followup/README.md)

### 3.7 최소 IMU 수신자: 누락 지점을 더 좁힘

제어·영상·진단 토픽 발행 없이 IMU만 받는 별도 프로세스를 선택적으로 추가했다. 기존과 같은 `BEST_EFFORT / KEEP_LAST / depth 5`, 같은 legacy 루프를 사용하고 종료 후 결과를 저장한다. 20.968초 입력을 A(없음)–B(있음)–B–A 순서로 비교했다.

최소 수신자는 두 회 모두 **5,242개 전량** 받았지만 지역 제어기는 같은 회에 **83/11개**를 놓쳤다. 모든 구독자에게 공통으로 발행되지 않았다는 설명은 배제할 근거가 생겼다. 다만 별도 reader·CPU 부하·진단 발행 유무까지 달라 **이 프로세스를 붙이면 해결된다는 결론은 아니다**.

마지막 D는 0명령 **2개**로 운영 실패했다. 해당 제어 호출의 최신 엔코더 나이 **35.08/33.07 ms**가 기존 외삽 한도 30 ms를 넘었다. SHM 16 MiB에서도 간헐적 정지가 남는 반례다. 다음 비교 대상으로 콜백 뒤 진단 JSON/발행 비용을 선정하고, 먼저 짧은 입력보다 긴 정상 기록을 확보했다. [최소 수신자 대조](../../artifacts/validation/2026-09-29/imu_probe_compare/README.md)

### 3.8 긴 정상 기록 확보 중 드러난 별도 경계 오류

목표 진행량을 12→70 m로 늘리자 짧은 시험에서 보이지 않던 두 문제가 드러났다.

| 입력 시도 | 결과/원인 | 수정 또는 처리 |
|---|---|---|
| 긴 `capture_v1` | 19.897 m에서 MCU `invalid_drive` 정지 고정. double 조향 상한이 float32 전송 후 약 1.33×10⁻⁹ rad 초과 | 송신 상한만 안쪽의 표현 가능한 float32로 제한. MCU 수신 한도/검사는 그대로. 실패 입력 보존 |
| 긴 `capture_v2` | 43.433 m에서 실제 실행 900초 초과. 그보다 먼저 기록기는 비압축 6 GiB 한도로 불완전 종료 | 주행/정지 루프에서 기록기 조기 종료를 즉시 실패 처리. 종료 코드 0이어도 조기 종료면 거절 |

기존 물리/MCU 한도 `0.3756455765751818 rad`는 전송 후 `0.37564557790756226 rad`가 됐다. 현재 시뮬레이션 송신값은 `0.37564554810523987 rad` 이내다. 허용 오차를 넓힌 것이 아니며 실차 설정도 전송 형식과 수신 한도를 맞춰야 한다.

기록 기본 상한 6 GiB/1,200초와 디스크 여유 보호는 유지했다. v3만 사전 산정에 따라 실행 2,400초·정지 120초·기록 16 GiB/2,700초로 지정했다. 기록기의 실제 소요 **약 22분 18초**는 느린 PC Gazebo/렌더링/저장 비용이며 Jetson 재생 속도가 아니다.

조향 경계 회귀 100개, 이후 기록기 관련 회귀 193개를 통과했다. v3 최고 속도 **8.21 km/h**, 이동 중앙값 **5.24 km/h**, 코너 표본 중앙값 **4.79 km/h**, 정지 요청 뒤 변위 **0.7113 m**는 시뮬레이션 측정이다. 실차 제동거리·경기 5랩 검증으로 쓰지 않는다. [실패·수정·정상 기록](../../artifacts/validation/2026-09-29/imu_long_capture/README.md)

| 주행 구간 IMU 취득 시각 간격 최대, ms | 16 | 28 | 44 | 20 |
| 재생 자식 CPU 중앙값, 코어 환산 | 3.31 | 2.76 | 2.76 | 3.32 |

`buffered`의 약 15초 정지는 지역 제어기의 엔코더 나이 **37~57 ms**, 약 24.067초 정지는 보호층의 **약 53 ms**와 대응했다. 기존 30 ms 외삽 한도를 넘었다. 마지막에는 엔코더가 전부 도착했어도 필요한 순간에는 최신 값이 없었다. 비슷한 시점의 지연이지만 GC·메모리 할당·스케줄러·수신 큐 중 근본 원인은 미확정이다. 단순히 “GC 때문”이라고 인수인계하지 않는다.

기존 topic의 10초 창별 엔코더 나이 p99 약 15~17 ms, IMU 약 18~20 ms에서 이번 약 49초 비교 구간에 지속적인 누적 적체는 보이지 않았다. 반면 buffered는 CPU/누락을 줄여도 최악 지연·운영 판정을 악화시켜 미채택했다. **평균 연산량과 최악 지연 중 하나만 보고 성공을 정하지 않는다.**

이 단계 PC 90개·분석 구간 4개·후속 배포 목록 2개, Jetson 89개 검사를 통과했다. 원격의 기존 엔코더 분석 검사에는 PC의 구간 경계 검사 한 개가 없었으므로 90/89를 동일 검사 집합으로 쓰지 않는다. 실제 결과 분석은 현재 PC 분석기로 했고 실행 소스 24파일·설정 동일성·설치본·원격/로컬 회수 해시도 확인했다. 준비 중 누락된 검사 파일로 멈춘 실행은 재생 회차로 세지 않는다. [최근 비교·해시·실패 근거](../../artifacts/validation/2026-09-29/timing_cost/README.md), [ABBA 집계](../../artifacts/validation/2026-09-29/timing_cost/comparison_v1.json), [0명령 시점 복원](../../artifacts/validation/2026-09-29/timing_cost/stop_evidence_v1.json)

### 5.3 현재 기준 재생 명령

아래는 **Jetson에서 추후 재개할 때**의 명령이다. 이 보고서 작성 중에는 실행하지 않았다. 새 소스를 전송했다면 Humble의 `arena_vehicle_interface`, `arena_autonomy` 두 패키지를 다시 빌드하고 Python이 실제 읽는 설치 모듈의 해시를 확인한다. 시험 폴더에 소스만 복사한 것으로 배포 완료를 판정하지 않는다.

```bash
cd /home/q/it_arena_a3_20260928
source /opt/ros/humble/setup.bash
source install/setup.bash

# 이전 결과와 겹치지 않는 이름을 정한다. 기존 폴더 삭제/덮어쓰기 금지.
python3 scripts/run_jetson_replay_trial.py \
  artifacts/validation/2026-09-29/imu_long_capture/capture_v3/sensor_recording \
  --output artifacts/jetson_a3/handoff_baseline_next \
  --rate 1 --executor-mode legacy --timing-mode topic \
  --trace-wheels-publication --trace-imu-publication \
  --dds-transport shm_16m \
  --dds-audit-library build/libarena_dds_probe_v1.so
```

probe 라이브러리는 해당 Jetson의 Fast DDS 버전에 맞춰 빌드한 진단 모듈이다. 파일이 없거나 participant 검사가 실패하면 옵션만 빼고 같은 조건으로 시험했다고 하지 않는다. 준비 절차는 [DDS 산출물 안내](../../artifacts/validation/2026-09-29/dds_transport/README.md)에 있다. 과거 `jetson_run_*` 배치 스크립트는 고정된 v1 출력 경로를 포함하므로 그대로 재실행해 기존 결과를 덮으려 하지 않는다.

재생 후에는 다음 순서로 확인한다.

1. `trial.json`: 실행 명령·실제 환경·프로세스 종료/오류/잔존 PID. 코드 0만 보고 끝내지 않는다.
2. `replay/report.json`: 기능·스케줄·계측·운영·전달량·EOF를 각각 확인한다. 원본 입력·소스 스냅샷·실제 설정을 대조한다.
3. 시간 해석: 전체/출발 전/10.92~59.52초 이동 비교/EOF 구간을 분리한다. 본문 소요시간과 시작 간격, 수신 개수와 최신 입력 나이를 따로 본다.
4. 원인 분석이 필요할 때만 `timing.jsonl`, observer 자료, IMU/엔코더 발행 추적을 읽는다. 대형 JSONL을 에이전트 문맥에 통째로 출력하지 않는다.
5. 결과를 회수할 때 원격/로컬 아카이브 해시·안전한 내부 경로·추출 해시를 확인하고, 입력 raw와 자격 증명을 넣지 않는다.
6. 새로운 정상 입력 없이 이 자료만 반복했다고 새로운 폐루프/장시간/실차 검증으로 기록하지 않는다.

접속은 [비공개 접속 안내](../hardware/JETSON_ACCESS.md)를 따른다. 비밀번호는 문서/Git에 넣지 않고 Windows DPAPI 저장본을 사용한다. OpenSSH는 되는데 Python 이름 조회만 실패했던 이력이 있으므로 현재 주소와 기존 SSH 키 일치를 확인한 경우에만 주소 선택을 사용한다. 키 자동 신뢰·기존 키 제거로 우회하지 않는다. 과거 승인 서비스 502/사용량 오류, 파일 묶음 누락, `set -u`와 ROS setup 변수 오류는 **재생 전에 중단된 준비 오류**이며 Jetson 연산 실패로 세지 않는다.

## 6. 후속 개발자가 지킬 우선순위

1. **다음 기능은 A4:** 순간 튐·NaN/Inf·고착·일시 단절에서 기존 거절/정지/복구를 먼저 확인하고, 실제 위험이 드러난 지점에만 필터/검출기를 보완한다. 영점·환산비·시계 교정은 실물 값이 나온 뒤 별도로 한다.
2. **구조 변경마다 제한된 성능 회귀:** 제어기·필터·영상·로그·드라이버를 바꿀 때 동일 정상 입력/조건으로 변경 전후를 비교한다. 과거의 모든 시행착오를 매번 전부 다시 실행할 필요는 없다.
3. **A3 재진입 조건:** 새 반복 보호 정지, 계속 늘어나는 입력 나이/메모리, EOF 정지·종료 실패, 입력/계측 무결성 실패가 나오면 우선 해결한다. 단일 누락 수 감소만 목표로 보호 시간·QoS·센서율을 함께 바꾸지 않는다.
4. **간헐 지연 재현 시:** 발행 지연인지 특정 reader/콜백 경로인지 먼저 나누고, 필요하면 RGB+엔코더와 최소 수신자로 축소한 뒤 DDS 내부 준비/복구 또는 스케줄링을 계측한다. 현재 자료로 GC·SHM 용량·executor 중 하나를 확정 원인으로 취급하지 않는다.
5. **실물 통합 전 필수:** 실제 센서 시각 계약·설치본/드라이버·MCU 피드백·ESC/조향/제동·원격 STOP을 확인하고 충분한 연속 운용과 실제 저속 폐루프 시험을 한다. PC의 가상 MCU 정지나 Jetson EOF 0명령으로 대체할 수 없다.
6. 이후 정지 차량/느린 앞차 추종·정지·저속 우회로 확장한다. 이동 차량 추월·고속화는 후순위다. 이번 인수인계 정리에서 새 기능이나 시험을 추가하지 않았다.

사용자는 10월부터 Claude 등과 병행 개발할 계획이다. 이 문서의 역할은 미해결을 지우거나 최적화를 영구 종료하는 것이 아니라, **무엇을 근거로 어디까지 확인했고 어떤 조건에서 다시 조사해야 하는지**를 보존하는 것이다.
