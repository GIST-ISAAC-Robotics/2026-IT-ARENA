## 11/13 일시 중단 중 요구사항 누락 대조

사용자가 Fast 모드 전환을 위해 개발을 중단한 뒤, 기존 요청의 누락을 별도로 점검하도록 요청했다. GPT 주 에이전트가 주행/실행 구성·우선순위를, Astra xhigh 두 담당이 구동/조향과 센서/운영을 나누어 읽기 전용으로 검토했다. 새 시뮬·장치 접근·빌드·검사 실행·코드 변경은 하지 않았다. 문서 정정과 미해결 항목 등록만 수행했다.

### 실제로 발견한 연결 공백

1. **축소 장착 조향 한계의 export 불일치 — 조립 전 수정 대상.** `steering_calibration.py`의 `cad_servo_goal()`은 고정 CAD 전체 명령 범위가 장착 count 범위에 들어가야 하며 `cpp_zero_profile()`은 중립 요청에서도 이를 호출한다. `runtime_installed_profile.py:headers()`는 board의 선택 `servo.command_limit`을 이 검사에 전달하지 않는다. 반면 C++ `ResolveCadServoGoal()`은 선택한 command_limit의 양끝만 검사한다. 실제 장착 한계가 더 좁아 상한을 낮추려 할 때 설정 생성에서 거절될 수 있다. 이는 코드의 조건부 불일치이며 실물 실패를 관측한 결과는 아니다. 재개 후 선택 범위/기하의 Python→C++ 전달을 맞추고 한 대표 계약을 대조한다. count 한계 확대·wrap으로 우회하지 않는다.
2. **시뮬 개선과 실물 채택을 구별하는 최종 실행 선택.** r426 scope는 `simulation_acquisition`·verified-only를 요구한다. r404 실제 입력의 `host_estimated_v1`을 통과시키는 정책이 아니므로 시뮬 보완을 실물 정체 해결로 합산하지 않는다. 최종 운영 묶음에서 실제 사용할 정책·옵션·미채택 후보를 명시한다. 가짜 검증 시각이나 없는 엔코더를 만들어 통과시키지 않는다.
3. **기존 STOP 확인의 범위.** 명령/피드백 만료와 GPIO8 검사는 MCU 루프가 실행되는 조건의 처리다. loop 자체 정지의 watchdog 활성·감시 대상과 실제 출력 상태는 별도이고 firmware 문서에도 미검증으로 남아 있다. 설치 빌드 설정/감시 대상부터 대조하고 실제 출력 확인은 기존 조립 후 최소 STOP 확인에 포함한다. 새 회로·전수 고장 주입·희귀 조건 개발을 추가하는 사항은 아니다.

r426 음수 측정속도 `−0.061225 m/s` 한 건은 이미0인 결과에 후보를 시도하지 않은 것이다. 기존 양수를 음수 부호만으로0으로 바꾼 회귀는 아니며 기존 signed 모터 PI/forward-drive 정책도 존재한다. 다만 원0을 회복하지 못했고, 음수 범위를 허용할 경우 기하까지 통과하는지와 실제 정체 영향은 미확인이다. r428 실제 기록과 대조할 대상이며 음수 값을0으로 바꿀 근거는 아니다.
