# Jetson 실행 주기·병목 검토와 조립 전 준비

기준: 2026-11-12, main 7bdbd6f927e5b8e85d91321bfe63b70b21820524. 사용자는 조립 전 소프트웨어 통합과 Jetson 성능/Hz, 랩타임·추월 작업 범위를 논의한 뒤 계획의 main 반영을 승인했다. **성능 개선 순서는 작업 계획이며, 8/6/5Hz는 미채택 비교 후보다. 새 Jetson 시험·주행·주기/전력 설정 변경 결과가 아니다.**

## 1. 현재 실행 주기를 먼저 구분한다

현재 선택된 비동기 구성은 이미 **계획 100ms 간격(명목 10Hz) + 부모 수신/출력 관리 50Hz**다. [G1/G2 노드](../../src/arena_autonomy/arena_autonomy/g1_g2_node.py)는 process_candidate에서 50Hz 부모와 시뮬 시간을 요구한다. [DecisionDelivery](../../src/arena_autonomy/arena_autonomy/decision_delivery.py)는 decision_dt_s=.1, 명령 나이 < .2초, 첫 광선 나이 < .3초를 유지하며 한 스캔을 중복 제출하지 않는다. 양수 후보의 적용 간격도 최소 100ms이므로, 부모 타이머 50Hz가 매 20ms 새 경로 판단을 만든다는 뜻은 아니다. [FreshStartDelivery](../../src/arena_autonomy/arena_autonomy/fresh_submission.py)는 스캔 완료 후 25ms 이내에 제출하는 조건을 추가한다.

| 계층 | 현재 확인/설정 | 검토 방향 |
|---|---|---|
| C1 취득 | 약10Hz | 유지. 계획 호출 빈도와 센서 회전수를 구분 |
| IMU 취득 | 약199Hz 실측 | 유지. 부모 콜백 지연을 줄여 운동 이력을 제때 사용 |
| 부모 수신/출력 관리 | 명목50Hz | 긴 계산 때문에 밀리는 부분을 분리/경량화.50Hz 전체 마감 달성은 미검증 |
| 경로/교통 계획 | 명목10Hz, 실제 계산이100ms를 자주 초과 | 우선10Hz 예산 확보.8/6/5Hz는 계획에만 적용할 미채택 비교 후보 |
| MCU 구동/STOP | 실물 공통 운용 연결 미완료 | 기존 구동 계약에 따라 구현·측정. 계획기 주기 하향을 MCU 정지·속도 제어 주기 하향으로 전파하지 않음 |

## 2. 저장 계측을 재집계한 결과

원본은 [r232 보고서](../../artifacts/validation/2026-11-12/combined_ros_cost_r232_v1/jetson_full/report.json)와 [호출별 비용632개](../../artifacts/validation/2026-11-12/combined_ros_cost_r232_v1/jetson_full/durations.json)다. 같은 기록의 child_ms, has_current=true인 recheck_ms, 각 행의 두 값 합을 읽었다. 새 계측이 아니며 Python 표준 통계의 평균/중앙값과 선형 보간 백분위로 재집계했다.

| 단계 | 표본 | 평균 | 중앙 | p95 | 최대 |
|---|---:|---:|---:|---:|---:|
| 계획 계산 | 632 |117.83ms|129.36ms|187.48ms|300.21ms|
| 현재 재검사 | 592 |24.76ms|17.00ms|48.74ms|256.91ms|
| 같은 호출의 계획+재검사 단순 합 |632|141.03ms|145.46ms|223.48ms|443.10ms|

두 단계 합은 직렬 처리할 경우의 부분 연산 예산 참고값이다. IPC·추가 부모 처리·실제 센서/영상/독립 보호/MCU 비용을 포함한 종단 지연이 아니며, 두 p95를 더해 계산하지 않았다. 계획과 재검사를 겹쳐 실행하는 새 구조의 성능도 아니다.

초과 비율은 현재 기록을 각 시간 예산에 대입한 산술 결과다. 실제 주기를 바꾸면 상태·관측·호출 비용이 달라지므로 특정Hz 운용의 실패 확률이나 통과율로 해석하지 않는다. r232는 오래된 요청도 모두 처리하므로 최대20.31초 누적 지연은 처리율 미달 지표이며 실차에서20초 전 명령을 사용했다는 뜻이 아니다. 합성 IMU19,823개 손실0과 콜백 지연 최대260.67ms도 별개다.

[과거 실제10Hz 시뮬 r91 run4](../../artifacts/validation/2026-11-11/control_10hz_r91_v1/README.md)는47.90m·한 랩·최고1.551m/s·접촉/노면 이탈0·dt=.1초610판단으로 등록 기능 기준을 통과했다. 원 final_gap 실패는 유지한다. 시뮬68.603초에 실제783.99초가 걸려 Jetson 실시간/2.8m/s 고속 증거가 아니다. [그 입력의 r98 Jetson 비용](../../artifacts/validation/2026-11-11/control_10hz_cost_r98_v1/README.md)은 전체610개 중272개가100ms를 초과했다. 따라서10Hz에서 경로 추종 가능성이 있다는 근거와 현재 하드웨어에서10Hz 마감을 지킨다는 근거를 구분한다.

## 3. Hz만 낮추면 해결되지 않는 이유

주기 하향은 단위시간당 새 계산 수를 줄이지만 한 번의 계산 지연187ms를 자동으로 줄이지 않는다. C1 한 회전 약100ms와 계획p95 약187ms를 단순히 이어 보면 첫 광선의 나이는 이미약287ms이고 제출/회수/재검사 시간이 추가된다. 실제 원천시각으로 판정해야 하며 이 산술 예시가 실측 전체 지연은 아니다. 현행300ms 원천 나이와200ms 명령 나이 경계에 가까운 이유를 보여준다.

현재 decision_dt_s=.1과50Hz 부모 조건은 코드 계약이다.5Hz로 바꾸려면 실제 경과시간·명령 적용 간격·스캔 제출 위상·상태 이력을 함께 정리해야 한다. 같은 오래된 명령에 새 시각을 붙이거나 TTL만 연장해 성능 문제를 숨기지 않는다. [과거 호출 생략 r90](../../artifacts/validation/2026-11-11/decision_cadence_r90_v1/README.md)도 단순 호출 생략/dt 변경이 상태와 출력을 바꾼다는 개방 루프 근거를 남겼다.

계획 간 이동거리는2m/s에서10Hz 20cm,5Hz 40cm이고,10km/h에서는약28cm/56cm다. 이는 제동거리나 반드시 그만큼 장애물을 늦게 본다는 뜻이 아니다. 센서/빠른 상태 확인을 유지하더라도 새 경로 판단 간 이동량이 커지므로 코너·합류·옆차 상황의 주행 손실을 함께 비교한다.

## 4. 권장 해결 순서

1. **현재 선택 구성의 같은 입력으로 단계별 비용을 고정한다.** r231 일반 재생기 공통 연결을 먼저 마치고 계획·snapshot/점군 투영·현재 재검사·IPC·기록·부모 콜백 지연을 분리한다. 이미 확보된 r232를 기준으로 사용하고, 같은 실패/계측을 근거 없이 반복하지 않는다.
2. **부모 수신/발행 경로의 긴 현재 재검사를 분리하거나 경량화한다.** 계획기는 이미 별도 프로세스이므로 그 분리를 새 해결책처럼 반복하지 않는다. 독립 프로세스/작업으로 재검사를 옮길 때도 결과의 원 관측시각·차체 상태·센서/MCU 세대·명시 STOP을 보존하고, 반환 뒤 최신 입력과 적용 가능한 범위를 확인한다. 오래된 결과를 무조건 현재 명령으로 재발행하지 않는다. 수신 큐만 늘려 메시지 손실을 숨기는 방식은 해결로 보지 않는다.
3. **실제 비용이 큰 기하 연산을 같은 판정을 유지하며 줄인다.** [r222 프로파일](../../artifacts/validation/2026-11-12/current_recheck_profile_r222_v1/README.md)에서는 옆차 재검사 중 이동 영역 생성·차체 외곽 질의·관측 지지/가림 계산이 컸다. 이는 옛24개 상태의 cProfile로 계측 오버헤드를 포함한다. 원호 질의 묶음은 [r226](../../artifacts/validation/2026-11-12/motion_query_batch_r226_v1/README.md)에서 이미 개선했고r227에 연결했으므로 같은 개선을 미래 성과로 다시 세지 않는다. 현재 코드의 남은 중복 배열/객체 생성·같은 호출의 질의/투영을 먼저 찾는다. 다른 스캔·이동 자세의 증거를 검증 없이 캐시로 재사용하지 않는다.
4. **부족하면 소수의 연산 핵심만 네이티브 코드 후보로 만든다.** 측정된 다각형/관측 질의처럼 입력·출력이 명확한 배치 함수가 후보이며 전체 제어기 C++ 재작성은 범위를 벗어난다. 함수/전체 판단 대조 후 실제 Jetson 같은 입력으로 전체 비용을 본다. GPU도 가능한 계산 경로지만 현재 작은 배열/상태 분기가 많은 CPU 경로에 자동 적용되지 않는다. GPU 전면 이관을 첫 과제로 두지 않는다.
5. **장치 상태와 운영 부하를 확인한다.** [r67 당시 계측](../../artifacts/validation/2026-11-11/jetson_native_r67_v1/README.md)은 이미6CPU·schedutil·MAXN_SUPER였고 GPU를 쓰지 않았다. 최신 실제 클럭/온도/전력 제한·코어별 점유·BLAS 스레드·다른 프로세스는 다음 시험에서 확인한다. MAXN 전환만으로 해결된다고 추정하지 않는다. 설정 변경을 비교할 때 기존 상태와 복원 방법을 보존하고 적용 가능한 전원/냉각 조건에서 실제 비용으로 판단한다.

NVIDIA는 [MAXN의 성능 한계와 클럭 관리](https://docs.nvidia.com/jetson/archives/r36.4.3/DeveloperGuide/SD/PlatformPowerAndPerformance/JetsonOrinNanoSeriesJetsonOrinNxSeriesAndJetsonAgxOrinSeries.html)에서 모드별 상한·실제 주파수 조절·열/전력 제한을 구분한다. 이 검토에서는 전력/클럭/OS·드라이버를 변경하지 않았다.

## 5. 주기 선택과 채택 기준 제안

**우선 목표는 C1 10Hz·IMU 약199Hz를 유지하며 계획10Hz와 빠른 수신/출력·독립 보호를 확보하는 것**이다. 계획p95를100ms보다 충분히 낮추는 방향으로 잡고, 예를 들어70~80ms는 다른 비용 여유를 두기 위한 설계 목표다. 달성한 성능이나 새로운 공식 통과 기준이 아니며, 긴 꼬리·명령 만료·실제 결합 부하가 남으면 p95만으로 채택하지 않는다. 현재187.48ms에서80ms는약2.34배의 비용 개선이 필요해 성공을 미리 보장할 수 없다.

계획8/6/5Hz는 성능 개선 뒤에도 필요한 경우 비교할 조건이다. 수신·독립 보호·MCU 정지까지 일괄 하향하지 않는다. 현재5Hz 시간 예산도 계획+재검사632개 중78개가 넘으므로 당장 안정된 대안으로 확정하지 않는다. 새 경과 dt/입력 선택 의미를 명시한 후보에서 단독·대표 교통·STOP/재개와 적용 명령의 원천 나이를 확인한다. 오래된 명령 폐기/정지를 없애거나 미관측 공간을 채워 성능을 얻지 않는다.

운영 성능의 확인 순서는 **저장 동일 입력 대조 → 같은 ROS 수신 부하와 출력/정지 지연 → 정지 실센서+영상/독립 보호 결합 → 계산 지연을 반영한 대표 주행 → 조립 후 실주행**이다. 단독/교통의 속도 유지·긴 저속·명령 만료·입력 누락·STOP·정상 종료를 함께 본다. 필수 연결을 금요일 밤으로 넘기면서 미세 성능만 계속 다듬지 않는다.

## 6. 계획 반영 범위

설계는11/12 저녁~11/13 새벽, 차량 완성은11/13 저녁이라는 사용자 예상에 맞춰 [현행 개발 계획](../DEVELOPMENT_PLAN.md)을 정리했다. 현재 센서 연결은 사용자 추정으로 기록하고 실제 수신/펌웨어 확인과 구분했다. 컴퓨터24시간 가동은 저장 재생·수신 결합·설계 반영 시뮬을 진행할 수 있는 시간으로 반영했다. 24시간 가동 계획을 자동 반복 작업의 실행 완료로 기록하지 않는다.

이번 변경은 문서와 저장 수치 재분석뿐이다. 원 주행 판정·원 계측·제어 코드·센서/제어 주기·전력 설정은 바꾸지 않았다. 성능/Hz와 랩타임·추월 작업 범위 논의 후 사용자 승인에 따라 계획을 main 반영 범위로 확정했다. 실제 실행 주기 채택과 성능 개선은 후속 구현·계측에서 판단한다.
